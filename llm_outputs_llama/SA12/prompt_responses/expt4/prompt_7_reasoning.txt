The provided repair addresses a vulnerability in the TLS 1.3 server implementation, specifically in the `DoTls13Finished` function. The vulnerability allows a malicious client to bypass mutual authentication by not sending the `certificate_verify` message, even if the server requires a certificate.

The root cause of the issue lies in the fact that the server does not properly check if a certificate has been received from the client before completing the handshake. In TLS 1.3, the `certificate_verify` message is optional, but if the server requires mutual authentication, it should not proceed with the handshake without receiving a valid certificate from the client.

The repair introduces a check for the `requireCert` flag in the `ssl.options` structure. This flag indicates whether the server requires mutual authentication. If this flag is set, the code checks the `gotCert` flag, which indicates whether a certificate has been received from the client. If no certificate has been received (`gotCert` is false), the server sends a fatal alert with a `bad_certificate` error code and returns an error.

This check is performed before setting the keys for the decryption side (`SetKeysSide` function) and before marking the handshake as complete (`handShakeDone` flag). By introducing this check, the server ensures that it does not proceed with the handshake without receiving a valid certificate from the client, thus preventing the bypass of mutual authentication.

The repair does not modify the existing logic for deriving the finished secret, building the TLS 1.3 handshake HMAC, or verifying the finished message. These operations remain unchanged, as they are not directly related to the vulnerability.

To further understand the context, here's a brief overview of the TLS 1.3 handshake:

1.  The client and server exchange hello messages, which include the supported protocol versions, cipher suites, and other parameters.
2.  The server sends its certificate and, if required, a certificate request to the client.
3.  The client responds with its certificate and a `certificate_verify` message, which contains a signature over the handshake transcript.
4.  The server verifies the client's certificate and the `certificate_verify` message.
5.  The client and server derive the shared secret and exchange finished messages to confirm the handshake.

In the vulnerable code, the server does not properly enforce the receipt of the `certificate_verify` message, allowing a malicious client to bypass mutual authentication. The repair addresses this issue by introducing a check for the `requireCert` flag and ensuring that the server does not proceed with the handshake without receiving a valid certificate from the client.

In summary, the repair introduces a critical check to ensure that the TLS 1.3 server enforces mutual authentication when required, preventing a malicious client from bypassing the `certificate_verify` message and completing the handshake without presenting a valid certificate.
