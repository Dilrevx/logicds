The core issue with the vulnerability was that in some cases a NULL algorithm parameter entry is indistinguishable from an empty array of REAL, since both would register as having zero length parameters. This oversight in the buggy code meant that even if a certificate contained a parameter that was fundamentally different (a NULL versus an empty array), it could still be mistakenly deemed valid because the check relying solely on the length of the parameters was insufficient.

In the original implementation, the code compared the overall lengths of the signature algorithm’s identifier and the signature parameters, and if the length was zero, it bypassed a deeper equality check on the actual content. In other words, if both certificate parameters were empty in length, the certificate was accepted without further verifying that the type of the empty parameters matched. This allowed a case where a certificate could use a NULL value in its parameters, which is semantically distinct from an explicit empty REAL value array, yet still pass the checks if only the length was considered.

The repair addresses this by adding an extra condition that checks for equality in the parameter “tag” before comparing their lengths and contents. The tag is an important component because it represents the type or classification of the data contained in the parameters. By ensuring the tags on both parameter sets match, the updated code distinguishes a truly NULL parameter from an empty array that might share the same length. This new comparison effectively differentiates between a certificate that explicitly defines no value (NULL) and one that defines an empty collection, thereby preventing certificates with mismatched semantic information from being accepted as valid.

In summary, the reasoning behind the repair is to enforce a stricter and more precise validation of the algorithm parameters. Instead of relying solely on the length of the parameter arrays and their byte-by-byte content, the repair incorporates a tag comparison that reflects the actual type of the parameters. This additional check ensures that any discrepancy, even if it results in the same length (or absence of content), is caught, thereby invalidating any certificate where the parameter types do not match precisely. This change closes the vulnerability by ensuring that certificates with a NULL entry (which might have been misinterpreted as an empty array) are correctly treated as invalid if they do not truly match the expected REAL (empty) parameters.
