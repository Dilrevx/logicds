The issue was that, in the DTLS handshake process, the client’s random value is crucial to ensuring proper security via unpredictability. In the flawed implementation, the condition controlling when to generate a new random value was inverted for DTLS sessions. The original logic mistakenly skipped generating a random client value when the session was DTLS with no Hello Verify Request received (indicated by a zero count). In that particular scenario, instead of generating a proper random value, the system would eventually end up using a fixed value—a sequence of 32 null bytes—which in turn undermines the cryptographic strength of the handshake.

The heart of the problem was how the code checked whether a DTLS session had already received a Hello Verify Request. The original check was structured so that if the session was DTLS and the count of Hello Verify Requests was exactly zero, the condition would evaluate in such a way that it avoided generating a proper random number. This inadvertently meant that in sessions without a Hello Verify Request—precisely when they should be getting a properly randomized value—the code would either not call the random generator or rely on an insecure default.

The repair adjusted the logical condition by reversing the check on the count of Hello Verify Requests. Instead of looking for a count equal to zero (which caused the condition to be misinterpreted), the fixed version checks if the count is not equal to zero. By doing this, the condition now correctly interprets the state of the handshake. Specifically, if the session is DTLS and a Hello Verify Request has been received, the client random generation is skipped, which is the intended behavior. However, if there hasn’t been any Hello Verify Request, the code proceeds to call the routine that generates a truly random client value.

In simpler terms, this logical flip ensures that the correct scenario triggers a proper random generation: for DTLS sessions that have not yet been challenged with a Hello Verify Request, the client will now generate a random value as originally intended. When a Hello Verify Request is present, the routine does not override any existing value. This repair eliminates the vulnerability where a DTLS client would always default to using a fixed, non-random value—thus fully restoring the intended security guarantees of the DTLS protocol.

Overall, by modifying the condition, the repair correctly distinguishes between DTLS sessions that need a fresh, cryptographically secure random value and those that do not. This careful correction eliminates the risk of predictable behavior in the key exchange process, thereby maintaining the cryptographic integrity of the DTLS negotiation.
