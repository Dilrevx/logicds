The vulnerability arises due to an insecure handling of the initial key exchange phase, where an attacker can manipulate or omit certain packets during the handshake. This manipulation allows the client and server to inadvertently downgrade or disable some essential security features. The original code only checked whether the client's and server's key exchange methods for specific algorithm groups differed, logging whether the initial guess was correct or not. However, this approach did not enforce a robust mechanism to ensure that all expected packets were received and correctly processed, leaving room for an attacker to exploit mismatches in sequence numbers.

The repair addresses this shortcoming by introducing an additional check for what is referred to as the "strict KEX" (key exchange) feature. This additional logic carefully examines whether the talking party – either client or server – supports a stricter version of the key exchange. The goal is to enforce a higher level of security by verifying packet sequence numbers explicitly when the peer advertises support for this stricter mode.

When the repair code checks for strict key exchange support, it does so by verifying the presence of a specific strict group within the key exchange methods. Essentially, if the peer’s key exchange methods include the strict mode indicator, the code then sets a flag within the session to indicate that strict mode is in effect. This flag acts as an assurance that both parties will adhere to tighter security checks throughout the session. With this flag enabled, the handling of sequence numbers becomes more robust, ensuring that all packets are accounted for and correctly ordered during the handshake process.

More precisely, this repair ensures two things. First, it ensures that if a client or server declares support for strict key exchange, its corresponding method will be used, thus mandating extra scrutiny during the handshake. Second, by setting the flag based on this check, subsequent processing stages within the session can perform additional validations. This reduces the risk of key exchange downgrade attacks because it binds the session to a negotiation process that cannot be easily manipulated by omitted packets or erroneous sequence numbers.

In summary, while the original code only assessed whether the guessed key exchange method was correct, the new repair strengthens the handshake protocol by explicitly enabling a strict key exchange mode when supported by either party. This mode introduces hardened checks on packet sequence numbers and overall packet handling, effectively mitigating the vulnerability associated with Terrapin attacks. The repair thereby ensures that even if an attacker attempts to bypass certain integrity checks through packet omission or manipulation, the additional enforced strict policy will detect and prevent such attempts, maintaining a secure session from the outset.
