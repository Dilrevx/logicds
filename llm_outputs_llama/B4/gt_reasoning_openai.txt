The vulnerability arose because the certificate's serial number was being compared against the OCSP response without ensuring that the length of the serial number was accurately set. In the original implementation, the function that retrieves the certificate's serial number returned the actual length of the serial number through an output parameter. However, this returned length was not used to update the corresponding field within the certificate serial structure. As a result, if memory allocated to store the certificate serial number was larger than the actual serial number, extra trailing bytes from previous allocations could be unintentionally included during the comparison.

If an attacker managed to craft an OCSP response that exploited these extra bytes, they could potentially bypass the certificate validation. Essentially, by not explicitly setting the correct length, the function risked comparing more data than intended—which might mismatch when trailing, unintended bytes were present—allowing malicious OCSP responses to be mistakenly treated as valid.

The repair addresses this problem by explicitly updating the certificate serial’s length right after retrieving the serial number. Once the certificate’s serial number is obtained, its actual length (provided by the function that extracted it) is stored in the serial structure. This ensures that when the serial number from the certificate is later compared to the one from the OCSP response, both comparisons use the correct, exact number of bytes. In other words, the serial's size reflects only the intended number of valid bytes, eliminating any trailing data that might have been left over from the initial memory allocation.

This simple update is crucial, as it rectifies the oversight where the previously allocated memory (which could have contained residual, non-serial data) might otherwise have been compared. With the correct length, the vulnerability is mitigated because any excess data (not part of the genuine certificate serial) is now disregarded. This means that if there is any tampering or discrepancy, it will be detected accurately during the comparison process.

In summary, the repair enforces proper memory handling by updating the size of the certificate serial immediately after reading it, ensuring that the verification step compares only the intended bytes. This prevents attackers from exploiting trailing garbage data in the buffer, thus strengthening the certificate validation process against potential OCSP response attacks.
