The repair addresses a critical security gap by ensuring that plain (unencrypted and unauthenticated) NAS messages are not accepted once a secure context is already in place. Originally, the code simply passed through the case for plain messages without checking whether security measures had already been established, which could allow an attacker or even a malfunctioning user equipment (UE) to send a plain identity request—even after the network has set up a secure communication channel. This behavior creates an opportunity for downgrade attacks, where an adversary forces the system to revert to an insecure mode.

In the modified logic, when a plain NAS message is received, the code now first sets an internal indicator for the type of message being processed. More importantly, it checks for the existence of an active security context. If a security context has been established, this indicates that all subsequent messages should be safeguarded by integrity protection or encryption. By detecting that a plain NAS message has arrived in violation of these rules, the system logs an error and terminates further processing, effectively rejecting the message.

The repair also establishes a structured way to differentiate between various types of messages by assigning a unique identifier (the current message header) based on the security header type. This not only helps in managing the different processing paths for each type of message but also enhances diagnostic capabilities, ensuring that each case is handled correctly and any deviation (especially the unexpected plain message after security activation) is clearly flagged.

For other security header types, such as those with integrity protection and ciphering, the code continues to perform the necessary checks and operations (like integrity verification and decryption) before processing the message. The explicit handling of these different cases reinforces the protocol’s security policy by confirming that messages are processed in a manner consistent with the established secure context.

In summary, the main reasoning behind the fix is to enforce protocol compliance and prevent the acceptance of unsecured messages once a security context is active. By adding a check for the security context in the case for plain messages, the patch ensures that any plain, unprotected NAS message—such as an identity request—is immediately rejected, thereby preventing potential downgrade attacks and improving overall system security.
