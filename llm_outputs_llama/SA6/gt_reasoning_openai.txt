The vulnerability arises from the fact that the ChaCha20-Poly1305 cipher mandates that each encryption operation use a truly unique nonce. According to RFC 7539, a nonce for this cipher must be exactly 12 bytes long, and if a nonce is not exactly this length, it can lead to the reuse of nonce values and, consequently, result in serious confidentiality and integrity issues.

Originally, the code checked if the provided nonce length was within a certain range by comparing it against a constant meant for a different context (CHACHA_CTR_SIZE). This constant does not correctly represent the maximum allowed nonce length for ChaCha20-Poly1305 according to its specification. Because OpenSSL allowed a variable nonce length and padded shorter nonces with zeros while ignoring any extra leading bytes if the nonce exceeded 12 bytes, using the incorrect check could inadvertently allow nonce lengths that are invalid for proper cryptographic operation. Essentially, if an application tried to change parts of the nonce expecting uniqueness without fully adhering to the 12-byte rule, it risked encrypting multiple messages with effectively the same nonce.

The repair addresses this issue by amending the range check to use the correct constant, CHACHA20_POLY1305_MAX_IVLEN, which enforces that the nonce length must not exceed the maximum expected for ChaCha20-Poly1305 (i.e., 12 bytes). By doing so, the repair ensures that any nonce provided to the cipher is within the bounds specified by RFC 7539—preventing scenarios where an application might mistakenly believe it is using a unique nonce while in fact part of the nonce is being ignored. This change is crucial in stopping the potential reuse of critical parts of the nonce when larger nonce values are supplied.

In summary, the remedial action involved replacing the incorrect validation constant with one that accurately reflects the nonce length rule for ChaCha20-Poly1305. This update is not just a syntactic fix but a necessary security improvement. It closes off the possibility of applications inadvertently reusing nonce values by enforcing the correct constraints on nonce length. Ensuring that nonce uniqueness, as required by the underlying cryptographic algorithm, is strictly maintained is essential for protecting the confidentiality and integrity of the encrypted messages.
