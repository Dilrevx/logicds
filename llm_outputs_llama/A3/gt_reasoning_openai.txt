The root of the vulnerability lies in how OpenSSL’s legacy custom ciphers were being handled. Specifically, when a custom cipher was created using legacy functions, the library was supposed to use that exact cipher. However, if the cipher’s identifier was misconfigured—most notably when the unique identifier (NID) was erroneously set to an undefined value—the library would mistakenly look up an equivalent cipher from the loaded providers. This error could cause the library to find and use the NULL cipher from the provider, which essentially passes the plaintext through as “encrypted” data, thereby exposing sensitive information.

The repair modifies the logic that determines whether to use the legacy handling path. In the buggy version, the code checked only a few conditions—primarily whether the context had a valid engine or implementation pointers—to decide if it should bypass the default provider look-up and handle the cipher as a legacy cipher.

The fix extends this logic by adding extra conditions to detect when the cipher was created via the legacy method. It does this by checking the origin property of the cipher. If the explicit cipher is not null and its origin value indicates that it was created using the legacy method, then the condition immediately qualifies for using the legacy code path. Similarly, if the explicit cipher is null but the cipher present in the context is non-null and also flagged as having a legacy origin, the code treats it as a legacy cipher as well.

By incorporating these extra checks, the repair ensures that any cipher constructed using the legacy functions (indicated by the legacy origin property) will not be inadvertently looked up in the available providers. This prevents the misinterpretation that leads to fetching the wrong cipher (such as the NULL cipher), which was at the heart of the vulnerability. In effect, the patch blocks the erroneous pathway where a custom cipher with an undefined identifier could be wrongly matched with the provider’s cipher, thereby ensuring that the method which should work with legacy behavior indeed proceeds in that manner.

Additionally, before transferring control to the legacy initialization section, the repair cleans up by freeing and nullifying any previously fetched cipher. This cleanup is important to avoid issues such as resource leaks or accidental use of stale pointers that could further compromise the encryption process.

Overall, the reasoning behind this repair is to strengthen the validation of the cipher’s origin. By clearly distinguishing between legacy-built ciphers and those that have been retrieved from providers, the patch prevents the unintended usage of a provider cipher (especially the insecure NULL cipher). This change is designed to maintain the integrity of encryption by ensuring only the correctly intended cipher implementation—be it legacy or provider-based—gets used, thereby mitigating the risk of unencrypted data exposure.
