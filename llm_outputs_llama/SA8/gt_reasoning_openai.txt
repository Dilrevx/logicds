The original issue stems from improperly handling extension tokens during the handshake phase, which could allow remote attackers to manipulate the negotiation process. In this particular vulnerability, attackers exploited the lack of integrity checks to essentially "skip over" parts of the handshake, forcing the client and server into a state where some security features were reduced or disabled. This discrepancy in negotiated security parameters contributes to a risk where the connection becomes weaker than expected—a situation known as a Terrapin attack.

Initially, the code only performed a check on the client's key exchange methods. It scanned the client's list for a specific token and removed any subsequent tokens if that special marker was found. This truncation was aimed at stripping out extensions that, if processed, could result in a degraded security negotiation. However, the code did nothing similar on the server's side, meaning that if the connection were initiated by a server sending its own extension tokens, there was no corresponding safeguard. The lack of symmetry in handling both ends of the connection presented a vulnerability, as attackers could target the server’s negotiation process just as effectively.

The repair addresses this flaw by introducing dual handling based on the session role. When the session is from the client's perspective, the same logic is applied: the client's key exchange method string is scanned for an extension marker, and if detected, it is truncated to eliminate potentially harmful tokens. The critical enhancement comes with the additional block of logic that performs a similar check when the session is a server. This new portion of the fix ensures that the server’s key exchange methods are also scrutinized for a corresponding server-specific marker before finalizing the negotiation parameters.

By discretely handling client and server sessions, the repair ensures that both parties participate in a cleaner, more secure negotiation process. Both the client and the server now actively look to remove any non-standard or extra tokens potentially introduced as part of the vulnerability exploitation. With this bilateral check, neither side will unknowingly agree to a weaker security protocol due to unvalidated, maliciously injected negotiation data.

This repair is significant because it prevents scenarios where one endpoint could be tricked into downgrading its security without the other endpoint noticing. It reinforces the integrity of the SSH handshake by making sure that any attempt to bypass security via extension tokens is consistently rejected. Thus, the attack vector that previously allowed for a downgrade in security is effectively closed, ensuring that both parties maintain the expected, secure parameters when establishing their connection.
