The repair provided for the ssl3_get_cert_verify function is aimed at fixing a vulnerability that allows remote attackers to obtain access without knowledge of a private key by sending crafted TLS Handshake Protocol traffic to a server that recognizes a Certification Authority with DH support. The vulnerability arises from the fact that the function does not always require a CertificateVerify message for client authentication with a DH certificate.

The repair involves modifying the condition that checks for the message type. In the original code, the function checks if the message type is not SSL3_MT_CERTIFICATE_VERIFY and if the peer is not null. If both conditions are true, the function proceeds without a CertificateVerify message. This is the root cause of the vulnerability.

To fix this, the repair removes the check for the EVP_PKT_SIGN flag, which is not necessary in this context. By doing so, the function will now always require a CertificateVerify message, even if the peer is not null. This ensures that the function will not proceed without a valid CertificateVerify message.

The reasoning behind this repair is as follows:

1.  **CertificateVerify message is essential for security**: In the TLS protocol, the CertificateVerify message is a crucial component of the handshake process. It allows the client to prove possession of the private key corresponding to the public key in its certificate. Without this message, an attacker could potentially impersonate the client and gain unauthorized access to the server.
2.  **DH certificates require special handling**: DH certificates are different from other types of certificates, as they do not contain a public key that can be used for authentication. Instead, the client must prove possession of the private key through the CertificateVerify message. Therefore, it is essential to always require a CertificateVerify message for DH certificates.
3.  **Removing the EVP_PKT_SIGN flag check**: The EVP_PKT_SIGN flag is used to indicate whether a certificate is a signing certificate. However, in the context of the ssl3_get_cert_verify function, this flag is not necessary. By removing the check for this flag, the function will always require a CertificateVerify message, regardless of the type of certificate.
4.  **Ensuring backward compatibility**: The repair does not introduce any changes that would break backward compatibility with existing clients or servers. The modified function will still work correctly with non-DH certificates and will only enforce the CertificateVerify message requirement for DH certificates.

In summary, the repair provided for the ssl3_get_cert_verify function fixes a critical vulnerability by ensuring that a CertificateVerify message is always required for client authentication with a DH certificate. This repair is essential for maintaining the security and integrity of the TLS protocol and preventing potential attacks.
