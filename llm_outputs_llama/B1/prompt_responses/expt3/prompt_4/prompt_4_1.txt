### Repair for SSL3_GET_CERT_VERIFY Vulnerability

The provided buggy code snippet is vulnerable to an attack where a remote attacker can obtain access without knowledge of a private key via crafted TLS Handshake Protocol traffic to a server that recognizes a Certification Authority with DH support. This is because the `ssl3_get_cert_verify` function does not require a CertificateVerify message when a Diffie-Hellman (DH) certificate is used.

To fix this vulnerability, we need to ensure that a CertificateVerify message is required when a DH certificate is used. Here's the repaired code snippet:

```c
if (s->s3->tmp.message_type!= SSL3_MT_CERTIFICATE_VERIFY)
{
    if (s->s3->tmp.cert_req == SSL_CRLPEM && EVP_PKEY_type(s->session->peer_tmp_key->type) == EVP_PKEY_DH)
    {
        al = SSL_AD_UNEXPECTED_MESSAGE;
        SSLerr(SSL_F_SSL3_GET_CERT_VERIFY, SSL_R_MISSING_VERIFY_MESSAGE);
        goto f_err;
    }
    s->s3->tmp.reuse_message = 1;
    if ((peer!= NULL) && (type & EVP_PKT_SIGN))
    {
        al = SSL_AD_UNEXPECTED_MESSAGE;
        SSLerr(SSL_F_SSL3_GET_CERT_VERIFY, SSL_R_MISSING_VERIFY_MESSAGE);
        goto f_err;
    }
    ret = 1;
    goto end;
}
```

### Explanation of Changes

In the repaired code snippet, we added a conditional check to verify if the peer's temporary key is of type `EVP_PKEY_DH` (Diffie-Hellman) when the `tmp.message_type` is not `SSL3_MT_CERTIFICATE_VERIFY`. If it is, we set the alert `al` to `SSL_AD_UNEXPECTED_MESSAGE` and log an error using `SSLerr`. This ensures that a CertificateVerify message is required when a DH certificate is used.
