The vulnerability arose because the system was accepting plain identity requests even after a security context had been established. In secure 5G configurations, once NAS security is activated, all messages must be protected—either by integrity checks alone or by both integrity and ciphering. Plain messages, which do not use these protections, should not be allowed once a secure context exists. Without this check, an attacker or any malicious process could potentially inject unprotected messages, undermining the security guarantees of the system.

The repair addresses this issue by explicitly checking whether a security context is already established when a plain NAS message is received. This fix ensures that if the system already has a valid security context (as indicated by the presence of a security context flag), it will not process a plain identity request. Instead, the system logs an error and rejects the message. This behavior guarantees that all messages transmitted after the establishment of security are sufficiently protected, thereby preventing the security breach.

In addition to this critical check, the repair also assigns a specific value to a variable that tracks the type of security header for the NAS message. This assignment allows subsequent parts of the code to correctly identify the message type, ensuring that any necessary operations (such as integrity checks or decryption) are consistently applied according to the message header. For messages that are supposed to be integrity protected, the repair retains the integrity check and, if applicable, the decryption process. This consistency is crucial for maintaining the intended functionality while upholding robust security measures.

The repair also includes in-line comments noting the presence of missing sequence number checks for the integrity-protected messages. While the primary focus of the patch is to prevent the acceptance of plain messages post-security activation, the mention of sequence number checks highlights an awareness of other potential vulnerabilities in the handling of protected messages. It serves as a reminder for further improvements to fully secure those message types in future updates.

Overall, the reasoning behind this repair is to enforce strict adherence to the 5G security requirements by ensuring that unprotected plain NAS messages are not processed once a security context has been established. This change closes the security gap that allowed the acceptance of such messages, thereby bolstering the overall integrity of the system by preventing potential exploitations or bypasses in the NAS message processing pipeline.
