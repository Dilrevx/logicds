The fix addresses the vulnerability by carefully reordering the operations when handling a detected SRTP replay error. In the original code, the procedure would stop the SRTP session first and then attempt to retrieve the cryptographic policies (the settings and keys used for encryption and decryption) for transmitting and receiving. However, stopping the session can alter the state of the SRTP object such that the precious secure parameters might be lost or incorrectly modified. As a result, when the system subsequently tries to restart SRTP using these potentially altered or invalid values, it may inadvertently fall back to using basic RTP instead. This fallback exposes the media stream to insecure transmission, defeating the purpose of encrypted communications.

The repaired version of the code resolves this by reversing the order in which the operations are performed. First, it retrieves and stores the current cryptographic policies from the SRTP object before any state changes occur. With these reliable and intact settings secured in temporary variables, the procedure then proceeds to stop the current SRTP session. After stopping the transport session, the code initiates a new SRTP session using the pre-stored encryption and decryption policies. By doing so, it guarantees that the restart process uses the correct parameters, thereby maintaining secure media transport. Only when the restart is successful does the code attempt to unprotect the incoming media packet.

This change is critical because it ensures that the transition between SRTP stops and restarts does not inadvertently lead to a reversion to an insecure transport method. In essence, capturing the SRTP policies before the session is terminated prevents the loss or corruption of the security context that is essential for correctly reestablishing the encrypted session. By avoiding any mix-up that could result in the use of basic RTP, the patch effectively stops the vulnerability that would have allowed secure media to be transmitted insecurely.

This reasoning underscores a broader security principle: when performing any state-changing operations on a security subsystem, it is crucial to preserve the necessary security context before those changes occur. In this case, the safe capture of the encryption and decryption settings ensures that the secure state is maintained even if errors require restarting the session. The order of operations, therefore, is not incidental; it is a deliberate measure to prevent unintended degradation of security.
