The vulnerability occurred because, in the DTLS handshake process, the implementation was not providing any true randomness. Instead of generating a genuine random client value, the system was inadvertently using 32 bytes of zeros. This lack of randomness undermines the security of the DTLS protocol, which relies on unpredictable values to protect against certain attacks.

The underlying problem was in the conditional logic that determined when to generate a random client value. In the handshake process, especially in DTLS, the client is required to generate a random value unless a particular state—in this case, related to the Hello Verify Request—is active. The Hello Verify Request is a mechanism used in DTLS to prevent denial-of-service attacks, and it involves the server challenging the client. The buggy code erroneously checked whether the DTLS session had received a Hello Verify Request by testing if the count of such requests was equal to zero. This condition was mistakenly interpreted, so when the system was actually in a state where Hello Verify Requests were present (meaning there had been one or more such requests), the condition did not behave as intended.

The repair fixes this by reversing the check for the DTLS Hello Verify Request count. Instead of checking if the count equals zero, it now checks if it is not equal to zero. In simpler terms, the code now correctly determines that if the client is using DTLS and there has been at least one Hello Verify Request, it should skip generating a new random value. This is crucial because, in such cases, the DTLS protocol has distinct handling rules; by not generating a new random value, the client avoids using a default or zeroed value erroneously.

Additionally, by aligning the condition checking with the intended logic—that is, ensuring that true randomness is generated when needed and only bypassed when the protocol state indicates that a Hello Verify Request has been received—the repair maintains the correct balance. The fix prevents the scenario where a predictable, non-random (all-zero) value is used during a DTLS handshake, which would otherwise render any cryptographic protections moot and expose the communication to attack.

In summary, the repair corrects the logical comparison concerning the count of Hello Verify Requests in a DTLS session. It ensures that a random client value is generated only under the proper preconditions. The change of the operator in the condition helps to enforce the security guarantees of DTLS by avoiding reliance on non-random (zero-filled) data. This subtle but critical correction reinstates the protocol’s intended use of randomness, thereby eliminating the weakness that had allowed predictable values to be used instead of secure, random ones.
