The repair addresses the vulnerability by explicitly marking when a ChangeCipherSpec (CCS) message is acceptable during the TLS handshake. In the original code, the state machine that handles various handshake messages did not clearly record when a CCS message was expected. This oversight allowed an attacker to inject a CCS message at an inappropriate time, which in some circumstances resulted in the use of a zero-length master key. By doing so, the attacker could hijack sessions or extract sensitive data.

To counter this, the patched code sets a special flag at key points in the handshake process. This flag, represented abstractly as an indicator that CCS is "okay," is set right before the call that processes critical parts of the certificate verification and again before processing the Finished message. Intentionally marking the state with this flag means that later in the handshake, if a CCS message is encountered, the system can determine that the message is expected and valid, rather than treating it as an unexpected injection possibly from an attacker.

The reasoning behind placing the flag at these specific transitions is to tightly control the timing and state conditions under which a CCS message is accepted. By marking the state immediately after verifying the certificate (and similarly after preparing the Finished message), the system guarantees that any subsequent CCS messages are only processed if the handshake has indeed reached an appropriate point. In effect, this change makes the acceptance of a CCS message explicitly contingent on the handshake’s progress rather than implicitly relying on the order of messages.

Additionally, the fix extends to parts of the state machine that handle protocol negotiation differences. In the branches dealing with next protocol negotiation, the flag is also set when CCS is allowed. This ensures that regardless of the variations in the handshake pathway (whether TLS extensions like NPN or session tickets are involved), the system consistently validates that a CCS message is part of an expected and secure handshake sequence.

This approach mitigates the vulnerability by preventing an attacker from tricking the server into transitioning into a state where an injected CCS message could force the establishment of a session key that is insecure (i.e., zero-length). Thus, the correction reinforces the handshake state machine by requiring an explicit acknowledgment (via setting the flag) that a CCS message is acceptable at that juncture, rather than accepting such messages based solely on the timing or the order of the handshake sequence.

In summary, by setting a specific flag to indicate that the CCS message is expected at certain points, the repair ensures that any injected CCS messages are either correctly anticipated or rejected. This prevents the exploitation that allowed a man-in-the-middle attacker to override critical parts of the handshake, thereby closing the security gap identified in the vulnerability.
