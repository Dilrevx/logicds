The repair involves switching which parameter is accessed from the provided parameters, so that the correct key is used for computing the MAC. Originally, the code was retrieving the AAD parameter – the additional authenticated data – when it should have been locating the MAC key parameter. In the vulnerable implementation, using the AAD data as the MAC key results in a key that is easily predictable, since AAD is typically either known or straightforwardly derived. This predictability allows an attacker, for example through a man-in-the-middle attack, to modify messages yet still generate valid MACs, successfully bypassing integrity checks.

By altering the code so that it now locates the parameter associated with the actual MAC key, the repair ensures that the MAC key used in the cryptographic operations is generated and managed securely and unpredictably. The proper MAC key is designed to be random and is kept secret between endpoints, making it exceedingly difficult for an attacker to guess or manipulate. This change directly thwarts the possibility of an attacker successfully modifying the message content without being detected by the integrity check, as the MAC now relies on a secure key rather than on a predictable piece of additional data.

In summary, the essence of the fix is to ensure that the system retrieves and uses the MAC key from the correct parameter. This prevents the earlier situation where a component intended as additional authenticated data was erroneously used as the MAC key. The shift to referencing the AEAD_MAC_KEY means that all security procedures relying on this key are now based on truly secure and random data, thus mitigating the vulnerability that could have been exploited for tampering.
