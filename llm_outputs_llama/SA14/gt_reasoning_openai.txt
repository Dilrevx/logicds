The vulnerability arises because during the TLS handshake, OpenSSL did not properly track when a ChangeCipherSpec (CCS) message was expected, which allowed an attacker to inject a CCS message at an inappropriate time. This could lead to the handshake proceeding even though a valid master key wasn’t established—in effect, letting attackers force the use of a zero-length master key. Such an attack enables session hijacking or exposure of sensitive data.

In the original code, when processing the Finished message state, the code does not update any internal indicators that a CCS message was correctly received. It only prints a message, calls the function to get the Finished message, and then advances the handshake state. Without setting an internal flag, the system might be misled by an injected CCS message earlier in the handshake.

The repair addresses the problem by explicitly marking the handshake state with a flag before processing the Finished message. This added flag serves as an internal marker that the CCS message has been correctly acknowledged as part of the handshake protocol. What happens is that even if an attacker injects a CCS message, the handshake will only continue if the appropriate conditions are met. By updating the internal handshake state with this flag, the system can later verify that the CCS message was legitimately received and timed appropriately within the exchange.

The repair essentially improves the protocol’s integrity checks. The new step adds a clear indicator in the state management, which functions as an additional verification point. This indicator helps ensure that only a properly processed CCS message will allow the handshake to move forward. Consequently, any unexpected or out-of-order CCS message—even one carefully crafted by an attacker—will not give the attacker the leverage to induce a protocol flaw like a zero-length master key.

In summary, the reasoning behind the repair is that by setting an internal flag at the correct moment in the handshake, it clarifies and reinforces the protocol’s expectations. This flag enforces that the CCS message is only considered valid if it appears at the correct stage of the communication process, thus blocking any attempt at CCS injection. The overall effect is a tighter and more robust handling of the handshake, which prevents attackers from exploiting the vulnerability to hijack sessions or obtain sensitive information.
