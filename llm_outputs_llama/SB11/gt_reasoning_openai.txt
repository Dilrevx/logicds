The original vulnerability arose because when an OCSP response was received for a certificate that didn’t actually belong to the chain in question, if that certificate contained the NoCheck extension, the verification process would be completely disabled. In other words, the presence of the NoCheck extension, which is meant to indicate that a certificate does not require OCSP checking under certain circumstances, was being misinterpreted. It ended up allowing a certificate—even one unrelated to the proper chain—to bypass all OCSP validation. This was dangerous because it could let an attacker supply an irrelevant certificate with NoCheck and undermine the trust model.

The initial, buggy code examined whether the certificate’s NoCheck flag was set while the verification mode was specifically “VERIFY_OCSP”. If both conditions were met, it unconditionally changed the verification mode to “NO_VERIFY”, effectively disabling any further verification of that certificate. This blunt treatment did not consider the context or the intended semantics of the check for OCSP responses pertaining to individual certificates versus whole chains. Therefore, the repair was necessary to address the problem more carefully.

The repair changes the logic in a couple of critical ways. First, it recognizes that there is a specific verification mode for checking individual certificates via OCSP responses; this mode is called “VERIFY_OCSP_CERT”. By testing for this mode explicitly, the fix makes sure that the behavior differs from a blanket “VERIFY_OCSP”. When the mode indicates that a certificate is being directly checked (as opposed to a more general chain-checking scenario), the code then examines whether the certificate has the NoCheck flag set.

If the certificate does have the NoCheck flag, the repaired logic no longer disables verification completely. Instead, it downgrades the mode to a more general “VERIFY” mode, which will still perform regular validation. This means that even though the certificate indicates that it should normally bypass OCSP checks, the system will not leave it unchecked if it is directly involved in an OCSP verification request. On the other hand, if the certificate does not have the NoCheck flag, the verification mode remains as “VERIFY_OCSP”, ensuring that the specialized OCSP verification process is maintained.

In summary, the repair refines the decision process for dealing with OCSP responses by carefully distinguishing between a certificate that is directly in need of an OCSP check versus one that is part of a broader chain. It avoids the dangerous behavior where the mere presence of the NoCheck extension would lead to a complete bypass of certificate validation. Instead, by reverting to a general verification mode when the NoCheck flag is encountered on a certificate intended for individual OCSP checking, it ensures that all certificates undergo proper scrutiny, thereby closing the vulnerability.
