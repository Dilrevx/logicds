The vulnerability existed because the code only compared the length of the algorithm parameters and their memory contents. A NULL parameter, which is supposed to represent an absence of parameters, can have a zero length, making it appear identical to an empty array when compared solely on length and byte value. This means that a certificate with actual parameters that are represented differently could be incorrectly validated as legitimate, even though the parameters do not truly match.

The repair fixes this by first comparing an additional field called the tag in both parameter sets. In many cryptographic data representations, including ASN.1, the tag indicates the type of the value that follows. By checking that the tags are equal, the fix ensures that the certificate’s signature algorithm parameters are not simply similar in length and content by chance but are of the same type. If one parameter is marked as a NULL type while the other might be encoded as an empty REAL array (despite both having zero length), the discrepancy in their tags will cause the verification to fail.

After the tag comparison, the repair still checks the length of the parameters to ensure they match exactly. Then, if the length isn’t zero, it goes on to compare the memory content. This multi-layered check ensures that not only the content and size are identical but also that the underlying representation (i.e., the type of the parameters) is the same.

Essentially, the reasoning for the addition is that matching a certificate’s signature requires strict equivalence between all aspects of the algorithm parameters, including their type information represented by the tag. Without this extra check, two values that look similar on the surface (same length and byte sequence) might represent different types of data, compromising the certificate’s validity. The extra tag comparison prevents a potential type confusion, thereby maintaining the integrity of the certificate verification process.

Overall, the repair improves the validation by ensuring that even subtle differences in parameter encoding lead to an invalid certificate, which is important for the correct operation of cryptographic protocols. This additional check helps to build confidence that the certificate’s contents have not been tampered with or misinterpreted, closing a gap where an attacker might exploit a misrepresentation of parameter types.
