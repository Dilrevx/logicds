The repair adds a critical check before accepting the SSH authentication as successful. Here’s a walkthrough of what was changed and why:

1. RFC-Compliant Check:  
   Before marking the authentication as complete, the code now verifies whether the authentication method (stored in cli_ses.lastauthtype) used in the success message is allowed. It does this by checking if the lastauthtype exists within a list (or string) of allowed authentication methods (cli_ses.allowed_authmethods). This step ensures the client won’t accept a success response for an authentication method that wasn’t advertised by the server.

2. Preventing Bypass of Extra Security Measures:  
   The vulnerability allowed an attacker to change the SSH login process, potentially bypassing additional security mechanisms such as FIDO2 tokens or SSH-Askpass. By explicitly verifying that the authentication method is one of the approved ones, the patch prevents a situation where an attacker could force a login using a weaker or different authentication mechanism. If the check fails, the code logs an error message, resets the authentication state (ses.authstate.authdone remains false), and sets the client session state to USERAUTH_FAILED. This effectively prevents the client from accepting a manipulated msg_userauth_success message.

3. Logging and State Updates:  
   Only if the authentication method matches an allowed value does the code proceed by logging a trace message that confirms the valid method, setting ses.authstate.authdone to true, and updating the session state to USERAUTH_SUCCESS_RCVD. This keeps the session information consistent with the actual authentication state.

4. Cleanup Specific to Public Key Authentication:  
   Instead of always calling the public key cleanup routine, the code now checks whether the last authentication method was public key-based. This conditional cleanup (if lastauthtype is AUTH_TYPE_PUBKEY) prevents unnecessary or potentially harmful side effects that could occur if cleanup is applied indiscriminately.

In summary, the repair fixes the vulnerability by ensuring that the client only accepts a user authentication success message if the authentication method is one that was previously negotiated and allowed. This stops attackers from exploiting non-RFC-compliant behavior to bypass additional security measures. The additional checks, correct logging, and state updates ensure that any authentication success message is correctly validated, thereby closing the security hole that previously allowed an attacker to abuse forwarded agents unnoticed.
