The repair starts by entering the TLS 1.3 finished state with the call to Tls13Helper.WOLFSSL_ENTER. This is unchanged from the original, ensuring that the entry log or initialization step is still executed at the beginning of the function handling the TLS finished message.

Immediately after this, the repair introduces a new early conditional block that verifies the client’s certificate. The purpose of this block is to enforce the mutual authentication requirement that the server expects. This check is only applicable on the server side—thus, it first checks if the current context is a server (ssl.role == SSL_SERVER). Next, it verifies if the server configuration requires mutual authentication by checking conditions like ssl.config.requireMutualAuth or ssl.config.failNoCert. These condition values indicate if the server is configured to require a valid client certificate or to fail the handshake if no certificate is provided.

Inside this block, the repair then checks two important flags: whether the peer's certificate has been validated (ssl.peerCertValidated) and whether the session is a resumed session (ssl.sessionResumed). In the normal case of a new handshake, the certificate must be verified, so if the certificate validation flag is not set and the session is not a resumed session (i.e., !ssl.peerCertValidated && !ssl.sessionResumed), then it is clear that the client either did not provide a valid certificate or intentionally skipped sending it. In a resumed session, certain verifications might be bypassed because the session is trusted from a previous handshake; that is why the resumed condition is considered acceptable.

If the check fails—meaning that the client did not meet the certificate requirements—the repair code immediately sends a fatal TLS alert using Tls13Helper.sendFatalAlert with the Constants.ALERT_BAD_CERTIFICATE constant. This action terminates the handshake by setting an error code (Constants.CERT_VRFY_E) and stops further processing. This is crucial because it prevents a malicious client from bypassing authentication checks by omitting the certificate_verify message or otherwise providing an unverified certificate.

After the mutual authentication block, the original code’s functionality is preserved: it still checks whether the buffer has enough space to accommodate the operations that follow. If the calculated size (inOutIdx[0] + size + ssl.keys.padSz) exceeds the total buffer size (totalSz), the code exits with an error code Constants.BUFFER_E. This original check is important for memory safety and remains unchanged.

In summary, by adding this early certificate validation check, the repair ensures that if the server requires a valid certificate, the handshake process will not proceed unless the client's certificate has been properly verified (unless it is a resumed session). This targeted change closes the vulnerability where a client could bypass necessary authentication checks, thereby preventing a scenario where the finished message is processed without having enforced mutual authentication.
