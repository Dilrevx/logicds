The repair introduces an additional check when iterating through the subjectAltNames of the certificate. Instead of blindly comparing every entry in the subjectAltName extension with the expected common name, the code now only performs the comparison if the entry is of type DNS name. Here’s how the repair addresses the vulnerability:

1. When the certificate has the subjectAltName extension (indicated by the corresponding flag in extTypes), the code loops through the sequence of alternate names. The original implementation compared the expected name (cn) against all entries, regardless of the actual name type.

2. The vulnerability arises because the certificate might contain entries representing an IPv4 or IPv6 address. Without checking the type, an attacker could exploit this by obtaining a certificate for an address (which might be a 4-byte or 16-byte value) that could improperly match the expected common name, thereby spoofing the identity.

3. The repair adds a conditional statement (if (cur.tag != MbedtlsConstants.MBEDTLS_X509_SAN_DNS_NAME) continue;) before the name comparison. This ensures that only entries with a tag corresponding to a DNS name (MbedtlsConstants.MBEDTLS_X509_SAN_DNS_NAME) are considered for matching against the expected common name. This filtering prevents IP address entries, or entries of any other type, from being used to bypass the common name verification.

4. If a matching DNS name is not found in the predicate-filtered subjectAltNames, then the verification flags are updated to indicate a common name mismatch. If no subjectAltName is present, the original fallback mechanism – checking the common name in the subject field – remains unchanged.

By requiring a DNS name match in the subjectAltName extension, the repair directly addresses the vulnerability. It prevents any inadvertent or malicious acceptance of non-DNS subject alternative names (like IP addresses) as valid matches for the expected common name, thus restoring the integrity of the certificate validation process.
