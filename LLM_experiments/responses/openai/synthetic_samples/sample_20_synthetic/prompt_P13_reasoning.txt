The repair adds an extra check to ensure that the certificate name being compared comes from a DNS entry in the subjectAltName extension. In the buggy code, any entry in the subjectAltName extension was used to match the expected common name regardless of its type. This behavior allowed an attacker to potentially use an IP address in the certificate—either a 4-byte IPv4 or a 16-byte IPv6 address—to impersonate a domain name.

Here's what the repair does:

1. It introduces a condition that explicitly checks whether the type of the subject alternative name is MBEDTLS_X509_SAN_DNS. This means that only those entries designated as DNS names will be evaluated for a match against the expected common name.

2. By limiting the comparison to DNS names, the repair prevents non-DNS names (such as IP addresses) from being used as valid identifiers. Even if an attacker controls an IP address or manages to get a certificate with a subjectAltName of an IP type, such entries will no longer be considered valid matches for a hostname expected by the client or server.

3. The change directly addresses the vulnerability described: it stops non-domain types from being considered equivalent to a domain name during certificate verification. The certificate check now explicitly separates the types of entries in the subjectAltName extension, protecting against the potential impersonation when non-DNS types inadvertently pass the CN check.

In summary, the fix ensures that only DNS entries are eligible for matching against the expected common name provided (cn). This targeted approach to certificate name verification removes the possibility of an attacker exploiting the type-blind matching behavior that was present in the original code, thereby mitigating the related vulnerability.
