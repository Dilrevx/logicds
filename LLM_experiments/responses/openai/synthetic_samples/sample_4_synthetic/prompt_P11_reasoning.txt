The original code locates the AEAD_TLS1_AAD parameter from the provided parameters. This value was originally intended to serve as additional data (AAD) for the encryption process. However, in the buggy code it was being misused as the MAC key, which makes it predictable. Because AAD is often either known or can be influenced by an attacker (especially in a man-in-the-middle scenario), relying on it as the MAC key undermines the integrity check. An attacker could manipulate the AAD, guess the MAC key, and forge data that passes the MAC verification.

The repair addresses this flaw by changing the parameter being located from AEAD_TLS1_AAD to a dedicated MAC key parameter, in this case labeled as OSSL_CIPHER_PARAM.AEAD_MAC_KEY. By doing so, the code now correctly retrieves the parameter intended to carry the actual, securely generated MAC key, rather than relying on potentially predictable additional authenticated data.

Here’s the step-by-step breakdown of what occurs after the repair:

1. The code calls OSSL_PARAM_locate_const with OSSL_CIPHER_PARAM.AEAD_MAC_KEY as the key, ensuring it retrieves the parameter that actually holds the MAC key.
2. The dedicated MAC key is expected to be generated and provided securely, independent of the AAD.
3. Since the MAC key is no longer derived from the AAD, it becomes unpredictable to an attacker. Even if the attacker can modify the AAD, they cannot influence the MAC key, ensuring the integrity verification cannot be easily bypassed.

This modification reinforces the security by ensuring the MAC key is properly separated from the AAD. Secure cryptographic protocols demand that keys must be unpredictable and secret; combining or conflating the key with data that might be controlled or known to an adversary is a critical flaw. The change aligns with cryptographic best practices and prevents a man-in-the-middle attack that exploits the vulnerability by forging a valid integrity check.

In summary, the repair fixes the vulnerability by ensuring that the MAC key is correctly obtained from its dedicated parameter rather than the AAD. This separation ensures that the MAC key remains secure and unpredictable, effectively closing the door on the type of man-in-the-middle attack described in the vulnerability notice.
