The repair adds a specific check to see if the current cipher in the context is RC4-MD5. With the vulnerability, the RC4-MD5 ciphersuite in OpenSSL 3.0 mistakenly uses the AAD (Additional Authenticated Data) as the MAC (Message Authentication Code) key. Because the AAD can often be controlled or predicted by an attacker, this makes the MAC key predictable and vulnerable to man-in-the-middle attacks.

To address this, the code now checks whether the active cipher is RC4-MD5 (using a condition like ctx->cipher->nid == NID_rc4_md5). If the cipher is indeed RC4-MD5, the code deliberately avoids calling OSSL_PARAM_locate_const to fetch the AEAD_TLS1_AAD parameter—setting the variable p to NULL instead. This bypasses the logic that would otherwise use the AAD as the MAC key. For all other ciphers, the function behaves normally by using the existing lookup function.

By skipping the lookup for the specific and vulnerable RC4-MD5 ciphersuite, we prevent the system from incorrectly using the predictable AAD for MAC validation. Therefore, even if an attacker tries to modify or predict the AAD data, it will not translate into a compromise of MAC integrity. This repair thus counters the security weakness without broadly affecting the functionality of other, unaffected ciphersuites.

In summary, the repair ensures that when using RC4-MD5, the flawed behavior is skipped. The modification effectively isolates the vulnerability to the problematic ciphersuite, avoiding the substitution of the AAD as the MAC key, and therefore mitigating the risk of a man-in-the-middle attack exploiting this flaw.
