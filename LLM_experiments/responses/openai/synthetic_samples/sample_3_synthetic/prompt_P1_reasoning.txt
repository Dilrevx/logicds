The repair adds an explicit check for a custom cipher with an undefined NID (NID_undef) before further processing. Here's the walkthrough:

1. The repair begins by verifying if the custom cipher belongs to a context that might use legacy handling (when an engine is present or specific implementation details exist). This mirrors the original condition.

2. A new conditional check was added to verify if the provided cipher is not null and if its NID equals NID_undef. The NID (Numerical Identifier) uniquely identifies a cipher. The vulnerability arose because a custom cipher could be created with NID_undef, which then allowed OpenSSL to mistakenly match it to the NULL cipher (i.e., a cipher that performs no encryption). This would effectively output plaintext as ciphertext.

3. If the custom cipher’s NID is found to be NID_undef, the code now immediately throws an IllegalArgumentException. This stops the execution path, ensuring that no further processing occurs with the insecure cipher. By rejecting the cipher early, the repair prevents the misinterpretation and the dangerous fallback to the NULL cipher provided by OpenSSL.

4. If the cipher passes the NID check (i.e., it’s not defined as NID_undef), the function continues with the original cleanup and legacy handling logic—resetting internal state and freeing the previously fetched cipher.

In summary, the fix ensures that any custom cipher created with an undefined NID is recognized and rejected early on. This eliminates the risk of inadvertently using the NULL cipher (and thus leaking plaintext) because the code now actively prevents insecure cipher configurations from being processed.
