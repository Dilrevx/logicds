The repair adds a check for an invalid cipher identifier (NID_undef) to ensure that only custom ciphers with a valid NID are processed. Here’s the breakdown of the changes:

1. Before performing any operations with the cipher, the code now calls EVP_CIPHER_nid(cipher) to get the NID associated with the cipher. The function gives an integer identifier that is expected to be unique for each valid cipher.

2. The code compares this NID with NID_undef. If the NID equals NID_undef, it indicates that an invalid or undefined identifier was provided when the cipher was instantiated. This is precisely the vulnerability: if an application inadvertently (or maliciously) passes NID_undef, the cipher lookup may inadvertently match the NULL cipher from the provider, resulting in plaintext output without proper encryption.

3. By detecting the NID_undef scenario, the repair immediately calls ERR_raise to record an appropriate error (using an error code like EVP_R_UNSUPPORTED_CIPHER). This prevents the vulnerable code path from continuing, thus guarding against the NULL cipher being fetched. The function then returns an error (in this example, returning 0) to indicate that the initialization has failed due to an unsupported cipher.

4. If the cipher’s NID is valid, the code continues with its processing: matching and possibly unsetting the fetched cipher, freeing it, and then calling legacyHandling to continue with the encryption or decryption initialization.

This repair ensures that only custom ciphers with a proper NID are allowed into the legacy handling process. By refusing to process ciphers with NID_undef, the repair prevents the function from mapping to the NULL cipher inadvertently—a situation that would allow plaintext to be output as ciphertext. This targeted check effectively mitigates the vulnerability found in OpenSSL versions 3.0.0 to 3.0.5.
