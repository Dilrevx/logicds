The vulnerability occurred because the code stopped the SRTP transport before it saved the current crypto policies. If stopping the transport altered or cleared these policies, the restart could use incorrect or uninitialized settings, leading to a fallback to basic, insecure RTP. The repair fixes this by changing the order of operations.

Before calling the stop function, the repair first retrieves and stores the current transmit (tx) and receive (rx) security policies from the SRTP context. By extracting these security-critical parameters beforehand, the integrity of the secure configuration is preserved across the stop and restart procedure.

After saving the policies, the code stops the SRTP transport using pjmedia_transport_srtp_stop(srtp). This step is necessary to deal with the error condition, but because the security policies were already saved, stopping the transport will not affect the critical configurations.

Next, the restart is attempted with pjmedia_transport_srtp_start(srtp, tx, rx), using the previously saved policies. If this restart is successful and SRTP is not being bypassed (as indicated by srtp.bypass_srtp being false), the code proceeds to process the received packet securely with srtp_unprotect(srtp.srtp_rx_ctx, pkt, len).

This reordering is key: by preserving the security context (tx and rx policies) before the transport stop, we ensure that the secure SRTP parameters are used in the restart process. Consequently, even if the SRTP context is reset or cleared during the stop operation, the correct and secure configuration information is available for reinitializing the session.

Thus, the repair ensures that even in error conditions—such as replay attacks or other cryptographic errors—the media stream is not downgraded to an unencrypted RTP session. By maintaining the security attributes, the integrity and confidentiality of the media transmission are preserved, preventing the inadvertent use of basic RTP which would transmit media insecurely.
