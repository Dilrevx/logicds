The repair fixes the vulnerability by ensuring that after an SRTP restart is performed due to replay-related errors, the code always validates the packet’s protection using srtp_unprotect. Previously, the reattempt of packet decryption was conditional on the bypass_srtp flag not being set (i.e., !srtp.bypass_srtp). This flag condition could allow packets to be processed without revalidating their protection, which in some edge cases might result in processing insecure media (i.e., basic RTP), defeating the purpose of SRTP protection.

In the repaired code, we removed the check for the bypass_srtp flag when reattempting srtp_unprotect after a restart. Now, when a replay-related error occurs during the probation period, the transport is stopped, restarted with the corresponding transmit and receive policies, and then the srtp_unprotect function is always called again regardless of the bypass_srtp flag’s status. This change ensures that any packet processed has its SRTP protection correctly validated. Only if the unprotection attempt returns PJ_SUCCESS will the callback be invoked to process the packet.

By doing this, the repair prevents the vulnerability where a mistaken switch from SRTP to basic RTP could occur after a restart. The removal of the bypass_srtp condition guarantees that packets will not be processed without proper SRTP decryption verification, maintaining the intended security level for all media streams. This fix effectively ensures that even in exceptional cases involving replay errors, packets are processed only if they have passed the secure SRTP unprotection step, preserving the integrity and confidentiality of the media transport as originally intended.
