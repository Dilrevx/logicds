The repair adds an additional check to distinguish between two cases:

1. No ACL file is configured at all – in this situation, where both aclList and aclPatterns are null, the function returns MOSQ_ERR_PLUGIN_DEFER to let other parts of the system handle permissions.

2. An ACL file is configured but its content is effectively empty (i.e. it contains only comments or blank lines). The enhanced logic checks if both aclList and aclPatterns are either null or empty. In that case, instead of deferring, the function returns MOSQ_ERR_ACL_DENIED. This change ensures that when an ACL file is explicitly provided yet has no meaningful rules defined, the system will deny all access rather than incorrectly allowing access via a default allow policy.

This fix addresses the vulnerability by preventing the scenario where an empty or comment-only ACL file is mistaken for “no ACL file at all.” Without this additional check, Mosquitto would mistakenly treat an empty ACL file as if no ACL file were defined. With the updated logic, administrators who supply an ACL file (even if it’s empty after filtering out comments and blank lines) will encounter strict deny-all behavior instead of unintentional access being granted. This makes the behavior consistent and more secure, as it avoids a subtle security misconfiguration that could otherwise lead to unexpected open access.

The repair is implemented by checking if aclList and aclPatterns are effectively empty, and if so, the function returns an error value (MOSQ_ERR_ACL_DENIED) that signals the deny-all policy. This clear differentiation aligns with a “fail closed” security model whereby missing or empty access control configurations do not default to permissiveness.
