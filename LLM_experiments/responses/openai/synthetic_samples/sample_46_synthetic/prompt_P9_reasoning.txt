The repair ensures that only the principal “kadmin/admin” is granted administrative access. Here’s how the changes address the vulnerability:

This logic left room for an attacker to craft a two-component principal such as “kadmin/somethingelse” (other than “history”) and inadvertently gain administrative privileges.

2. In the repaired code, we now require a strict match: not only must the realm be correct and the first principal component be “kadmin”, but the second component must exactly be “admin”. By checking for “admin” instead of any string that is not “history”, we remove the possibility of bypass. The vulnerability arose from the fact that any non-“history” second component would have led to administrative access. Now, only “kadmin/admin” is permitted. 

3. The explicit check prevents misuse because an attacker can no longer pass any arbitrary value in the second component. Rather than only excluding “history”, the new check ensures that only the expected value “admin” will be accepted. This means that a principal with “kadmin/history” or any other alternative than “admin” in the second component won’t be granted access.

4. The code is structured so that if the conditions for both components (and the realm) are met, the variable (e.g., success) is set to 1 (indicating success). For any other case, it sets it to 0 (indicating failure). This provides a clear and strict check.

Ultimately, this change is a more secure design because it involves a whitelist approach (only “kadmin/admin” is allowed) rather than a blacklist approach (blocking only specific undesired values, like “history”). A whitelist-based check is generally preferred because it minimizes the risk that an attacker might exploit unanticipated or future substitutions that the blacklist did not cover.

In summary, by replacing a lenient authorization check with a strict equality check for both expected principal components, the repair directly addresses the vulnerability that allowed bypassing kadmin authorization by ensuring that only the fully expected two-component principal (i.e., “kadmin/admin”) can obtain administrative access.
