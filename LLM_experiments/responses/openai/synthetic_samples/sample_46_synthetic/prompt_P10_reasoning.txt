The repair modifies the logic used to decide whether to grant administrative access by enforcing that the principal must match exactly "kadmin/admin" within the proper realm rather than allowing any two-component principal that doesn’t have “history” as its second component.

Originally, the function first checked that the principal had exactly two components. Then it inspected the first component (c1) and the realm. If both matched—the realm equal to the server realm and c1 equal to "kadmin"—it would then check if the second component (c2) was set to "history." If c2 was "history" the code explicitly set success to 0 (denying access), but if c2 was anything else it set success to 1 (granting access). This behavior allowed an attacker to bypass the intended authorization check simply by ensuring their principal had two components, with the first being "kadmin" and the second being anything other than "history."

In the repaired code, the following changes were made:

• The code still verifies that the principal has exactly two components. This limits the eligible names to a two-component form.

• When comparing the principal’s components and realm, the repair now explicitly checks that the first component is "kadmin" AND the second component is "admin." This tighter check ensures that only a principal that is exactly "kadmin/admin" is allowed administrative access.

• If the principal’s realm does not match the server’s realm, or if either the first component is not "kadmin" or the second component is not "admin," the function logs an error and returns success as 0 (i.e., access denied).

By requiring the second component to be "admin" rather than simply not "history," the patch prevents attackers from crafting alternative two-component principal names (such as "kadmin/special") to obtain administrative access. This correction directly fixes the vulnerability described by ensuring that only explicitly recognized administrative service principal names (“kadmin/admin”) are granted elevated privileges.

Overall, the repair strengthens the authentication mechanism by performing an exact match on the expected principal name components instead of accepting a broader range of valid names, thereby closing the gap that could be exploited for unauthorized administrative access.
