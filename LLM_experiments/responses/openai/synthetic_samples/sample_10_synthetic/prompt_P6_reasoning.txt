The repair distinguishes a truly NULL algorithm parameters entry from an empty (zero-length) array. In the original code, a zero length (len == 0) was treated the same regardless of whether the pointer was NULL or not. Under the vulnerability, a NULL entry (which should be invalid if the other parameter isn’t also NULL) could be mistaken for an empty array, causing the certificate to be accepted improperly.

In the fixed code, the conditional now checks the following: If the lengths of sig_params1 and sig_params2 differ, it immediately flags an error. For the case where the length is zero (sig_params1.len == 0), instead of ignoring the pointer values, it explicitly verifies that the pointers are identical. If they are not identical, even though the lengths are both zero, this indicates a mismatch between a true NULL parameter and a non-NULL (but empty) parameter; hence the certificate is considered invalid. For cases where the length is non-zero, the function uses equalBytes (with the correct length specified) to ensure that the parameter contents are identical.

This approach fixes the vulnerability by ensuring that any discrepancy in the algorithm parameters—even differences that occur with zero-length data due to NULL versus non-NULL pointer values—results in the certificate being rejected, thereby preventing an attacker from exploiting parameter mismatches in the certificate validation process.
