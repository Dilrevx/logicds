The original code allowed a range of nonce lengths rather than enforcing a strict requirement. Since OpenSSL’s ChaCha20-Poly1305 implementation permits nonce lengths up to 16 bytes, accepting any value within an interval can mislead an application into thinking that varying the higher-order bytes creates a unique nonce. In reality, only the last 12 bytes are used, which means that the variability outside those bytes is effectively ignored. This discrepancy can lead to a scenario where an application inadvertently reuses a nonce, thereby compromising the cryptographic guarantees of the encryption scheme.

The repair changes the validation condition so that only a nonce with a length of exactly 12 bytes is accepted. This update is crucial because the RFC 7539 specification explicitly mandates a nonce length of exactly 96 bits, which is equivalent to 12 bytes, for ChaCha20-Poly1305. By enforcing this exact length, the repair ensures that each nonce is used uniquely and correctly, removing the ambiguity that could arise when nonces of other lengths are considered.

When a nonce of any length other than 12 bytes is encountered, the function now reliably rejects it. This prevents any usage of nonce values where the application might falsely believe that modifying the forbidden higher-order bytes would result in a distinct nonce. Consequently, the risk of nonce reuse—and thereby the potential for nonce-related cryptographic failures—is mitigated.

In short, this change aligns the code with the recommended cryptographic practices and standards. It eliminates a subtle vulnerability that, if exploited, might allow harmful attacks due to improper nonce management. The repair achieves this by reducing the attack surface to a single valid nonce length, aligning closely with the intended and secure use of the ChaCha20-Poly1305 construction.
