The repair adds a check to ensure that a ChangeCipherSpec (CCS) message is only processed once during the handshake. Here’s a breakdown of how the repair works:

If this flag is already true, it indicates that a CCS message has been processed previously. In this case, the code writes an error message to the error stream and returns an error code (–1). This behavior prevents an attacker from injecting a duplicate CCS message to trigger the use of a zero‐length master key.

2. When the CCS message is processed for the first time, the code proceeds to execute the existing logic by calling ssl3_get_finished(). If this call fails (i.e., ret is less than or equal to 0), the handshake is aborted by returning the error code.

3. After successful processing of the finished message, the repair sets the state.ccsReceived flag to true. This flag makes sure that if any further CCS messages are received later in the handshake, they can be detected and rejected, mitigating any potential manipulation.

4. Finally, the handshake state is updated to indicate that the SSL/TLS handshake is successful (SSL_ST_OK).

By adding this check, the repair prevents an adversary from being able to send an unexpected or duplicated CCS message. In the original vulnerability, the attacker could inject an extra CCS message that exposed the protocol to the possibility of using an incorrect (zero-length) master key. Restricting the CCS message to a single valid instance ensures that any crafted additional messages are caught early and do not compromise the session’s cryptographic integrity.

In summary, the repair addresses the CCS Injection vulnerability by tracking whether a CCS message has already been received and by rejecting any duplicates. This change prevents the exploitation where a duplicate CCS could be injected, thereby preserving the integrity and security of the session during the TLS handshake.
