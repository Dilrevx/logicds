The repair introduces an explicit check to confirm that a valid ChangeCipherSpec (CCS) message has been received before processing the Finished message. Here’s how the changes work:

1. Before executing the original logic, the code verifies the handshake state by checking the state.ccsReceived flag. This flag is assumed to be set when a valid CCS is processed earlier in the handshake. If it isn’t true, the code logs an error and aborts processing by returning an error code (in this case, -1). This prevents the handshake from continuing if the CCS message wasn’t received in the correct order.

2. By ensuring that the CCS message came before the Finished message, the code averts the possibility of an attacker injecting a spurious CCS message with a zero-length master key. The CCS Injection vulnerability occurs when a CCS message not properly tied to the handshake is accepted, potentially undermining key derivation, causing the session to use insecure keys, or leading to other cryptographic anomalies.

3. The repair allows the handshake to proceed only if the flag state.ccsReceived is true. Once confirmed, it logs that processing will continue, and then it calls ssl3_get_finished(), which computes or verifies the Finished message. Successfully completing this means the handshake is in its correct sequence, and then the handshake stage is advanced to SSL_ST_OK.

4. Overall, this fix enforces the proper sequence of events. If an attacker were to try a CCS injection, the handshake state would not indicate that a proper CCS was received, and the Finished message would be rejected. This stops the compromised handshake completion and mitigates session hijacking or sensitive information exposure.

In summary, by introducing the state.ccsReceived check, the repair ensures that the handshake adheres to the expected message order (i.e., a valid CCS before Finished), thus effectively closing the vulnerability that allowed CCS injection in certain OpenSSL-to-OpenSSL communications.
