The repair addresses the vulnerability by preventing the processing of multiple ChangeCipherSpec (CCS) messages, which is one of the root causes exploited by the CCS Injection vulnerability. In the original code snippet, the function proceeds to process the Finished message without checking if a CCS has already been handled during the handshake. This lack of verification potentially allows an attacker to inject a CCS message at an earlier stage of the handshake and manipulate the state of the connection, such as by causing a zero-length master key to be used. This could lead to session hijacking or other security breaches.

To mitigate this, the repair introduces a check against a flag—here represented as state.ccsReceived—that indicates whether a CCS message has already been processed. Specifically, before proceeding with the normal Finished state processing, the code examines if the flag is set. If it is, the method logs an appropriate message ("Duplicate CCS message detected; aborting handshake.") and returns an error code (in this case, -1), effectively aborting the handshake process. This prevents any duplicate or unexpected CCS messages from being processed further.

The flag itself (state.ccsReceived) plays a crucial role in maintaining the integrity of the TLS handshake. By marking the point in the handshake where a valid CCS message is received, the system ensures that subsequent attempts to process additional CCS messages are rejected. Essentially, it transforms the handshake process from one where such messages may be accepted without validation into a process where the order and uniqueness are strictly enforced. This simple, yet effective, change stops the CCS Injection attack because any attempt by an attacker to inject another CCS message after one has already been processed will immediately cause the handshake to fail.

Another important point is that the error handling ensures that the handshake stops in a controlled manner. Instead of blindly accepting subsequent messages, the server (or client, depending on context) logs the abnormal behavior and terminates the session, alerting the underlying system to a potential attack. This is preferable to allowing a handshake to complete, potentially with compromised parameters, which would be much more dangerous.

It is also worth noting that this solution integrates easily into a system that already understands and maintains state information throughout the handshake process. The introduction of the state.ccsReceived flag is a minimal and non-intrusive change that leverages existing state management infrastructure. Thus, it preserves compatibility with the system’s overall design while significantly enhancing security.

Overall, the repair prevents the CCS injection vulnerability by ensuring that only one CCS message is considered valid for each handshake, thereby preserving the integrity of the TLS session establishment. It demonstrates the principle of state-checking and validation in security-critical protocols, making sure that protocol rules are strictly adhered to, and any deviations are treated as potential threats.
