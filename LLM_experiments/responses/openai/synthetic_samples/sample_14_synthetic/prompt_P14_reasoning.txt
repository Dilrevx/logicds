The repair adds an explicit check for a properly received ChangeCipherSpec (CCS) message before processing the Finished message. Here's a step-by-step explanation:

1. Detection of CCS reception:  
Before processing the Finished message through the function call ssl3_get_finished(), the code now verifies that a legitimate ChangeCipherSpec message has been received by checking the state flag (state.ccsReceived). This flag should be set when a proper CCS message arrives earlier in the handshake, ensuring that the protocol sequence is being followed rightly.

2. Aborting on improper sequence:  
If the flag is not set, which suggests that an attacker might have injected a CCS message or manipulated the handshake sequence, the code immediately logs an error message and aborts the handshake by returning an error code (in this case, -1). This prevents the continuation of any further processing that might lead to the use of an incorrect or zero-length master key.

3. Verification and State Transition:  
When the flag confirms that a CCS message has been received, the code proceeds with processing the Finished message by calling ssl3_get_finished(). On successful processing (i.e., return value > 0), the handshake state is updated to SSL_ST_OK, finalizing this crucial phase of the handshake.

4. Resetting the Flag:  
After processing, the flag state.ccsReceived is reset to false. This is an important step because it ensures that any later unsolicited or extra CCS messages during subsequent handshake phases will not be mistakenly trusted. It forces the system to validate each critical transition step per handshake session individually.

How This Fixes the Vulnerability:  
The vulnerability, known as the CCS Injection, occurs when an attacker can force the use of a zero-length master key by injecting rogue CCS messages. By introducing a check for the proper order of the handshake (requiring a legitimate CCS message ahead of the Finished message), the repair ensures that an attacker cannot manipulate the state transition without triggering an error. This enforcement of protocol order safeguards the transition between pending and current cipher states, preventing the handshake from using an insecure or improperly configured master key.

In summary, the repair makes the handshake more robust by adding a check that strictly enforces the correct sequence of messages. The repair aborts the handshake when it detects a violation of this sequence, thereby blocking any attempted CCS injection, and thus helps secure the session against man-in-the-middle attacks.
