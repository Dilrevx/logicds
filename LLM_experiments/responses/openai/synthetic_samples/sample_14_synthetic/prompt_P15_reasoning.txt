The repair adds an explicit step to mark that a ChangeCipherSpec (CCS) message is allowed in this specific handshake state. Previously, when handling the Finished message from the client, the code would simply move on to fetching the Finished message without any indication to other parts of the system that a CCS message was expected. This omission allowed an attacker to potentially inject a CCS message at an inappropriate time, leading to the possibility of creating a zero-length master key and compromising session security.

In the repaired code, before the function obtains the Finished message (via the ssl3_get_finished function call), a flag is set in the handshake state structure. Specifically, the code uses a bitwise OR (|= operator) to set a flag (named CCS_ALLOWED) within a flags field. This flag acts as a signal that, during this phase of the handshake, it is explicitly allowed to accept a CCS message. Later in the protocol processing, any module that checks whether a CCS is valid can confirm that CCS messages are acceptable at this point in the handshake.

Only after this flag is set does the function proceed to call ssl3_get_finished. If obtaining the Finished message fails, the connection is aborted by returning early, ensuring that the handshake does not continue in an incomplete or insecure state. If the call is successful, the handshake state is updated to indicate that the handshake process has completed (transitioning to SSL_ST_OK).

By inserting this flag-setting operation, the code now tightly controls when CCS messages are allowed. It prevents attackers from taking advantage of the earlier vulnerability by injecting these messages at times when they should not be processed. Consequently, the attack surface for triggering a zero-length master key is removed, thereby addressing the vulnerability known as CCS Injection.

Essentially, the repair mitigates the vulnerability by ensuring that the system recognizes the legitimate context for a CCS message. The explicit flag helps subsequent parts of the code confirm that the CCS message is not an unexpected or malicious injection, reinforcing the integrity of the handshake process and bolstering overall session security.
