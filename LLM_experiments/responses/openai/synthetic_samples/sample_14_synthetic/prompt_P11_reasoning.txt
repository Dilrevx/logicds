If the flag isn’t set, it implies that the CCS message was received out‐of-order, which could indicate a CCS Injection attack.    By checking the flag, the repair ensures that the processing of the Finished message can only occur if a valid CCS message was seen in the proper sequence during the handshake. This prevents an attacker from injecting a CCS message (allowing a session hijack with a zero-length master key) earlier than intended. The check effectively mitigates the vulnerability whereby an attacker could force a situation with a compromised master key.

   Once the CCS flag has been confirmed and the message processed, the repair clears the flag (using bitwise AND with the inverse of the flag) to prevent subsequent re-use. This ensures that any additional CCS messages (which might be maliciously injected later) are recognized as invalid, further safeguarding the state of the handshake.

   After verifying the order of operations and clearing the flag, the code continues with the existing logic to process the Finished message (ssl3_get_finished) and update the handshake stage. This ensures that the handshake only completes if all steps have been securely and properly executed.
