The original code was intended to retrieve the CRL entries from the OpenSSL store context so that revoked certificates can be verified during the TLS handshake. In a correct implementation, the retrieval of CRLs should consider the certificate issuer as a key detail because CRLs are issued by certification authorities (CA) and contain the signatures of revoked certificates issued by them. However, the buggy code mistakenly uses the subject variable in both the OpenSSL 1.1 and earlier (OpenSSL 1.0) branches when calling the get1_crls function. This double-checking of the certificate subject field (rather than using issuer for one of the checks) could potentially ignore valid CRL entries whose issuer would normally be checked. This misstep could permit a scenario in which a certificate, even if it has been revoked, might be accidentally allowed to proceed through the TLS connection if the appropriate check against the certificate’s issuer is not executed.

The repair addresses this vulnerability by replacing the incorrect use of the variable “subject” with “issuer” in both branches of the version check. The logic behind this repair can be explained as follows:

1. For the branch handling OpenSSL version 1.1 (when Commons.OPENSSL_VERSION_NUMBER is greater than or equal to Commons.OPENSSL_1_1 and LibreSSL is not in use), the function storeCtx.get1_crls was erroneously passed the subject value. Instead, it should be passed the issuer because the CRL should be identified by the certificate's issuer. This is important since CRLs are generally stored under the issuer name, not the subject name of the certificate requesting validation.

2. For the earlier version of OpenSSL (version 1.0), again ensuring that LibreSSL is not used, the function Commons.get1_crls takes the CRL store context and the identifier parameter. In the buggy version, the same mistake occurs by using the subject value. Replacing it with the issuer correctly aligns with the expected behavior of verifying the certificate’s status by checking against the corresponding CRL published by the certificate authority.

3. The security rationale behind this change is that without examining the issuer field, the code risks missing the necessary CRL. This omission could inadvertently allow connections that should have been terminated because one or more certificates in the chain possibly have been revoked. An attacker might force scenarios where the revoked certificate is evaluated against a CRL entry that exists under its issuer rather than its subject; if the subject is used, such CRL entries would be overlooked, potentially establishing a connection based on incomplete trust chain verification. Therefore, ensuring that the issuer is checked is crucial for preventing unauthorized or potentially malicious connections during TLS negotiation.

4. This fix restores the intended security check: a proper CRL lookup against the issuer’s CRL database is now implemented regardless of the OpenSSL version. This ensures that any certificate revocation, based on correctly referenced CRL entries, is adequately enforced throughout TLS sessions, thereby mitigating the risk of allowing revoked certificates to be used in secure connections.

By making these modifications, the vulnerability is effectively addressed, and the integrity of the TLS certificate validation process is reinforced, reducing the risk of a man-in-the-middle or impersonation attack that could exploit a revoked certificate.
