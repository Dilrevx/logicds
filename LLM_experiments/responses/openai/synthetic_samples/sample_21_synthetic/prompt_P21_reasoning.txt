The repair first retrieves the pre-shared key (PSK) extension from the negotiated extensions and checks if a valid, chosen PSK is present. It then also retrieves the key share extension and determines whether it is present. This dual-check is critical because the vulnerability arises when neither a valid PSK nor a key share is provided—conditions under which earlier versions would fall back on a default, predictable input key material (IKM) value. A predictable IKM severely compromises the security of the session, since an attacker who knows or can anticipate this default material may be able to recreate the master secret and, therefore, decrypt or tamper with the session traffic.

In our repair, we add an explicit check: if there is no chosen PSK (i.e., no valid PSK extension) and the key share extension is also missing, the function aborts the handshake by returning a handshake failure error code. This change ensures that insecure fallback to a predictable default IKM does not occur, forcing the handshake to fail instead of transitioning into an insecure state.

If a valid PSK is present, the repair invokes the SetupPskKey function to securely establish the PSK key. Even though handling for a key share extension is noted as “additional key share processing should occur here,” the repair does not allow the handshake to continue solely on the basis of a key share if it isn’t properly processed. The secure path explicitly relies on proper, non-default inputs to generate the session keys.

Finally, after successful PSK and (if applicable) key share processing, the encryption is enabled and the server state is set to indicate that the server hello is complete. This orderly progression ensures that only adequately authenticated and securely negotiated parameters are used in the cryptographic processes.

Summing up, the repair fixes the vulnerability by: 

1. Avoiding the fallback to a predictable IKM when neither a valid PSK nor a key share is provided.
2. Checking for both PSK and key share extensions, thereby ensuring that a secure, fresh input is used to generate keys.
3. Aborting the connection (with a handshake failure) when secure parameters are not established, which prevents the establishment of an insecure session.

This approach upholds the security guarantees of TLS 1.3 by only proceeding when sufficient cryptographic material is provided, thereby mitigating risks of eavesdropping or tampering.
