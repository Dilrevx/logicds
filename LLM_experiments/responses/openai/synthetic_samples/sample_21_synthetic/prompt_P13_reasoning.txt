The repair introduces an explicit check for the presence of a key share extension (in addition to checking for a PSK). Previously, if neither a PSK nor a key share extension was received, the code would fall back to using a default predictable IKM, which compromised the security of the TLS 1.3 session. Here’s a step-by-step walkthrough of the changes:

1. Checking for a Key Share Extension:
   • After looking for a PSK extension and iterating to find the chosen one, the repair adds a call to check if the key share extension exists within the SSL extensions.
   • The code uses the TLSX.find() function with the key share constant. By creating a variable (keyShareExt) that holds this extension if found, we now have evidence of key share usage.

2. Aborting the Handshake if Both PSK and Key Share are Absent:
   • With the added key share check, if both the PSK (psk) and key share (keyShareExt) are absent, the repair immediately aborts the handshake by returning an error code (in this case, -1).
   • This prevents the use of a predictable “default” IKM for key derivation, thus enforcing that at least one secure method (PSK or key share) is used to derive session keys.

3. Maintaining Legacy Behavior When One Method is Present:
   • If the PSK is not provided but a key share extension is present, the handshake continues as other parts of the TLS protocol are expected to complete the key derivation using the key share.
   • If the PSK is available (i.e., not null), the code proceeds by setting up the PSK key with SetupPskKey() and marks that PSK negotiation took place.

How It Fixes the Vulnerability:
• The vulnerability arose because, without a PSK or a key share, the system defaulted to a known IKM value, making the session master secret derivation vulnerable. 
• By forcing an explicit check and refusing to continue if both secure methods are missing, the repair ensures that the TLS 1.3 client always uses a secure, unpredictable key derivation process.
• This prevents an adversary from exploiting the fallback predictable key material when they control one end of the connection.

In summary, the repair strengthens the TLS handshake by making it mandatory for at least one secure key exchange mechanism (PSK or key share) to be used, thereby eliminating the risk of falling back to an insecure default IKM.
