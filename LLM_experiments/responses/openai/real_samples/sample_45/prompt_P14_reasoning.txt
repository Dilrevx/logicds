The vulnerability was caused by the default listener’s ACL file (acl_file) not being copied over when a new listener was created with per_listener_settings set to true. In the buggy code, while several properties of the default listener were assigned to the new listener, the acl_file property was omitted. This omission meant that if the default listener specified an ACL file, it wouldn’t be applied to the new (default) listener. As a result, clients might bypass the intended access controls defined in the ACL file, leading to unauthorized access or misconfigurations.

The repair adds a new line that explicitly copies the acl_file field from the default listener’s security_options to the new listener’s security_options:

  config->listeners[config->listener_count-1].security_options.acl_file = config->default_listener.security_options.acl_file;

This line makes sure that when a new listener is configured, its ACL settings (including the ACL file path) are correctly inherited from the default listener. This consistency prevents the ACL file from being ignored. By ensuring the acl_file is copied along with all the other security options, both anonymous and authenticated clients will now be subject to the access control rules specified in the ACL file.

In summary, the repair works as follows:
1. It acknowledges that the default listener’s acl_file setting is critical for defining ACLs which control topic access.
2. The new line in the copy routine ensures that if per_listener_settings is enabled, the ACL file is applied to the current listener configuration, thereby avoiding the bypass scenario.
3. This fix enhances the security by making sure that ACLs are not skipped or misconfigured, preserving the integrity of the intended access restrictions on topics.

Thus, the repair directly addresses the vulnerability by ensuring the acl_file setting is applied consistently across all listeners under the specified configuration conditions.
