The repair adds a line that explicitly copies the ACL file setting from the default listener into the newly configured listener. In the original buggy code, if the default listener had an ACL file specified and per_listener_settings was active, the ACL file configuration was not transferred to the newly added listener. This oversight could allow clients to connect without the appropriate ACL restrictions, thereby bypassing the intended access controls.

Here's a breakdown of the fix:

1. In the repaired code, after configuring common settings (such as max_connections, protocol, socket_domain, etc.) and before setting up the security options, a new line is added:
  config->listeners[config->listener_count-1].acl_file = config->default_listener.acl_file;
 This ensures that if the default listener has an ACL file configured, the same ACL file is assigned to the newly created listener. In doing so, the ACL rules defined in the ACL file are applied as intended even when per_listener_settings is enabled.

2. The fix directly addresses the vulnerability by preventing the scenario where the default listener's ACL file is ignored—thus ensuring that all listeners are subject to the same access control policies defined by that ACL file. By copying the ACL file setting, the code no longer bypasses important security checks for connections.

3. The remaining code lines (including those managing TLS settings and other security options) continue to function as before. The only change is the addition of the ACL file copying, which directly targets the vulnerability described.

In summary, the repair ensures that the ACL file setting is not inadvertently omitted for listeners created under per_listener_settings. This means that even if the system is configured with a default listener specifying an ACL file, the access control list will be properly applied to all relevant listeners, thereby mitigating the ACL bypass vulnerability.
