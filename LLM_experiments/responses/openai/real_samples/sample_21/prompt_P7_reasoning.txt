The repair’s primary goal is to ensure that a handshake does not proceed using predictable keying material when neither the Pre-Shared Key (PSK) nor the Key Share extension is provided by the server. Previously, if neither extension was present, the code would fall back to a predictable “zeroed” PSK buffer, which could be exploited by a malicious party to force the client into using weak or known keying material for session key derivation.

The updated code first checks for a valid PSK extension if PSK support is enabled. It searches for the PSK extension and iterates through the available PSKs until it finds one that has been marked as “chosen.” Then, if key share support is present (indicated by HAVE_KEY_SHARE), it checks for the key share extension by looking it up in the extensions list.

The crucial change comes in the added conditional block that verifies whether at least one of the necessary extensions (either PSK or key share) is present. The logic now tests whether both the valid PSK and key share extension are missing. If that check determines that neither a valid PSK nor key share extension is present, the code then immediately aborts the handshake by returning an error. This prevents the client from proceeding with insecure default values that were previously used as a fallback (like the “zeroed” PSK buffer).

By aborting the handshake, the repair stops the client from engaging in a cryptographic exchange that could be compromised due to predictable keying material. This approach improves security by rejecting a handshake where the necessary and secure inputs for key derivation are absent. It ensures that cryptographic keys are derived only when the handshake features are properly negotiated, thereby upholding the cryptographic strength of the session.

In addition, if a valid PSK is found, then its key setup is processed with the proper function call. If the PSK is absent but the key share is present, the code resets the state related to the PSK by ensuring that any previously held PSK values are securely cleared and that the session is flagged as not resuming. This selective processing guarantees that the correct cryptographic material is used based on which extensions are provided during the handshake and that the system does not default to a weak, predictable state.

Overall, this repair mitigates the vulnerability by enforcing a stricter validation of the received handshake messages. Instead of allowing a fallback to a default, insecure key state, it requires the presence of at least one secure extension (either PSK or key share) before proceeding. This eliminates the risk of using a default and predictable IKM value, thereby maintaining the intended security properties of the handshake protocol and preventing potential man-in-the-middle or replay attacks that could exploit this vulnerability.
