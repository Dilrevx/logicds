The repair primarily addresses the vulnerability by preventing a potential infinite or cyclic traversal of the PreSharedKey (PSK) chain. Here’s how the changes fix the issue:

1. Limiting PSK Chain Traversal:  
   In the original code, the while loop traverses the PSK chain looking for a chosen key. However, if a malicious entity supplies a cyclic or excessively long PSK chain, the loop could run indefinitely or cause performance issues. To mitigate this, we introduce a counter variable (named “count”) and a preprocessor definition “MAX_PSK_CHAIN_LEN” to restrict the number of iterations. This ensures that no matter how the linked list is structured, the loop will exit after a limited number of steps.

2. Preprocessor Definition for Flexibility:  
   The repair includes:
   • A check to see if “MAX_PSK_CHAIN_LEN” is already defined, ensuring that users can override this limit if needed.
   • A default limit of 16 iterations if not defined elsewhere.  
   This gives a configurable and safe boundary to the traversal, reducing the risks involved with malicious input.

3. Handling Excessive or Cyclic Chains:  
   Inside the while loop, the counter is incremented each time we traverse to the next node (psk = psk->next). If the counter exceeds “MAX_PSK_CHAIN_LEN”, it assumes something is wrong (e.g., a cyclic chain) and resets “psk” to NULL. This forces the code to treat the situation as though no valid PSK was found, which, in turn, disables resumption and clears the PSK key buffer.

4. Ensuring Safety and Robustness:  
   With these changes, the repair stops the potential denial-of-service attack vector by trapping the infinite loop condition. If an attacker tries to craft a cyclic or overly long chain, the loop will exit gracefully after the maximum iteration count is reached, and the SSL session won’t use the dangerous input.

5. Normal Flow for Valid PSK Chains:  
   When the PSK chain is well-formed (i.e., it has a valid “chosen” key well within the limit), the loop exits normally. At that point, the function “SetupPskKey” is called to set up the PSK key, and the appropriate flags (like pskNegotiated) are marked, ensuring that the repaired code behaves correctly when provided with valid input.

In summary, the repair adds a safeguard against infinite or excessive loops by limiting how many nodes the PSK chain traversal can process. This systematic guard against cyclic or adversarially long chains both enhances program stability and prevents a class of denial-of-service vulnerabilities.
