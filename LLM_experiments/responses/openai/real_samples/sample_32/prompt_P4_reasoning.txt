The repair fixes the vulnerability by ensuring that one error condition does not inadvertently override another. In the original buggy code, two separate checks were performed sequentially when the X509_V_FLAG_X509_STRICT flag was enabled. The first check called check_curve(x) to detect the presence of explicitly encoded elliptic curve parameters, which, on failure, would set an error in ctx->error. The subsequent check, which verified whether the certificate had the appropriate CA attributes, would then execute without taking into account any error that might already have been set by check_curve. This means that if check_curve had flagged an error, the second block could overwrite ctx->error with a different error code. That unintended consequence led to the possibility of bypassing crucial certificate validation steps, thereby nullifying the purpose of using the strict flag in certain configurations.

The repair addresses this problem by adding a condition that checks if ctx->error is still set to X509_V_OK before executing the second CA certificate check. X509_V_OK represents a state where no error has been recorded so far during the certificate chain verification process. By testing if ctx->error is still clean, the code ensures that if check_curve has already marked a failure (for example, by setting an error for explicit elliptic curve parameters), the subsequent CA verification check will not run and hence will not override the previous error result. This means that any failure in the certificate chain due to explicit elliptic curve parameter issues remains effective and unperturbed by further checks that could mistakenly reset or change the error indication.

In particular, the vulnerability allowed an error from the valid CA certificate check to override an existing error from check_curve when non-CA certificates in the chain were being evaluated. The repair thus reinstates the proper validation order by first performing the check for explicit elliptic curve parameters, then ensuring that if an error is recorded, no additional CA certificate validity checks are performed. This logic addresses the vulnerability by preserving the error returned from check_curve, providing consistency in error reporting and maintaining strict checking as intended. Under the repair, the CA-related check is only performed if no previous error was detected (i.e., ctx->error is still X509_V_OK). Therefore, if check_curve fails, the repair prevents further modifications to ctx->error.

Another way to view the repair is that it reinforces the principle of “first error wins.” In security-critical code, it is important that once a violation is detected, subsequent operations do not modify the error state in a way that hides or replaces the original cause of the failure. This principle is vital in cryptographic and certificate validation contexts where error conditions must be accurately reported to prevent misinterpretation of a certificate’s legitimacy. By ensuring that the second check respects the outcome of the first check, our fix guarantees that the certificate chain will be rejected for the correct reason. This properly aligns with the intended security model of the X509_V_FLAG_X509_STRICT flag and prevents insecure configurations that might otherwise allow invalid certificates to pass verification checks.
