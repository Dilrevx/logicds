The repair adds a crucial check to verify that the length of the certificate’s serial number, as returned by gnutls_x509_crt_get_serial (stored in t), exactly matches the length provided in the OCSP response (rserial.size). Here’s how it works:

1. Previously, the code only compared rserial.size with cserial.size and then used memcmp on a fixed length. This left room for an attacker to manipulate the OCSP response by appending extra bytes to the serial number if the allocated buffer contained additional trailing bytes from a previous allocation (thanks to gnutls_malloc caching memory). This could let an attacker bypass certificate validation.

2. In the repair, immediately after the call to gnutls_x509_crt_get_serial, the actual length of the serial number is captured in the variable t. This value represents the true, verified length of the serial number as determined by the certificate parser.

3. The repaired code then checks if t (the real certificate serial length) matches the expected OCSP serial size (rserial.size). If these lengths don't match, it indicates that the OCSP response might be tampered with (e.g., containing trailing unnecessary bytes), so the function returns an error.

4. The memcmp is then performed using the exact length t (or rserial.size, since they are now equal) so that the comparison precisely covers only the valid part of the serial number. This ensures that any extra bytes that might be present in the buffer due to uninitialized memory do not interfere with the validation.

This repair effectively mitigates the vulnerability by ensuring that only an OCSP response with a serial number of the expected length—and with content that exactly matches the certificate’s serial number—is considered valid. This protects against the manipulation potential where an attacker might use trailing bytes from the memory allocation to bypass certificate validation.
