Explanation:
• In the original code the DTLS condition was inverted. It would skip generating the client random when running in DTLS mode (i.e. when no HelloVerifyRequest has yet been received) while regenerating it if one had been received. According to the intended protocol behavior the client should generate (and use) a fresh client random for TLS sessions and for DTLS sessions only when it is the very first ClientHello (when hsk_hello_verify_requests is zero). In contrast, if a HelloVerifyRequest has already been received then the original client random must be preserved.
• The repaired code explicitly generates the client random only if no HelloRetryRequest has been received, and in the DTLS case only if no HelloVerifyRequest has been performed. This fixes the vulnerability with respect to re‐generating (or not generating) the client random under the wrong conditions.
