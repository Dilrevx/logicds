The repair addresses a vulnerability where an attacker might force the handshake to negotiate a lower protocol version (a downgrade attack) by manipulating the session’s default hello version. Here’s how the repair works:

1. In the original code, the data for the advertised version (tver) could be taken either from the session’s default_hello_version or from the negotiated version (hver). In some scenarios, if default_hello_version were improperly set, it could lead to a protocol downgrade.

2. The repair removes the conditional branch that uses session->internals.default_hello_version. Instead of checking if the default_hello_version field is non-zero and then using its values, the code always sets tver directly from the ‘hver’ structure. The ‘hver’ pointer is derived either by negotiation (if a rehandshake is occurring) or by getting the maximum supported protocol version. This ensures that no malicious override of the version occurs.

3. By explicitly setting tver[0] and tver[1] to hver->major and hver->minor respectively, the repair guarantees that the advertised version comes solely from the negotiated parameters rather than from an overriding variable that might have been tampered with.

4. The rest of the code remains essentially unchanged. The versions for the handshake (advertised version, default record packet version, etc.) are still correctly set up based on the negotiated values. This consistency ensures that downstream components (like RSA or other handshake components) are using the appropriate protocol version.

5. This cleanup mitigates the potential vulnerability because an attacker would no longer be able to cause the handshake to use a less secure (deprecated or vulnerable) protocol version by controlling the default_hello_version field. The secure design now strictly enforces the version negotiated and provided by the correct negotiation process.

6. Moreover, by keeping the rest of the handshake logic intact—logging the advertised version, initializing the random client data, and setting up security parameters—the repair maintains the original functionality while bolstering the security of the protocol negotiation.

In summary, the vulnerability fix is all about eliminating the opportunity for a downgrade by ensuring that the advertised protocol version (tver) is never set to a value different from what the negotiation (the ‘hver’ value) determines. This change is crucial for preventing downgraded sessions, which could be exploited by attackers to access weaker encryption or protocols, thus reinforcing the overall security of the TLS handshake process.
