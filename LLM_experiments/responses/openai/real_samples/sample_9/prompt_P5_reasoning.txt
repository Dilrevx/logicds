The repair removes the faulty branch for DTLS that previously skipped generating randomness when hello-verify was not used. In the original code, the condition was written as:

  if (!(session->internals.hsk_flags & HSK_HRR_RECEIVED) &&
    !(IS_DTLS(session) && session->internals.dtls.hsk_hello_verify_requests == 0))

This conditional meant that for DTLS sessions where hsk_hello_verify_requests is zero, the randomness generation (_gnutls_gen_client_random) was bypassed. As a result, the client would end up with a client random value consisting only of 32 null bytes. This loss of randomness directly compromises the security of the DTLS negotiation, because a truly random client random is essential for establishing secure session keys.

The repair simplifies the condition by removing the DTLS-specific check from the logic. Now, the randomness generation occurs as long as the HSK_HRR_RECEIVED flag is not set:
  if (!(session->internals.hsk_flags & HSK_HRR_RECEIVED))
This change ensures that regardless of whether the session is DTLS or not, the client always generates a random value. This correction guarantees that every session uses the cryptographically secure randomness strategy intended, thereby maintaining DTLS security guarantees.

In summary, the repair fixes the vulnerability by:

• Removing the improper exception for DTLS sessions with zero hello-verify requests.
• Guaranteeing that the client random is always generated, providing the necessary randomness for the key exchange.
• Ensuring that both DTLS and non-DTLS sessions adhere to the same secure process, which prevents the potential security breach resulting from an all-zero client random.

This change directly addresses the vulnerability by restoring the intended behavior of secure, random value generation for the DTLS client and thereby upholds the protocol's security guarantees.
