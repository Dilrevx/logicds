The original vulnerability arose because the DTLS client wasn’t actually generating a new, random client random value when it should have. Instead, when no HelloVerifyRequest (HRR) had been sent—that is, when session->internals.dtls.hsk_hello_verify_requests was zero—the DTLS code would skip the call to _gnutls_gen_client_random. Consequently, the session would end up using a default value of 32 null bytes as the client random. This predictable value seriously undermines the DTLS protocol, where high-entropy randomness is essential to secure key generation and overall handshake security.

In the original code snippet, the generation of the client random was conditioned on a compound boolean expression that combined the state of HRR reception with an additional check for DTLS sessions. For non-DTLS sessions, the code only generated a random if an HRR had not been received. However, for DTLS sessions, the code inadvertently disabled random generation when the DTLS-specific counter (hsk_hello_verify_requests) was zero. In essence, the logic was structured as follows:

  if (not HRR received) and (not (DTLS session with zero hello_verify_requests)) { generate client random }

This logic meant that in a DTLS session with zero hello_verify_requests, the if condition evaluated to false and therefore the _gnutls_gen_client_random() function was not called. This was problematic because DTLS clients must always have a fresh, random client random to ensure that the ensuing cryptographic operations, like key derivation, have sufficient entropy. If the random value is predictable, attackers might exploit it to derive session keys or perform other cryptanalytic attacks.

To fix this issue, the repaired code alters the condition for client random generation. We change the logic from essentially “generate random if not HRR and not (DTLS with no hello_verify_requests)” to “generate random if either HRR has not been received or if it is a DTLS session.” This is achieved by using the logical OR (||) operator instead of an AND (&&) with inverted logic. The revised condition ensures that for DTLS sessions (where IS_DTLS(session) returns true), the _gnutls_gen_client_random() function will always be called, regardless of the count of hello_verify_requests. This guarantees that even when a DTLS session does not receive a HelloVerifyRequest, it still generates a truly random client random value.

This repair aligns well with the cryptographic requirements of DTLS as established in various security standards and best practices. It preserves the original behavior for traditional TLS sessions—ensuring that we are still respecting the HRR logic where required—while rectifying the DTLS-specific vulnerability. By ensuring that a genuinely random client random is used in every DTLS negotiation, we effectively restore the full randomness necessary to secure the handshake process. This change mitigates any potential security risks caused by predictable or static random values, thereby strengthening the overall security guarantees of DTLS.
