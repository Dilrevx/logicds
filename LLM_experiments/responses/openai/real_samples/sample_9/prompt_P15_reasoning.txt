The vulnerability stemmed from a faulty logic check that led the DTLS client to skip generating a secure client random in certain situations. In DTLS, generating an unpredictable client random is critical to ensure sufficient entropy in the cryptographic handshake. Instead of generating a secure random value during the initial handshake, the buggy code ended up using a fixed 32-byte null array, undermining the protocol’s security.

In the original code, the compound conditional intended to decide whether a fresh client random should be generated was misconfigured. The check was:

  if (!(session->internals.hsk_flags & HSK_HRR_RECEIVED) &&
    !(IS_DTLS(session) && session->internals.dtls.hsk_hello_verify_requests == 0))

What this did was: if either it wasn’t a DTLS session or it was DTLS but with a non-zero hello verify requests count, the generation function _gnutls_gen_client_random would be triggered. However, for an initial DTLS handshake (where hello verify requests count equals zero), the negated condition prevented the client random from being generated, resulting in the use of insecure, constant null bytes.

The repair inverts the DTLS-specific logic, changing the conditional to:

  if (!(session->internals.hsk_flags & HSK_HRR_RECEIVED) &&
    (!IS_DTLS(session) || session->internals.dtls.hsk_hello_verify_requests == 0))

Let’s break this down:

1. The first part of the check for HSK_HRR_RECEIVED remains unchanged. This flag indicates that a “Hello Retry Request” was received. If it has been received, the secure random might already have been set up during an earlier exchange, so the generation step can be skipped.

2. The second part of the condition has been modified. It now reads:
  (!IS_DTLS(session) || session->internals.dtls.hsk_hello_verify_requests == 0)

   — For non-DTLS sessions, the condition evaluates as true and moves ahead to generate client random.
   
   — For DTLS sessions, the random generation is only triggered if the hello verify request count is exactly zero. This is essential for an initial handshake when the random has not been generated yet. If the hello verify request count is non-zero (i.e., DTLS handshake is in a subsequent phase where the client random should not be re-generated), the generation step is skipped.

By switching the condition from checking for equality to checking for non-equality in the original code, the repair guarantees that only when no hello verify request has been received for a DTLS session (i.e., session->internals.dtls.hsk_hello_verify_requests equals 0), the client random gets securely generated. This reinforcement prevents the situation where a DTLS client inadvertently uses a fixed, constant value — ensuring that a proper secure random value is produced and used during critical phases of the handshake.

In summary, the repair corrects the faulty DTLS logic by adjusting the conditional so that the randomness generation function is properly called during the initial DTLS handshake. This maintains the security properties of the DTLS protocol by ensuring that real entropy is used instead of a predictable null byte sequence.
