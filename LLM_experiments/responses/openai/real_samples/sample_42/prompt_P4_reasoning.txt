The repair aims to restrict the set of NAS message types that are accepted without integrity protection. In the original code, several types of messages were explicitly allowed even when they arrived in plaintext (i.e., without built-in integrity protection). However, the vulnerability description indicates that allowing plain NAS messages such as Detach Request, EMM Information, and EMM Status (and even Attach/Service Reject with a specific emm_cause) opens up a risk. Attackers might exploit these messages because they can be manipulated without the safeguard of integrity checks, thereby potentially interfering with the normal functioning of the mobility management entity or triggering unauthorized state transitions in the device.

In the repaired code, only the message types that are considered safe to handle in plaintext are accepted. These messages are Identity Request, Authentication Request, Authentication Reject, Detach Accept, and Tracking Area Update Reject. Each of these types was chosen because their usage in the protocol, by design, does not lead to significant security implications if mishandled. For instance, while an Identity Request can reveal sensitive information such as the IMSI, it is generally assumed that any risk from passing such information in plaintext is mitigated further down the protocol stack (for example, by additional checks inside parse_identity_request()). Similarly, Authentication Request and Authentication Reject are part of the procedures where their misuse would be harder to weaponize in a denial-of-service attack against the core network. Detach Accept and Tracking Area Update Reject are chosen because, while important, they are responses to client requests, and when there is no malicious intent in the initial request, they are less likely to be misused.

On the other hand, the messages that have been removed from the plaintext list in the repaired code—EMM Information, EMM Status, Detach Request, Attach Reject, and Service Reject—are those that could be misused by attackers. For example, allowing a Detach Request without integrity protection might let an attacker force a device to detach from the network, thereby causing a denial-of-service situation. Similarly, the EMM Information and EMM Status messages could be exploited to glean internal state or orchestrate subtle changes in connection status if they are sent in plaintext. The Attach/Service Reject message with a specific emm_cause (#25) might be used to drop an ongoing attach or service procedure, again resulting in possible service disruption.

By removing these message types from the list of accepted plaintext messages, the new implementation ensures that all potentially vulnerable messages are only processed when they are backed by integrity protection. This design choice narrows the attack surface, ensuring that only NAS messages that do not open the device or network to manipulation will get processed. Furthermore, it enforces a strict policy for NAS message handling: if an incoming message does not belong to the explicitly defined “safe” subset (when integrity protection is absent), the code logs an error and drops the message. This proactive security measure prevents attackers from exploiting the protocol’s ability to handle plaintext messages that should have been integrity protected.

Overall, the repair provides a more secure approach by filtering out risky message types under specific security conditions, thus addressing the vulnerability of accepting sensitive NAS messages in plaintext and ensuring a more robust handling of security-sensitive NAS operations.
