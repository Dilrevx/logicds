The primary change in the repair is in the block that handles NAS messages with a plaintext security header (SEC_HDR_TYPE_PLAIN_NAS). Originally, the code allowed multiple message types—even those that should be integrity protected—to pass through when received in plaintext. The vulnerability arose because messages such as Detach Request, EMM Information, EMM Status, and Attach/Service Reject (even with emm_cause = 25) were accepted without verifying integrity, exposing the system to potential attacks.

Here’s how the repair fixes the issue:

1. Enforcing Integrity Protection for Sensitive Messages:
  • In the original code, there was a switch-case that permitted several plaintext message types based solely on their message type. This logic inadvertently allowed critical messages to be accepted in plaintext.
  • In the repaired code, the condition handling plaintext messages now only allows the Identity Request message (LIBLTE_MME_MSG_TYPE_IDENTITY_REQUEST) to be accepted without an integrity check. Any other message type received in plaintext is immediately rejected by logging an error and returning. This ensures that sensitive messages cannot be processed without first passing through the necessary integrity checks.

2. Clear Logging and Early Exit:
  • The repair introduces an if-statement that checks: if the security header type is plaintext and the message type is not Identity Request, then it logs an error with details about the rejected message and returns without further processing.
  • This early exit prevents the continuation of processing any potentially tampered NAS messages, thereby protecting against attacks that exploit accepting critical messages without proper integrity verification.

3. Alignment with 3GPP TS 24.301:
  • The comment in the repaired code references TS 24.301 Sec.4.4.4.2, explaining that only the Identity Request should be accepted in plaintext. This change ensures that the implementation is compliant with the standard, further mitigating the risk by correctly applying message integrity.

4. Maintaining Existing Functionality:
  • Other security header types (e.g., integrity protected messages, ciphered messages) continue to be processed as before if they pass integrity and decryption checks.
  • The repair does not affect implementation for messages that are already validated; it only introduces stricter conditions for plaintext ones.

In summary, by restricting acceptance of plaintext NAS messages to only the Identity Request type, the repaired code guarantees that more sensitive message types (such as Detach Request, EMM Information, EMM Status, and Attach/Service Reject) are not processed unless they are adequately protected with integrity (and decryption when required). This adjustment eliminates the vulnerability wherein an attacker could maliciously inject or modify critical NAS messages delivered in plaintext.
