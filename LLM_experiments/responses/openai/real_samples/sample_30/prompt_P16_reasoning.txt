In the original code, the CRL retrieval functions were called using the certificate’s subject as the parameter to filter CRLs. This was problematic because CRLs (Certificate Revocation Lists) are indexed by the issuer of the certificate being verified, not the certificate’s subject. If a certificate is revoked, the revocation information provided by its issuer may not be identified correctly if the subject is used. Therefore, this could lead to the scenario where a revoked certificate might be mistakenly accepted.

To fix this, the repair replaces the use of the "subject" variable with the "issuer" variable in both CRL retrieval function calls. Specifically:

1. For OpenSSL versions 1.1.0 and above (and where LibreSSL is not present), the function call:
   X509_STORE_CTX_get1_crls(store_ctx, subject);
   is changed to:
   X509_STORE_CTX_get1_crls(store_ctx, issuer);

2. Similarly, for OpenSSL versions between 1.0.0 and 1.1.0, the function call:
   X509_STORE_get1_crls(store_ctx, subject);
   is corrected to:
   X509_STORE_get1_crls(store_ctx, issuer);

By substituting the correct parameter (issuer), the CRL lookup is now properly aligned with the underlying logic of the CRL verification. Since the CRL provided by the issuer contains the revocation information, the verification process can now correctly match the certificate with its corresponding CRL. As a result, if a certificate is revoked by its issuer, this status will be detected, ensuring that the certificate is not erroneously accepted.

The repair is done conditionally based on the version of the OpenSSL library. For OpenSSL versions that are 1.1.0 or later, as well as for those from 1.0.0 to before 1.1.0, the appropriate API is invoked with the corrected "issuer" parameter. For older versions of OpenSSL (pre-1.0.0), the code maintains its behavior by setting crls to NULL and includes a note suggesting an upgrade, which is advisable given the outdated API and related security safeguards in later versions.

This change not only prevents the vulnerability of improperly verifying certificates (by ensuring that the issuer’s CRLs are now checked) but also reinforces the correct handling of CRLs during TLS verification. Ultimately, this adjustment makes sure that the mechanism verifying certificate revocation is robust, securing the TLS connection against the risk of accepting a certificate that should have been revoked.
