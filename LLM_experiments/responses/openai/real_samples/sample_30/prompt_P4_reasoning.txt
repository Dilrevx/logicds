The vulnerability in the original code snippet arises from the fact that the function inadvertently uses the certificate’s subject field in two different CRL retrieval calls, when it should be using the subject for one check and the issuer for the other. The intended behavior is to verify revoked certificates accurately by ensuring that the correct CRL – one that pertains to the certificate issuer – is used. However, if the subject field is used twice, there is a risk that CRLs that should match the issuer (and thereby prevent connections for revoked certificates) will be ignored. As a result, a client whose certificate is revoked might still successfully establish a connection to the server, defeating the purpose of the certificate revocation process.

In our repair, we directly address this issue by changing the parameter passed to the CRL retrieval functions from "subject" to "issuer" when obtaining the CRLs from the certificate store. For OpenSSL versions 1.1.0 and later, as well as for version 1.0.0 up to 1.1.0 (provided LibreSSL is not used), the API function X509_STORE_CTX_get1_crls (or its predecessor X509_STORE_get1_crls) should be given the issuer parameter. This ensures that the function retrieves CRLs that are associated with the certificate issuer, rather than incorrectly using the certificate’s subject field.

By applying this change, the code now correctly filters the CRLs, ensuring that revoked certificates are properly identified based on the CRLs’ issuer information. This change is crucial because the CRL contains information about the intermediary or certification authority that issued it. Clients must check that the certificate revocation list corresponds to the issuer of the certificate rather than the certificate itself. If a CRL intended to list revoked certificates by a particular issuer is not considered because the subject is mistakenly checked twice, then the client might inadvertently trust a certificate that has been revoked, leading to a security breach.

The use of conditional compilation directives (the #if, #elif, #else blocks) is preserved in our repair to maintain compatibility. Those preprocessor conditions ensure that the correct function is called depending on the version of OpenSSL being used. For OpenSSL versions prior to 1.0.0, the repair does not attempt any operation because these older versions do not support the required functions to properly process CRLs based upon issuers. Instead, it outputs a NULL for the CRLs, along with a comment suggesting that an upgrade is necessary.

The repair therefore not only fixes the vulnerability by ensuring proper CRL retrieval using the issuer field but also maintains backward compatibility with older versions of OpenSSL. This distinction prevents introducing additional issues in environments where newer or more secure versions of OpenSSL are not available. It highlights the importance of matching CRL entries to the correct certificate field and consequently reinforces certificate security mechanisms. Overall, this repair eliminates a critical flaw that could have allowed revoked certificates to bypass revocation checks, thereby significantly enhancing the integrity of the TLS certificate verification process.
