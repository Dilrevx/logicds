The repair changes the parameter passed into the X509_STORE_CTX_get1_crls (or its older equivalent) function from subject to issuer. In the original code, the implementation erroneously used the certificate’s subject name when retrieving CRLs. However, according to proper certificate revocation handling, CRLs are issued by the Certificate Authority (CA) which is identified by the issuer name. By using the subject, the code may end up validating against the wrong CRL—potentially ignoring an applicable revocation list—thus allowing revoked certificates to be accepted.

Here's how the repair addresses the vulnerability:

1. In both the OpenSSL 1.1.x case (using X509_STORE_CTX_get1_crls) and the 1.0.x case (using X509_STORE_get1_crls), the code now passes issuer instead of subject. This correctly aligns with the CRL mechanism because CRLs are signed and issued by the certificate authority that holds the issuer’s name. When a certificate is revoked, its revocation details are found in the CRL maintained by the issuer (CA).

2. The vulnerability was that by checking twice for subject information (or never checking the issuer properly), a valid CRL may have been ignored, allowing a revoked certificate to be accepted and establish a connection. The repair ensures that CRL lookup uses the issuer name, which is the appropriate field to verify against.

3. This change not only adheres to standard practices in certificate handling but also enhances the security by ensuring that if a client's certificate has been revoked by the CA, the corresponding CRL would be accurately located and applied during the verification process. This proper validation helps prevent malicious or outdated certificates from being incorrectly accepted.

4. The code maintains compatibility with the different OpenSSL versions; it applies the change only when using OpenSSL 1.0.0 or later (and not under LibreSSL). For older OpenSSL versions, the code still defaults to a message advising an upgrade, which is acceptable given the security standards expected.

In summary, the fix corrects the CRL retrieval process by replacing the parameter "subject" with "issuer". This correction ensures that the CRL corresponding to the issuer (and thus potentially containing the revocation information for the certificate in question) is properly retrieved and checked. By doing so, it reduces the risk of accepting a revoked certificate and strengthens the overall security of the TLS verification process.
