The repair adds an explicit check for encoded forward slashes in the URI before calling the existing security function. The vulnerability described indicates that an attacker might bypass access restrictions by using an encoded forward slash (i.e. "%2F" or "%2f") in the URL. When the forward slash is encoded, the check in mk_security_check_url might not detect it as a dangerous character, thus allowing the attacker to bypass rules that depend on the unencoded “/”.

The repair starts by checking if the URI string (sr->uri) contains "%2F" or its lowercase variant "%2f". It uses the C library function strstr() to look for the presence of these substrings. If either encoded version of the forward slash is found, the connection is immediately terminated by setting the HTTP status to MK_CLIENT_FORBIDDEN and returning MK_PLUGIN_RET_CLOSE_CONX. This ensures that any URL that attempts to hide dangerous characters within an encoding scheme is blocked early on.

This early check is important because it acts as a whitelist filter, preventing encoded special characters from slipping through. The vulnerability lies in the fact that, despite the caller thinking that the URL is safe, the encoded version could be decoded later in the request handling process, potentially bypassing access restrictions that are in place for unencoded characters. By explicitly checking for these encoded sequences and refusing the connection, the code now prevents an attacker from successfully using such techniques to bypass access control measures.

After the check for encoded forward slashes, the code then calls the existing mk_security_check_url function as before. This call remains in place to catch any other malicious patterns or anomalies in the URI that might not be related to the encoded forward slashes. Maintaining this check ensures that the overall security for filtering potentially dangerous URIs is not compromised by adding the new check, but rather complements it by adding an extra safety measure.

The reasoning behind the repair focuses on addressing the specific vulnerability mentioned in the security advisory. The idea is that if the original function fails to detect the encoded forward slash, the added check will intercept these cases. This layered approach in security, where multiple checks cover different aspects of the input validation, is a common defensive programming strategy. One check verifies the integrity of the incoming URI by looking for known dangerous encoding sequences while another check (the inherited call to mk_security_check_url) manages broader URL inspection.

Additionally, the use of both uppercase and lowercase variants for the encoded forward slash ensures that case differences in the encoding do not allow an attacker to bypass the filter. As HTTP_URI can sometimes include variances in how characters are encoded, covering both "%2F" and "%2f" mitigates a potential edge case. The trace logging (PLUGIN_TRACE) is retained so that any events where a connection is closed due to a malicious URL can be debugged or audited effectively.

Overall, the repair reinforces input validation and sanitization by catching a vulnerability where an encoded forward slash might bypass the intended access controls. This adjustment enhances the security posture of the Monkey HTTP Daemon plugin and minimizes the risk of unauthorized access via crafted URIs.
