The repair begins by decoding the URI before performing any access checks. Previously, the code used the raw URI (sr->uri), which allowed an attacker to bypass restrictions by encoding characters—for example, an encoded forward slash (%2F) that could change the logical structure of the URL. By decoding the URI first, we “normalize” it, converting any encoded characters to their literal representations. This way, the check function receives the true content of the URI, making it harder for malicious requests to slip by.

Here is what happens step by step in the fixed code:

1. We call the API function (mk_api->uri_decode) to decode the incoming URI. This function likely converts encoded sequences (like %2F) to their actual character equivalents. If decoding fails for any reason (e.g., malformed input), the repair immediately logs the error and aborts the connection by setting the HTTP status to forbidden. This ensures that a problematic or unresolved URI is not processed further.

2. Next, the decoded URI is passed to the security checking function (mk_security_check_url). This function is responsible for analyzing the URI for any patterns or strings that should trigger a denial of service or access control signal. Since the URI is now in a normalized state, any encoded characters that could have been manipulated to bypass security checks are now in plain form and will be correctly identified by this function.

3. If the security check determines that the decoded URI is unsafe, the connection is immediately closed, and the appropriate HTTP status (MK_CLIENT_FORBIDDEN) is set. This effectively blocks any malicious requests detected during validation.

4. Finally, whether the URI is allowed or not, the dynamically allocated memory for the decoded URI is freed using mk_api->mem_free, which prevents memory leaks.

In summary, by decoding the URI before running the security check, the repair eliminates the discrepancy between the encoded presentation and the decoded, true path of the URI. This normalization step is crucial because it prevents attackers from hiding maliciously intended characters behind percent-encoding. The new approach ensures that the security check function is assessing the actual URL content, effectively mitigating the vulnerability that allowed bypassing access restrictions due to encoded forward slashes.
