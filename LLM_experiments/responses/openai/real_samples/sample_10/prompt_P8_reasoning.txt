The original vulnerability stemmed from using the standard memcmp function to compare memory regions that contain cryptographic data. memcmp is not guaranteed to run in constant time, which means that the time it takes to perform the comparison can vary based on the data. An attacker could potentially exploit these timing variations to deduce information about the cryptographic material, leading to a side-channel attack.

In the repair, every call to memcmp has been replaced with a call to mbedtls_ct_memcmp—a function specifically designed to perform memory comparisons in constant time. Constant-time functions ensure that the time taken to compare two pieces of data does not depend on their contents. This uniform execution time is crucial in cryptographic contexts because it prevents attackers from gathering useful timing information that could help them infer sensitive data.

The vulnerable code was comparing two sets of cryptographic parameters (namely, signature OID and signature parameters). By using mbedtls_ct_memcmp, the repair ensures that regardless of any differences in the input data, the comparisons complete in the same amount of time. This protects against timing-based side-channel attacks without changing the logic of the comparison itself.

Additionally, while the length comparisons are still performed using standard integer comparisons, they do not introduce the same risk as byte-wise comparisons of sensitive cryptographic data. The primary security improvement comes from eliminating the variable timing behavior in the sensitive parts of the code.

Overall, the repair mitigates the vulnerability by ensuring that all sensitive memory comparisons are executed in a constant time, thereby significantly reducing the risk of timing attacks that could otherwise compromise the cryptographic integrity of the application.
