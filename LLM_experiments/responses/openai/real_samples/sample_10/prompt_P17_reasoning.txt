The vulnerability resided in how the code recalculated the pointer offset after allocating and copying the certificate's raw data into a new buffer. Originally, after calling mbedtls_calloc and copying buf into crt->raw.p, the code used the calculation “crt->raw.len - len” to adjust the pointer p. This meant that p was advanced by an offset that might not correctly reflect the number of bytes already processed in the original buffer. If the length calculations weren’t perfectly aligned, this could result in p pointing to an incorrect region of the newly allocated buffer. In other words, any miscalculation during the arithmetic might have caused p (and thus later parsed certificate parts) to refer to the wrong memory region, potentially exposing certificate data to incorrect processing or even out-of-bound accesses.

The repair fixes this vulnerability by recalculating the pointer offset relative to the original buffer base. Specifically, the fixed code uses the expression p = crt->raw.p + (p - buf). Here’s the step-by-step explanation:

1. When make_copy is true, the code first allocates a new buffer (crt->raw.p) whose size exactly matches the certificate’s raw length. This ensures that the certificate data will be stored contiguously in a newly owned buffer.

2. The certificate data from the original buffer (buf) is copied into crt->raw.p. At this point, p was originally pointing somewhere in the original buffer. The vulnerability occurred because the pointer p wasn’t updated in a way that correctly “remapped” it into the new memory location.

3. The repair computes the correct offset by subtracting the original base pointer (buf) from p, giving the number of bytes that have already been processed in the original buffer. It then adds that offset to the beginning of the new buffer (crt->raw.p). This means if p had advanced 42 bytes into the original buffer, then in the newly allocated buffer p will also advance 42 bytes from crt->raw.p. This arithmetic is safe and precise, aligning the pointer correctly within the new memory region.

4. Finally, the pointers end and crt_end are recalculated relative to the adjusted p and the parsed length from the current ASN.1 tag. Thus, every subsequent parsing function (e.g., mbedtls_asn1_get_tag, mbedtls_x509_get_name) works off the correctly positioned pointer.

By ensuring that p is adjusted with “crt->raw.p + (p - buf)”, the repair prevents misaligned memory accesses which could result in either data corruption or potential security issues, such as buffer overreads or incorrect signature verifications. This careful pointer remapping stops the vulnerability that stemmed from using an imprecise offset (“crt->raw.len - len”) and ensures that the parsing logic continues through the correct indices of the duplicated data.
