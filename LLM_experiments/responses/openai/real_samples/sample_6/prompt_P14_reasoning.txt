The original code allowed any nonce length up to CHACHA_CTR_SIZE (likely 16 bytes), which means that if an application set a nonce longer than 12 bytes, OpenSSL would only use the last 12 bytes. This behavior could lead an application to inadvertently reuse nonces—even if it believed it was altering the nonce by changing the extra bytes. Reusing nonces in ChaCha20-Poly1305 can allow attackers to break confidentiality and integrity guarantees provided by the AEAD scheme.

The repair fixes this by enforcing a hard check that the nonce length (IV length) is exactly 12 bytes. Here’s how the repair works:

1. The condition now checks if the provided nonce length (arg) is exactly 12. If it isn’t, the function returns 0 (failure), thereby not allowing any nonce length other than the 96-bit (12-byte) nonce specified by RFC 7539.

2. By ensuring that the nonce length is fixed at 12, the repair prevents any chance of using a longer nonce where the leading bytes might be discarded, which in turn prevents nonce reuse under a false sense of uniqueness.

3. The line “actx->nonce_len = arg;” now only executes if arg equals 12, so the context ends up with a nonce length consistent with the specification.

With this repair, the vulnerability is mitigated because:

• Only the exact nonce size required for ChaCha20-Poly1305 is accepted, so the potential misinterpretation of longer nonces is eliminated.
• The uniqueness requirement for nonce values is maintained. Any attempt to use a nonce that deviates from the 12-byte standard will fail immediately, protecting against accidental reuse of nonces.

Overall, by enforcing the correct nonce length, the repair adheres strictly to the crypto specification and prevents attackers from exploiting any inadvertent nonce reuse that could compromise the security of the encrypted messages.
