The repair introduces two main changes:

1. It checks whether authentication has already been flagged as done.  
   By adding an if-statement at the beginning of the function, the repair prevents processing duplicate "userauth_success" messages. This is important because if an SSH server sends multiple success messages, the client would have otherwise processed them repeatedly, potentially allowing an attacker to change or manipulate the expected authentication flow. By ignoring duplicates after the first success, it prevents scenarios where additional security measures (like FIDO2 tokens) could be bypassed by replayed or unexpected messages.

2. It retains the original authentication type value.  
   In the buggy version, the code resets cli_ses.lastauthtype to AUTH_TYPE_NONE. This reset could allow an attacker, by changing the login process, to effectively hide the fact that a stronger authentication method (e.g., FIDO2 or SSH-Askpass) was required, thereby facilitating unauthorized access. In the fixed version, we explicitly avoid resetting cli_ses.lastauthtype. By preserving the actual authentication method used, the client maintains an accurate record of the authentication type. This is critical for subsequent validation steps that verify compliance with RFC4252 and for enforcing any additional security measures. An accurate record helps ensure that even if the server tries to change the login process, the client can detect that discrepancy.

Additionally, cleanup operations related to public key authentication (conditional on DROPBEAR_CLI_PUBKEY_AUTH) remain intact to ensure that resources are properly managed post-authentication.

In summary, the repair adds a safeguard against multiple invocations of the success handler and preserves the integrity of the authentication method details so that the server cannot simply discard or modify them. This prevents attempts by an attacker to bypass additional security measures such as second-factor authentication or agent forwarding misuse.
