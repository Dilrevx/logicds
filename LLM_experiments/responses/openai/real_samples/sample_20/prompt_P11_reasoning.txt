The repair modifies the certificate name verification code when the subjectAltName extension is present. Originally, the code iterated over all subject alternative names and compared each name—even if it was not a DNS name—with the expected common name. This allowed an attacker to potentially match a valid certificate by presenting an alternative name of a different type (for example, an IP address) that happened to pass the check.

To fix this issue, the repair adds an extra check: it now compares the expected common name only with subjectAltName entries that are specifically DNS names. This is done by checking if the tag of the current SAN entry (cur->buf.tag) equals MBEDTLS_X509_SAN_DNS_NAME. If the SAN entry is of this type and the common name comparison succeeds (x509_crt_check_cn returns 0), then the loop breaks and the certificate is considered valid with regard to the common name.

The key points in the repair are:

1. When the subjectAltName extension is present, the loop now starts with “cur = crt->subject_alt_names” (instead of "&crt->subject_alt_names") to properly traverse the SAN chain.
2. Inside the loop, there is an additional condition that checks if the current alternate name's tag is MBEDTLS_X509_SAN_DNS_NAME. This ensures that only DNS names are considered for a match.
3. If no DNS name in the subjectAltName extension matches the expected common name, an error flag (MBEDTLS_X509_BADCERT_CN_MISMATCH) is set.

By applying this change, any subject alternative name entry that is not a DNS name (such as an IPv4 or IPv6 address) no longer gets compared to the common name. This prevents a certificate with an IP address as a SAN entry from improperly matching a domain name, effectively mitigating the vulnerability described.
