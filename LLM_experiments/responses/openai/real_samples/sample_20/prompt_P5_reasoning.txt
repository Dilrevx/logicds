The original vulnerability stems from how the code handles the X.509 certificate’s subject alternative names (SANs). When a certificate contains a SAN extension, it might include more than just DNS names – it can also include entries like IPv4 or IPv6 addresses. The buggy code simply iterates over all SAN entries and compares them to the expected common name (CN), regardless of the entry type. This means that if an attacker manages to obtain a certificate with an IP address in the SAN extension that corresponds to a valid domain name (or vice versa), it could erroneously pass the CN check, potentially allowing impersonation.

In the repaired code, a critical change is added within the loop that processes the SAN entries. The additional check:

  if( cur->tag == MBEDTLS_X509_SAN_DNS_NAME && ... )

ensures that only entries explicitly tagged as DNS names are used for comparison. By filtering on the tag, the code ignores other types of SAN entries (like IP addresses), which directly addresses the vulnerability. Now, even if the SAN extension contains an IP address or other non-DNS data, these entries are skipped when checking against the expected CN.

If no matching DNS name is found in the SAN extension, the code sets the flag MBEDTLS_X509_BADCERT_CN_MISMATCH, indicating a mismatch and prompting further certificate rejection. The section for when no SAN extension is present remains unchanged, as it directly compares the subject’s common name (CN) with the expected value. This maintains proper functionality when no SAN extension is present.

In summary, the repair fixes the vulnerability by explicitly verifying that the compared SAN entry is a DNS name (using the MBEDTLS_X509_SAN_DNS_NAME tag) before performing the CN matching. This prevents attackers from exploiting the flawed logic by using certificates with SANs of other types (such as IP addresses) to impersonate a valid domain.
