The repair adds a check to ensure that when using legacy custom ciphers, the cipher’s NID is not NID_undef. Here’s how the fix works:

1. Inside the conditional block that deals with dynamic loading of ciphers (i.e. using an engine, tmpimpl, or impl), the code now checks if the cipher pointer (ctx->cipher) is not NULL and, if so, whether its nid field equals NID_undef.

2. If the condition is true—that is, if the cipher is using NID_undef—it logs an error (via EVPerr) and jumps to an error handling section (label “err”). This immediately aborts further processing.

3. By rejecting ciphers with NID_undef early in the initialization process, the code prevents the fallback mechanism from improperly mapping a legacy custom cipher to the NULL cipher. This is important because the vulnerability arose when OpenSSL fetched the NULL cipher (which does no encryption) and used it, thereby leaking plaintext.

4. After performing this additional validation step, the rest of the legacy processing is executed: if the current cipher is the same as the fetched cipher, it sets the cipher pointer to NULL and then deallocates the fetched legacy cipher. This ensures the application continues processing only if a valid custom cipher (with a proper NID) is present.

In summary, the repair closes the vulnerability by verifying that a legacy custom cipher does not use NID_undef. This is critical because, if NID_undef is used, it causes unintended behavior during initialization – specifically, matching and using the NULL cipher from the available providers. By aborting this configuration scenario early, the fix ensures that encryption or decryption operations are only carried out with a validated cipher, thus preserving the intended security properties of the cryptographic operations.
