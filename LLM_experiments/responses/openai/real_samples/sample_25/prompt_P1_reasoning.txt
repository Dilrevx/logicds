The repair strengthens the TLS 1.3 client signature verification process by ensuring that the required public key for the given signature algorithm is indeed present before proceeding. Here’s how each change helps mitigate the vulnerability:

1. For ED25519, ED448, and ECC signatures, the repair adds an error return when the expected key (peerEd25519Key, peerEd448Key, or peerEccDsaKey, respectively) is not present. In the original code, a log message was printed when the key was missing but no further action was taken. This could allow the process to continue in an unexpected state, potentially leaving the client vulnerable to a man in the middle attack. The repair calls ERROR_OUT immediately, preventing the session from continuing insecurely.

2. For RSA signatures using PKCS#1.5, the insecure algorithm is explicitly rejected. The repair logs an error message stating that these signatures are not permitted in TLS 1.3 and then exits by calling ERROR_OUT. This prevents any further processing of an insecure signature method that could be exploited by network attackers.

3. For RSA-PSS signatures, the repair similarly checks if the RSA key is either missing or not present. The original code merely logged an error if the peer RSA key wasn’t validated but didn’t explicitly stop the operation. The repaired code ensures that if the required RSA key is missing, it triggers an error and exits, thus ensuring that all necessary authentication information is provided before continuing with the TLS handshake.

By adding the ERROR_OUT calls after critical verification checks, the repair effectively prevents the operation from proceeding if the proper public key is not supplied. This change is essential because if the client accepts a TLS 1.3 server without the appropriate key, an attacker with a privileged network position could impersonate a legitimate server by exploiting weak signature validation. The immediate termination of the connection stops any potential man in the middle attack from occurring.

Overall, the fix enforces strict validation of signature algorithms and corresponding public keys, ensuring that any deviation from the expected behavior results in an immediate failure of the TLS handshake. This prevents malicious servers from bypassing authentication, which is the vulnerability described in earlier versions of wolfSSL.
