The repair adds extra checks to ensure that both handshake identifiers (authzeid and authzid) are present and that they match before proceeding. Originally, if the mu pointer was null, the code simply checked if authzeid was present and then tried to find the user account based solely on this value. This left a vulnerability because an attacker might deliberately end the handshake early, bypassing the proper challenge-response process even if authzid was not properly verified.

Here's a walkthrough of the changes:

1. The repair first checks whether both authzeid and authzid are provided:
  if (!*p->authzeid || !*p->authzid || strcmp(p->authzeid, p->authzid) != 0)
This line ensures that:
  • Neither identifier is missing.
  • They are exactly equal. By calling strcmp(), the code confirms that the provided values are identical.
This prevents an attacker from providing a partial handshake (e.g., only one of the IDs) or mismatched values, which might allow bypassing proper authentication if only one of them is validated.

2. If either of the identifiers is missing or they do not match, a log is created and a cancellation notice is sent:
  (1) A log entry is made to record that there was an issue with the identifiers.
  (2) A notice is sent to the user, informing them that the login was cancelled.
This immediate return prevents further processing of an authentication attempt with incomplete or inconsistent data.

3. If the identifiers pass the checks, only then does the code attempt to find the user account using myuser_find_uid(p->authzeid). This ensures the lookup is only carried out if the handshake has properly completed (i.e., both identifiers are present and equal).

By enforcing that the handshake must include both valid and matching identifiers before any account lookup is attempted, the repair effectively prevents an attacker from exploiting the vulnerability. The vulnerability in the buggy code was due to incomplete validation that could allow premature handshake termination in a challenge-response login sequence. The repair eradicates this weak point by making sure that a valid handshake with consistent identifiers is a mandatory precondition for authenticating the user.

In summary, by introducing a strict check on the handshake block (both IDs are required and must match), the vulnerability is fixed, reducing the risk of authentication bypass attacks when integrating Atheme IRC Services with InspIRCd.
