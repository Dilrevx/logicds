The repair focuses on addressing the CCS Injection vulnerability by ensuring that a negotiated session does not use a zero-length master key when processing a ChangeCipherSpec (CCS) message. In the original code, after the ChangeCipherSpec is sent, no explicit check is performed on the session’s master key length. This omission can be exploited by an attacker, injecting a CCS message to force the use of an invalid master key. If the master key length is zero, it indicates a compromised or incomplete negotiation, which could lead to security breaches such as hijacked sessions or exposed sensitive data.

The repair introduces a check immediately before the key block is set up in the case handling for SSL3_ST_SW_CHANGE_A/SSL3_ST_SW_CHANGE_B. Specifically, it tests whether "s->session->master_key_length" is zero. If it is, the repair calls SSLfatal with the appropriate alert description (SSL_AD_HANDSHAKE_FAILURE) and error code (SSL_R_CCS_INJECTION) to signal a handshake failure. This not only aborts the current handshake sequence by returning an error but also ensures that the session is not inadvertently established with an invalid or zero-length master key. In doing so, the system is prevented from proceeding into a state where cryptographic parameters are unsound.

Additionally, the repair leaves the original flow for the other handshake messages intact. For example, it retains the existing calls to "ssl3_get_cert_verify", "ssl3_get_next_proto", "ssl3_get_finished", and the further processing dependent on whether the session is resumed (s->hit) or requires additional steps such as sending a session ticket. Ensuring compatibility with, for example, TLS extensions (like Next Protocol Negotiation) is important, so specific blocks conditioned by OPENSSL_NO_TLSEXT and OPENSSL_NO_NEXTPROTONEG are maintained.

The critical emphasis in the repair is placed on the state transition involving the ChangeCipherSpec message. By inserting the master key length validation at this point, the code prevents a man-in-the-middle (MITM) attack from exploiting the handshake sequence. This targeted fix ensures that even if an attacker manages to perform a crafted handshake attempt, they cannot force the server into using a zero-length key, which would completely undermine the encryption guarantees of the TLS protocol.

In summary, the fix works by adding a simple conditional check that effectively mitigates the vulnerability. If a session with an improperly negotiated key (a zero-length master key) is detected, the handshake is terminated, thereby avoiding the re-keying process that would otherwise proceed unsafely. This is a straightforward but critical change, as it directly addresses the root cause of the vulnerability with minimal disruption to the overall handshake protocol flow. The repair ensures that each established session has a valid master key before proceeding to send the ChangeCipherSpec message, thereby preserving the integrity and confidentiality of the secure connection against CCS injection attacks.
