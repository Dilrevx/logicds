The repair introduces an additional check to ensure that only the certificate associated with the expected OCSP responder (obtained from the certificate chain) is allowed to bypass verification when the NoCheck extension is set. Here’s a walkthrough:

1. In the original code, if a certificate had the ocspNoCheckSet flag and the verification type was VERIFY_OCSP, the code disabled further verification by setting verify to NO_VERIFY. This logic had a major flaw: any certificate—even one unrelated to the responder in the chain—could bypass verification if it had the NoCheck extension. An attacker might misuse this loophole by injecting a certificate with this extension, even if it doesn’t belong in the OCSP context.

2. The repair introduces a conditional that compares the certificate being processed (cert) with the expected OCSP responder’s certificate (ocsp_resp_cert). The function X509_cmp is used to perform this comparison. Only if they match (i.e., X509_cmp returns 0) does the code disable verification (set verify to NO_VERIFY).

3. The additional null check on ocsp_resp_cert ensures that when no expected responder certificate is available, the new condition will not be erroneously satisfied or trigger any runtime errors.

4. This extra condition guarantees that even if an unrelated certificate carries the NoCheck extension, it will not bypass the verification process because it won’t match the responder certificate derived from the chain. Thus, the attacker can no longer exploit the weakness by using a certificate with NoCheck to disable the vital OCSP response integrity checks.

In summary, the repair tightens the validation process by ensuring that the NoCheck behavior is only applied to the correct OCSP responder certificate. This precise certificate matching prevents malicious actors from sidestepping the verification process through unrelated certificates with the NoCheck extension, directly addressing and fixing the vulnerability described.
