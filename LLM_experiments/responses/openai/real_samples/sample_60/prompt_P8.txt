Explanation:
In the original code the result of the bcrypt comparison was cached regardless
of whether authentication succeeded or failed. This may be exploited by an attacker
to “poison” the cache: repeated failed logins could force a cached false value,
possibly interfering with subsequent verifications (or vice‐versa). The repair above
caches only a successful (true) result, so that each authentication failure always forces
a real bcrypt comparison rather than allowing an attacker to force an incorrect cache entry.
This mitigates the vulnerability.
