The original code incorrectly accepted NAS messages with a plain header even after NAS security activation. This posed a security vulnerability because a plain NAS message, which is unprotected in terms of integrity and encryption, may be replayed, intercepted, or manipulated by attackers once the secure context is in place. The plain messages may expose sensitive signaling information or allow unauthorized access if security has already been applied. In such scenarios, it is crucial to ensure that plain (unsecured) messages, which lack integrity protection or encryption, must be rejected once the network has activated NAS security mechanisms.

To repair this, the code has been modified within the plain NAS message case (nas_5gs_hdr::security_header_type_opts::plain_5gs_nas_message). A conditional check is introduced by calling a helper function, is_nas_security_activated(), to verify if NAS security is already active. If the function indicates that security has been initialized, the code logs an error message and returns an error code (SRSRAN_ERROR), thereby preventing further processing of an insecure message. This function is assumed to be defined elsewhere in the codebase and correctly reflects the current security state. This change ensures that the plain NAS message, which is otherwise acceptable before security activation, is correctly blocked as soon as a secure context is established.

For the other cases related to integrity protection and encryption, the code structure has been kept nearly unchanged as it already handles their respective operations appropriately. In the “integrity_protected” and “integrity_protected_and_ciphered” cases, the code first validates the integrity of the message through the integrity_check() function. If the check fails, it logs an error and returns an error code. In the case of messages with both integrity protection and encryption, after the integrity check passes, it proceeds to decrypt the message with cipher_decrypt(). These cases are not modified because they do not pose the same vulnerability — they already apply the necessary security validations that the plain message case was missing.

The rationale behind this repair is to enforce a strict security policy based on the current NAS state. Once the security framework is active, the system should no longer process unsecured messages, as these present a significant risk. Allowing unsecured messages post-activation may lead to scenarios where an intruder can exploit legacy behavior to inject malicious messages into a secure session, thus undermining the overall security of the NAS. Consequently, the added check in the plain message case prevents any plaintext messages from being mistakenly treated as valid once NAS security is activated.

This repair ensures that even if a UE or attacker sends a plain NAS message after security has been activated, the system will detect this misalignment and safely reject the request, thus maintaining the integrity of the secure communication session. Overall, this repair effectively addresses the vulnerability by aligning the message handling logic with the expected post-security activation behavior, ensuring that the communication system only processes NAS messages that comply with the current security context.
