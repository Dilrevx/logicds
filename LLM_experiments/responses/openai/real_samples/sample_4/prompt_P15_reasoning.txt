The original issue arose because the code was using the Additional Authenticated Data (AAD) as the Message Authentication Code (MAC) key. Since AAD is derived from predictable protocol information, this allows an attacker to potentially compute or predict the expected MAC value, thereby facilitating man-in-the-middle modifications without detection.

In the buggy code, the parameter lookup was performed using:

  p = OSSL_PARAM_locate_const(params, OSSL_CIPHER_PARAM_AEAD_TLS1_AAD);

This line retrieves the AAD parameter. The vulnerability stems from using this value where the algorithm actually requires the MAC key—a cryptographically secure, unpredictable key that should be known only to the communicating parties.

The repair changes the parameter lookup to retrieve the correct MAC key by replacing the AAD parameter identifier with the proper MAC key parameter identifier:

  p = OSSL_PARAM_locate_const(params, OSSL_CIPHER_PARAM_AEAD_TLS1_MAC_KEY);

By doing so, the function now locates the correct parameter intended for the MAC key. This ensures that the MAC (used for integrity verification) is computed using a securely generated key, rather than a value that can be intercepted or predicted by attackers. Thus, even if an adversary can modify the intercepted data, they would not be able to forge a valid MAC without knowing the secret MAC key.

To summarize, the repair:
• Corrects the parameter reference so that it fetches the intended MAC key rather than AAD.
• Prevents exploitation through man-in-the-middle attacks, by ensuring that the integrity check is based on a securely generated, unpredictable key.
• Enhances the overall cryptographic security by ensuring that each parameter is properly verified and used as intended in the MAC computation process.

This simple yet vital change highlights the importance of precise parameter management in cryptographic protocols.
