The original code used OSSL_CIPHER_PARAM_AEAD_TLS1_AAD to locate a parameter, which means it was retrieving the additional authenticated data (AAD) instead of the MAC key needed for message authentication. AAD is typically derived from protocol data and is predictable. When predictable data is used as the MAC key, it compromises the cryptographic security of the MAC, enabling an attacker to potentially predict and forge valid MAC values.

The repaired code replaces OSSL_CIPHER_PARAM_AEAD_TLS1_AAD with OSSL_CIPHER_PARAM_AEAD_TLS1_MAC_KEY. This change means the function now retrieves the actual MAC key rather than the AAD. In cryptographic operations, the MAC key is a securely generated secret value that is meant to be unpredictable and is used to compute the message authentication code.

Using the correctly sourced MAC key prevents an attacker from exploiting the predictable sequence of the AAD. With the MAC key properly retrieved, the integrity verification process now relies on a cryptographically secure key. Thus, even if an attacker can observe or manipulate the protocol data, they lack the confidential MAC key necessary to produce a valid MAC, effectively thwarting man-in-the-middle type attacks.

In summary, by simply replacing the parameter lookup, we ensure that the MAC computation uses a securely generated and secret key rather than predictable data. This reinforces the security foundation of the cryptographic operations and preserves the integrity of the message authentication process.
