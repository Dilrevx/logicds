The original vulnerability occurred because the code was mistakenly retrieving the AAD (Authenticated Associated Data) and using it as the MAC key. The AAD is typically meant for safeguarding data integrity of certain header fields in TLS, not for secret key material. When the MAC key is predictable or derived from data that isn’t intended to be secret, an attacker could exploit this by predicting or even tampering with the key used for message authentication, compromising the integrity of the encrypted communication.

The repair addresses this risk by changing the lookup parameter to retrieve what is designated as the MAC key instead of the AAD. The repaired logic now checks for a dedicated MAC key parameter. If this parameter is not provided, it responds by handling the error (or potentially deriving the MAC key securely using an approved key derivation method). This separation ensures that the MAC key used in the encryption process is either explicitly supplied or generated in a secure manner, distinct from the AAD.

By isolating the MAC key parameter from the AAD, the vulnerability is mitigated because even if the AAD data is observable or predictable, it no longer influences the MAC key directly. This adherence to the TLS specification ensures that the MAC key is treated as sensitive secret material, which might typically be derived via a secure pseudorandom function based on initial secrets negotiated during the handshake, rather than being repurposed from data that also has an integrity protection role.

Essentially, the patch corrects the error by ensuring that the proper parameter—one intended solely for the MAC key—is being used. This correction is critical as it aligns with the principle of key separation, an important security practice in cryptographic implementations. By doing this, the repair maintains the integrity guarantees of the TLS protocol and prevents any predictable relationship between AAD and MAC key that could assist an attacker in mounting a man-in-the-middle attack or other related exploits.

In summary, the repair changes the code’s behavior from wrongly repurposing a non-secret parameter to explicitly acquiring (or deriving) the correct secret MAC key, thereby ensuring that the security of message authentication is not undermined by predictable or weak key generation.
