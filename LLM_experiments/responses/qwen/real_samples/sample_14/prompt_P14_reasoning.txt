The provided repair addresses the "CCS Injection" vulnerability in the OpenSSL implementation by ensuring that the ChangeCipherSpec (CCS) message is received at the correct point in the TLS handshake sequence. This vulnerability arises because an attacker can inject a CCS message out of order, potentially leading to the use of a zero-length master key, which can compromise the security of the session.

### Understanding the Vulnerability

In a typical TLS handshake, the CCS message is sent by both the client and the server to indicate that they are ready to switch to the newly negotiated encryption algorithms. The CCS message must be sent after the security parameters have been established but before the Finished messages, which confirm that both parties have successfully computed the same master secret and can communicate securely.

The vulnerability occurs when the CCS message is injected out of order. An attacker can send a CCS message prematurely, causing the recipient to switch to a potentially insecure state where the master key might be uninitialized or zero-length. This can allow the attacker to intercept and decrypt the subsequent traffic, effectively hijacking the session.

### Analysis of the Buggy Code

The original code snippet checks for the validity of the CCS message format and whether there is a cipher to change to. However, it does not verify that the CCS message is received at the correct point in the handshake sequence. Specifically, it does not ensure that the CCS message is received after the ServerHelloDone message and before the Finished message from the server.

### Implementation of the Repair

1. **Check for ServerHelloDone**: The code now verifies that the `server_finished_received` flag is set, indicating that the ServerHelloDone message has been received. This ensures that the CCS message is not processed before the server has completed its part of the handshake.

2. **Check for Finished Message**: The code also checks that the `client_finished_received` flag is not set, ensuring that the CCS message is not processed after the client has already sent its Finished message. This prevents the CCS message from being processed out of order, which could lead to the use of an uninitialized master key.

These checks prevent the CCS message from being processed too early or too late in the handshake sequence, thereby mitigating the risk of a CCS injection attack.
