The repair provided addresses a critical security vulnerability in the Eclipse Mosquitto MQTT broker configuration handling, specifically related to Access Control List (ACL) settings when `per_listener_settings` is enabled. The vulnerability arises from the fact that the ACL file specified for the default listener is not being properly applied to newly created listeners, potentially leading to unauthorized access to topics on the broker.

### Understanding the Vulnerability

In the context of MQTT brokers, Access Control Lists (ACLs) are crucial for defining which clients can publish to or subscribe to specific topics. This is particularly important in environments where multiple clients with varying levels of access need to interact with the broker. The `acl_file` parameter in Mosquitto's configuration specifies the path to the ACL file that contains these rules.

When `per_listener_settings` is set to `true`, each listener can have its own set of security options, including its own ACL file. However, the original code snippet did not ensure that the ACL file from the default listener was correctly assigned to new listeners. As a result, if the default listener had an ACL file specified, it would be ignored for any additional listeners created, leading to a potential ACL bypass vulnerability.

### The Repair

The repair involves adding a line of code to ensure that the ACL file from the default listener is assigned to the new listener being configured. Specifically, the following line is added:

```c
config->listeners[config->listener_count-1].security_options.acl_file = config->default_listener.security_options.acl_file;
```

This line ensures that the `acl_file` setting from the default listener is copied to the new listener being added. By doing so, the ACL rules defined in the specified file are applied consistently across all listeners, maintaining the intended security policies.

### Why This Repair Works

1. **Consistency Across Listeners**: By copying the `acl_file` setting from the default listener to new listeners, the repair ensures that all listeners adhere to the same security policies defined in the ACL file. This prevents any discrepancies in access control that could arise from different listeners having different or no ACL settings.

2. **Preventing ACL Bypass**: The vulnerability allowed unauthorized access because the ACL file was not being applied to new listeners. By ensuring that the ACL file is set for each listener, the repair effectively prevents any ACL bypass attacks that could exploit this oversight.

3. **Maintaining Security Policies**: The repair aligns with the intended behavior of the `per_listener_settings` option, which is to allow individual listeners to have their own security settings while still respecting the default settings unless explicitly overridden. In this case, since no explicit override is provided, the default ACL file should be applied.

4. **Simplicity and Effectiveness**: The repair is straightforward and effective, requiring only a single line of code to be added. This simplicity reduces the risk of introducing new bugs while addressing the existing vulnerability.

### Conclusion

The repair provided ensures that the ACL file specified for the default listener is correctly applied to all newly created listeners when `per_listener_settings` is enabled. This change maintains the integrity of the security policies defined in the ACL file, preventing any potential ACL bypass vulnerabilities and ensuring that all clients connecting to the broker are subject to the appropriate access controls.
