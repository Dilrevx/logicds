The repair addresses the vulnerability by reordering the sequence of actions when handling SRTP restarts. In the original, vulnerable code, the function that stops the SRTP transport is called before the encryption policies (used for secure transmission) are retrieved. When the transport is stopped first, it may inadvertently clear or alter important cryptographic parameters, leaving the subsequent restart with potentially incorrect or insecure settings. This can lead to the system mistakenly falling back to a basic, insecure RTP mode, which is exactly what the vulnerability describes.

In the revised sequence, the cryptographic policies for both transmitting and receiving SRTP media are saved before stopping the transport. By doing this, the repair ensures that the precise secure settings in effect prior to stopping are captured intact. When the SRTP system is restarted afterward, it uses these pre-saved policies, thereby preserving the intended secure configuration.

The critical change is the order: obtaining the secure context's parameters first and then halting the SRTP—which prevents loss or corruption of the configuration details. This proper sequence ensures the security posture does not inadvertently degrade. As a result, even if a restart is needed due to issues such as replay attacks (as indicated by the error conditions), the system can safely and securely resume SRTP operation without unintentionally reverting to a fallback mode that is less secure.

Consequently, this repair mitigates the vulnerability by maintaining the security guarantees provided by SRTP, ensuring that the media remains protected even after restarts. The vulnerability was due to an unintended switch from SRTP to basic RTP, exposing communications to potential interception. With the corrected order, the system reliably uses the secure cryptographic settings, preventing the insecure transmission of media and preserving the confidentiality and integrity expected by all PJSIP users employing SRTP.
