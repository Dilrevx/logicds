The vulnerability was caused by the fact that srsRAN would accept a security header type that is meant to be integrity protected and ciphered using the new EPS security context, but it did so without performing the mandatory integrity check. In the original (buggy) implementation, there was a specific case for this header type that simply allowed the message to pass without any verification. That meant an attacker might be able to manipulate or inject messages with that header type, bypassing the crucial integrity validation step.

The repair addresses this issue by eliminating the special handling for the security header type that combines both ciphering and the new EPS security context. Instead of breaking out of the switch statement for this header type, thus granting it free passage, the repair removes the case entirely. Without a dedicated case for the "integrity and ciphered with new EPS security context" header, any message bearing this header type now falls through to the default case. In the default case, the system logs an error message and returns without processing the message. This conservative approach ensures that messages using this header, which have not been verified with the integrity check, are now explicitly rejected.

By forcing the system to handle such messages in the default branch (and therefore reject them), the repair closes the security gap where an integrity check was omitted. This change ensures that only those security header types that have either been properly verified for integrity or are deemed safe by design (for example, plain NAS messages) are processed. In essence, the repair tightens up the security posture of the system by disallowing any implicit acceptance of messages that should require integrity verification before any decryption or further processing.

The overall reasoning behind the repair is to enforce strict adherence to security rules as per the specifications: any NAS message that is transmitted with the new EPS security context and is both integrity protected and ciphered must not be accepted without performing the necessary integrity check. By modifying the switch statement so that the problematic header type is no longer silently accepted, the repair mitigates a potential vector for integrity attacks.
