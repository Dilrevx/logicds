The vulnerability arises when an application creates a custom cipher using legacy OpenSSL functions. In some cases—specifically when the custom cipher is constructed with an undefined unique identifier—the library mistakenly matches it to the built-in NULL cipher from the loaded provider. Consequently, encryption decryption routines use the NULL cipher, which means that data is not truly encrypted; plaintext becomes output as ciphertext.

The faulty logic in the code base allowed a scenario where legacy custom ciphers might inadvertently be treated as if they were provided by the default provider. The vulnerability was triggered when an improper or undefined identifier is passed (such as the undefined identifier), leading the library to fetch an incorrect cipher. This could potentially allow data to be output directly in plaintext, undermining intended security.

The repair addresses the issue by refining the detection criteria in the conditional that decides whether legacy handling should be applied. Originally, the condition only checked for the presence of an engine or an implementation detail that might indicate non-standard circumstances. In the fixed version, the condition has been extended with two additional checks.

First, the new condition examines whether the cipher is not null and, if so, whether it originates from the legacy method. This extra check helps determine if the cipher in question is indeed a custom cipher constructed using the legacy method rather than a cipher obtained from any provider. If the cipher originates from the legacy method, it is a sign that special handling is required because it might have an undefined or improperly specified unique identifier.

Second, the repair also accounts for the situation where the provided cipher reference is null, but there is another cipher present in the context that comes from the legacy method. This ensures that even if the direct cipher parameter is missing, legacy custom ciphers that might be stored within the context are correctly identified and handled.

By introducing these additional conditions, the fix ensures that the function does not mistakenly use the fetched cipher from available providers when a legacy custom cipher (with its special characteristics) is intended for use. The underlying principle is to avoid an erroneous fallback to the NULL cipher that might occur when the legacy cipher’s identity is not correctly determined because of the undefined unique identifier.

This repair thereby preserves the intended behavior for custom legacy ciphers and prevents the accidental use of a NULL cipher. As a result, it stops plaintext from being output as ciphertext, restoring the expected security in encryption processes. The adjustment demonstrates a targeted approach, ensuring that only ciphers explicitly marked as originating from legacy methods bypass the default provider lookup, thereby maintaining the correct and secure operation of the encryption and decryption routines within OpenSSL.
