The vulnerability arose because the DTLS client was not contributing any randomness during the handshake by using a fixed set of 32 null bytes instead of a truly random value. In the buggy code, the condition that checked whether client random values should be generated was flawed: it incorrectly bypassed the proper random generation routine in certain DTLS scenarios. Specifically, the logic was intended to prevent re-generating a random value when a HelloVerifyRequest had already been processed in a DTLS session. However, due to the condition comparing the number of HelloVerifyRequests to zero, it ended up generating the client random value even when it shouldn’t have been. In the process, the generated value was not properly randomized, degrading the security of the DTLS handshake.

The repair fixes this issue by inverting the check in the condition. Instead of testing if the count of HelloVerifyRequests equals zero, it now checks if the count is not zero. This inversion ensures that if a HelloVerifyRequest has already occurred, the function will correctly avoid regenerating (and potentially mishandling) the client random data. This more accurate condition guarantees that, when a DTLS session is ongoing and a HelloVerifyRequest has been received, the system does not mistakenly generate or reuse a non-random sequence, as it should already have a properly random value in place.

In summary, the change corrects the logic error. With the condition adjusted, the code now properly distinguishes between DTLS sessions that have received a HelloVerifyRequest and those that have not. For those sessions without a HelloVerifyRequest (or in the TLS case), the client random value is generated correctly using the intended random data source. For sessions with at least one HelloVerifyRequest, the code correctly bypasses generating a new value—preventing the insecure state where a default, non-random value might be used.

This alteration preserves the security properties of the DTLS protocol by ensuring that the randomness intended for cryptographic operations is indeed random. It stops the DTLS client from inadvertently using a predetermined, insecure value during handshake negotiations. This repair is a sound adjustment that upholds the protocol's guarantees and addresses the underlying issue of potential exploitation due to poor randomness in cryptographic operations.
