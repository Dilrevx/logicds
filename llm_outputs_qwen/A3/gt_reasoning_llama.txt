The vulnerability in OpenSSL versions 3.0.0 to 3.0.5 arises from the incorrect handling of custom ciphers created using the legacy EVP_CIPHER_meth_new() function. When an application passes NID_undef as the NID value to EVP_CIPHER_meth_new(), the encryption/decryption initialization functions incorrectly match the NULL cipher as equivalent and fetch it from the available providers. This results in the plaintext being emitted as the ciphertext, effectively bypassing encryption.

The buggy code snippet is part of the logic that determines whether to use a custom cipher or a fetched cipher from the available providers. The condition checks if the context's engine, temporary implementation, or implementation is not null. If any of these conditions are true, it frees the fetched cipher and jumps to the legacy handling code.

However, this condition is insufficient to handle the case where a custom cipher is created with NID_undef. To fix this vulnerability, the repair adds two additional conditions to the if statement. The first condition checks if the cipher is not null and its origin is EVP_ORIG_METH, indicating that it is a custom cipher created using EVP_CIPHER_meth_new(). The second condition checks if the cipher is null but the context's cipher is not null and its origin is EVP_ORIG_METH.

By adding these conditions, the repair ensures that the code correctly handles custom ciphers created with NID_undef. If a custom cipher is detected, the code frees the fetched cipher and jumps to the legacy handling code, preventing the NULL cipher from being used and thus preventing the plaintext from being emitted as the ciphertext. This fix effectively addresses the vulnerability and ensures that encryption is properly performed even when custom ciphers are used.
