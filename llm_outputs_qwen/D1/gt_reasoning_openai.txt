The core issue was that the process of restarting SRTP was inadvertently discarding or corrupting the original security policies needed to preserve the secure media transport. Originally, upon detecting conditions such as an SRTP restart—where a new RTP sequence is coming in while old packets might be arriving—the code first stopped the SRTP transport and then attempted to restart it by retrieving the transmission and reception policies. However, stopping the SRTP effectively disrupted or reset part of the internal state, including potentially the storage of the policy parameters. As a result, when the code later fetched the policies, it might have obtained incorrect or default values, which could lead the restart process to reinitialize SRTP in a misconfigured manner. This misconfiguration could cause the system to mistakenly switch over to basic, insecure RTP transport instead of continuing with the secure SRTP, exposing the media stream to significant security risks.

The repaired approach addresses this vulnerability by reordering the operations. Instead of stopping SRTP first, the code now retrieves and locally stores the transmission and reception security policies before the transport is stopped. This change is crucial because it guarantees that the security settings, which define how SRTP should operate, are preserved intact and are not affected by the state changes triggered by halting the SRTP session. With the correct policies safely stored, the code then stops SRTP and subsequently restarts it using the unchanged, reliable policy values.

This subtle shift ensures that when the SRTP is restarted, it is configured exactly as it was before the interruption, maintaining the proper secure media transport. Consequently, packets will no longer be erroneously processed using basic RTP, and the media confidentiality is preserved throughout the connection, thereby mitigating the vulnerability. The logic behind the fix is fundamentally about preserving essential security configuration data during state changes, ensuring that the transition from a problematic SRTP restart scenario does not inadvertently compromise the security of the media stream.

In summary, by saving the SRTP crypto policies before stopping the transport, the repair prevents the loss or corruption of the configuration that is critical for maintaining secure RTP communication. This corrective action closes the security loophole that could otherwise lead to the insecure transmission of media, ensuring that PJSIP users continue to operate with the expected level of security when SRTP is restarted.
