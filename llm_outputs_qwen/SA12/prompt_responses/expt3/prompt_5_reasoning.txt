### Context of TLS Handshakes

TLS (Transport Layer Security) is a protocol designed to provide secure communication over a computer network. It uses cryptographic techniques to ensure confidentiality, integrity, and authenticity of data exchanged between two parties. The TLS handshake is the initial process where both parties agree on the parameters to be used for the secure connection, including the choice of encryption algorithms and the exchange of keys.

In TLS 1.3, the handshake process has been streamlined compared to previous versions, reducing latency and improving performance. However, the security aspects remain paramount, especially when it comes to verifying the identities of the communicating parties through mutual authentication.

### Importance of Mutual Authentication

Mutual authentication is a security mechanism where both parties involved in a communication session verify each other's identities. In the context of TLS, this typically involves both the client and the server presenting digital certificates signed by a trusted Certificate Authority (CA). This process ensures that both parties are who they claim to be, enhancing the overall security of the communication.

### Role of Certificates

Certificates play a crucial role in TLS handshakes by providing proof of identity. They contain information about the entity (such as a domain name or an organization) and are digitally signed by a CA. When a client connects to a server, the server presents its certificate, which the client verifies against its list of trusted CAs. If mutual authentication is enabled, the client also presents its certificate, which the server verifies similarly.

### The Vulnerability

The original code snippet lacked checks to enforce mutual authentication, potentially allowing a client to establish a secure connection without presenting a valid certificate. This could lead to unauthorized access and compromise the security of the communication channel. The absence of these checks means that the server does not verify the presence of the client's certificate, even if mutual authentication is configured.

### The Repair

To address this vulnerability, the repair introduces several checks within the `DoTls13Finished` function, which is likely a part of the TLS 1.3 handshake process. Here’s a breakdown of the added logic:

1. **Server Role Identification**: The first step is to determine whether the current entity is a server (`ssl.options.side == Constants.WOLFSSL_SERVER_END`). This ensures that the subsequent checks are only applied to the server side, as mutual authentication enforcement is primarily the server's responsibility.

2. **Mutual Authentication Requirement Check**: The next check evaluates whether mutual authentication is required (`ssl.options.mutualAuth`) or if the server should fail if no certificate is provided (`ssl.options.failNoCert`). These options indicate the server's policy regarding client certificate verification.

3. **Peer Certificate Verification**: If mutual authentication is required or failing without a certificate is set, the server then checks whether it has verified the peer's certificate (`ssl.options.havePeerVerify`) or if the session is being resumed (`ssl.options.resuming`).
