The vulnerability in question allows remote attackers to obtain unauthorized access to a server by exploiting a flaw in the ssl3_get_cert_verify function. This function is responsible for verifying the authenticity of a client's certificate during the TLS handshake protocol. The issue arises when the function accepts client authentication with a Diffie-Hellman (DH) certificate without requiring a CertificateVerify message.

In the buggy code, the function checks if the message type is not a CertificateVerify message. If this condition is met, it then checks if the peer is not null and if the type includes EVP_PKT_SIGN. If both conditions are true, it sends an alert and returns an error. However, this check is insufficient because it does not account for cases where the peer is not null but the type does not include EVP_PKT_SIGN.

The repair addresses this vulnerability by removing the unnecessary check for EVP_PKT_SIGN. Now, if the message type is not a CertificateVerify message and the peer is not null, the function immediately sends an alert and returns an error. This ensures that the server will not accept client authentication with a DH certificate without a CertificateVerify message, thereby preventing unauthorized access.

In essence, the repair strengthens the verification process by making it more stringent. By removing the conditional check for EVP_PKT_SIGN, the function now consistently enforces the requirement for a CertificateVerify message when the peer is not null, thereby plugging the vulnerability. This change ensures that the server will only accept client authentication when the necessary verification steps have been completed, thereby preventing potential security breaches.
