The original code snippet contains a vulnerability related to the handling of client authentication using Diffie-Hellman (DH) certificates in the `ssl3_get_cert_verify` function. The issue arises because the function does not enforce the requirement for a `CertificateVerify` message when a client presents a DH certificate. This allows an attacker to bypass the need for proving possession of the private key associated with the certificate, thus gaining unauthorized access.

### Vulnerability Analysis

In the original code, the condition `if (s.s3.tmp.message_type != Constants.SSL3_MT_CERTIFICATE_VERIFY)` checks whether the current message type is not a `CertificateVerify` message. If this condition is true, the code proceeds to check if the peer supports signing (`(type & Constants.EVP_PKT_SIGN) != 0`). However, it fails to specifically check if the peer's certificate uses a DH algorithm before deciding whether a `CertificateVerify` message is necessary.

This oversight means that even if a client presents a DH certificate, the server might not require a `CertificateVerify` message, allowing the client to authenticate without demonstrating knowledge of the private key. This is a significant security flaw, as it undermines the integrity and confidentiality of the TLS handshake process.

### Proposed Repair

To address this vulnerability, the repair introduces a specific check to determine if the peer's certificate uses a DH algorithm. This is done by adding the condition `if (peer.supportsDH())` within the existing `if` block. Here's a detailed breakdown of the changes:

1. **Check for DH Support**: The new condition `if (peer.supportsDH())` ensures that the server only skips the `CertificateVerify` message requirement if the peer's certificate does not use a DH algorithm. If the peer's certificate does use DH, the server will enforce the presence of a `CertificateVerify` message.

2. **Enforce CertificateVerify Requirement**: When the peer's certificate uses a DH algorithm, the server sends a fatal alert (`SSL3_AL_FATAL`) with the error code `SSL_R_MISSING_VERIFY_MESSAGE`. This effectively terminates the TLS handshake, preventing the client from authenticating without providing proof of possession of the private key.

3. **Maintain Existing Functionality**: For peers that do not use a DH algorithm, the server continues to behave as it did in the original code, allowing the handshake to proceed without requiring a `CertificateVerify` message if the peer does not support signing.
