The vulnerability existed because the function was too lenient when a client used a Diffie-Hellman certificate and omitted the CertificateVerify message during the handshake. In the original implementation, when the handshake message was not a CertificateVerify, the code set a flag to reuse the message and then checked whether the peer object was not null and if a specific signing flag was present. Only under those conditions did it raise an alert and abort the handshake; otherwise, it accepted the handshake process. This meant that in some scenarios—specifically when a client presented a DH certificate without providing the necessary CertificateVerify message—attackers could manipulate the handshake process to bypass authentication, even without the correct private key.

The repair addresses this key oversight by simplifying the logic. Instead of conditionally accepting the handshake based on an extra check of a signing flag, the modified code no longer considers that extra condition. Now, if the message type isn’t CertificateVerify and a peer is present (which implies that a client certificate was used), the code will always send an alert and immediately terminate the connection. By doing this, the repair removes any loophole that previously allowed a crafted message to be interpreted as a valid handshake in the absence of the certificate verification.

This change is important because it enforces the protocol requirements strictly. Every legitimate client is expected to supply a CertificateVerify message when using certain types of certificates. Without this message, there is no cryptographic proof that the client holds the corresponding private key. Any relaxation of this rule could allow malicious actors to pretend they possess a valid certificate when they do not, thereby compromising secure communications. The repair eliminates the possibility that a server could be tricked into accepting an incomplete or improperly authenticated handshake simply because specific flags were set. 

In summary, the repair ensures that the absence of a required CertificateVerify message is always treated as a fatal error when a client certificate is involved. This removes the conditional bypass that previously existed and hardens the TLS handshake process against attackers trying to exploit a gap in certificate validation.
