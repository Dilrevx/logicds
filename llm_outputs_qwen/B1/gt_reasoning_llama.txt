The vulnerability in question allows remote attackers to obtain unauthorized access to a server by exploiting a flaw in the ssl3_get_cert_verify function. This function is responsible for verifying the authenticity of a client's certificate during the TLS handshake protocol. The issue arises when the function accepts client authentication with a Diffie-Hellman (DH) certificate without requiring a CertificateVerify message.

The CertificateVerify message is a crucial component of the TLS handshake protocol, as it ensures that the client possesses the private key associated with the certificate. By not requiring this message, the server essentially allows an attacker to authenticate without actually having the private key.

The buggy code snippet provided does not explicitly check for the presence of a CertificateVerify message when the peer is not null and the type is EVP_PKT_SIGN. This oversight enables the vulnerability.

The repair addresses this issue by removing the condition that checks for EVP_PKT_SIGN. As a result, the function will always check for the presence of a CertificateVerify message when the peer is not null, regardless of the type. If the message is missing, the function will return an error (SSL_AD_UNEXPECTED_MESSAGE) and terminate the handshake.

In essence, the repair ensures that the server will only accept client authentication with a DH certificate if a valid CertificateVerify message is present. This fix effectively closes the vulnerability by preventing attackers from obtaining unauthorized access without knowledge of the private key.

By making this change, the server will now correctly enforce the requirement for a CertificateVerify message, thereby maintaining the security and integrity of the TLS handshake protocol.
