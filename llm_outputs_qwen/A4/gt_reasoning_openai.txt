The vulnerability arose because the OpenSSL 3.0 implementation of the RC4-MD5 ciphersuite was mistakenly using the Additional Authenticated Data (AAD) as the key for the Message Authentication Code (MAC). The AAD is intended only to provide supplementary data that is authenticated alongside the ciphertext, not to serve as a secret key. Since the AAD is often predictable or even publicly known, using it as the MAC key means that an attacker could easily anticipate or determine the key required to authenticate data. This flaw would allow an attacker, for instance, to perform a man-in-the-middle attack and modify data without detection, as the MAC check would still pass.

The repair fixes this problem by changing the parameter that the function searches for. Instead of locating the AAD parameter, the function now correctly searches for the MAC key parameter. This adjustment is crucial because it directs the implementation to obtain the correct, secret MAC key that should have been used for authentication. The secure MAC key is meant to be unpredictable and kept confidential, ensuring that even if an attacker can modify data in transit, they would not be able to forge a valid MAC without knowing this secret key.

In essence, the correction involves proper parameter identification. Rather than mistakenly using the publicly available AAD, the repair ensures that the implementation derives the MAC key from the secure parameter assigned for that purpose. This not only eliminates the vulnerability by removing the use of a predictable key but also restores the intended integrity of the cryptographic process. Thus, by pointing the function to the correct parameter, the repair strengthens the overall robustness of the cipher, aligning its operation with secure cryptographic practices.
