The vulnerability existed because the system did not always perform the necessary security check for zone transfers on DLZ zones. In the original logic, a check was made to see if a DNS zone existed in the primary (or normal) zone table. If no match was found, the code then attempted to consult the DLZ databases. However, this approach overlooked the situation where a zone is present in the zone table and is flagged as a DLZ type. For writable DLZ zones, the extra transfer permission check—conducted via the allowzonexfr method—was never triggered, leaving a gap where unauthorized transfers could potentially succeed.

The repair addresses this shortcoming by altering the condition that decides when to check the DLZ databases. Now, rather than only checking the DLZ databases when the lookup in the primary zone table fails, the condition also explicitly checks whether the zone's type is DLZ. This means that even if the zone is found in the table, if it is of the DLZ type, the system will still invoke the allowzonexfr method to enforce proper permissions.

In practical terms, this change makes sure that all zone transfers involving DLZ zones undergo the same rigorous security scrutiny that non-writable zones receive. If the allowzonexfr method determines that the transfer request does not have the necessary permissions, the transfer is explicitly rejected and the event is logged. Logging such events is crucial for auditing and tracking potential security incidents.

By enforcing a dual-path check—either if the primary zone lookup fails or if the zone is marked as DLZ—the fix ensures that no DLZ zone escapes the additional permission verification. This prevents situations where an unauthorized user might exploit the writable nature of a DLZ zone to perform an illicit zone transfer, thereby mitigating the risk of unauthorized data access or manipulation.

Overall, the reasoning behind this repair is to close the security gap that allowed a bypass of the proper DLZ transfer controls. By including a check for the zone type, the system reliably applies the same transfer control logic to every zone marked as DLZ, irrespective of its presence in the primary zone table. This change strengthens the security posture by ensuring consistent enforcement of zone transfer policies, ultimately protecting against potential exploits involving writable DLZ zones.
