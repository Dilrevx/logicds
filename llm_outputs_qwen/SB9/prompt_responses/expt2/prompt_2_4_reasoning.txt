### Original Vulnerability

In the original code, there were multiple conditional checks for different signature algorithms (`ed25519`, `ed448`, `ecc_dsa`, `falcon_level1`, `falcon_level5`, `rsa`, `rsa_pss`). Each check verified if the `sigAlgo` matched a specific constant and then checked if the corresponding key was present in the server's certificate. However, the logic was flawed in several ways:

1. **Incorrect Handling of RSA Signature Algorithms**: The code returned `CommonsConstants.INVALID_PARAMETER` for `rsa_sa_algo` but did not properly validate `rsa_pss_sa_algo`. It only checked if `ssl.peerRsaKeyPresent` was true without verifying the existence of `ssl.peerRsaKey`.

2. **Lack of Final Validation**: There was no final check to ensure that the signature algorithm matched any of the expected public keys. If none of the conditions were met, the function would implicitly proceed without returning an error, potentially allowing a mismatched signature algorithm to pass through.

3. **Inconsistent Error Messages**: The error messages were inconsistent and sometimes misleading. For example, the message "Peer sent Falcon Level 1 sig but different cert" was incorrect and could confuse developers or auditors.

### Repair Strategy

The repair strategy involves introducing a new boolean variable `validSigAlgo` to track whether the signature algorithm in the `certificate_verify` message corresponds to the public key present in the server's certificate. Here’s a detailed breakdown of the repair:

At the beginning of the repair logic, the `validSigAlgo` flag is initialized to `false`. This sets up a default state where the signature algorithm is assumed to be invalid until proven otherwise. This approach ensures that if none of the conditions are met, the function will return an error, preventing any potential bypasses.

```java
boolean validSigAlgo = false;
```

#### Evaluation of Signature Algorithms

For each supported signature algorithm, the code checks if the `sigAlgo` from the `certificate_verify` message matches the respective constant. This pattern is repeated for all supported signature algorithms, ensuring that each one is properly validated.

#### Handling RSA Signature Algorithms

The RSA signature algorithms (`rsa_sa_algo` and `rsa_pss_sa_algo`) are handled separately. For `rsa_sa_algo`, the repair code immediately returns `CommonsConstants.INVALID_PARAMETER` because PKCS#1.5 is not a valid signature algorithm for TLS 1.3.

For `rsa_pss_sa_algo`, the repair checks both the existence of `ssl.peerRsaKey` and the value of `ssl.peerRsaKeyPresent`. If either condition fails, the signature algorithm is considered invalid.

#### Final Validation Check

After evaluating all possible signature algorithms, the repair code checks the `validSigAlgo` flag.
```java
if (!validSigAlgo) {
    Wslib.WOLFSSL_MSG("Peer sent sig but no matching cert");
    return CommonsConstants.SIG_VERIFY_E;
}
```
