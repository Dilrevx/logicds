The vulnerability arose because the DTLS client was using a fixed, non-random set of zero-bytes for generating client randomness, undermining the security guarantees of the DTLS protocol. In DTLS, client randomness is critical to ensuring that each session is secured with unpredictable values. The buggy code intended to generate new client randomness under specific conditions but failed to account correctly for one particular scenario in DTLS handshakes involving HelloVerifyRequest messages.

The original code contained a condition that aimed to determine whether to call the function for generating client randomness. It checked two things: first, whether the handshake had not already received a HelloRetryRequest, and second, whether the session was a DTLS session with no HelloVerifyRequests received. However, the check for the DTLS session was flawed because it explicitly looked for sessions where the number of HelloVerifyRequests was equal to zero. This meant that in DTLS sessions where a HelloVerifyRequest was present (which is a signal that a cookie exchange is in progress), the condition was erroneously satisfied. As a result, the client would inefficiently generate a new, deterministic (zeroed) client random even when it was not appropriate to do so.

The repair corrects the logic of the condition by reversing the equality check for DTLS sessions. The fixed version now checks if, for a DTLS session, the number of HelloVerifyRequests is not equal to zero. In other words, if any HelloVerifyRequests have been received, it prevents the generation of client randomness by not calling the generation function. This ensures that the function responsible for generating random values is only invoked when the session is in the correct state—namely, when it is safe and appropriate to do so based on the handshake progress.

This change is important because in DTLS, the receipt of a HelloVerifyRequest is a clear indication that the server is verifying the client’s ownership of the claimed IP address and is attempting to mitigate denial-of-service attacks. In such cases, regenerating client randomness (especially one generated in a fixed and predictable way) can lead to replay or man-in-the-middle attack vulnerabilities. The modified condition now properly distinguishes between scenarios where generating a random value is secure and those where it could contribute to a security weakness by defaulting to zero bytes.

In conclusion, the repair corrects the conditional logic that decides whether to generate client randomness. By checking for a non-zero count of HelloVerifyRequests in DTLS sessions, it prevents using inadequate randomness at a stage where a secure and unpredictable value is critical, thereby fixing the vulnerability and strengthening the security of the DTLS handshake process.
