### Understanding the TLS Handshake

The Transport Layer Security (TLS) handshake is a critical phase in establishing a secure connection between a client and a server. It involves several messages exchanged between the two parties to negotiate encryption algorithms, exchange keys, and authenticate each other. A simplified sequence of the TLS handshake includes:

1. **ClientHello**: The client initiates the handshake by sending a ClientHello message containing supported versions, cipher suites, compression methods, and a random value.
2. **ServerHello**: The server responds with a ServerHello message, selecting a version, cipher suite, compression method, and sending its own random value.
3. **Certificate**: The server sends its certificate to authenticate itself to the client.
4. **ServerKeyExchange** (optional): If necessary, the server sends additional information to facilitate key exchange.
5. **CertificateRequest** (optional): The server may request the client's certificate for mutual authentication.
6. **ServerHelloDone**: The server indicates that it has finished sending messages and is waiting for the client's response.
7. **Certificate** (optional): The client sends its certificate if requested.
8. **ClientKeyExchange**: The client generates a pre-master secret, encrypts it with the server's public key, and sends it.
9. **ChangeCipherSpec**: Both the client and server send a ChangeCipherSpec message to indicate that they are about to start using the negotiated encryption keys.
10. **Finished**: Both the client and server send a Finished message, which is a hash of all previous handshake messages, encrypted with the newly negotiated keys to verify the integrity of the handshake.

### Role of the ChangeCipherSpec Message

The ChangeCipherSpec (CCS) message is a control message that signals the transition from plaintext communication to encrypted communication using the negotiated keys. It is a critical step because it marks the point at which both parties agree to start using the encryption parameters established during the handshake. The CCS message must be processed at the correct time to ensure that all handshake messages have been received and verified before switching to encrypted mode.

### The Vulnerability: CCS Injection

The CCS Injection vulnerability occurs when an attacker can inject a CCS message prematurely, causing the client or server to switch to encrypted mode before the handshake is complete. This can lead to several issues, including the use of a zero-length master key, which would allow an attacker to intercept or manipulate the encrypted traffic. The vulnerability arises because the original code does not properly restrict the processing of CCS messages, allowing them to be accepted at inappropriate times.
