The repair provided addresses the "CCS Injection" vulnerability by ensuring that a ChangeCipherSpec (CCS) message is received and processed before the Finished message during the TLS handshake. This is crucial because the CCS Injection vulnerability arises from an attacker being able to inject a CCS message in a way that tricks one party into believing that the encryption keys have been successfully negotiated, when in fact they have not. This can lead to a situation where the session is vulnerable to man-in-the-middle attacks.

### Understanding the Vulnerability

In a typical TLS handshake, the ChangeCipherSpec message is sent immediately after the client and server have exchanged their cryptographic parameters and agreed on a shared secret. The CCS message signals that the sender is about to start using the newly negotiated encryption keys for subsequent messages. After the CCS message, the Finished message is sent to confirm that the handshake was successful and that both parties have the same set of keys.

The vulnerability occurs when an attacker can inject a CCS message in such a way that it appears legitimate to one of the parties, causing them to prematurely switch to using the new encryption keys. If the other party has not yet received or processed its own CCS message, this can result in a mismatch in the encryption states, allowing the attacker to intercept and decrypt traffic.
