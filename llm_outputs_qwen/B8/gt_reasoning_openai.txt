The underlying vulnerability arises when a client, during a TLS 1.3 handshake, receives neither a pre-shared key (PSK) extension nor a key share (KSE) extension from a malicious server. In earlier versions, when both of these critical elements were missing, the implementation would instead rely on a default, predictable buffer as input when generating the session master secret key. This predictable input key material (IKM) could allow an attacker to reconstruct the session key, undermining the security of the connection.

The repair addresses this issue by introducing an additional safeguard—a sanity check—that verifies whether the necessary security parameters have been negotiated before allowing the connection to proceed. In the fixed version, the code first goes through its regular process: it attempts to find and validate a PSK if available. If no valid PSK is found (that is, if the PSK negotiation flag remains unset), then in a correctly functioning secure handshake there should be an alternative mechanism, such as a valid key share provided by a named group, to contribute to the IKM.

The critical change lies in the explicit check inserted after processing PSK data but before finalizing the server hello message. This check confirms that if no PSK has been negotiated, then the named group used for the key share extension must be non-zero (indicating that a key share was indeed received). If both conditions fail—meaning neither a PSK has been negotiated nor a valid key share is present—the function returns an error. This prevents the code from proceeding further with the handshake process.

By aborting the handshake early when neither security extension is provided, the system no longer resorts to using a predictable default IKM value. This is crucial because it eliminates the possibility for an attacker to force a scenario in which both PSK and KSE information are absent, thereby negating the chance to derive the session master secret from flawed, predictable data. The fix thus directly prevents the creation of an insecure TLS 1.3 session when there isn’t proper control over the connection endpoints.

In summary, the repair logic effectively enforces a requirement: a valid PSK or a legitimate key exchange via a named group must be present. If not, the handshake is terminated, ensuring that a session cannot be established on the basis of insecure, predictable key material. This robust validation step helps mitigate the vulnerability by ensuring that both potential attack vectors—missing PSK and missing key share—are covered.
