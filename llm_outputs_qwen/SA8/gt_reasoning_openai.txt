The repair’s primary goal is to ensure that during handshake negotiations the list of key exchange methods is properly sanitized for both client and server contexts, rather than only for the client side. In the original code, the focus was exclusively on the client: if a specific extension string was found in the client's list of key exchange methods, it was removed. This selective processing inadvertently left the server side unchecked. The oversight meant that if an attacker manipulated messages on the server side—such as by omitting or altering parts of the extension negotiation—the server might still accept a downgraded or insecure method, paving the way for a Terrapin attack.

By adding a separate check for server sessions, the repair addresses this vulnerability head-on, ensuring both parties in the connection correctly process their lists of key exchange methods. When the session is identified as a client, the code behaves as before, looking for the designated client extension marker in the client’s list and truncating it if found. This step prevents the client from inadvertently or maliciously advertising insecure options that could lead to integrity check bypasses.

Similarly, when the session is identified as a server, an analogous operation is performed: the server’s list of key exchange methods is scanned for a specific server extension marker. If this marker exists, it is removed from further negotiations by truncating the method list accordingly. This additional check is crucial because it ensures that any potentially exploitable extensions on the server side are not left active, thereby preventing an attacker from exploiting differences in how clients and servers handle the key exchange phases.

The reasoning behind this repair is grounded in the necessity of symmetry in security negotiations. Both the client and server have matching expectations for the cryptographic methods and integrity measures that are used during a successful handshake. If one side retains an insecure extension while the other does not, attackers can manipulate the handshake. Such an imbalance may allow them to bypass integrity checks or force the use of weaker algorithms that degrade overall session security.

Ultimately, by enforcing proper filtering on both sides of the connection, the repair prevents any opportunity for an attacker to trick one party into downgrading its security posture. This full-spectrum validation in the handshake phase is a critical step in mitigating the vulnerability, as it closes off an avenue for remote attackers to succeed in bypassing SSH’s intended security mechanisms, particularly those related to the proper use of algorithms like ChaCha20-Poly1305 and the Encrypt-then-MAC construct in CBC mode.

Thus, the repair is a proactive measure that reinforces high security standards on both ends of the SSH connection, ensuring that no party inadvertently enables a path for a Terrapin attack.
