The provided repair addresses a critical vulnerability in the `tls_verify_crl` function, which is responsible for verifying Certificate Revocation Lists (CRLs) during the TLS handshake process. The vulnerability stems from an incorrect method of retrieving and checking CRLs based on the certificate's subject rather than its issuer. This oversight can lead to scenarios where valid CRLs are ignored, potentially allowing revoked certificates to pass validation, thus compromising security.

### Original Vulnerable Code Analysis

In the original code, the function attempts to retrieve CRLs twice using the `subject` of the certificate. First, it tries to find a CRL that matches the subject of the current certificate to verify its integrity. This part is correct and necessary to ensure that the CRL itself is valid. However, the second retrieval also uses the `subject` instead of the `issuer`. This means that the function does not correctly check if the certificate has been revoked according to the CRL issued by the certificate's issuer. Instead, it checks if the certificate has been revoked according to a CRL issued by the certificate itself, which is logically incorrect and often non-existent.

### Repair Explanation

The repair involves modifying the second CRL retrieval process to use the `issuer` of the certificate instead of the `subject`. This change ensures that the function checks the correct CRL to determine if the certificate has been revoked.

#### Key Changes

1. **First CRL Retrieval**:
   - The first retrieval of CRLs remains unchanged. It still uses the `subject` of the certificate to verify the integrity of the CRLs.
   - ```c
     crls = X509_STORE_CTX_get1_crls(store_ctx, subject);
     ```
   - This step ensures that the CRLs themselves are valid and signed by the appropriate authority.

2. **Second CRL Retrieval**:
   - The second retrieval now uses the `issuer` of the certificate to find the relevant CRL.
   - ```c
     crls = X509_STORE_CTX_get1_crls(store_ctx, issuer);
     ```
   - By using the `issuer`, the function can accurately check if the certificate has been revoked according to the CRL issued by the entity that issued the certificate.

3. **Revocation Check**:
   - After retrieving the CRLs using the `issuer`, the function proceeds to check if the certificate's serial number appears in the list of revoked certificates within the CRL.
   - ```c
     n = sk_X509_REVOKED_num(X509_CRL_get_REVOKED(crl));
     for (j = 0; j < n; j++) {
       X509_REVOKED *revoked;
       ASN1_INTEGER *sn;

       revoked = sk_X509_REVOKED_value(X509_CRL_get_REVOKED(crl), j);
       #if OPENSSL_VERSION_NUMBER >= 0x10100000L && \
       !defined(HAVE_LIBRESSL)
       sn = X509_REVOKED_get0_serialNumber(revoked);
       #else
       sn = revoked->serialNumber;
       #endif /* OpenSSL-1.1.x and later */

       if (ASN1_INTEGER_cmp(sn, X509_get_serialNumber(xs)) == 0) {
         long serial = ASN1_INTEGER_get(sn);
         char *cp = tls_x509_name_oneline(issuer);

         tls_log("certificate with serial number %ld (0x%lX) revoked per CRL "
           "from issuer '%s'", serial, serial, cp ? cp : "(ERROR)");

         X509_STORE_CTX_set_error(ctx, X509_V_ERR_CERT_REVOKED);
         sk_X509_CRL_free(crls);
         X509_STORE_CTX_cleanup(store_ctx);
         X509_STORE_CTX_free(store_ctx);
         return FALSE;
       }
     }
     ```
   - This loop iterates over all revoked entries in the CRL and compares their serial numbers with the serial number of the certificate being verified. If a match is found, it indicates that the certificate has been revoked, and the function sets an error and returns `FALSE`.

### Conclusion

By correcting the logic used to retrieve and check CRLs, the repair ensures that the TLS handshake process correctly validates whether a certificate has been revoked according to the CRLs issued by the certificate's issuer. This change enhances the security of the system by preventing the acceptance of revoked certificates, thereby mitigating the vulnerability described.
