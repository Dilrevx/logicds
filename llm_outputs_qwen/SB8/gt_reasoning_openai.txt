The core of the issue was that, when neither a pre-shared key (PSK) nor a key share extension was received from the server in a TLS 1.3 handshake, the client would fall back to a default, predictable input keying material (IKM) value when generating the session master secret. Relying on such a known or predictable value compromises the randomness and security of the derived session keys, potentially allowing an attacker to reconstruct the secret key used for encryption and integrity, which undermines the overall security of the session.

The repair addresses this by adding an extra verification step. After examining the PSK extension from the server, if no PSK was successfully negotiated, the patch does not merely proceed with a fallback. Instead, it introduces a condition that checks whether the PSK was negotiated and also verifies the presence of a complementary key share exchange (indicated by a non-default identification of the named group). Essentially, if the connection does not have a valid PSK and there is no proper key exchange mechanism in place (as inferred by a zero value for the named group), then the repair causes the function to return a specific error indicating the absence of a required extension.

This additional check ensures that the session will not proceed with an insecure default value. The new condition effectively stops the negotiation, preventing the client from completing the handshake without proper cryptographic material. By doing so, it bars the potential for an unsuspecting client to use a predictable IKM value, thus mitigating the risk of an eavesdropper being able to compute the session keys.

The reasoning behind the repair is grounded in a security-first mindset. Instead of allowing the connection to continue—despite the lack of both critical extensions, PSK and key share—the function now fails fast, returning an error code that indicates the missing or improperly negotiated extension. This proactive prevention strategy avoids the situation where a fallback to a known value would compromise session security by making the key material predictable and possibly recoverable by attackers.

In summary, the repair reinforces the proper exchange of cryptographic material during a TLS handshake by ensuring that if neither a valid PSK nor a key share extension is present, the handshake is aborted. This step is critical in upholding the intended security guarantees of TLS 1.3, particularly against scenarios where an attacker could manipulate the connection to force the use of weak, predictable values in cryptographic key derivation.
