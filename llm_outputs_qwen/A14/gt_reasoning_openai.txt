The core of the vulnerability lies in OpenSSL’s handling of ChangeCipherSpec (CCS) messages during a TLS handshake. Attackers could take advantage of the fact that the protocol wasn’t strictly limiting when a CCS message could be processed. This flaw might allow a malicious party to inject a CCS message, ultimately setting up a situation in which an incorrect, zero-length master key is used. Such a condition can compromise the session’s encryption, facilitating session hijacking or the exposure of sensitive data.

The repair centers on ensuring that the processing of CCS messages is only permitted when it is explicitly expected. To achieve this, the patch sets a flag (the CCS OK flag) in the session data structure at key points within the handshake state machine. This flag acts as an explicit marker, denoting that the state is indeed at a point in the handshake where a CCS message should be expected. Essentially, by adding this flag, the code creates a safeguard that distinguishes between valid, expected CCS messages and unsolicited or malicious injections.

In more detail, the flag is set before certain critical operations. For example, at the start of processing certificate verification and again during the finished message phase, the flag is set. This proactive marking ensures that if a CCS message is encountered later in the handshake, the code can verify that it comes at an appropriate time. Otherwise, if the flag had not been set, the presence of a CCS message could erroneously lead the state machine to transition as if the handshake were proceeding normally, even though it might be tampered with by an attacker.

Moreover, in cases involving optional protocol extensions such as next protocol negotiation, the repair handles the flag setting in a similar guarded fashion. When transitioning between states that involve receiving or sending protocol elements like the finished messages or new session tickets, the flag is again explicitly set to validate that a CCS message is indeed sanctioned at that moment. This consistent flag setting across different states reduces the risk of an unexpected CCS message slipping through unnoticed.

In summary, the update introduces an extra layer of verification by marking the session state with an indication that a CCS message is expected. This prevents the state machine from inadvertently accepting a CCS message at the wrong time—a scenario that previously allowed attackers to trigger unpredictable and insecure behavior. By embedding these checks into the handshake process, the patch effectively blocks the potential exploitation path that could result in session hijacking or sensitive information disclosure.
