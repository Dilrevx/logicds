The repair provided addresses a critical vulnerability in the way X.509 certificates are verified, specifically concerning the handling of the Subject Alternative Name (SAN) extension. This vulnerability arises from the fact that the original code does not properly differentiate between types of names listed in the SAN extension, leading to potential security risks such as domain name spoofing using IP addresses.

### Understanding the Vulnerability

In X.509 certificates, the SAN extension is used to specify alternative names that the certificate can be valid for, beyond the common name (CN) specified in the subject field. These alternative names can include DNS names, email addresses, IP addresses, and more. The vulnerability stems from the original code's approach to verifying the certificate's validity against an expected common name. Specifically, the code checks only the CN field or, if the SAN extension is present, compares the expected name against all entries in the SAN extension without regard to their type. This means that if the SAN contains IP addresses, they are incorrectly treated as potential matches for domain names, which can allow an attacker to impersonate a domain by obtaining a certificate for the corresponding IP address.

### Identifying the Problematic Code

The problematic line of code is:

```c
if (CommonUtils.x509_crt_check_cn(cur.buf, cn, cn_len) == 0)
    break;
```

This line indicates that the system was primarily checking the Common Name field for a match with the expected CN. However, it does not account for the SAN extension, which can contain multiple names of different types. When the SAN is present, the code should ideally parse it and compare the expected CN against only the DNS names within the SAN, ignoring other types such as IP addresses.

### Developing a New Verification Function

To address this vulnerability, a new function, `x509_crt_check_san`, was introduced. This function is designed to correctly parse and compare the SAN extension against the expected CN, ensuring that only domain names (DNS names) in the SAN are considered for matching. This selective approach prevents IP addresses from being mistakenly accepted as valid domain names.

#### Implementation Details

1. **Parsing the SAN Extension**: The function first parses the SAN extension to extract all entries. This involves iterating over the ASN.1 encoded data structure that represents the SAN extension.

2. **Type-Specific Checks**: For each entry in the SAN extension, the function checks its type. Only entries of type General Name (DNS Name) are considered for comparison. This is done by examining the tag associated with each entry. The tag for a DNS name is typically `2` (as per RFC 5280).

3. **Comparing DNS Names**: If an entry is identified as a DNS name, the function compares it with the expected CN. If a match is found, the function returns success.

4. **Fallback to Common Name**: If the SAN extension is not present or does not contain any matching DNS names, the function falls back to checking the Common Name field. This ensures backward compatibility with certificates that do not use the SAN extension.

5. **Handling Edge Cases**: The function must also handle cases where the SAN extension might be malformed or contain no DNS names. In such scenarios, it should behave consistently with the original code, checking the CN as a fallback.
