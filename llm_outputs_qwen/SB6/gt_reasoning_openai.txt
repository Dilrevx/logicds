The vulnerability arose because the certificate verification process was incorrectly handling the validation of expected names when the subject alternative name (SAN) extension was present. In the original code, the function used to check the certificate against the expected common name only validated the common name field. However, when a SAN extension is present, best practices and standards dictate that the names listed under this extension should be used for name verification instead. Unfortunately, the previous implementation did not enforce checks on the type of names within the SAN extension. As a result, if an attacker managed to obtain a certificate with a SAN containing a different type of name (for instance, an IPv4 or IPv6 address), they might be able to impersonate domains even if they were not supposed to.

The repair addresses this issue by switching the validation function from one that checks the common name (the CN) to one specifically designed to check the SAN extension. This new function, designed for checking the SAN, is implemented to correctly handle the name types, ensuring only valid, matching names are used during the certificate verification process. In doing so, it prevents a scenario where an attacker could exploit a discrepancy between the types of names allowed in the SAN extension and the intended domain names in the certificate.

By prioritizing the SAN check rather than the CN check, the repair aligns with current security recommendations and certificate verification practices. The correct implementation ensures that when a SAN extension is present, the expected name must match a valid entry from that list, respecting the intended distinctions between different types of names. This adjustment closes the loophole that would have otherwise allowed an attacker to use a certificate with a misleading SAN, potentially impersonating a domain by leveraging control over a specific IP address.

In summary, the rationale behind the fix is to enforce a stricter and more secure verification by relying on the SAN extension when it is present. This resolves the vulnerability by ensuring that only names of the appropriate and expected type are considered during the validation process, thereby mitigating the risk of domain impersonation through flawed name-matching logic.
