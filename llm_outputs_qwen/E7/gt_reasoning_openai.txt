The vulnerability arose because the implementation was allowing certain NAS messages—specifically EMM Information, EMM Status, and Detach Request as well as particular cases of Attach/Service Reject—to be processed without any integrity protection. In a secure mobile network, these messages should only be accepted if they have the appropriate security headers to ensure message authenticity and protect against tampering or spoofing. Accepting these messages in plaintext (without integrity checking) opens the door for attackers to forge or inject malicious traffic, potentially causing unauthorized actions or denial of service.

The repair addresses this issue by modifying the message-handling logic. Essentially, it removes the processing for the vulnerable message types when they are received in plaintext. In the original code, a switch-case statement allowed several message types to be processed without security checks. The repair comments out the cases for EMM Information, EMM Status, and Detach Request, which are the problematic types according to the vulnerability description. By doing this, the system will no longer mistakenly process these sensitive messages unless they come with the correct security header that verifies their authenticity.

The reasoning behind this change is straightforward. Since messages like EMM Information and EMM Status—which can contain important signaling information—and Detach Request are now known vectors for potential attacks, they must not be allowed unless they are protected by integrity checks. Allowing them in plaintext could enable attackers to disrupt service or spoof a network's internal signaling messages by exploiting these vulnerabilities. The patch avoids this possibility by ensuring that only messages that are deemed safe to process in plaintext—the ones which have been rigorously vetted and determined not to carry high security risks—are accepted.

Also notable is that Attach/Service Reject messages with a specific cause (emm_cause = 25) were part of the vulnerability. Although the repair does not directly inspect the emm_cause value, it implicitly protects this message type by ensuring that such messages, if potentially carrying sensitive rejection information subject to spoofing, will only be processed if they meet the stricter security requirements.

In summary, the repair's reasoning is to close the security gap by preventing the processing of sensitive NAS message types in plaintext, thereby forcing them to be accompanied by integrity protection. This measure significantly reduces the attack surface by ensuring that all critical signaling messages are subject to verification before being accepted, thereby maintaining the overall security posture of the srsRAN system.
