### Initial Context and Vulnerability Overview
The vulnerability in question pertains to the SSH transport protocol, particularly involving OpenSSH extensions that mishandle the handshake phase and sequence numbers. This can allow attackers to omit certain packets, leading to a situation where security features might be downgraded or disabled. The primary affected algorithms include ChaCha20-Poly1305 and CBC with Encrypt-then-MAC (ETM).

### Core Components of the Repair

#### 1. **Retaining Existing Functionality**
The repair begins by retaining the existing logic that checks the state of the SSH session and handles the reception of the KEXINIT message. This ensures that the fundamental operations of the key exchange process remain unchanged, preserving compatibility and functionality.

The repair introduces a new concept called "Strict KEX." This feature is designed to enforce stricter adherence to the agreed-upon key exchange methods and sequence numbers. It involves setting a new flag, `SSH_SESSION_FLAG_KEX_STRICT`, which indicates that the session should operate under stricter security conditions.

On the server side, the repair checks if the client supports the "strict KEX" feature by examining the client's key exchange methods. This is done using the `ssh_match_group` function, which checks if the client's methods include a specific constant (`KEX_STRICT_CLIENT`). Additionally, a debug log is generated to confirm that strict KEX is enabled.

#### 4. **Client-Side Strict KEX Implementation**
Similarly, on the client side, the repair checks if the server supports strict KEX by examining the server's key exchange methods. #### 5. **Logging for Debugging**
Throughout the implementation of strict KEX, logging statements are added to help with debugging and verification.
