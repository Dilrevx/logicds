The root of the vulnerability lies in the fact that during the SSH handshake, certain OpenSSH extensions can omit parts of the negotiation, which leads to a mismatch in the security assumptions between the client and server. An attacker could exploit this to downgrade or disable some security features by taking advantage of how packet sequence numbers and handshake messages are handled during key exchange. In essence, if parts of the handshake are missing or altered, the session could proceed without proper verification of the connection integrity.

The original code only focused on comparing the initially negotiated key exchange (KEX) and host key algorithms to determine whether the initial guess was correct. This approach was insufficient because it did not safeguard against scenarios where the handshake and sequence numbers might be manipulated—a necessary step to prevent attackers from disrupting the integrity checks that underpin the security of the connection.

The repair introduces an additional, critical step: enabling what is referred to as “strict KEX.” This enhancement is based on the idea that some peers support a more rigorous approach to key negotiation. By explicitly checking if the client’s or server’s key exchange methods include the strict variant (for either the client or the server, depending on which side is functioning in that role), the repair ensures that if supported, the corresponding strict mode flag is set for the session.

By setting this strict key exchange flag, the repair forces the session to adopt tighter controls when verifying packet sequence numbers and managing the handshake process. This means that even if an attacker manages to omit or manipulate parts of the key exchange messages, the protocol will rigorously enforce the expected sequence of packets. The adherence to strict sequence number verification and enhanced message integrity checks prevents attackers from exploiting the flexibility that led to the Terrapin attack.

In summary, the repair works by adding a check for strict key exchange support—depending on whether the session is acting as a client or a server—and then enabling a flag that mandates rigorous handling of packet sequence numbers and handshake messages. This additional verification mechanism helps to mitigate the vulnerability by closing the gap that allowed attackers to bypass integrity checks and ensures that both parties in the connection are aligned in their security posture throughout the key negotiation process.
