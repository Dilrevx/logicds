Below is one example of how to “patch” this code so that if the key isn’t a fully trusted anchor the mirror‐zone copy is not implicitly accepted. In our fix we no longer “succeed” when a key is only a partial match (or not found at all), but instead we return an error status (for example, DNS_R_BOGUS) so that the validated mirror data isn’t used. (Of course, the exact error code and “error‐path” handling may be adjusted to integrate with the rest of your validation framework.)

In this patched version the code no longer “ignores” keys that are not an exact trust anchor match. Instead, by returning DNS_R_BOGUS in the DNS_R_PARTIALMATCH and ISC_R_NOTFOUND cases, the caller will know that the mirror zone data is not completely validated – causing the server to fall back to performing traditional recursion rather than accepting potentially forged zone data.

This fix addresses the vulnerability by ensuring that an on-path attacker cannot trick the recursion logic into accepting forged mirror-zone data.
