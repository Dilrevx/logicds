The repair focuses on addressing the core issue that allowed forged root zone data to be accepted by the recursive server when using mirror zones. The original code segment was intended to verify whether a provided key exists in the trust anchor table by checking for a match in the DNSKEY RRset. If a full match was found (ISC_R_SUCCESS), the key was detached from the keytable and the trust on both the keyset and keysigs was established, marking the data as secure. However, in the cases where the key was only partially matched or not found (DNS_R_PARTIALMATCH or ISC_R_NOTFOUND), the code did not raise an error but instead silently fell back to the use of data that did not have a valid trust anchor. This fallback mechanism creates a vulnerability by allowing an on-path attacker to inject forged data into the mirror zone and bypass the DNSSEC validation.

In mirror zones, the data that initially appears secure (i.e., coming with a trusted signature from a trust anchor) must be strictly validated. If data derived from a mirror zone cannot be validated against any trust anchor, it can no longer offer the same security guarantee. Instead, it poses a risk – the attacker might exploit this behavior to inject forged zone data into the recursive DNS process. In the initial implementation, the improper handling of keys that were not exactly matching (only partial or missing) allowed such an attack vector by not strictly enforcing the trust anchor check.

The repair now explicitly handles the DNS_R_PARTIALMATCH and ISC_R_NOTFOUND conditions by returning an error code (DNS_R_TRUSTANCHOR_MISSING), rather than silently ignoring the anomaly and accepting the mirror zone response. By doing so, if the provided key isn’t correctly found as an absolute trust anchor, the function does not mark the corresponding datasets as secure. Instead, it terminates and signals an error, which prevents the fallback to potentially compromised mirror zone data. This is crucial because it ensures that the recursive server does not inadvertently validate and serve forged data as if it were secure, particularly when the key data has been compromised or tampered with during transit.

Furthermore, by propagating an error in these cases, the repair reinforces the trust model that DNSSEC and mirror zones rely upon. Trust anchors serve as fixed points of security based on known, authentic sources of DNS data. If a key doesn’t match any of the trusted keys, the server should not assume that there is an alternative secure configuration simply because other keys may sign the records. In sensitive configurations, especially those handling root zone data, it is imperative to have a hard check that prevents the use of unverified data.

Additionally, the cleanup step (where dst_key_free is called) is maintained as is, ensuring that all resources are freed appropriately. This change does not affect the memory/resource management but solely focuses on the secure handling of trust anchor verification. Overall, this repair tightly couples the trust anchor verification process with the overall DNSSEC validation path, ensuring that any deviation from a full match is treated as a security-critical failure, thereby mitigating the risk posed by the original vulnerability.
