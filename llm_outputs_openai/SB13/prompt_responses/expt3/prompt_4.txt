One common cause of vulnerability in TSIG handling is that the code originally checked the "msg.tsigstatus" field first—even though attackers might be able to influence this field—while the more reliable TSIG‐internal error code held in "tsig.error" was checked afterward. Reordering the checks ensures that if the TSIG-internal error is set (indicating verification problems), the error is reported immediately. This prevents any attacker from potentially using a crafted "msg.tsigstatus" to bypass the intended response.
