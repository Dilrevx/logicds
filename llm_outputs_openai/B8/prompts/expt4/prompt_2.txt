<vulnerability_description>
In previous versions of wolfSSL if a TLS 1.3 client gets neither a PSK (pre shared key) extension nor a KSE (key share extension) when connecting to a malicious server, a default predictable buffer gets used for the IKM value when generating the session master secret. Using a potentially known IKM value when generating the session master secret key compromises the key generated, allowing an eavesdropper to reconstruct it and potentially allowing surreptitious access to or meddling with message contents in the session. This issue does not affect client validation of connected servers, nor expose private key information, but could result in an insecure TLS 1.3 session when not controlling both sides of the connection. 
</vulnerability_description>

The repair primarily adds an extra validation step to ensure that the necessary key exchange information is present before proceeding with the handshake. In the original code, after handling the PSK extension, there was no explicit check to confirm that either a pre-shared key (PSK) was negotiated or the key share extension (KSE) was provided. This omission allowed a scenario where, if neither extension was present, the code would fall back on a default, predictable buffer for the key derivation process. Using a predictable Initial Key Material (IKM) in generating the session master secret could lead to security compromises, as an attacker might anticipate or reconstruct the key.

The repair first executes the normal logic of searching for and selecting a valid PSK when processing a server hello message. If a valid PSK is found, the code sets up the PSK key and records that a PSK was negotiated. If not, it resets the PSK-related session parameters, making sure that any previous or partial PSK data is cleared.

The crucial change comes immediately after the PSK-handling logic. At this point, the repair introduces a sanity check that simultaneously assesses whether either a valid PSK has been negotiated or a key share extension is present. More specifically, it checks that if a PSK negotiation is not confirmed (which might be the case if the PSK extension is missing or invalid) then the key share’s parameter (typically represented by a named group identifier) must be set. A named group value of zero indicates that no key share extension was provided. 

If this combined condition indicates that neither a PSK nor a key share is present, immediately an error is returned, aborting the handshake. This prevents the code from falling back to a default or predictable buffer for the IKM. Only when at least one of these security parameters is provided does the handshake continue. The subsequent steps, including enabling encryption and updating the server state to indicate a successful server hello, only occur if the handshake passes this additional security check.

In summary, the repair adds rigorous validation to ensure that TLS sessions do not operate with default, predictable keys. By confirming that at least one of the critical key exchange methods—either the PSK or the key share via a non-zero named group—is present, it blocks any potential for using insecure, guessed buffers. This mitigates the vulnerability by ensuring that an eavesdropper cannot exploit the predictable IKM value to reconstruct the session keys, thereby maintaining the intended security guarantees of TLS 1.3.
