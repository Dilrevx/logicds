The repair adds a safeguard after processing the PSK extension so that the handshake does not proceed if both the PSK and key share information (indicated by the named group) are missing. Here’s a breakdown of the changes:

1. PSK Handling Remains Intact:  
   The code first checks for the PSK extension in the Server Hello message. It locates the PSK list, iterates through the entries until it finds one marked as "chosen," and calls SetupPskKey() if a valid PSK is found. If no chosen PSK is present, it zeroes out the PSK key buffer. In previous versions, this would allow the handshake to continue using a default, predictable key if no PSK was negotiated.

2. New Safety Check for Key Share:  
   After the PSK handling block, the repair introduces a new conditional check. This check verifies two things:  
   - That no valid PSK was negotiated (i.e., the flag ssl->options.pskNegotiated remains false), and  
   - That the key share information is missing (determined by checking that ssl->session.namedGroup is zero).  
   If both conditions are met, it means neither secure PSK data nor valid key share data is available for deriving the master secret.

3. Early Termination on Error:  
   When both a PSK and a key share are missing, the function immediately returns an error code (EXT_MISSING). This prevents the handshake from continuing with an insecure, default key generation process. By aborting the handshake early, the repair ensures that session master secret derivation only happens when unpredictable key material is available.

4. Normal Flow Otherwise:  
   If at least one of the crucial components (a negotiated PSK or a valid key share indicated by a non-zero namedGroup) is present, the handshake proceeds normally. The encryption is enabled and the server state updated to complete the Server Hello phase.

In summary, the repair fixes the vulnerability by adding this critical conditional check. Instead of allowing the handshake to continue—potentially generating a session master secret from a predictable IKM when both PSK and key share are missing—the patch aborts the process. This stops an attacker from exploiting the predictable default key material to reconstruct secure session keys, thereby significantly tightening the security of the TLS 1.3 session setup.
