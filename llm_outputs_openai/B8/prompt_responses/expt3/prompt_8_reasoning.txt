The repair enhances security by ensuring that the TLS 1.3 handshake only proceeds if at least one valid key exchange mechanism is in place. Here’s a breakdown of what changed and why:

1. The initial code segment remains largely unchanged: it continues to search for a valid pre-shared key (PSK) by iterating through potential PSK objects until one is found that is marked as “chosen.” If no valid PSK is found, the code clears any existing PSK session state.

2. The critical change is the added check immediately after the PSK-handling logic. This new check looks at two conditions:
   • It verifies whether a PSK was negotiated (using the ssl->options.pskNegotiated flag).
   • It checks whether the key share extension is present, determined by ensuring that ssl->options.keyShareNamedGroup is nonzero (a zero indicates that no valid key share extension was provided).

3. If neither a valid PSK is negotiated nor a valid key share is provided (i.e., both conditions fail), the code then returns an error. This prevents the handshake from continuing with a predictable default key, which was the vulnerability. By abandoning the handshake in this case, the repair ensures that no insecure “fallback” occurs.

4. If at least one of these secure key exchanges is present, the function proceeds to enable encryption and update the server state accordingly, ensuring that subsequent communications use proper session keys generated from secure key exchange data.

Thus, the repair fixes the vulnerability by enforcing that the system does not rely on a default or predictable key buffer for generating the session master secret. By introducing a safeguard that aborts the handshake when neither a PSK nor a key share extension is provided, it eliminates the potential use of compromised or predictable Initial Key Material (IKM), thereby preserving the security integrity of the TLS 1.3 session.
