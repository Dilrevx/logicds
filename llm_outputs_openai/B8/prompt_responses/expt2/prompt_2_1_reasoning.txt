The repair introduces an additional and vital security check immediately after processing the Pre-Shared Key (PSK) extension to ensure that the key exchange process is not inadvertently left with insecure defaults. In previous versions of the code, if neither a valid PSK nor a key share extension was provided, the implementation would use a default, predictable buffer when deriving the Initial Key Material (IKM). This predictable IKM could allow an attacker to reconstruct session keys, potentially leading to compromised message confidentiality and integrity. The repair fixes this vulnerability by making sure that at least one secure key exchange mechanism (either PSK or key share) is present before proceeding.

Initially, the code still searches for a valid PSK among the provided extensions. If a PSK is found and marked as chosen, the PSK key is set up, and the appropriate flag is raised. Conversely, if no valid PSK is negotiated, the PSK-related session parameters are cleared, avoiding any unintended reliance on potentially stale or insecure data. However, rather than allowing the handshake to continue blindly, the repair adds an indispensable post-PSK validation.

In the new validation block, the code checks if no PSK was successfully negotiated. If that is the case, it then attempts to locate the key share extension. The search for the key share extension is performed similarly to how the PSK extension was located, using the same mechanism. The repair then examines the contents of the key share extension – specifically, it checks the named group identifier within the key share structure. A key share with a named group value of zero is considered invalid, indicating that proper key share values were not provided by the server. In either case – if the key share extension is missing or if its named group is zero – the handshake is immediately aborted by returning an error.

This layered checking mechanism ensures that the cryptographic negotiation does not fall back to using default and predictable IKM values. In TLS 1.3, it is critical that either a PSK or a valid key share is present to establish a secure session. By enforcing this requirement, the repair prevents any situation where an attacker could manipulate the handshake, leading to a session key generated from insecure data. It eliminates the risk associated with falling back to defaults that could be predictable by an adversary.

Furthermore, by explicitly checking the validity of the key share data, the repair avoids scenarios where configuration errors or malicious server responses might otherwise allow the handshake to complete under compromised conditions. It forces the implementation to abort the handshake when neither secure exchange method is available, thereby upholding the security guarantees of the TLS 1.3 protocol. This extra guard is a proactive measure to ensure that all critical cryptographic elements are present and valid, reinforcing the overall robustness of the secure communication session.

Overall, the repair significantly enhances the security posture of the TLS implementation. It ensures that the derivation of the session master secret is based only on secure, non-predictable values, maintaining the confidentiality and integrity of the communication channel under all circumstances.
