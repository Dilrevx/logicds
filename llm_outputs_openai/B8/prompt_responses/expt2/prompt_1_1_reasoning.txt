The vulnerability stems from the use of a fallback mechanism where a default, predictable IKM (Input Key Material) buffer is used when the PSK (Pre-Shared Key) extension is missing. When a TLS 1.3 client does not receive either a valid PSK extension or a proper key share extension from the server, the original code zeros out or initializes the session’s PSK key buffer with a known pattern rather than truly random data. An attacker who can potentially control one side of the connection might leverage the fact that the IKM is predictable to reconstruct the session master secret, thereby compromising the confidentiality of the secure connection.

In the original code, when the function finds that no PSK is chosen (i.e., psk == NULL), it opts to disable session resumption and sets the PSK key buffer to zeros using XMEMSET. While this might have been intended as a safe fallback, it inadvertently creates a scenario where the client uses a well-known and predictable buffer for key derivation. This can lead to a situation where an eavesdropper, aware that a default buffer is being used, has a theoretical advantage in breaking the session’s security.

The repair for the vulnerability takes a significantly different approach. Rather than compensating for the absence of a valid PSK by initializing a predictable buffer, the revised logic aborts the handshake. Specifically, if no valid PSK is found (i.e., if “psk” remains NULL), the condition now immediately returns a TLS handshake failure alert (TLS_ALERT_HANDSHAKE_FAILURE) instead of setting a default key. This design decision is based on the principle that in a TLS 1.3 session, critical security parameters should always be derived from unpredictable, securely negotiated input material. By aborting the handshake, the client ensures that an insecure session is never negotiated, thereby avoiding the risk of potential key reconstruction by an attacker.

Aborting the handshake is a robust strategy because it does not attempt to fallback to a weakened security mode. Instead, it forces both sides—the client and the server—to re-establish a new connection under correct and secure parameters. In scenarios where both parties are under adversarial influence or if one side is compromised, forcing an abort helps prevent an insecure session from being finalized. This strict stance ensures that the cryptographic guarantees offered by TLS 1.3 remain intact and the session master secret is derived only from truly random and confidential inputs.

Furthermore, introducing this fail-fast approach aligns with widely accepted best practices in secure protocol design where the presence of essential cryptographic parameters is non-negotiable. In cryptography, it is preferable to fail an operation than to proceed under ambiguous or weakened conditions, as any compromise in randomness directly undermines the entire security model.

In summary, the repair removes the fallback mechanism that led to using a predictable IKM buffer and replaces it with a strict check that aborts the handshake if a valid PSK isn’t found. This effectively eliminates the attack vector that allowed an attacker to potentially predict the key material used for securing the session, thereby ensuring a higher level of security in compliance with TLS 1.3 standards.
