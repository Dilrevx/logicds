Below is an explanation of the repair:

1. The original vulnerability stemmed from the fact that if a TLS 1.3 server did not send either a valid Pre Shared Key (PSK) extension or a Key Share extension, the implementation would end up using a predictable, zeroed buffer as the IKM. An attacker with control of one end of the connection could force this state and potentially derive the session keys.

2. In the repair code, immediately after fetching the PSK extension (if available), the code now also looks for a Key Share extension by calling TLSX_Find with TLSX_KEY_SHARE. This extra check ensures we know whether at least one of the two required extensions is present.

3. If neither a valid PSK (one with the ‘chosen’ flag set) nor a Key Share extension is detected, the function returns a fatal error rather than proceeding. This prevents the situation where a default, predictable IKM value would be used.

4. Furthermore, if no PSK is provided (but a valid key share extension is present) then instead of simply zeroing out the PSK key buffer (which could result in the use of a predictable IKM), the repair code now fills the PSK key buffer with random data generated by wc_RNG_GenerateBlock. By doing this, even if a PSK isn’t provided, the IKM derivation will use a random value rather than a constant one, eliminating the vulnerability.

5. The repair retains the original functionality for scenarios when a valid PSK is available. It checks the PSK list for an entry marked as “chosen” and, if found, continues with the setup (via SetupPskKey) and marks that PSK was negotiated.

6. Finally, after handling the PSK/key share situation, the repair code continues to set the encryption flag and adjust the server state accordingly. This ensures that the normal handshake progress is maintained once the vulnerability has been mitigated.

In summary, by adding a check for a valid key share extension along with the PSK extension and ensuring that no default or zeroed-out buffer is used to derive the session master secret, the repair stops attackers from influencing or predicting the IKM. Instead, a fatal error is raised (or alternatively, random data is used in scenarios without a PSK), forcing the handshake to abort under unsafe conditions. This fixes the vulnerability by eliminating the possibility of generating an insecure TLS 1.3 session using a known IKM value.
