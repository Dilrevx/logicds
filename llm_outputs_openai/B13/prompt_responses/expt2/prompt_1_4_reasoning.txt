The repair was made by introducing an explicit check for the type of DNS message before relying solely on the TSIG authentication results. The root of the vulnerability was that attackers, knowing a valid TSIG key name and being able to communicate with an authoritative DNS server, might manipulate the server into accepting potentially harmful operations such as AXFR (zone transfer) requests or NOTIFY messages. In the original implementation, the code only checked the TSIG verification statuses, which could be insufficient if an attacker crafted a malicious packet that still passed TSIG verification. This is particularly worrisome because TSIG is designed to validate message authenticity and integrity, but it does not inherently restrict the sensitive operations (like zone transfers) allowed by the server.

To prevent such potential abuse, the repair introduces an additional condition to explicitly reject requests associated with either zone transfers or NOTIFY messages. The repaired code first continues to perform the conversion of the TSIG RDATA into a structured format using dns_rdata_tostruct and confirms the success of that operation using INSIST. This ensures that before any further checking, the TSIG data is properly interpreted.

Following that, the code examines whether the incoming message is an AXFR (zone transfer) request or a NOTIFY message. Specifically:
• It checks if the message opcode corresponds to a query and then ensures that the query’s type, retrieved from dns_message_getquestion(msg), is dns_rdatatype_axfr. This targets the case where a zone transfer might be requested.
• It also checks if the message’s opcode indicates a NOTIFY message.
If either of these conditions is met, the code does not even proceed to the usual TSIG verification comparisons that follow. Instead, it immediately sets the result to DNS_R_REFUSED—this is a clear refusal of the request without providing any opportunity for an attacker to exploit the TSIG processing.

By doing this, we effectively add an additional layer of security wherein the server, in a security-sensitive scenario, will not trust TSIG alone for the authorization of operations that should be guarded by stricter policies such as ACLs. This approach aligns with the defense-in-depth principle: even if an attacker manages to craft a packet that can pass the TSIG check, they will still be blocked if the packet is attempting to carry out a sensitive operation like AXFR or NOTIFY.

The rest of the verification remains intact: if the message’s TSIG status or the TSIG data’s error code indicates a problem, the appropriate error result is set. If not, the overall result remains successful. This way, the server continues to perform the necessary cryptographic verification, while also ensuring that only appropriately authorized operations are processed.

Overall, this repair enhances the security of the system by ensuring that TSIG authentication is not the only mechanism responsible for validating the request, especially for sensitive commands like zone transfers or notifications. Such a design change results in a more robust defense against potential attackers who might otherwise leverage the TSIG mechanism in isolation to compromise or misuse the DNS server’s functionality.
