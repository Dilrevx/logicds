The original vulnerability arose because the DTLS client was not generating a fresh, random value in every case when it should have. Instead, for DTLS sessions that had not yet processed a Hello Verify Request (i.e., when session->internals.dtls.hsk_hello_verify_requests was zero), the condition incorrectly prevented a new random value from being generated. This meant that the code would use a default of 32 null bytes for the client random, which undermined the cryptographic security guarantees of DTLS. Client random values are critical for the key derivation process; they need to be unpredictable to ensure forward secrecy and resistance to various cryptographic attacks. 

The original condition checked that a Hello Retry Request flag (HSK_HRR_RECEIVED) was not set and also made a check for DTLS sessions so that if the DTLS session had no Hello Verify Requests (i.e., when hsk_hello_verify_requests was 0), then it would not generate a new random. However, this logic was inverted, because in a DTLS session that begins the handshake, hsk_hello_verify_requests would naturally be zero. The intent was to bypass random generation only when there had been at least one Hello Verify Request already (indicating a retry state where the client random must be preserved and consistent). Generating a new random value in that scenario would be incorrect because it would alter the established randomness needed for the second leg of the handshake.

To remedy this, the repaired code changes the condition that guards the random generation. Instead of inhibiting random generation for DTLS sessions that have zero Hello Verify Requests, we now only avoid random generation in cases where a DTLS session has already received one or more Hello Verify Requests (i.e., when hsk_hello_verify_requests is not equal to zero). This means that for new DTLS sessions (where hsk_hello_verify_requests remains at zero), or for non-DTLS sessions where this aspect is irrelevant, the client will always generate a fresh random value by calling _gnutls_gen_client_random. In contrast, if the DTLS session is in a retry state — indicated by having a nonzero count of Hello Verify Requests — the random generation function is bypassed, thereby preserving the client random that has already been generated during the initial handshake.

This realignment of conditions ensures that every new DTLS handshake begins with a truly random value, contributing to the secure derivation of encryption keys and overall randomness of the handshake process. The repair prevents potential downgrade or replay attacks based on predictable elements such as constant zero bytes and avoids inconsistencies in DTLS negotiations between the client and server.

Furthermore, the modified condition preserves the integrity of sessions by ensuring that random generation is performed exactly when it is needed: for fresh handshakes. This resolves a critical cryptographic flaw and secures the DTLS negotiation process by strictly adhering to protocol requirements. In summary, by inverting the second part of the condition—specifically, changing the check from “== 0” to “!= 0”—the patch successfully ensures that randomness is generated for every DTLS session initiation, while consistently preventing unnecessary changes if a Hello Verify Request has already been processed. This repair thus maintains the proper flow of a secure handshake and upholds the intended security measures of the DTLS protocol.
