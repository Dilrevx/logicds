The original buggy code was structured so that a random client value was generated only when certain conditions were met. For DTLS sessions that already met those conditions (i.e., not matching the specific “DTLS & no hello-verify” case), the code fell through without generating any new randomness. This resulted in DTLS sometimes using a fixed, zero-filled (32 ‘\0’ bytes) client random, which completely removes the intended randomness and weakens the protocol’s security guarantees.

The repair removes the conditional check so that the code always generates a random client value regardless of whether the session is DTLS or TLS. This is accomplished by unconditionally calling _gnutls_gen_client_random(session) before proceeding further in the DTLS handshake process.

Here’s how the repair resolves the issue:

1. Unconditional randomness generation: Instead of checking various flags (specifically the DTLS condition involving hello-verify requests), the function _gnutls_gen_client_random(session) is now always called for every session. This ensures that every connection uses a genuine cryptographically secure random value for the client random, contributing necessary entropy.

2. Correct entropy even in DTLS: By having the DTLS session generate the client random value (and not simply defaulting to 32 ‘\0’ bytes), the session avoids the scenario where an attacker might exploit the predictable “random” value to compromise the subsequent key exchange or handshake mechanisms.

3. Consistent treatment across protocols: With the repair, both TLS and DTLS sessions utilize the same entropy source (via _gnutls_gen_client_random(session)). This consistent handling prevents subtle differences in behavior between TLS and DTLS that could inadvertently weaken the DTLS protocol’s intended security properties.

4. Security guarantee preservation: The generation of a true random value strengthens the overall handshake by ensuring that the input to key derivation functions is unpredictable. This is vital for the security of the cryptographic operations that follow (like key generation and message authentications).

In summary, the repair eliminates the condition-based selection of randomness for DTLS, which previously could lead to weak, predictable client values. The unconditional randomness generation now guarantees that all sessions, regardless of being TLS or DTLS, get the necessary randomness. This remedy ensures that the DTLS handshake retains its intended security properties by contributing genuine entropy, thereby mitigating the vulnerability where the DTLS client provided no randomness during negotiation.
