The original code had a flaw in its conditional logic that prevented proper generation of a fresh random value for DTLS sessions during the handshake process. In DTLS, the client must generate a true random value as part of its handshake messages, unless a hello verify request has already been received. However, the buggy condition inadvertently skipped the randomness generation when the DTLS session had not yet received a hello verify request (i.e., when the count was 0).

The buggy condition was written as:

  if (!(session->internals.hsk_flags & HSK_HRR_RECEIVED) &&  
    !(IS_DTLS(session) && session->internals.dtls.hsk_hello_verify_requests == 0)) {

This compound condition performed an overall negation that caused the random generation function (_gnutls_gen_client_random) not to be called when it should have been. In effect, for DTLS sessions with no hello verify request (hello verify request count equals 0), the condition evaluating to false prevented random values from being generated and instead defaulted to insecure null bytes.

The repair fixed this by restructuring the condition to more clearly distinguish between DTLS and non-DTLS sessions. The updated conditional is:

  if (!(session->internals.hsk_flags & HSK_HRR_RECEIVED) &&
    (!IS_DTLS(session) || session->internals.dtls.hsk_hello_verify_requests == 0)) {

Let’s break down what this new condition does:

1. The first part !(session->internals.hsk_flags & HSK_HRR_RECEIVED) remains the same, ensuring that if an HRR (Hello Retry Request) has already been received, we don’t regenerate the random.

2. The second part of the condition is now (!IS_DTLS(session) || session->internals.dtls.hsk_hello_verify_requests == 0):
  • If the session is not DTLS (i.e., a standard TLS session), the condition is satisfied regardless.
  • For DTLS, the condition requires that session->internals.dtls.hsk_hello_verify_requests equals 0, meaning no hello verify request has been received yet. 

This distinction ensures that for DTLS sessions, a new secure random value is generated when operating in the initial stage of the handshake (i.e., when no hello verify has been received) rather than mistakenly using a series of zero bytes. 

Thus, by splitting the condition into the DTLS-specific part and the non-DTLS part, the repair ensures that the generation of randomness only gets bypassed when it’s appropriate (after a hello verify request), and that in a fresh DTLS handshake, the client random is properly generated by invoking _gnutls_gen_client_random. 

In summary, the logic now correctly enforces that any DTLS session that has not yet processed a hello verify request will generate a secure, random client value for the handshake, effectively restoring the security guarantees of the DTLS protocol.
