The original code conditionally generated the client random value only if the handshake record flag HSK_HRR_RECEIVED was not set and one additional condition was met: if DTLS was being used then the dtls.hsk_hello_verify_requests must not be equal to 0. This additional condition effectively bypassed the generation of a random value for DTLS sessions when no Hello Verify Requests occurred. In DTLS, however, contributing sufficient randomness is critical. If the DTLS client uses a fixed 32-byte zero array rather than a random value, it undermines the security of the negotiation by reducing entropy.

The repair removes this extra condition that selectively bypassed the random generation for DTLS sessions. Now, the code always calls _gnutls_gen_client_random() when the handshake flag HSK_HRR_RECEIVED is not set, regardless of whether the session is DTLS or not. This change ensures that every connection, including those using DTLS, properly generates a random value as part of the client handshake. This contributes proper entropy to the cryptographic process and maintains the security guarantees of the DTLS protocol.

In essence, the steps are:
1. The removal of the DTLS-specific check forces the function to generate a random client value in all appropriate cases.
2. By doing so, the vulnerability is remedied because the previous branch that could lead to a DTLS session using an insecure, constant 32-byte value is eliminated.
3. The code now operates reliably: regardless of whether the session is DTLS or TLS, if the handshake record hasn’t received the HSK_HRR flag, the client random is generated using secure randomness.

By ensuring randomness is consistently introduced, the vulnerability that resulted from always sending 32 null bytes in DTLS contexts is fixed.
