The fix adjusts the condition that determines whether a new client random should be generated during a DTLS handshake. In the original code, the condition used a negation that inadvertently prevented the generation of a proper random value for DTLS sessions when none of the hello verify requests had been received. This meant that the DTLS client ended up using a default value of 32 null bytes, thereby compromising the protocol’s security.

Here's how the repair works:

1. The original condition checked:
  if (!(session->internals.hsk_flags & HSK_HRR_RECEIVED) &&
    !(IS_DTLS(session) && session->internals.dtls.hsk_hello_verify_requests == 0))
This was interpreted as: if no Hello Retry Request (HRR) flag is set and it is not the case that the session is DTLS with a count of zero hello verify requests, then generate the client random.

2. The logical problem arises because for DTLS sessions that have not yet received any hello verify requests (i.e., count equals zero), the condition inside the negation IS_DTLS(session) && ... becomes true, and its negation becomes false. This prevented the generation of randomness when it was needed.

3. The repair revises the expression to:
  if (!(session->internals.hsk_flags & HSK_HRR_RECEIVED) &&
    (!IS_DTLS(session) || session->internals.dtls.hsk_hello_verify_requests == 0))
This new condition breaks down as follows:
  • First, if the session has not already handled a Hello Retry Request.
  • Second, either the session is not a DTLS session, or – if it is a DTLS session – then it must have zero hello verify requests (i.e., the initial handshake is underway).

4. With this change, for DTLS sessions in which no hello verify request has been received (a scenario that requires generating a fresh, random value), the condition correctly evaluates as true. Consequently, the _gnutls_gen_client_random(session) function is called to create a new secure random client random.

5. This fix ensures that the randomness needed to maintain the cryptographic security of the handshake is provided, rather than using a predictable and insecure all-zero value, thus preserving the integrity of the DTLS handshake process.

By reordering the logic to use an OR (||) for the DTLS session check instead of a negated AND, the repair directly addresses the vulnerability by avoiding the bypass of the randomness generation step in critical situations.
