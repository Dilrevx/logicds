The repair fixes a critical vulnerability related to how the DTLS client random value is generated. In the original code, the condition to generate a new client random was written in such a way that, for DTLS sessions that have not received a hello verify request, the function _gnutls_gen_client_random() was not called. This resulted in the client random remaining set to its default (32 null-bytes), which removes the necessary entropy and compromises the security of the DTLS handshake.

In the repaired code, notice the change in the conditional expression:

 if (!(session->internals.hsk_flags & HSK_HRR_RECEIVED) &&
  (!IS_DTLS(session) || session->internals.dtls.hsk_hello_verify_requests == 0)) {

This is how the new logic works:

1. The first part, !(session->internals.hsk_flags & HSK_HRR_RECEIVED), checks whether a Hello Retry Request (HRR) has been received. If an HRR was received, then we might not need to regenerate the client random value immediately.

2. The second part uses a logical OR: (!IS_DTLS(session) || session->internals.dtls.hsk_hello_verify_requests == 0).  
  • For non-DTLS sessions, !IS_DTLS(session) evaluates to true, so the condition is satisfied and a new random is generated.  
  • For DTLS sessions, this clause ensures that the random is generated only when no hello verify request has been received (i.e., session->internals.dtls.hsk_hello_verify_requests equals 0).

This change in the logic ensures that for DTLS sessions which have not received a hello verify request (a scenario that demands high entropy to secure the handshake), the _gnutls_gen_client_random() function is properly invoked. In contrast, if a hello verify request is in progress (i.e., session->internals.dtls.hsk_hello_verify_requests is nonzero) then regenerating the client random might not be necessary.

By correcting the logic in the condition, the client random value is properly generated with high-quality randomness at the appropriate time. This reinforces the cryptographic guarantees of the DTLS handshake by ensuring the random number used is unpredictable rather than a fixed value of 32 null bytes, which is a critical requirement for secure DTLS communications.

Overall, this repair directly addresses the vulnerability by switching the check from a flawed “not equal” to the correct logic that distinguishes DTLS sessions needing randomness from those already in a hello verify cycle. This control flow adjustment makes sure that every new, security-critical handshake gets a newly generated, random client value, thereby maintaining the integrity and security that DTLS is designed to provide.
