Explanation:
In the original code the decision when to (re)generate the client random was based on a compound negation that omitted the case when a HelloRetryRequest (or a DTLS HelloVerifyRequest) had been received. This could result in a client re‐using an old client random despite the handshake having “retried” its parameters. The fixed code now explicitly regenerates the client random either if the HRR flag is set (for TLS handshakes) or when DTLS is in use and there has been at least one hello‐verify request, ensuring that the client random is freshly computed in all cases where the handshake has been retried.
