Below is one way to fix the issue. In the original code the client’s random value for DTLS sessions is generated only if (a) a Hello Retry Request (HRR) has been received or (b) the session is not DTLS with zero hello verify requests. In DTLS the “hello verify request” is part of a cookie exchange and in the current code path when there is no verify request the random value is left uninitialized (or filled with 32 zero‐bytes), which effectively contributes nothing to the overall randomness.

A corrected version ensures that the client random is always generated (using a cryptographically secure random source) regardless of whether or not a hello verify request has been received. One repair is to remove the DTLS exception from the conditional check so that the random is always generated unless an HRR was actually received. For example, change this:

--------------------------------------------------------
if (!(session->internals.hsk_flags & HSK_HRR_RECEIVED) &&
    !(IS_DTLS(session) && session->internals.dtls.hsk_hello_verify_requests == 0)) {
	ret = _gnutls_gen_client_random(session);
	if (ret < 0) {
		gnutls_assert();
		goto cleanup;
	}
}
--------------------------------------------------------

to the following:

--------------------------------------------------------
/* Always generate the client random unless an HRR was received. */
if (!(session->internals.hsk_flags & HSK_HRR_RECEIVED)) {
	ret = _gnutls_gen_client_random(session);
	if (ret < 0) {
		gnutls_assert();
		goto cleanup;
	}
}
--------------------------------------------------------

This change ensures that even when no hello verify request is present for DTLS (i.e. session->internals.dtls.hsk_hello_verify_requests == 0), the client still uses a proper random value instead of a fixed all-zero sequence. This repair contributes proper entropy to the DTLS handshake and fixes the vulnerability.
