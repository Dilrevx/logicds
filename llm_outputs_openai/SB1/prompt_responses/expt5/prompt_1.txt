Below is one example of a repaired version. In this case the fix is to remove the unconditional setting of s.s3.tmp.reuse_message to “1” before making the signature‐related check. In some situations marking the message as “reusable” may let an attacker replay a (stale) message even when a certificate verify message is expected. The following fix removes that assignment so that the handshake won’t accidentally reuse a later unexpected message when a signature is required.

<repair>
        if (s.s3.tmp.message_type != Constants.SSL3_MT_CERTIFICATE_VERIFY) {
            /* Removed the unconditional reuse_message flag to prevent replay/reuse
               of a message that does not have the expected certificate verify type */
            if (peer != null && (type & Constants.EVP_PKT_SIGN) != 0) {
                al = Constants.SSL_AD_UNEXPECTED_MESSAGE;
                Helper.SSLerr(Constants.SSL_F_SSL3_GET_CERT_VERIFY,
                        Constants.SSL_R_MISSING_VERIFY_MESSAGE);
                Helper.ssl3_send_alert(s, Constants.SSL3_AL_FATAL, al);
                return ret;
            }
            return 1;
        }
</repair>

This change ensures that if the received message isn’t a certificate verify while a signature is expected, the error is raised rather than reusing the prior message, which fixes the vulnerability.
