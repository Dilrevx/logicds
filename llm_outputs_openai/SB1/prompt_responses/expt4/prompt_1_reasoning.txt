The vulnerability stemmed from the fact that the original code only enforced the requirement to receive a CertificateVerify message when the peer’s certificate possessed signing capabilities (checked via the EVP_PKT_SIGN flag). Because Diffie-Hellman (DH) certificates do not set this flag, they could bypass verification, letting an attacker gain access without properly proving ownership of the private key.

The repair unconditionally triggers an error if a client provided a certificate (i.e., if peer is not null) but did not send a CertificateVerify message, regardless of the certificate's signing capabilities. Here’s how it works:

1. The conditional check now solely depends on whether a client certificate (peer) was provided. The original check further inspected the certificate’s flags, meaning that only certificates with signing capability were forced to include CertificateVerify. By removing the flag check, all client certificates, including those with DH certificates, must provide the CertificateVerify message.

2. If the client certificate is present (peer != null) and the expected message type isn’t CertificateVerify, the server treats this as an error case. It sets a fatal alert (SSL_AD_UNEXPECTED_MESSAGE) and logs this error (SSL_R_MISSING_VERIFY_MESSAGE). The alert is then sent back to the client, causing the handshake to end in an error state.

3. The security improvement is straightforward: by enforcing that every client certificate must be accompanied by a CertificateVerify message, you eliminate the possibility of an attacker bypassing signature verification simply by using a DH certificate.

4. This approach closes the door on the previously exploitable flaw, ensuring that even if the certificate lacks inherent signing flags (as is the case with DH certificates), the client must still demonstrate possession of the corresponding private key via a valid CertificateVerify message.

In summary, the repair removes the condition that used the certificate's capability flags to decide whether to demand a CertificateVerify message and instead requires it unconditionally when a client certificate is present. This change solidifies the authentication process by guaranteeing that all client certificates undergo the complete verification process, thereby mitigating the risk of unauthorized access through crafted TLS handshake sequences.
