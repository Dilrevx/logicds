The repair changes the logic that handles the case when the TLS handshake does not include a CertificateVerify message. In the original code, the absence of a CertificateVerify was conditionally flagged as an error only if the client certificate (peer) was present and its type indicated signing capability (using a specific signature flag). This meant that if the certificate was of a type like Diffie-Hellman (DH)—which might not set that flag—the lack of a CertificateVerify message would not trigger an error, allowing potential bypass of the authentication mechanism.

In the repaired code, the condition is modified so that if a client certificate (peer) is present, then the missing CertificateVerify message will always be treated as an error regardless of any flags. This is accomplished by unconditionally checking for the presence of a peer when the received message type is not CertificateVerify:

  if (s.s3.tmp.message_type != Constants.SSL3_MT_CERTIFICATE_VERIFY) {
    s.s3.tmp.reuse_message = 1;

      al = Constants.SSL_AD_UNEXPECTED_MESSAGE;
      Helper.SSLerr(Constants.SSL_F_SSL3_GET_CERT_VERIFY, Constants.SSL_R_MISSING_VERIFY_MESSAGE);
      Helper.ssl3_send_alert(s, Constants.SSL3_AL_FATAL, al);

By removing the conditional dependency on the signature flag (which was previously checking whether the certificate was signing-capable), the repair enforces that any certificate, including DH certificates, must be followed by a CertificateVerify message. This ensures that the client must prove possession of the private key corresponding to its certificate, as prescribed by the protocol.

Overall, the fix makes the error handling more robust. Rather than permitting the possibility of accepting a handshake with a missing CertificateVerify message under specific conditions, the code now immediately logs an error, sends a fatal alert, and terminates the handshake if the client certificate is provided but the CertificateVerify message is absent. This can effectively prevent attackers from exploiting the gap in the protocol implementation to bypass authentication using DH certificates.

Thus, the repair corrects the security vulnerability by strictly enforcing the TLS protocol requirement: when a client presents a certificate, it must also provide a valid CertificateVerify message, ensuring that the possession of the associated private key is proven.
