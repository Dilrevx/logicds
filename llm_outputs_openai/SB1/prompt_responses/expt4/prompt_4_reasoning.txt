The original code conditionally flagged an error when the incoming message wasn’t CertificateVerify only if both a peer was present and a specific signature flag was set. This meant that if the peer was present but the signature flag (i.e., the flag indicating that the certificate should be accompanied by a CertificateVerify message) wasn’t set, then the missing CertificateVerify message would be ignored. Attackers could exploit this loophole, particularly with Diffie-Hellman certificates, by crafting handshake traffic that did not include the CertificateVerify message and still bypass authentication.

In the repair, we removed the check for the signature flag. The updated code now unconditionally checks for the existence of the peer when the message type isn’t CertificateVerify. Here’s what happens step by step:

1. The code first checks if the message type is not equal to CertificateVerify. If it is not, it sets a flag to indicate the current message should be reused.

2. Next, rather than checking a combination of a non-null peer and the specific signature flag, the repaired code simply checks if the peer is non-null. This means that if there is a peer certificate available, the absence of a CertificateVerify message is always treated as an error.

3. If the peer is not null, the code sets an error code for an unexpected message, logs the error using a diagnostic function, sends a fatal alert to the peer, and then terminates the handshake by returning without further processing.

By unconditionally enforcing the requirement for a CertificateVerify message when a peer is present, the repair eliminates the potential loophole that attackers could exploit using DH certificates. Every valid client authentication now requires the CertificateVerify message regardless of the certificate type or any signature flags. This strict checking conforms to the TLS protocol specification, ensuring that a client cannot bypass the authentication step.

In summary, the fix works by:

• Removing the dependence on the signature flag in the error-checking logic.
• Ensuring that if a peer certificate exists and the message is not a CertificateVerify, then it is an error.
• Logging the error and terminating the handshake to prevent an attacker from leveraging the weakness.

This approach guarantees that all authentication attempts comply with the protocol requirement, thereby maintaining the continuity and security of the TLS handshake and protecting against unauthorized access.
