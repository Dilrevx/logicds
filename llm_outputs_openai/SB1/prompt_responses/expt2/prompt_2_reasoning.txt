The repair changes the condition that previously only flagged an error for missing CertificateVerify messages when both a non-null peer and a certain signature flag were present. In the revised version, the error condition is now checked solely based on the presence of a peer, regardless of any flags.

Originally, the code checked if the received message was not of type CertificateVerify. If it wasn’t, the code set a flag to reuse the message and then checked if a valid peer exists and if the certificate had a signature flag (Constants.EVP_PKT_SIGN). Only when both conditions were met would it trigger an error. This allowed an attacker to bypass the requirement for sending the CertificateVerify message by using a certificate that did not set the signature flag, such as one using Diffie-Hellman (DH). Without the CertificateVerify message, under these circumstances the authentication could incorrectly pass, effectively granting unauthorized access.

The repair eliminates the additional check for the specific signature flag. Now, if a non-null peer is present and the message type is not CertificateVerify, it automatically triggers the error handling. The error path logs the error, sets an appropriate alert code for an unexpected message, sends a fatal alert to the client, and terminates the process. This ensures that every client must send a proper CertificateVerify message regardless of the type of certificate used.

By forcing the error when a non-null peer exists (and the message is missing CertificateVerify), the vulnerability is fixed because there’s no longer an optional bypass path for certificates where the signature flag might not be set. Now, even if the client is using a DH certificate, the absence of the CertificateVerify message will cause the handshake to fail, thereby closing the loophole that previously allowed the handshake to continue without the necessary authentication.

In summary, this repair enforces strict adherence to the TLS protocol by ensuring that any client, regardless of the certificate type, must supply a CertificateVerify message to complete the authentication. This eliminates the risk where attackers could manipulate the handshake process by taking advantage of certificate policy variations, thus maintaining the security integrity of the handshake process.
