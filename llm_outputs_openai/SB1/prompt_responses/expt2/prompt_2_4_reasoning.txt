The original vulnerability was due to a logic flaw in determining when the absence of a CertificateVerify message should be treated as a security breach. In the buggy implementation, after detecting that the message type was not SSL3_MT_CERTIFICATE_VERIFY, the code marked the message as reusable and then performed a check that was conditional on two factors: whether a peer certificate existed and whether the certificate had the signing capability (EVP_PKT_SIGN flag). This conditional allowed some clients to bypass the CertificateVerify requirement if their certificate did not include the signing flag, even if the client did in fact provide a certificate. Attackers who managed to use a certificate that didn’t explicitly indicate signing might then be able to complete a TLS handshake without proving possession of the corresponding private key, effectively bypassing authentication altogether.

The repair addresses this vulnerability by simplifying the conditional logic to mandate that if a peer certificate is present at all, then the absence of a CertificateVerify message should be considered a fatal error. The revised logic eliminates the reliance on the signing capability flag, thereby closing the bypass route previously available to some clients.

In the repaired code snippet, the following steps are performed:

1. First, the function checks whether the incoming handshake message is a CertificateVerify message. If it is not, then it marks the message as reusable with “s.s3.tmp.reuse_message = 1;”. This step ensures that the message can be handled as needed, even if it is not the expected type.

2. The subsequent check now only looks at whether a peer certificate is present, removing any additional conditions related to certificate flags. The idea behind this is that any client presenting a certificate must include a valid CertificateVerify message to prove control of the corresponding private key, irrespective of any certificate-specific flags. This change enforces a strict protocol adherence, ensuring that all client certificates behave as intended.

3. If a peer certificate is detected (i.e., “peer != null”), the absence of the expected CertificateVerify message triggers a security violation. The code then sets an alert level (using “al = Constants.SSL_AD_UNEXPECTED_MESSAGE”), logs an error with a specific code (using “Helper.SSLerr(Constants.SSL_F_SSL3_GET_CERT_VERIFY, Constants.SSL_R_MISSING_VERIFY_MESSAGE);”), sends an alert to the peer (using “Helper.ssl3_send_alert(s, Constants.SSL3_AL_FATAL, al);”), and immediately returns an error code. This sequence effectively terminates the handshake process, preventing the potential exploitation of the vulnerability.

4. If no peer certificate is present, the code would simply return a success indicator, as no client certificate authentication is being attempted in that scenario.

By making these changes, the repair ensures that any client presenting a certificate must send a CertificateVerify message as part of the TLS handshake. This prevents attackers from crafting handshake traffic that omits the CertificateVerify message to obtain unauthorized access. The revised conditional, being simpler and stricter, removes the loophole that previously allowed Diffie-Hellman certificates (or any other certificates lacking the EVP_PKT_SIGN flag) to bypass authentication, thereby closing the security gap.
