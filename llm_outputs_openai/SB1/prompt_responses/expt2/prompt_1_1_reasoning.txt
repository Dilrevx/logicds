The repair is aimed at enforcing strict adherence to the TLS protocol requirements for client authentication. In the original buggy code, if the certificate verify message was missing, the logic would set a flag “reuse_message” and behave differently based on the presence of a peer certificate and whether the certificate type supports signing (checked via EVP_PKT_SIGN). This conditional allowed a scenario wherein clients using Diffie-Hellman (DH) certificates could bypass sending an explicit CertificateVerify message. Essentially, the pathway to reuse the prior message state was exploited by specifically crafted handshake traffic, thereby weakening the authentication by not confirming the client's possession of the corresponding private key.

In TLS, the CertificateVerify message plays a crucial role in assuring the server that the client indeed possesses the private key corresponding to the public key in the provided certificate. For instance, with certificates relying on traditional RSA signatures, the CertificateVerify message would contain a digital signature generated using the client’s private key over previous handshake messages. However, if the protocol permits bypassing this message—especially for DH-based certificates (which should still authenticate the client through a signature verification at some point)—an attacker might be able to trick a server into accepting a connection even without a genuine demonstration of key possession. This undermines the core authentication mechanism, making it possible for the attacker to obtain access without the rightful private key.

The repair removes the earlier conditional reuse of the CertificateVerify message by eliminating the path where the absence of the CertificateVerify message would be accepted via a “reuse_message” flag. Instead, regardless of whether the certificate key is DH-based or some other signing mechanism, the absence of the expected CertificateVerify message now immediately triggers an error. This uniform error handling simplifies the logic and ensures that no certification scenario is inadvertently accepted without the appropriate validation steps. As a result, if the CertificateVerify message is missing, the application immediately generates an alert indicating an “unexpected message” and logs this as a missing verify message error. The TLS alert (with level set to fatal) is then sent, and processing is terminated to prevent further exploitation.

By removing the exception for DH certificates and enforcing the CertificateVerify requirement across the board, the repair guarantees that every client must prove possession of the private key corresponding to its certificate. In doing so, it prevents the specific vulnerability described where remote attackers could bypass authentication. This fix is crucial because it preserves the intended security user-by-user, ensuring that even if the client’s certificate structure (e.g., DH type) might have led to a conditional bypass previously, the server will now always enforce the requirement for a CertificateVerify message.

In summary, the repair strengthens the overall SSL/TLS handshake process by ensuring that all clients, regardless of certificate type, are required to send a valid CertificateVerify message. This eliminates the possibility of bypassing client authentication, thereby mitigating the risk of unauthorized access that was present in the previous implementation.
