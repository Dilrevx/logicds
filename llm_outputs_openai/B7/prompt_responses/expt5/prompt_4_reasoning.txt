The repair reorders and extends the leaf certificate verification process to ensure any errors that occur are captured correctly. Here’s how it works:

1. Initially, the code validates the legacy chain using x509_verify_ctx_validate_legacy_chain. This step remains unchanged since it ensures that the basic chain structure meets expected conditions.

2. Next, instead of immediately duplicating the chain, the repair first verifies the leaf certificate’s validity through x509_verify_cert_valid. If this check fails, it inspects the context’s error information. If the error depth is still at its initial state (indicating that no subsequent check has updated it) and the error isn’t the expected “unable to get issuer certificate locally,” then the code duplicates the certificate chain and explicitly records the encountered error (by storing it in the first slot of the chain’s error list). This ensures that if a verification callback allowed processing to continue despite the invalid certificate, the original error isn’t lost.

3. A similar pattern is applied to the hostname verification check using x509_verify_cert_hostname. If hostname verification fails and the error meets the same conditions as above, then the error is captured within a duplicated chain. This mirrors the validation step, ensuring that any issues arising from hostname mismatches are also properly recorded.

4. Only after these leaf certificate checks succeed does the code duplicate the chain normally. Even in this success scenario, it checks whether the duplication is successful (handling out-of-memory errors appropriately). This guarantees that any failure during memory allocation can still be reported accurately without overriding the context of an earlier error.

5. Finally, once the chain is successfully duplicated and stored in the context’s array of chains, the context’s error is explicitly cleared (set to X509_V_OK) and the error depth is updated. This final step confirms that the chain processing has completed successfully and any earlier error information has been separately captured in the chain’s error array.

By verifying and capturing errors from the leaf certificate before duplicating the chain, the repair addresses the vulnerability where errors might be overwritten or lost when a callback instructed the process to continue on an invalid certificate. The modifications ensure that these errors are recorded and preserved for subsequent processing or logging, leading to more accurate error reporting and making it easier to diagnose issues in the certificate chain validation process.
