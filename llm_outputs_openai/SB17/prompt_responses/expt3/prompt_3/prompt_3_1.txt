Below is one possible repair. The problem was that the routine only looked up CRLs by comparing the certificate subject – effectively checking the wrong field twice – causing valid CRLs (using the issuer field) to be ignored. One way to correct this is to perform two lookups (one by subject and one by issuer) and then combine the results. For example:

-----------------------------------------------------------
if (Commons.OPENSSL_VERSION_NUMBER >= Commons.OPENSSL_1_1 && !Commons.HAVE_LIBRESSL) {
    // Look up CRLs both with the certificate subject and its issuer.
    List<X509_CRL> crlsSubject = storeCtx.get1_crls(subject);
    List<X509_CRL> crlsIssuer  = storeCtx.get1_crls(issuer);
    // Combine both lists (implement a merge or simply add all elements)
    crls = merge_crl_lists(crlsSubject, crlsIssuer);
} 
else if (Commons.OPENSSL_VERSION_NUMBER >= Commons.OPENSSL_1_0 && !Commons.HAVE_LIBRESSL) {
    List<X509_CRL> crlsSubject = Commons.get1_crls(storeCtx, subject);
    List<X509_CRL> crlsIssuer  = Commons.get1_crls(storeCtx, issuer);
    crls = merge_crl_lists(crlsSubject, crlsIssuer);
}

-----------------------------------------------------------

In this example, the code now correctly obtains two sets of CRL entries:
1. Those corresponding to the certificate’s subject.
2. Those corresponding to the certificate’s issuer.

Then the two lists are merged (using helper function merge_crl_lists, which you’d need to implement so that duplicates—if any—are properly handled). This ensures that any CRL entry that matches either the certificate subject or the issuer is taken into account. This change fixes the vulnerability where valid CRLs were being ignored and potentially allowed revoked certificates to be accepted.
