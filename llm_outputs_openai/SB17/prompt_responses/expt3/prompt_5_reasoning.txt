The repair addresses a fundamental flaw in the way the certificate revocation list (CRL) is obtained. Initially, the code mistakenly used the certificate subject for the CRL lookup instead of the issuer. This means that the function responsible for retrieving the CRL was being provided with the subject of the certificate rather than the issuer, which could lead to an incorrect revocation check.

By using the subject, the code might retrieve CRL information that doesn’t accurately reflect the revocation status issued by the certificate authority. Essentially, even if a certificate was revoked by its issuing authority, relying on the subject could allow a revoked certificate to pass the CRL check because the integrity of the lookup was compromised. This discrepancy could leave the connection process vulnerable, potentially trusting certificates that have been invalidated.

The repair corrects this vulnerability by replacing the usage of the certificate subject with the certificate issuer. This change ensures that the system fetches the CRL based on the issuing authority, which is the proper source of trust regarding revocation information. Using the issuer guarantees that the CRL obtained is the one that definitively indicates if a certificate has been revoked by the authority that issued it.

In the repair, both branches of the conditional undergo the same change. The logic examines the version of OpenSSL being used as well as whether LibreSSL is not present. For both branches (corresponding to OpenSSL version 1.1 and above, and OpenSSL version 1.0 and above), the call that retrieves the CRL is updated to accept the issuer as a parameter. This consistency is vital to avoid different behaviors depending on the OpenSSL version while still upholding secure practices across all supported versions.

With this update, the application’s certificate revocation checking process now accurately determines whether a certificate has been revoked by querying the correct CRL based on the issuer. It prevents potential bypasses of revocation checks that could occur when the certificate’s subject is used incorrectly. This improvement is significant for maintaining the integrity of secure connections and ensuring that communications are not established with revoked or potentially malicious certificates.

In summary, the repair fixes the vulnerability by ensuring that the CRL is properly retrieved using the certificate issuer rather than the subject. This change strengthens the security posture by aligning the CRL lookup with the correct source of trust, thereby preventing the misuse or oversight of certificate revocation information.
