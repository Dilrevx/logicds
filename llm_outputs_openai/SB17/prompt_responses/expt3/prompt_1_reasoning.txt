In the original code, two branches check for CRLs (Certificate Revocation Lists) using the same field—specifically, they both rely on the "subject" field. This is problematic because the verification process requires looking up CRLs based on the “issuer” of the certificate revocation entry, not the “subject.” By inadvertently using ‘subject’ in both cases, the code might not retrieve the correct CRL entries reflecting revoked certificates. This inadvertent error potentially allows revoked certificates to be accepted because the relevant CRL entries are simply not considered.

The repair replaces the ‘subject’ parameter with ‘issuer’ in both calls to the function that gets CRL entries. Specifically:

1. In the OpenSSL 1.1 branch, instead of using:
   crls = storeCtx.get1_crls(subject);
   it now uses the issuer:
   crls = storeCtx.get1_crls(issuer);

2. Similarly, in the OpenSSL 1.0 branch, the code is updated from:
   crls = Commons.get1_crls(storeCtx, subject);
   to:
   crls = Commons.get1_crls(storeCtx, issuer);

By making these modifications, the function correctly retrieves the CRLs based on the certificate issuer, thus ensuring that any revoked certificates are properly detected and blocked during the TLS handshake process.

This fix directly addresses the core issue mentioned in the vulnerability description (i.e., checking the wrong CRL entry field) and aligns the code behavior with both security standards and robust TLS practices.

Overall, this repair ensures that:
- The code verifies the intended field (issuer) when retrieving CRLs.
- The correct CRL is fetched, so any revoked certificates (identified based on issuer matching) will not inadvertently be allowed to establish a secure connection.
- The vulnerability, which could have allowed revoked certificates to bypass CRL checks, is mitigated.

This explanation shows how the update fixes the vulnerability by ensuring that the CRL lookup key corresponds to the correct identification field, making the client-server connection process more secure by properly validating if the client’s certificate has been revoked.
