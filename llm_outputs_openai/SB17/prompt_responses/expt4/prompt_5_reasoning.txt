The repair addresses the vulnerability by correcting which field is used when retrieving the CRL entries. In the buggy code, the CRL lookup was mistakenly performed using the certificate’s subject name (xs.getSubjectName()) instead of the issuer name. This misstep could cause valid CRLs to be overlooked, meaning that a certificate revoked by its CA might not trigger the proper error.

Here’s how the repair fixes this:

1. Changing the CRL lookup key:  
   Instead of using the subject name, we now properly use the issuer name. The CRL store is searched using xs.getIssuerName() (previously stored in the variable issuer). This makes sense because CRLs are issued by the Certificate Authority (CA) and are associated with the CA’s identity—not the certificate’s subject. Hence, searching by issuer ensures that the correct, valid CRL for the issuing CA is retrieved.

2. Consistency in both checks:  
   The code performs two separate CRL retrievals: one part verifies the signature and validity of the CRL (by checking the issuer’s CRL) and another part iterates over revoked certificates to see if the certificate’s serial number appears on the CRL. The fix applies the correct issuer-based lookup in both instances, ensuring that all checks are now aligned with the intended logic.

3. Proper CRL verification:  
   The rest of the code verifies the CRL’s signature using the client certificate’s public key, checks the nextUpdate field, and finally inspects each revoked certificate entry for a match with the certificate’s serial number. By getting the CRL based on the issuer, these verifications now relate to the correct CRL provided by the CA, eliminating the risk that an attacker might bypass revocation checks using an incorrectly associated CRL.

4. Eliminating the workaround vulnerability:  
   The original issue allowed a certificate to be mistakenly trusted if the CRL didn’t reflect the correct issued-by data. This could potentially be exploited by using revoked certificates. The fix ensures that a certificate’s revocation status is accurately determined against the issuing CA’s CRL, thereby improving overall security.

In summary, by using the issuer name instead of the subject name for retrieving CRLs, the repair ensures that the CRL validation process correctly aligns with the CA’s revocation data. This change addresses the vulnerability precisely, preventing revoked certificates from being wrongly accepted and enhancing TLS security for client-server connections.
