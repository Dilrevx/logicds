The repair fixes the vulnerability by changing the key used to look up Certificate Revocation Lists (CRLs) from the certificate’s subject to its issuer. In the original code, both branches for different OpenSSL versions were incorrectly retrieving CRLs based solely on the subject. This mistake meant that the CRL entries were not properly validated against the issuer information, which is essential for confirming that a certificate comes from a trusted revocation list. An attacker or misconfiguration could potentially allow revoked certificates to bypass the revocation checks.

To correct the logic, the repaired code replaces the subject variable with the issuer variable in both conditional branches. Specifically, when using OpenSSL version 1.1 or newer (and not using LibreSSL), the method get1_crls is now called with issuer as its argument. Similarly, for the branch handling OpenSSL version 1.0 (again ensuring LibreSSL isn’t involved), Commons.get1_crls is also called with issuer instead of subject.

This alteration is critical for two reasons:

1. Accuracy in revocation list matching: CRLs are generated and signed by the issuer. Validating against the issuer ensures that the code is checking the CRL corresponding to the entity that issued the certificate. This step is essential to confirm if the certificate has been explicitly revoked by the correct authority.

2. Elimination of logical errors: By switching the parameter from subject to issuer, the repair removes the error where the same field was mistakenly used in both contexts (i.e., comparing against itself). This change forces the CRL verification mechanism to properly pair the certificate with the specific revocation list signed by the certificate’s issuer. With this pairing, if a certificate is indeed revoked (and the issuer’s CRL confirms it), the connection process correctly identifies and blocks such certificates.

In summary, the repair ensures that CRL retrieval checks are based on the certificate’s issuer – the correct identification field – rather than the subject. This correction reinforces the security of the revocation verification process, preventing potentially revoked certificates from being mistakenly accepted during a TLS connection.
