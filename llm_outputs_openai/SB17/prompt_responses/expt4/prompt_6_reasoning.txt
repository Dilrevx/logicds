The repair addresses the vulnerability by ensuring that the Certificate Revocation List (CRL) lookup uses the certificate issuer instead of the certificate subject. Originally, the code mistakenly used the subject field twice, which could cause valid CRLs to be overlooked and allow revoked certificates to pass through the verification process. Here’s a step-by-step explanation of how the fix works:

1. First, the code retrieves details from the certificate (xs) obtained from the context. It correctly gets both the subject name and the issuer name. Debug logs are printed to track these values.

2. The crucial change occurs in the CRL retrieval process. Instead of calling the function to get CRLs using the subject, the repair modifies the function calls to use the issuer. In both branches (for OpenSSL version 1.1 and above, and for version 1.0 and above), the parameter passed to get1_crls (or Commons.get1_crls) is now the issuer. This change ensures that the lookup for CRLs targets the correct field, because CRLs are typically associated with the issuer who has signed the list of revoked certificates.

3. The repair applies this similar change in both sections where the CRLs are fetched. The first retrieval validates the CRL’s signature, nextUpdate field, and expiration; the second retrieval iterates through the list of revoked certificates to see if the serial number of the client certificate has been marked as revoked. In each case, using the issuer ensures that the CRL is correctly associated with the authority responsible for revoking certificates.

4. With these corrections, when a CRL is fetched, it accurately corresponds to the issuer that signed the certificate. This guarantees that all CRLs from the correct issuer are checked. If the certificate’s serial number is found within any of these lists, the code logs the event, sets an error, and rejects the certificate as revoked.

5. Finally, the code performs proper cleanup of resources before returning. This maintains good resource management while ensuring that the certificate validation pathway is secured.

In summary, by replacing the use of the subject with the issuer for CRL lookups, the repair guarantees that the certificate verification process checks against the correct set of CRLs. This eliminates the possibility of revoked certificates being inadvertently accepted due to a misdirected CRL lookup.
