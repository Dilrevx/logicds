The repair fixes the vulnerability by replacing the use of the certificate’s subject with its issuer when retrieving the Certificate Revocation Lists (CRLs). In the original code, both calls to retrieve the CRLs were using the subject from the certificate. However, CRLs are issued by a Certificate Authority (CA) and are signed using the issuer’s key. By using the subject in the lookup, the CRL lookup could retrieve an incorrect list, possibly missing revocation checks for certificates, thereby allowing revoked certificates to be incorrectly accepted.

Here’s a step-by-step explanation of the repair:

1. When fetching the CRLs, the code now passes the issuer rather than the subject. This change is made in both the initial verification loop (which checks for valid signatures and expiration) and the loop that looks for a matching revoked certificate. Depending on the version of OpenSSL, the appropriate method is called (either storeCtx.get1_crls(issuer) for OpenSSL 1.1+ or Commons.get1_crls(storeCtx, issuer) for OpenSSL 1.0+). This ensures we are querying the CRLs produced by the proper authority.

2. After obtaining the CRLs using the issuer, the code then iterates over each CRL to:
   - Verify its signature using the certificate’s public key. This check ensures that the CRL is indeed properly signed by the expected authority.
   - Check the CRL’s "nextUpdate" field to confirm that the CRL is current and hasn’t expired or is ill-formed.

3. Once the CRLs have passed these verifications, they are then scanned for any revoked certificate entries. Each entry is compared against the certificate’s serial number. If a match is found, the certificate is correctly flagged as revoked and the function returns an error.

By changing the CRL lookup to use the issuer, the code now accurately obtains the CRLs that were signed by the CA responsible for revoking certificates. This prevents the possibility of overlooking revoked certificates that might have been missed due to mistakenly using the subject as a lookup parameter.

In summary, the fix addresses the vulnerability by ensuring that the CRL retrieval process correctly uses the issuer of the certificate. This means that only the CRLs relevant to the certificate’s issuing CA are considered during the verification process. As a result, clients whose certificates have actually been revoked are properly identified and denied access, reinforcing the security of the TLS session.

This repair reinforces the integrity of certificate validation, ensuring that no revoked certificate is erroneously accepted, thereby preventing potential unauthorized access or security breaches.
