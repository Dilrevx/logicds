The repair replaces the use of the “subject” variable when retrieving Certificate Revocation Lists (CRLs) with the “issuer” variable. The vulnerability was caused by the code checking the same CRL field — subject — both times instead of checking once for subject and then for issuer. This error results in some valid CRLs not being taken into account, potentially allowing connections even when the client’s certificate has been revoked. 

In practice, a server obtains CRLs to verify if a certificate presented by a client has been revoked by the Certificate Authority (CA). The CRLs, however, are associated with certificates by the issuer field because the revocation is issued by the same CA that issued the certificate. By incorrectly using the subject (which identifies the certificate itself) in the CRL retrieval process, the code may not correctly match the CRL with the certificate trust chain. This mismatch means that the system might miss valid CRLs for a certificate, undermining the revocation check. 

The original “buggy” code checks for different versions of OpenSSL to decide how the CRL retrieval is performed. In both branches, the function get1_crls (or its equivalent) is called with the wrong parameter — subject instead of issuer. By switching to the issuer, the logic aligns with the secure practices of CRL verification. When a CRL is issued, its revocation details are linked to the issuer (CA) information, and thus retrieving CRLs based on the issuer ensures that all relevant revoked certificates are checked properly during TLS handshake procedures.

Additionally, the repair takes into account the differences in the API provided by different OpenSSL versions. For OpenSSL version 1.1 and higher, the code calls storeCtx.get1_crls with the correct issuer input. Similarly, for OpenSSL version 1.0, it calls Commons.get1_crls with the storeCtx and issuer as parameters. This ensures that regardless of the underlying OpenSSL version, the logic is consistently based on the correct field. This uniform correction across different branches of the conditional statement guarantees that CRL validation operates on a consistent and reliable principle.

This change is significant because many potential vulnerabilities in certificate handling can lead to unintended acceptance of revoked certificates, which in turn compromises secure communication channels. By ensuring that the validation logic checks the revoked certificate list against the issuer, we avoid any potential bypass of revocation checks. In effect, this guarantees that if a certificate has been revoked by its issuing CA, the system will correctly prevent the connection, thus maintaining the integrity of the TLS protocol.

Moreover, this repair directly addresses the vulnerability stated in the vulnerability description. Instead of checking the same field twice (subject), we have replaced the second call to retrieve CRLs by using the issuer, ensuring the code now correctly reflects the intent: one lookup for the certificate subject and one for the issuer’s CRL. The consistency of this approach is critical in security-sensitive operations like certificate revocation verification, as even minor errors can lead to significant exploitation risks.

Overall, the repair fixes the logic mismatch that previously undermined the HTTP/TLS revocation checking process, restoring secure, expected behavior in the TLS handshake.
