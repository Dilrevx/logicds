The original bug arose because the retrieval of Certificate Revocation Lists (CRLs) was incorrectly performed using the certificate’s subject for both comparisons. Typically, a CRL is issued by an entity (the issuer) that signs and maintains the list of revoked certificates. Thus, the proper way to retrieve or check the CRL is by using the issuer information rather than the certificate subject. Failing to use the issuer for the appropriate role could allow revoked certificates to be mistakenly validated, as the legitimate CRL “issuer” would be misidentified.

In the repaired code, you’ll notice that the variable previously used for both branches (subject) is now replaced with issuer in the function calls:
 • For OpenSSL 1.1 and above (assuming LibreSSL is not present), the function call becomes storeCtx.get1_crls(issuer). 
 • Similarly, for OpenSSL 1.0 and above, the call is modified to Commons.get1_crls(storeCtx, issuer).

This change ensures that the right field—the issuer—is being used to obtain the relevant CRLs. In practical terms, this means that when the software checks for revocation, it is now properly identifying the CRL associated with the CA or authority that issued the certificate. Since the CRL is signed by the issuer, this correction ensures that the revocation list actually corresponds to the certificate’s issuing authority, thereby preventing any revoked certificate from slipping through due to a mismatch in verification.

By making sure the lookup is performed using the issuer, the repair reinforces the security protocol. The system can now accurately determine if a certificate, even if presented, has been correctly invalidated by its issuer. This gives an improved matching between a certificate and its revocation information, closing the loophole that could allow revoked certificates to be treated as valid.

In summary, replacing “subject” with “issuer” during the CRL retrieval directly fixes the vulnerability by ensuring that the software is comparing and validating certificates against the CRL issued by the correct issuing authority. This correct interpretation and matching prevent revoked certificates from being accidentally accepted, thereby upholding the integrity of the TLS connection process.
