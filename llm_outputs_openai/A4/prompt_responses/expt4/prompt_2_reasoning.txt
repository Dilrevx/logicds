The repair involves changing the parameter that’s being fetched from the parameter list. Originally, the line of code was:

  p = OSSL_PARAM_locate_const(params, OSSL_CIPHER_PARAM_AEAD_TLS1_AAD);

This code was locating the "Additional Authenticated Data" (AAD) parameter. However, due to a mistake in the implementation of this RC4-MD5 ciphersuite, the AAD data was inadvertently being used as the MAC (Message Authentication Code) key. Since the AAD is typically derived from predictable protocol elements, using it as a MAC key makes the key trivially predictable. An attacker could then perform a man-in-the-middle attack by intercepting and modifying data while still passing the MAC check, thus compromising the integrity of the communications.

The repair changes the lookup parameter from OSSL_CIPHER_PARAM_AEAD_TLS1_AAD to OSSL_CIPHER_PARAM_AEAD_TLS1_MAC_KEY as shown below:

  p = OSSL_PARAM_locate_const(params, OSSL_CIPHER_PARAM_AEAD_TLS1_MAC_KEY);

By making this change, the function now correctly looks up and retrieves the actual MAC key rather than the AAD. The MAC key is intended to be a securely generated and secret value, not something that can be easily derived or predicted from publicly available protocol information.

Here’s how this repair fixes the vulnerability:

1. Correct Data Retrieval: The new code targets the correct parameter, ensuring that any computation related to MAC generation uses the secure MAC key instead of the predictable AAD. This means the MAC value will be generated using proper cryptographic material that an attacker cannot anticipate.

2. Enhanced Security: MACs are used to verify the integrity and authenticity of data. By deriving the MAC from the right cryptographic key, we ensure that any change in the transmitted data would require an attacker to also forge the MAC, which is computationally infeasible without knowing the secret key. The change prevents the attacker from being able to modify the data and still pass the MAC check.

3. Prevention of Man-In-The-Middle Attacks: Since the vulnerability arose from the use of predictable AAD as a MAC key, an attacker could previously calculate what the MAC should be. Now, with the use of a robust and unpredictable MAC key, an attacker no longer has the means to predict or manipulate the MAC, thus mitigating the risk of man-in-the-middle attacks.

4. Code Stability and Maintainability: This straightforward change reinforces the security of the overall cryptographic implementation. It highlights the importance of correctly binding cryptographic keys to their intended purposes, reducing potential oversights that could lead to vulnerabilities in the future.

In summary, this repair reinforces the fundamental security principle of using secure, unpredictable key material for cryptographic operations. By switching to the correct parameter for obtaining the MAC key, the fix eradicates the vulnerability stemming from the use of predictable AAD data, thereby greatly reducing the risk associated with unauthorized data manipulation.
