The original vulnerability stemmed from the fact that the code was mistakenly retrieving the Additional Authenticated Data (AAD) rather than the Message Authentication Code (MAC) key. In secure communication setups like those using TLS, the MAC key is crucial because it is a secret value used to verify the integrity and authenticity of the transmitted data. The MAC key should remain unpredictable and confidential. On the other hand, the AAD is either known or can be easily guessed by an attacker, making it a poor substitute for the MAC key. By incorrectly using the AAD as the secret key in the MAC computation, the system allowed an attacker to potentially forge a valid MAC, thereby compromising the integrity check and enabling a man-in-the-middle attack.

The repair performed involved a precise change in the code using the function OSSL_PARAM_locate_const. This function is designed to search through a list of parameters for a particular cryptographic parameter. In the buggy code, the search parameter used was OSSL_CIPHER_PARAM_AEAD_TLS1_AAD, which refers to the AAD specifically. This is incorrect for MAC validation purposes, as the AAD is either predictable or outright known, and it should not be used as the secret key for MAC computations. Therefore, the fix required swapping out the constant OSSL_CIPHER_PARAM_AEAD_TLS1_AAD for the correct one representing the MAC key.

By switching the lookup parameter to OSSL_CIPHER_PARAM_AEAD_MAC_KEY, the code now retrieves the actual MAC key stored securely. This MAC key is intended to be a secret component, unique to the specific encryption key or session, and not known to external parties. When this MAC key is then used in subsequent cryptographic processes, its secret nature ensures that any attempt by an attacker to forge or alter data would fail the integrity check, because the attacker would be unable to generate the correct MAC without having access to the genuine secret key.

Understanding why this correction is critically secure requires delving into how MACs work. A message authentication code is a short piece of information used to authenticate a message and to provide integrity and authenticity assurances on the message. It is computed based on both the message content and a secret key—that is, the MAC key. If the key is predictable (like the AAD), an attacker could compute the MAC without possessing the secret information, undermining the cryptographic integrity of the communications. This is why the MAC key must be kept secret and generated from secure and unpredictable sources.

Moreover, the implications of using the wrong key are severe. Attackers might exploit the predictable nature of the AAD to modify data in transit, knowing that the MAC validation process would incorrectly accept the manipulated content. By retrieving and using the appropriate MAC key, the data integrity check is re-established correctly; any modifications to the message would result in a mismatch between the computed MAC and the expected MAC, triggering a failure in validation.

In summary, the repair changes the parameter lookup from one that would inadvertently select a non-secret, predictable value (AAD) to one that selects the correct secret key (MAC key). This repair is a critical update to ensure that the system's cryptographic operations rely on secure, confidential data, thus preventing man-in-the-middle attacks by maintaining the robustness of the MAC integrity check.
