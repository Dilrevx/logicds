The repair of the code snippet was necessary to address a critical cryptographic vulnerability in OpenSSL 3.0’s implementation of the RC4-MD5 ciphersuite. The vulnerability arose because the code erroneously retrieves the additional authenticated data (AAD) parameter instead of the intended message authentication code (MAC) key when performing integrity checks. The AAD, being either known or easily predicted, does not provide the level of secrecy required for secure MAC computations. This error results in the MAC key being trivially predictable, thereby weakening the cryptographic defenses and enabling an attacker to forge valid MACs. Such a situation can permit a man-in-the-middle attack, wherein the attacker intercepts and modifies transmitted data without detection. Consequently, it is imperative to correct the parameter used for the MAC key lookup to ensure that secure, unpredictable keys are utilized throughout the encryption process.

Upon examination of the original code, it was apparent that the function call OSSL_PARAM_locate_const was invoked with the constant OSSL_CIPHER_PARAM_AEAD_TLS1_AAD. This constant clearly identifies the AAD parameter, which is intended for use in the TLS 1.x encryption process. However, in the context of MAC verification, the secret MAC key should be used rather than the publicly known AAD. The decision to use AAD as a MAC key is inherently flawed, as its predictability significantly undermines the encryption scheme’s integrity and provides an exploitable avenue for attackers.

To remediate this vulnerability, the repair involved altering the constant passed to the OSSL_PARAM_locate_const function. Instead of using OSSL_CIPHER_PARAM_AEAD_TLS1_AAD, the revised code now employs the constant OSSL_CIPHER_PARAM_AEAD_MAC_KEY. This modification ensures that the retrieval process correctly locates the memory holding the secret MAC key, rather than a publicly accessible or predictable value. The use of the correct cryptographic parameter is crucial because the MAC key is a secret value used to generate or verify the MAC, thus maintaining the integrity and authenticity of the transmitted data.

This repair not only rectifies the immediate issue but also reinforces the overall cryptographic robustness of the system. By ensuring that the MAC key is used in place of the AAD, the change effectively closes the door on potential man-in-the-middle attacks that could exploit the previous implementation flaw.
