The fix changes the parameter lookup from using OSSL_CIPHER_PARAM_AEAD_TLS1_AAD—which retrieves the Additional Authenticated Data (AAD)—to using OSSL_CIPHER_PARAM_AEAD_MAC_KEY. In the buggy code, the AAD (which is typically sent in plaintext and is predictable) was mistakenly being used as the MAC key. Since AAD is not secret and is predictable by an attacker, using it as a MAC key compromises the integrity—it makes it easy for an attacker to manipulate the data and have the modified data pass the MAC check.

By replacing the constant with OSSL_CIPHER_PARAM_AEAD_MAC_KEY, the code now correctly retrieves the actual MAC key, which is expected to be generated securely and kept secret. This change ensures that the MAC operation relies on a non-predictable key, thereby preserving the intended security level against man-in-the-middle attacks.

In summary, the repair fixes the vulnerability by ensuring that:

1. The correct parameter (the MAC key) is obtained and used for the integrity check.
2. The key used for MAC computations is not trivial or predictable (as would be the case if the AAD were used).
3. The integrity check remains robust against attackers attempting to modify data, because the MAC verification now depends on a secret, unpredictable key.

This targeted change directly addresses the reported vulnerability, enhancing the security of the RC4-MD5 ciphersuite in the context of OpenSSL 3.0.
