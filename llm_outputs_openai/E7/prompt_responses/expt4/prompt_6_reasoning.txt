The repair primarily changes the handling of NAS messages when they are received in plaintext (i.e. with the LIBLTE_MME_SECURITY_HDR_TYPE_PLAIN_NAS header). In the original code, certain message types—specifically, EMM Information, EMM Status, and Detach Request—were allowed to bypass the integrity check. This is a security risk because these messages should only be accepted if they come with proper integrity protection.

Here’s how the repair works:

1. In the section that checks for plaintext messages (when sec_hdr_type equals LIBLTE_MME_SECURITY_HDR_TYPE_PLAIN_NAS), the code uses a switch statement to determine which message types are allowed. Initially, the developer listed several cases, including the ones that are vulnerable: EMM Information, EMM Status, and Detach Request. In the patched code, these specific cases have been commented out. This means that if a plaintext message of these types is received, it will not match any of the allowed cases.

2. When a plaintext message for one of these vulnerable types (EMM Information, EMM Status, or Detach Request) is encountered, the switch’s default branch is executed. This branch logs an error stating that the message with that particular type and security header type isn’t handled, and then the function returns early. As a result, even if an attacker sends one of these messages in plaintext, the system will not process it.

3. This safeguard ensures that any critical message that requires an integrity check is not inadvertently processed in an insecure manner. By removing the ability to accept these messages under plaintext conditions, the repair enforces that they must come with appropriate security context (i.e., integrity and possibly ciphering) before processing.

4. It’s important to note that the second switch statement (which later directs the processing of messages based on msg_type) still includes cases for EMM Information, EMM Status, and Detach Request. This is acceptable because if these messages are received with the appropriate security header type (not plaintext), they will bypass the earlier plaintext check and be handled securely by their respective functions. The repair effectively restricts plaintext messages to only those which are considered safe (e.g., Identity Request) and known not to introduce the same type of risk.

Overall, the repair fixes the vulnerability by ensuring that only messages that are deemed safe to be received in plaintext are allowed to be processed when no integrity checks are in place. This change prevents potential attackers from sending critical control messages in plaintext to manipulate or disrupt the system, thereby enforcing the intended security policies based on integrity protection.
