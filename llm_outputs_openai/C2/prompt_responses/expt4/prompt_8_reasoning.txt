The repair introduces additional checks to ensure that if any earlier validation fails (indicated by ret not being greater than 0), the subsequent strict verifications do not override the error already set. Here’s what changed:

1. Before verifying the explicit elliptic curve parameters, the patch now checks if the prior certificate validations were successful (i.e. ret > 0). In the original code, the curve check was run unconditionally if the strict flag was set and there was more than one certificate in the chain. This revision prevents the curve check from executing if an error was already detected in an earlier CA verification step.

2. The modified logic stores the return value (ret) from the CA check (or non-CA, depending on must_be_ca). Only if ret is positive (meaning no error has been flagged so far) does the code proceed to call check_curve(x). If check_curve(x) returns a negative or zero value, the error code is immediately set (either a specific error for explicit EC parameters or a generic unspecified error) and ret is set to 0. This ensures that once an error is detected at this stage, it will not be masked by later validations.

3. This repair also adds a similar guard before checking extensions related to whether the certificate is a CA. Specifically, it avoids performing the check that sets X509_V_ERR_INVALID_EXTENSION for certificates that are not CA certificates if an error has already been flagged. This way, the chain verification process respects the first encountered error rather than allowing later operations to override it.

In essence, the vulnerability arose because the check for explicitly encoded elliptic curve parameters (an additional strict check) could override previous important checks about the validity of CA certificates. By introducing the guard (if ret > 0) before these subsequent checks, the repair ensures that when an earlier step sets an error (for example, determining that a certificate is not a valid CA when it should be), that error is preserved. This sequential failure propagation prevents certificates with improper parameters or CA configuration from being wrongly validated later because of a successful curve check.

By preserving the error state and halting further validation processing when an error is detected, the secure certificate chain validation logic is restored. Therefore, if any certificate in the chain has an error—be it due to an explicit curve parameter issue or an invalid CA marker—the error is not inadvertently cleared by executing later checks. This approach eliminates the risk of bypassing critical checks against non-CA certificates issuing certificates when the strict flag is enabled, thereby mitigating the vulnerability as described.
