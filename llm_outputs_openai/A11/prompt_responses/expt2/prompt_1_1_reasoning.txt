The original code used the certificate’s revocation_date to decide if a certificate found in the CRL (Certificate Revocation List) should be considered revoked. In this setup, the code checks if the current time is past the revocation_date (using mbedtls_x509_time_is_past), and only then returns a revocation indication (returning 1). The vulnerability here stems from the fact that relying on the local clock allows an attacker to manipulate the system time to see if it is “earlier” than the revocation_date—even if the certificate is meant to be revoked. By changing the system clock, an attacker might trick the software into believing that the certificate is still valid even when it has actually been revoked.

The repair provided addresses this issue by eliminating the local clock check entirely. If the certificate serial number in the supplied certificate (crt) matches one found in the CRL (cur), then the certificate should be considered revoked immediately, regardless of what the system clock might say. This is important because the revocation information provided by the CRL should be absolute – its presence means “this certificate has been revoked” without the need for any additional temporal validation via the client’s clock. Thus, the code now directly returns 1 when there is a match on the certificate serial number, ensuring that any certificate explicitly listed in the CRL is unconditionally marked as revoked.

By removing the call to mbedtls_x509_time_is_past(), the repair stops using the local clock as a factor in certifying revocation. This is crucial from a security standpoint because the local clock is an insecure source of truth in adversarial environments; attackers could manipulate the system time to bypass this check. In environments where maintaining secure and correct certificate validation is critical—such as in network communications—the certificate revocation process must be independent of any mutable, user-controlled parameters. The presence of a CRL entry should be enough; the revocation date is informational rather than a conditional check.

Furthermore, from a design perspective, the purpose of CRL checks is to ensure that any certificate that was once valid but later compromised or revoked is not trusted, regardless of the current date. The original intent of having a revocation_date might have been to handle edge cases in which a certificate was scheduled to be revoked at some future time. However, when the certificate is already present in the CRL, it indicates that revocation is already in effect and should be immediately enforced.

With this repair, the software no longer depends on the system’s current time, mitigates a potential attack vector, and ensures that once a certificate is deemed revoked by being listed in the CRL, this status is honored without any time-based conditions. This makes the certificate revocation logic both simpler and more robust against tampering, upholding the security intended by revocation mechanisms.
