Below is one possible fix. In the original code, the presence of a matching serial number in the CRL entry is combined with checking that the revocation date is in the past (using the local clock). Because an attacker can tamper with the local system time, relying on that check lets an attacker “hide” a revoked certificate simply by setting the clock to a different time. In practice, if a certificate’s serial number appears in the CRL, it should be considered revoked immediately rather than “waiting” for the revocation date to elapse.

For example, the repaired code removes the reliance on the revocation date check and immediately returns an error when a matching CRL entry is found:

------------------------------------------------------------
        if( crt->serial.len == cur->serial.len &&
            memcmp( crt->serial.p, cur->serial.p, crt->serial.len ) == 0 )
        {
            /* Since a matching serial number is found in the CRL,
               consider this certificate revoked regardless of the local clock.
               It is not necessary (and is insecure) to check cur->revocation_date. */
            return( 1 );
        }
------------------------------------------------------------

In this fix the certificate is marked revoked immediately when its serial number is found in the CRL. Any checks regarding the CRL’s own validity period (such as comparing the current time to the CRL’s nextUpdate field) should be done elsewhere in the certificate validation process using a trusted time source.
