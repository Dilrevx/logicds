In the original snippet the revocation decision depended on the outcome of mbedtls_x509_time_is_past( &cur->revocation_date ), which compares the current (local) time to the stored “revocation date.” This lets an attacker tamper with the decision by changing the system clock. One fix is to remove that dependency entirely so that if a certificate’s serial number is found on the CRL it is revoked regardless of the (possibly manipulated) local time.

For example, the fixed code becomes:

  if( crt->serial.len == cur->serial.len &&
    memcmp( crt->serial.p, cur->serial.p, crt->serial.len ) == 0 )
  {
    /* If the certificate serial is found in the CRL, always treat it as revoked */
    return( 1 );
  }

In this revised code the revocation status is determined solely by the presence of the certificate’s serial number in the CRL. This removes the reliance on the local clock and prevents an attacker from bypassing revocation by manipulating system time.

Alternatively, if it is important to support scheduled revocations (where a certificate should only be considered revoked after a certain date), then a secure solution must obtain a trusted current time (from, for example, a secure time server) rather than relying on the local system clock. However, in many deployments simply treating any certificate on the CRL as revoked is sufficient for ensuring security.
