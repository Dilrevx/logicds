This repair adjusts when compression is enabled during authentication. In the original code, the flag that allows compression (authdone) is immediately set when a user authentication succeeds. When delayed-zlib mode is active, compressing the data too early can open the door for exploits (like CRIME attacks) that take advantage of the early activation of compression.

The repair introduces a conditional check that determines whether the system is in delayed-zlib mode before setting the compression flag. If the system is not in delayed-zlib mode, it safely sets the flag to enable compression immediately. However, if the system is using delayed-zlib mode, the flag is not set immediately. This postpones the activation of compression until a later, more secure point in the session management process.

By ensuring that compression only begins under secure conditions (or only when not in delayed mode), this repair minimizes the risk of an attacker exploiting the compression mechanism during a sensitive window immediately following authentication. The overall flow of authentication state and logging remains unchanged, but with the added security check guarding the moment when compression is enabled.

This targeted change repairs the vulnerability by guaranteeing that compression is never turned on prematurely in contexts where the system would be exposed to compression-related attacks.
