We can fix the vulnerability by not unconditionally marking the session as “authenticated” when a USERAUTH_SUCCESS message is received. Instead, we must verify that the success message is only accepted when no additional authentication methods are still expected. In other words, the client should check that the server-provided list of remaining acceptable authentication methods is empty (or that it matches the method we actually requested) before transitioning into an “authenticated” state. One repair is to only set ses.authstate.authdone after validating that the authentication “layer” has really been completed per RFC4252 rather than just following the server’s message. For example, suppose the client stores the set of methods still required in a variable (often built by processing the USERAUTH_FAILURE message) called avail_auth_methods. Then the patch would look something like this:

-----------------------------------------------------------
/* Log receipt of the success message */
TRACE(("received msg_userauth_success"));

/* Before marking authentication complete, check that there are no extra required auth methods.
 * According to RFC4252, the server should not be allowed to claim success when additional
 * authentication factors (e.g. FIDO2 token or SSH-Askpass) are required. */
if (avail_auth_methods != NULL && strlen(avail_auth_methods) > 0) {
    logit("Warning: server sent USERAUTH_SUCCESS but still advertises additional auth methods (%s).",
          avail_auth_methods);
    /*
     * Optionally, you can choose to treat this as a failure:
     */
    auth_clear_state();  /* Clean up sensitive state */
    fatal("Authentication aborted because server did not complete all required steps");
}

/* If no extra authentication methods remain, it is safe to mark the session as authenticated */
ses.authstate.authdone = 1;
cli_ses.state = USERAUTH_SUCCESS_RCVD;

/* Instead of clearing the authtype, record the current auth method that finished authentication.
 * This can help auditing further if needed.
 */
cli_ses.lastauthtype = current_auth_method;
-----------------------------------------------------------

Step by step, what is happening:
1. After receiving USERAUTH_SUCCESS, we first check that the server has not advertised any remaining acceptable authentication types in the variable avail_auth_methods. (In a proper implementation, this variable is built by processing the USERAUTH_FAILURE reply that normally contains a comma‑separated list of auth methods.)
2. If extra authentication methods remain (i.e. additional second factor is expected), we log a warning and abort authentication. This prevents the server from “downgrading” the process by sending a USERAUTH_SUCCESS too early.
3. Only if no extra methods remain do we mark the authentication as completed.

This change makes sure that the login process follows the RFC’s rules by ensuring that additional security measures (like FIDO2 tokens or SSH-Askpass) are not bypassed by a misbehaving server.

By adding this check, we prevent the vulnerability where a server could abuse the forwarded agent to log onto another server unnoticed.
