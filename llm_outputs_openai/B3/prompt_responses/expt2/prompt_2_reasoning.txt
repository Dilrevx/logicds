The repair adds a conditional check right after receiving the authentication success message. Here's the step-by-step breakdown of the changes:

1. When the SSH client receives the success message (msg_userauth_success), the code now immediately evaluates if trivial authentication is being used. It does so by checking two conditions:
   - Whether the client has explicitly disabled trivial (or less secure) authentication through its configuration (indicated by options.disable_trivial_auth).
   - Whether the authentication method used (tracked by cli_ses.lastauthtype) is identified as trivial using a helper function, is_trivial_auth().

2. If both conditions are true, this means that the session relied on a trivial method while the configuration forbids such methods. In that case, the code logs an error message to indicate that trivial authentication is not allowed and aborts the session by calling session_cleanup(ses) followed by an immediate return. This early exit prevents marking the authentication as complete.

3. If the check passes (i.e., either trivial authentication is not disabled, or the authentication method used is considered secure), the code proceeds as before:
   - It marks the authentication process as complete by setting ses.authstate.authdone to 1.
   - It updates the client session state to USERAUTH_SUCCESS_RCVD.
   - It resets the last authentication type (cli_ses.lastauthtype) to AUTH_TYPE_NONE, readying the session for further operations.

By introducing this check, the repair prevents a potential attack where an SSH server could modify the login process to use a trivial authentication method. Without this validation, an attacker might abuse features like agent forwarding to bypass stronger authentication mechanisms (e.g., FIDO2 tokens or SSH-Askpass) by using non-compliant login processes.

In summary, the repair enforces the client's security policy regarding authentication strength. It ensures that even if the server behaves in a non-RFC-compliant manner, the session will not complete if only a trivial (and disallowed) authentication method is used. This maintains the integrity of the greater authentication workflow and prevents unauthorized access using less secure or manipulated methods.
