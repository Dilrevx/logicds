The original code only checked whether an ACL list or ACL patterns were provided. In the absence of both, it returned MOSQ_ERR_PLUGIN_DEFER, which effectively handed off access control to a default permissive mechanism. This creates a vulnerability when an ACL file is used but is empty (or contains only comments/whitespace), because an empty ACL file is intended to deny all access—not to trigger the fallback permissive policy.

The repair adds another check to see if an ACL file has been specified. Specifically, the condition now tests whether acl_list, acl_patterns, and acl_file are all missing. If all three are absent, then the code returns MOSQ_ERR_PLUGIN_DEFER. However, if an ACL file is provided—even if it’s empty—the condition will evaluate to false, and the code will continue with the ACL evaluation. This ensures the system recognizes that the administrator explicitly configured an ACL file, and it treats an empty ACL file as an intentional configuration that should result in no access being allowed.

To summarize, here’s how the repaired code works:
1. It first checks if none of the ACL mechanisms (list, patterns, or file) are set.
2. If none are provided, it defers to the plugin (which could lead to default permissive handling).
3. If an ACL file is provided—even if it’s empty—the new condition ensures the code bypasses deferral, and the ACL file is processed. This maintains the secure behavior (i.e., deny all access if no valid ACLs are present).

This modification directly addresses the vulnerability by ensuring that a deliberate configuration (having an ACL file, albeit empty) is not misinterpreted as “no ACL configuration,” thus preventing the potential security breach where unauthorized access might be granted under the default allow policy.
