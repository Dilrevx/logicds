The repair changes the behavior when an ACL file has been configured but is effectively empty (i.e. it contains no usable ACL entries because it is either completely empty, only has comments, or blank lines). In the original code, if both acl_list and acl_patterns are not present (indicating an empty ACL file), the function returns MOSQ_ERR_PLUGIN_DEFER. This return value instructs the broker to “defer” the decision on an authorization request, thereby falling back to a default allow policy. This behavior poses a vulnerability because an administrator may expect that if an ACL file is provided—even an empty one—the administrator is explicitly denying any access until proper rules are inserted. The vulnerability lies in the fact that an empty ACL file does not result in a “deny by default” situation but rather in an implicit allow all, which might lead to unauthorized client access if misconfigured.

In the repair, we deliberately replace the error code MOSQ_ERR_PLUGIN_DEFER with MOSQ_ERR_ACL_DENIED when both acl_list and acl_patterns are null. The new error code signifies that the access control should explicitly deny all access. This is based on the rationale that if there is an ACL file in use, it represents an intent by the administrator to manage access explicitly. Therefore, when that file does not contain any valid ACL entries, it does not make sense for the broker to assume a permissive default. Instead, it should enforce a secure default – denying access until the administrator provides sufficient ACL entries to permit connections.

The reasoning behind this repair is founded on the principle of least privilege. Secure default configurations should ensure that unless specifically allowed, no action is authorized. By switching the return value to MOSQ_ERR_ACL_DENIED, the broker honors the security expectation conveyed by the use of an ACL file. In a typical enterprise or sensitive environment, administrators rely on ACL files for setting explicit policies rather than relying on default behaviors. Hence, an empty policy file is seen as an error state rather than a state of permissiveness. This repair prevents any accidental lapse in security policy due to what might seem like a benign omission—an empty or trivial ACL file—thus closing a loophole that could lead to unintended access permissions.

In addition, this change forces better operational practices. Administrators become immediately aware (by noticing a consistent ACL denied error) that the ACL file is not correctly populated, prompting them to review and update the file with the intended permissions. If the broker were to allow access by default, such misconfigurations might go unnoticed, exposing the system to security risks over an extended period.

Overall, the modification reinforces the contract between the administrator and the broker. An ACL configuration is a deliberate security measure, and an empty or misconfigured ACL file should not be silently tolerated by allowing access. Instead, by returning a specific denial error (MOSQ_ERR_ACL_DENIED), the broker enforces a secure posture and encourages immediate corrective actions by the administrator, thereby improving the overall security and reliability of the system.
