We can fix the vulnerability by ensuring that the existence of an ACL file is taken into account. In the original code the program only checked whether the ACL list and ACL patterns were set. This oversight means that if an ACL file is specified (even if it’s empty or only contains comments) then it is ignored and results in the default permissive behavior. The idea of the patch is to add an extra check for the explicit presence of an ACL file.

Step by step:

1. In the original code the condition is:
  if(!security_opts->acl_list && !security_opts->acl_patterns){
   return MOSQ_ERR_PLUGIN_DEFER;
  }

2. The problem occurs when the ACL file is provided but does not contain any effective rules. In the old logic, an administrator providing an ACL file (but leaving it empty) is treated the same as not providing one at all—leading to an inadvertent permissive, default allow behavior.

3. To fix this, we add a check for the ACL file’s existence (e.g., security_opts->acl_file). If an ACL file is provided—even if its content is empty or only comments—the condition should not trigger the MOSQ_ERR_PLUGIN_DEFER return. In other words, we only want to return MOSQ_ERR_PLUGIN_DEFER if none of the ACL mechanisms (list, patterns, or file) are set.

4. The patched code will therefore combine all these conditions in the if-statement. Only if all three are absent should we fall back to the permissive behavior.

The final patched code is:

------------------------------------------------
  if (!security_opts->acl_list && !security_opts->acl_patterns && !security_opts->acl_file) {
   return MOSQ_ERR_PLUGIN_DEFER;
  }
------------------------------------------------

With this patch, if an ACL file is set—even if it is empty or effectively contains no active rules—the system will treat the ACL configuration as present (and thus deny access by default rather than deferring and letting access pass). This behaviour better reflects the administrator’s intent and secures the access control configuration.
