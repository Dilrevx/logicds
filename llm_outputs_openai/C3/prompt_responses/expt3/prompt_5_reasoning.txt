The vulnerability arose because the original code only checked whether an ACL list or ACL patterns were provided. This meant that if an administrator specified an ACL file—even if it was empty or contained only comments—the system would ignore it and default to a permissive behavior by returning MOSQ_ERR_PLUGIN_DEFER. In practical terms, this could unintentionally allow access when the expectation was to enforce some level of access control.

The repair adds an extra condition to the existing if-statement to also look for the ACL file. By checking for the existence of an ACL file along with the ACL list and ACL patterns, the logic now recognizes that any ACL configuration provided by the administrator should be taken as intentional. Even if the provided ACL file does not contain active rules, its mere presence indicates that the ACL mechanism has been activated.

When all three—ACL list, ACL patterns, and ACL file—are absent, the system concludes that no explicit ACL configuration is provided and it returns MOSQ_ERR_PLUGIN_DEFER. However, if any one of these elements is present, the condition fails, and the system does not revert to the default permissiveness. This ensures that an ACL file is honored if provided, avoiding the risk of inadvertently allowing access.

In summary, the repair fixes the vulnerability by incorporating a three-part check instead of a two-part check. It now ensures that the code properly respects the administrator’s intent by treating the presence of any ACL configuration, including an ACL file, as a signal to enforce access control rather than to permit default behavior.
