The key change is the addition of a check for the existence of an ACL file (security_opts->acl_file). Previously, the code only looked at acl_list and acl_patterns. This meant that when an administrator provided an ACL file—even if it was empty or contained only comments—the code incorrectly treated it as if no ACL configuration existed, defaulting to a permissive access policy.

The patched condition now checks whether all three components are missing: the ACL file, the ACL list, and the ACL patterns. If all are absent, the function returns MOSQ_ERR_PLUGIN_DEFER, indicating that no ACL configuration is available. However, if an ACL file is present (even if empty), the program will not defer, which in turn enforces the intended secure behavior: an empty ACL file should lead to access being denied rather than full access being granted.

In this way, the repair prevents a situation where an administrator’s deliberate configuration—by providing an ACL file—is misinterpreted as an absence of configuration. The system no longer defaults to an overly permissive state when the ACL file lacks effective rules. Instead, it treats the explicit configuration as a signal to apply ACL-based access control, which in the case of an empty file correctly results in denying all actions.

Thus, the patch reinforces the security policy by strictly differentiating a deliberate ACL configuration (even one with no effective rules) from a scenario where no ACL configuration is provided at all.
