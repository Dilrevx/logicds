The repair introduces a check for an invalidity date (cur.invalidityDate) and uses it preferentially over the revocation date. Originally, the code only inspected the revocation date field (cur.revocationDate). Since an attacker could manipulate the system local clock, this could lead to incorrect decisions about whether a certificate should be trusted.

Here's the step-by-step explanation:

1. We begin by checking that the certificate numbers match using the serial numbers. This part remains unchanged; it confirms that the entry provided in the CRL corresponds to the certificate being verified.

2. The repair then checks if cur.invalidityDate is available (i.e. it is not null). According to the specification, the invalidity date indicates when the certificate became untrusted (for example, when it was compromised) and may predate the revocation process date. This date is a more reliable indicator for determining the true moment of certificate compromise.

3. If the invalidity date is present (cur.invalidityDate != null), we then verify whether that date is in the past using the Helper.mbedtls_x509_time_is_past() function. If the invalidity date is indeed in the past, it implies that the certificate should be considered revoked, and the function returns 1 (indicating a revocation).

4. If the invalidity date is not available, the code falls back to the original behavior and checks if the revocation date is in the past. This ensures that, even if the invalidity date isn’t provided, the revocation status is still validated using the revocation date.

By applying this change, the code uses the more accurate invalidity date information when it is available, thus avoiding potential errors from local clock manipulation. If an attacker changes the clock, the invalidity date remains a solid reference point because it captures the actual time of compromise, rather than the time the CA processed the revocation. If only the revocation date is available, then the system continues to use that information, maintaining compatibility.

In summary, the repair addresses the vulnerability by allowing the CRL check to rely on the certificate’s invalidity date when it exists, reducing the risk of erroneously trusting a certificate based solely on the revocation date influenced by a manipulated clock.
