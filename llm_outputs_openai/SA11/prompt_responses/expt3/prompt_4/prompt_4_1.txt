Below is one safe way to fix the bug. The vulnerability arises because the code only rejects a certificate when the local system time is later than the stored revocationDate. An attacker who can change the clock (for example, setting it backward) might trick the check into “accepting” a revoked certificate. In practice, a CRL already implies that if a matching serial number is found then the certificate is revoked—there’s no need to further check a date that may be manipulated. To repair the vulnerability, remove the dependency on the revocationDate and simply report the certificate as revoked when the serial numbers match.

For example, change the buggy code:

  if (crt.serial.len == cur.serial.len
     && MemUtil.memcmp(crt.serial.p, cur.serial.p, crt.serial.len) == 0) {
     if (Helper.mbedtls_x509_time_is_past(cur.revocationDate))
       return 1;
   }

to the following safe version:

  if (crt.serial.len == cur.serial.len
     && MemUtil.memcmp(crt.serial.p, cur.serial.p, crt.serial.len) == 0) {
    // The certificate is revoked if its serial matches an entry in the CRL.
    return 1;
  }

This fix ensures that if the certificate’s serial number appears in the CRL, it is immediately rejected—regardless of the local clock or the revocationDate field.
