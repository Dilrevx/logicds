The repair replaces the original constant CHACHA_CTR_SIZE with CHACHA20_POLY1305_MAX_IVLEN in the nonce length validation check. This change is crucial for addressing the vulnerability related to nonce reuse in ChaCha20-Poly1305.

In the original code, the condition checks if the provided nonce length (represented by arg) is less than or equal to 0 or greater than CHACHA_CTR_SIZE. However, CHACHA_CTR_SIZE does not accurately represent the upper limit for nonce sizes required for ChaCha20-Poly1305. According to RFC 7539, the nonce for ChaCha20-Poly1305 must be exactly 12 bytes (96 bits). OpenSSL allows nonces with a length different from 12 bytes and then only uses the last 12 bytes while the earlier bytes are ignored. This behavior can lead to unsafe scenarios: if an application mistakenly modifies only the leading (ignored) bytes assuming it creates a unique nonce, it might end up reusing nonces inadvertently.

By changing CHACHA_CTR_SIZE to CHACHA20_POLY1305_MAX_IVLEN, the code now validates the nonce length against the constant that explicitly defines the maximum nonce length (or IV length) appropriate for ChaCha20-Poly1305 operations. This update ensures any nonce used in the encryption process must fall within a secure and well-defined boundary. In essence:
 
• The check now correctly disallows nonce lengths that would be considered unsafe because they might contain superfluous leading bytes, which could lead to reuse.

• It enforces that the provided nonce length must not exceed the maximum allowed length for ChaCha20-Poly1305 encryption. This change helps prevent subtle bugs where nonces with incorrect lengths might be mistakenly accepted, thereby reducing the potential for nonce reuse.

Overall, by updating the validation check to reference CHACHA20_POLY1305_MAX_IVLEN, the code now aligns with the intended use of the ChaCha20-Poly1305 cipher and its nonce constraints as specified in RFC 7539. This straightforward modification mitigates the risk of compromising both the confidentiality and integrity of the encrypted data due to nonce reuse, thereby enhancing the security of the encryption process.
