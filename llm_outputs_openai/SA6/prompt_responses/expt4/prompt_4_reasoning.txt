The repair modifies the validation check for nonce length used in the ChaCha20-Poly1305 encryption. Originally, the code validated the nonce length using CHACHA_CTR_SIZE, which might have been appropriate under a different context or cipher mode. However, ChaCha20-Poly1305 specifically requires a 96-bit (12-byte) nonce and is sensitive to any adjustments in the nonce length due to how OpenSSL handles nonce padding and truncation.

Here's what happened in the repair:

1. Changing the constant: The original check was:
  if (arg <= 0 || arg > CHACHA_CTR_SIZE)
This was replaced with:
  if (arg <= 0 || arg > CHACHA20_POLY1305_MAX_IVLEN)
By using CHACHA20_POLY1305_MAX_IVLEN, the validation now reflects the actual upper boundary for a nonce in ChaCha20-Poly1305. This ensures that the nonce provided does not exceed the defined limit that is safely processed by the cipher.

2. Preventing nonce reuse risks: The vulnerability is related to how nonces above the recommended size allow for modification in leading bytes — which are ignored by the encryption logic — to falsely appear as unique. This could result in reusing the same actual 12-byte effective nonce. By enforcing that the nonce length cannot exceed CHACHA20_POLY1305_MAX_IVLEN, the repair stops nonces that are too long from being accepted. This means there is no room for an application to “tweak” extra bytes that are not cryptographically used.

3. Enhancing security: The repair enforces the expected nonce length boundary directly aligned with the ChaCha20-Poly1305 specification (RFC 7539). This alignment prevents an attacker or inadvertent misuse from having any extra bytes that could lead to nonce collisions. Using the correct constant prevents scenarios where applications mistakenly think that changing the ignored extra bytes creates a new nonce, which is not true in practice.

In summary, the repair works by updating the constant that defines the maximum nonce length to CHACHA20_POLY1305_MAX_IVLEN. This change precisely validates the size according to the ChaCha20-Poly1305 requirements, eliminating the risk of subtle nonce reuse vulnerabilities due to extra non-significant bytes being misinterpreted as part of a unique nonce. The updated conditional check thereby mitigates potential security breaches that could arise from misuse of nonce lengths in this encryption mode.
