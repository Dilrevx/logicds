The repair ensures that the nonce length used in the ChaCha20-Poly1305 operation is exactly what the algorithm expects per its specification. ChaCha20-Poly1305 is an AEAD cipher that requires a unique nonce for every encryption operation to maintain both confidentiality and integrity. RFC 7539 specifies the nonce (or IV) length to be exactly 96 bits (12 bytes). The bug in the original code arises because it allowed a range of values for the nonce length (from a value greater than 0 up to CHACHA_CTR_SIZE) rather than enforcing the precise 12-byte requirement. OpenSSL’s behavior to “front pad” nonces shorter than 12 bytes, while ignoring any extra leading bytes in nonces larger than 12 bytes, only compounds the issue.

When nonces of lengths other than 12 bytes are permitted, it opens up the risk that the application logic might inadvertently reuse the effective nonce. For instance, if an application decides to use a 16-byte nonce and only varies its leading 4 bytes, while the last 12 bytes (i.e. the effective nonce used by the cipher) remain the same as a previous message, this leads to nonce reuse. Nonce reuse in an AEAD mode like ChaCha20-Poly1305 results in catastrophic failures in the security guarantees offered by the cipher: an attacker can potentially perform both confidentiality and integrity attacks on the encrypted data.

Hence, the repaired code now strictly checks that the provided nonce length equals CHACHA20_POLY1305_NPUBBYTES. This constant is defined to be 12 bytes, which directly adheres to the RFC specification. By enforcing this one allowed value, the repair eliminates the chance of accidental misuse where an application might pass a nonce length outside the valid set, thinking that it would result in a new unique nonce.

Furthermore, by replacing the conditional check from a range (arg <= 0 || arg > CHACHA_CTR_SIZE) to an equality verification (arg != CHACHA20_POLY1305_NPUBBYTES), the fix reinforces strict enforcement of cryptographic best practices. This measure prevents cryptographic misconfiguration that could lead to nonce reuse. In essence, even if a bug elsewhere in the system leads to a change in the expected nonce length, this part of the code will immediately flag the inconsistency, thus preventing the insecure state.

It is also important for developers to understand that AEAD schemes, like ChaCha20-Poly1305, rely on the guarantee that nonces are never reused with the same key. Even minor deviations from the proper nonce length can lead to scenarios where nonce values might be mistakenly reused, even if only the non-significant portion (due to OpenSSL’s behavior) is altered. This repair simplifies the logic and the developer’s intent, ensuring that there is no permissible value that could lead to misinterpretation or accidental reuse.

Overall, this repair addresses the vulnerability by ensuring that only a 12-byte nonce is accepted, which is in full compliance with the security requirements of the encryption algorithm and the associated cryptographic standards.
