The vulnerability arises because ChaCha20-Poly1305 requires a unique nonce (or IV) for every encryption operation, where RFC 7539 strictly mandates a 96-bit (12-byte) nonce. OpenSSL, however, permits a nonce length of up to 16 bytes. In cases where a nonce longer than 12 bytes is used, only the last 12 bytes are considered significant while any additional leading bytes are ignored. This policy introduces a risk: if an application changes only the leading bytes and mistakenly assumes that the resulting nonce is unique, it might inadvertently reuse the effective nonce value. Such nonce reuse is dangerous in AEAD (Authenticated Encryption with Associated Data) ciphers like ChaCha20-Poly1305 because it can lead to critical confidentiality and integrity attacks.

Originally, the buggy code was performing a check on the provided nonce length argument (represented as “arg”) against the constant CHACHA_CTR_SIZE. The constant CHACHA_CTR_SIZE is more suitably aligned with the requirements of the ChaCha counter mode rather than the specifics of ChaCha20-Poly1305. Consequently, this check could allow nonce lengths that are either too short or exceed the intended maximum for ChaCha20-Poly1305, which inadvertently could permit programmers to rely on the behavior of OpenSSL’s nonce padding. If a programmer mistakenly assumes that altering the padded, leading bytes would generate a new nonce, they might inadvertently be reusing the same effective 12-byte nonce, thus undermining the encryption’s security.

The repair addresses this by replacing the constant CHACHA_CTR_SIZE with CHACHA20_POLY1305_MAX_IVLEN. The new constant explicitly defines the maximum allowed IV length for the ChaCha20-Poly1305 cipher. This change is critical because it directly ties the nonce validation logic to the actual requirements of the cipher as specified by RFC 7539. When the program checks whether (arg <= 0 || arg > CHACHA20_POLY1305_MAX_IVLEN), it now guarantees that only nonce values within a safe and permissible range are accepted. This prevents the possibility of using a nonce that might seemingly be different because of alterations to the non-significant leading bytes but is in fact the same effective nonce for encryption (the vital 12 trailing bytes).

By enforcing a strict check using CHACHA20_POLY1305_MAX_IVLEN, the repaired code ensures that nonce values cannot be manipulated in a way that might lead to reuse of the effective nonce. This is in line with best practices for using AEAD ciphers where nonce uniqueness is paramount. Ensuring that the nonce adheres strictly to the defined length discourages any changes that might be misinterpreted as creating a new unique nonce when, in reality, the crucial portion remains unchanged. In summary, the repair not only corrects the immediate bug by using the right constant, but it also strengthens the overall cryptographic robustness of the implementation by precluding the possibility of dangerous nonce reuse. Such careful adherence to RFC specifications is essential for safeguarding both the confidentiality and the integrity of data encrypted using ChaCha20-Poly1305.
