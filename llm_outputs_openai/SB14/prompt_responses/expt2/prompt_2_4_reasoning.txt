The repair introduces an additional check that verifies whether a close handle callback is already associated with the socket before proceeding with an immediate detachment on the NodeManager thread. In the original code, if the socket’s thread identifier (sock.tid) equaled the NodeManager’s thread identifier (NodeManager.nmTid()), it would unconditionally call NodeManager.nmhandle_detach_cb(handle). This unguarded approach could trigger multiple detachment operations when certain malicious TCP streams manipulated the timing or sequence of events. In turn, this created a scenario in which connections could linger in the CLOSE_WAIT state indefinitely because the state transition was mismanaged by overlapping or redundant callbacks.

In the repaired code, the immediate detachment callback is now invoked only when the socket is managed by the NodeManager thread and, importantly, does not already have a close handle callback registered. This extra check is performed by a function (NodeManager.hasCloseHandleCallback(sock)) that assesses whether a detachment or closure process has already been initiated for the socket. By including this condition, the repair ensures that if the close handle callback is already in place, the immediate detachment is bypassed, preventing multiple or conflicting detach operations.

If the conditions for immediate handling are not met—specifically, if either the socket is not on the NodeManager thread or if the close handler is already active—the code falls back to a safer, event-driven mechanism. In this branch, a detachment event is created using NodeManager.getNetiEventDetach(sock.mgr, sock). The event encapsulates all information necessary to process the detach operation and is then passed to the event dispatcher with EventPasser.passEvent(event). Finally, it is enqueued to one of the worker threads corresponding to the socket’s thread identifier. This asynchronous event processing ensures that the detachment operation is handled in a controlled manner, rather than executing immediately in a potentially unsafe context.

This separation between immediate callback execution and event-based processing is crucial. It targets the root cause of the problem: ensuring that the detach sequence is initiated only once for a particular socket connection. When a socket is already in the process of being handled, performing another detach operation can leave the connection in an improper state (such as lingering in CLOSE_WAIT), which could be exploited by attackers or lead to resource leakage. By verifying the existence of a “close handle callback” first, our repair effectively acts as a safeguard against this duplicate operation.

In summary, the repair makes the following changes: (1) it adds a condition to check whether a close handle callback is already present on the socket (using NodeManager.hasCloseHandleCallback(sock)), and (2) it uses this check to decide between invoking an immediate callback on the NodeManager thread or falling back to an event-driven detachment process. This dual-path approach ensures that the detachment operation is executed only once, thereby mitigating the risk of connections remaining indefinitely in a problematic state. Such a strategy bolsters resource management, ensuring that a socket’s life cycle progresses correctly even in the presence of maliciously crafted inputs, thereby rectifying the vulnerability.
