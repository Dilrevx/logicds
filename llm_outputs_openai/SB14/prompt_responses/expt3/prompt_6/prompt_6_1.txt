            sock->close_cb_pending = true;

            immediate_detach(sock);

            // Fall back to using the asynchronous mechanism to safely perform cleanup later.
            Event *evt = create_detach_event(sock);

    } else {
        // Not the designated thread: queue the detach event for asynchronous handling.
        Event *evt = create_detach_event(sock);
        enqueue_event(evt);
    }
}

   - in_designated_thread(sock): returns true if the current thread is the one responsible for detaching this socket.

   - create_detach_event(sock): creates an event that encapsulates the detach operation.
   - enqueue_event(evt): puts the event in the appropriate event queue for future handling.
   
   The Socket structure now includes a flag (close_cb_pending) that is used to keep track

Explanation:

1. The added condition (checking sock->close_cb_pending) prevents the situation where, even if you’re on the designated thread, you would immediately call immediate_detach() if another detach operation is already in progress or pending. This extra safeguard is key to avoiding duplicate cleanup runs.

2. When the close-handle callback is already marked as pending, the code enqueues a detach event. This makes sure that the cleanup will be handled in an orderly, asynchronous manner without immediate interference.

3. This update prevents a malicious actor from causing connections to get stuck in CLOSE_WAIT indefinitely by repeatedly triggering overlapping or conflicting detach operations.

This repair ensures that each socket’s cleanup is only executed once and in the correct context, thereby mitigating the vulnerability described.
