<vulnerability_description>
When getting a reply from a forwarded query, dnsmasq checks if the reply destination address/port is used by the pending forwarded queries. However, it does not use the address/port to retrieve the exact forwarded query, substantially reducing the number of attempts an attacker on the network would have to perform to forge a reply and get it accepted by dnsmasq. This issue contrasts with RFC5452, which specifies a query's attributes that all must be used to match a reply. This flaw allows an attacker to perform a DNS Cache Poisoning attack.
</vulnerability_description>

<repair_description>
The repair introduces additional checks that ensure a DNS reply matches a pending query more strictly, in line with the requirements of RFC5452. Initially, the original logic only compared the reply’s query identifier (ID) and an optional hash against each forwarded query. This was insufficient because it did not verify the originating port and address details used when sending the query, allowing an attacker to forge replies with less effort.

The first repair step is to validate whether the reply actually originates from the expected network interface by checking the file descriptor associated with the socket that sent the query. For queries using the IPv4 protocol, the repair inspects the random port used for the query. It confirms that if the reply is for an IPv4 query, the file descriptor in the IPv4-related structure matches the file descriptor from which the reply was received. This extra validation step prevents accepting forged responses that might accidentally have the correct query ID and hash but originate from an incorrect source.

Similarly, for IPv6 queries, the code now checks the corresponding IPv6 file descriptor. This ensures that a reply coming from the IPv6 path really belongs to the pending forwarded query. Only if this check passes is the query considered as a match for the reply.

In addition to handling replies that come directly from the randomly chosen port, the repair also covers a scenario where the query might have been sent from a bound socket configured for communication with upstream servers. In this case, if the sent query indicates that it was transmitted from a specific bound socket, the code validates that the file descriptor associated with that bound socket matches the one from which the reply originated.

Overall, the repair reinforces the matching process by not just relying on logical identifiers like the query ID or a hash comparison, but by also tying the reply to a specific network socket and port. This additional check makes it substantially harder for an attacker to successfully forge a DNS reply that would be accepted by the system. By ensuring the reply's source endpoint corresponds accurately to the original forwarded query's sending endpoint, the patch adheres closer to the secure practices advocated by RFC5452.
