The repair adds extra network channel validations to ensure that the reply to a DNS query is received via the same network socket that was used to send the query. The original code only checked if the reply’s identifier (and optionally a hash) matched a pending query record. This repair mitigates the possibility of an attacker forging DNS responses (i.e., DNS cache poisoning attacks) by adding socket verification.

First, after confirming that a reply has been received for a pending query based on an identifier and, if present, a hash match, the repair starts checking that the reply originated from the same network context as the query. This step is crucial because normally a DNS query is transmitted from a specific network socket—whether it’s an IPv4 socket or an IPv6 socket. If the response comes on a different socket, it could indicate tampering or an off-path attack.

The repair first determines if the query was sent over an IPv4 channel by checking a specific attribute indicating the address family. If the query was sent over IPv4, the corresponding file descriptor, which is essentially the identifier for the socket used, is compared with that of the incoming reply. A mismatch immediately results in rejecting the reply. The same logic applies when the query was transmitted using an IPv6 socket. By requiring the same socket to be used for both sending the query and receiving the reply, the repair ensures that an attacker can’t simply forge a reply by guessing the identifier and hash; they’d also need to be able to control or spoof the network channel, which is much more difficult.

Additionally, some queries might be sent via a socket that is specifically bound to an upstream interface. In these cases, an extra check confirms that if such a binding exists, the reply must have arrived on the same bound socket as well. This further restricts the reply path, making it harder for attackers to hijack the communication.

In summary, by chaining three pieces of validation—query ID (and hash), IPv4/IPv6 indications, and optionally a bound upstream interface—the repair substantially increases the security by ensuring that only responses coming from the same network socket as the query are accepted. This makes it significantly harder for an attacker to spoof responses on a different network channel, thereby mitigating DNS cache poisoning vulnerabilities.
