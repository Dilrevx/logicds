The vulnerability existed because dnsmasq originally relied solely on comparing a query’s identifier (ID) and an optional hash to identify whether an incoming DNS reply corresponds to a previously sent query. This approach is problematic because it does not verify that the reply comes from the same network endpoint (i.e., the same socket and port) that was used to send the original query. Consequently, an attacker could potentially forge a response with a valid ID and hash, but from a different IP address or port, thereby bypassing the intended validation process. This is a clear deviation from the stricter matching requirements prescribed by RFC5452, which mandates that a DNS reply be matched using all attributes of the original query, including network-level details such as source endpoint information.

The repair addresses this vulnerability by incorporating an additional check that verifies whether the reply comes from the correct network socket. The code now retrieves an expected file descriptor (fd) that corresponds to the original query’s sending parameters. This is done in a context-specific manner. If the original query was sent using a dedicated, bound socket (indicated by the “bound” flag in the query structure), then the expected file descriptor is taken directly from the bound socket’s file descriptor. This ensures that replies for queries sent via a configured upstream server socket match exactly the socket that was used to dispatch that query.

In scenarios where the query was not sent via a bound socket, the repair differentiates based on the network family (IPv4 or IPv6). For queries over IPv4 (AF_INET), the expected file descriptor is chosen from the IPv4-specific field in the query structure. Similarly, for IPv6 (AF_INET6), the corresponding IPv6 file descriptor is used. By making this distinction, the repair ensures that replies are validated against the correct underlying network interface corresponding to the IP family.

After determining the expected file descriptor, the repair compares it with the file descriptor from which the reply was actually received, represented by the variable “reply_fd”. If the two fds match, it confirms that the reply came from the correct network endpoint, and the query is considered a valid match. If not, the reply is rejected as it could be an attempt by an attacker to forge a response from an incorrect source, potentially undermining the integrity of the DNS cache.

Additionally, a check is incorporated for an unrecognized network family. If the query's family does not match any known types (i.e., neither AF_INET nor AF_INET6), the repair immediately rejects the reply. This is a safety measure to avoid processing replies for unknown or unsupported network configurations, thereby further strengthening the security posture of the system.

Overall, the repair reinforces the matching process by not only evaluating logical identifiers (the query ID and hash) but also by ensuring that the file descriptor (and by implication, the network socket and port) matches exactly between the sent query and the incoming reply. This comprehensive verification minimizes the attacker’s ability to correctly forge a DNS reply, adhering more closely to RFC5452 guidelines and significantly bolstering the security of dnsmasq against DNS Cache Poisoning attacks.
