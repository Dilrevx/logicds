The vulnerability in the wpa_supplicant implementation of PEAP (Protected EAP) allows an attacker to bypass authentication by sending an EAP-TLV Success packet instead of starting Phase 2 authentication. This is possible when wpa_supplicant is configured to not verify the network's TLS certificate during Phase 1 authentication. The attacker can then impersonate Enterprise Wi-Fi networks.

The root cause of this vulnerability lies in the way the code handles the EAP-TLV Success packet. In the buggy code, when an EAP-TLV Success packet is received (tlvStatus == EAP_TLV_RESULT_SUCCESS), the code checks if a forced failure is required. If not, it immediately returns a success status and an unconditional success decision. This allows an attacker to bypass Phase 2 authentication by sending a fake EAP-TLV Success packet.

The repair addresses this vulnerability by adding an additional check when an EAP-TLV Success packet is received. The new check, peapPhase2Sufficient(sm, data), verifies whether Phase 2 authentication has been completed successfully. If Phase 2 authentication is not sufficient, the code returns a failure status and a failure decision, preventing the attacker from bypassing Phase 2 authentication.

In essence, the repair ensures that even if an EAP-TLV Success packet is received, the code will not immediately return a success status without verifying that Phase 2 authentication has been completed successfully. This prevents an attacker from impersonating Enterprise Wi-Fi networks by sending a fake EAP-TLV Success packet.

The addition of the peapPhase2Sufficient(sm, data) check provides an additional layer of security, ensuring that both Phase 1 and Phase 2 authentications are completed successfully before allowing access to the network. This repair effectively closes the vulnerability and prevents authentication bypass attacks.
