The original code snippet unconditionally disables further certificate verification if an OCSP response contains the NoCheck extension (i.e. if cert->ocspNoCheckSet is true and verify equals VERIFY_OCSP). This behavior introduces a critical vulnerability. In particular, an attacker could supply an OCSP response signed using a certificate that does not belong to the correct certificate chain and still include the NoCheck extension. Because the code merely checks for the presence of the NoCheck flag without any validation of the responder’s legitimacy relative to the intended chain, the attacker can bypass proper trust chain verification.

In our repair, we address this shortcoming by adding an additional layer of validation. We introduce a check using the placeholder function OCSP_responder_id_matches_chain(cert, chain), which is assumed to verify whether the certificate used to sign the OCSP response has the proper relations (or is part of) the certificate chain in question. By using this function, we ensure that the NoCheck extension only disables further verification when the responder certificate is indeed a trusted and legitimate part of the certificate chain.

Here’s how the repair works in more detail:

1. The condition verify == VERIFY_OCSP remains as the outer check, ensuring that we only apply this logic during OCSP verification. This means that our modifications are strictly confined to OCSP-related verification scenarios and do not affect other parts of certificate validation.

2. Within this block, the code first checks if the certificate has the NoCheck extension, as determined by cert->ocspNoCheckSet. Instead of immediately setting verify to NO_VERIFY (which would bypass further security checks), the new code performs an extra validation step.

3. The function OCSP_responder_id_matches_chain(cert, chain) (you would need to implement or call an existing function that performs this check) validates whether the responder certificate (denoted by cert) is actually linked to the certificate chain under scrutiny (chain). This is crucial because it ensures that no arbitrarily chosen certificate – even if it carries the NoCheck extension – can bypass chain verification if it is not trusted for the given chain. It stops an attacker from using a misissued certificate.

4. Only if both conditions are met (the NoCheck extension is set and the certificate is validated as part of the proper certificate chain), then and only then is further verification disabled by setting verify to NO_VERIFY. For cases where the NoCheck extension is present but the OCSP responder certificate does not match the chain, the code will continue with the usual verification process, thereby preventing a situation where an unrelated or malicious certificate bypasses security checks.

By incorporating this additional check, the repair ensures that the NoCheck extension cannot be abused by malicious actors. It tightly couples the presence of the NoCheck flag with a strict check to confirm that the certificate belongs to the chain in question. This safeguards the certificate validation process and prevents verification bypass, thus addressing the vulnerability described.
