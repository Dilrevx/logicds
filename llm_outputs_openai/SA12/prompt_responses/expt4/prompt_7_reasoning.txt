The repair adds an explicit check on the server side to verify that if mutual authentication is required, the client must have sent the certificate_verify message. Here’s a breakdown of the important changes and how they mitigate the vulnerability:

1. Mutual Authentication Flag and Certificate Verify Check:
   • A new conditional block is introduced:
     "if (ssl.options.side == Constants.WOLFSSL_SERVER_END && ssl.options.requireMutualAuth && !ssl.receivedCertVerify)"
   • This block checks three things:
     - The connection is being handled on the server side.
     - Mutual authentication is required (a flag that should be set when the server mandates client certificates).
     - The client has not sent (or the flag for) the certificate_verify message.
   • If these conditions are met, it calls Tls13Helper.SendAlert to send a fatal alert with a handshake failure, then returns the VERIFY_FINISHED_ERROR, effectively aborting the handshake.

2. How It Fixes the Vulnerability:
   • The vulnerability allowed a client to bypass mutual authentication by omitting the certificate_verify message, even when the server required it. Without the new check, the handshake could complete even if the client did not prove control of the private key corresponding to its certificate.
   • With the repair, the server explicitly verifies that the certificate_verify message has been received when mutual authentication is mandated. If the message is missing, the handshake is terminated.
   • This ensures that only clients providing the necessary proof of possession of the private key can complete the TLS handshake, hence properly enforcing mutual authentication.

3. Additional Context:
   • The booking is done after the Finished message validation process. This is a critical point because by the time the Finished message is processed, the server should have validated all required client authentications.
   • The added logic prevents a malicious client, which might try to skip sending the certificate_verify message to avoid authentication, from establishing a connection.
   • The alert generated follows standard TLS procedures, notifying the client of the error and ensuring proper logging and error handling flow.

In summary, the repair ensures that in TLS v1.3 connections requiring mutual authentication, the absence of a certificate_verify message results in a handshake failure. This directly addresses the vulnerability by enforcing that the client must prove its identity with a valid certificate_verify message, closing the gap that previously allowed bypassing client authentication.
