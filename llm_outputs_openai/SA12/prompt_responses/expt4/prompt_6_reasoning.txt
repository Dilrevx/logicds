The repair begins by inserting a new conditional check at the very start of the function. This check targets the specific situation described in the vulnerability: a TLS v1.3 server configured to require mutual authentication may allow a handshake to proceed even when the client omits the certificate_verify message. Here’s how the new code prevents that:

1. Server-side check: The new if-statement only runs when the SSL object indicates that the current connection is on the server-side (ssl.options.side == Constants.WOLFSSL_SERVER_END). This guarantees that the additional verification is only applied where it is relevant.

2. Mutual authentication requirement: It then checks if mutual authentication is mandated by the server (ssl.options.requireMutualAuth). This flag would be set in scenarios when the server is configured to require clients to present valid certificates.

3. Resumed session exception: The condition also checks whether the session is a resumed session (ssl.options.resumedSession). Resumed sessions sometimes rely on cached security parameters, so the certificate verification might not be repeated. In such cases, bypassing the certificate_verify message is acceptable. Thus, if it is a resumed session, the check is skipped.

4. Certificate verification status: Finally, the condition checks whether the client certificate has been successfully verified (ssl.options.certVerified). If this flag is not true, it means that the client did not correctly provide or verify its certificate.

If all these conditions are met—in other words, if the connection is on the server side, mutual authentication is required, it is not a resumed session, and the client’s certificate hasn’t been verified—the server immediately sends a fatal alert using Tls13Helper.SendAlert() with an alert code for a bad certificate. It then returns an error code (Constants.PEER_CERT_MISSING), halting the handshake process.

This early exit effectively prevents a malicious client from bypassing mutual authentication by omitting the certificate_verify message. The rest of the function is not executed in this case, so no further handshake steps are taken for a client that failed the required certificate check.

By adding these checks right at the beginning of the function, the repair eliminates the vulnerability where a client could connect without proper certificate verification. Only if the client meets all the authentication requirements does the function continue with its original logic—including handling buffer safety, secret derivation, handshake HMAC construction, and key setting. This ensures that both authentication and overall handshake security are maintained.

In summary, the repair fortifies the server-side TLS handshake process by validating that the client has been properly authenticated when mutual authentication is required. This closes the potential bypass path that could allow a client to skip the certificate_verify step, ensuring that the server does not inadvertently accept unauthorized client connections.
