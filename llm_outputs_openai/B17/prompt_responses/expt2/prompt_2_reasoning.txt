The repair changes the parameter passed to the CRL retrieval functions from “subject” to “issuer.” Originally, both OpenSSL API calls used the subject identifier to filter CRLs, which is problematic. In TLS verification, it’s essential to check the Certificate Revocation List (CRL) against the issuer of the certificate rather than the subject. A revoked certificate should be identified via its issuer's CRL entry. By mistakenly using the subject for both checks, some revoked certificates could bypass the validation, allowing an untrusted connection to proceed.

In our fix, we replace “subject” with “issuer” in the calls to X509_STORE_CTX_get1_crls (for OpenSSL 1.1.0 and newer) and X509_STORE_get1_crls (for OpenSSL versions between 1.0.0 and 1.1.0). This adjustment ensures that when the CRL is retrieved, it correctly targets the CRL that corresponds to the certificate authority responsible for issuing the certificate. This proper mapping of issuer to CRL is vital because the CRL is meant to list certificates that have been revoked by the issuing authority. By using the issuer field, the code now correctly implements a critical part of the revocation checking process.

The conditional compilation remains intact to maintain backward compatibility. For versions of OpenSSL older than 1.0.0, the code still does nothing beyond indicating that an upgrade is recommended. This means that while the fix is applied to supported versions, it avoids introducing changes in environments where the library may not support the corrected behavior.

In summary, the repair addresses the vulnerability by ensuring that the correct CRL entry is fetched. Instead of using the subject to query the list of CRLs, the issuer is now used, which aligns the CRL lookup process with the intended logic: the certificate must be checked against its issuer’s revocation status. This simple but crucial change reinforces the certificate validation process, thereby stopping revoked certificates from being mistakenly accepted during secure TLS connections.
