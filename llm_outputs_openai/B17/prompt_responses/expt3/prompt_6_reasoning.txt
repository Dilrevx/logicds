By checking for the LibreSSL definition first, the code avoids attempting to call a function that isn’t available. This is crucial because otherwise, if the OpenSSL version check were done first, a LibreSSL build might incorrectly enter a branch where an unsupported function is called, potentially leading to undefined behavior or even exploitable crashes.

The repair thus begins by checking explicitly if the build is using LibreSSL. If it is, the code bypasses the newer X509_STORE_CTX_get1_crls function even if the numerical version might suggest that function should be available. Instead, it falls back to the legacy X509_STORE_get1_crls function, which is implemented in LibreSSL. This not only fixes a compatibility issue but also prevents a situation where the wrong function would be used on a given platform.

For builds that are not using LibreSSL, the code then uses a version check against the OpenSSL version. For version numbers equal to or above 1.1.0, the repair utilizes the new X509_STORE_CTX_get1_crls function, as this function is available and expected to be present in those versions. For builds with OpenSSL versions between 1.0.0 and 1.1.0, the legacy function is used.

This ordered checking mechanism is important in preventing vulnerabilities because selecting an unsupported function call can lead to crashes, memory corruption, or other forms of undefined behavior which could be exploited. By ensuring that only the supported API is called on any given build of OpenSSL or LibreSSL, the repair reduces the risk of running insecure or incompatible code.
