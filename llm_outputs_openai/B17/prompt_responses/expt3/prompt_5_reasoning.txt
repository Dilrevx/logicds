The change replaces the use of the certificate’s subject with the certificate’s issuer when retrieving the certificate revocation lists (CRLs). In the original code, the CRL lookup functions were called with the subject parameter, which is designed to represent the entity for which the certificate was issued. However, CRLs are issued by the authority that revokes certificates, meaning the lookup should be based on the issuer.

By passing the issuer to the CRL retrieval functions, the repair ensures the code searches for CRLs that are actually associated with the entity that can revoke certificates. This adjustment is important because using the subject could result in failing to find the correct CRL for a given certificate. Such a failure might allow a revoked certificate to be mistakenly validated, thereby creating a vulnerability where revoked certificates could be improperly trusted.

The repair addresses two OpenSSL API variants depending on the version in use. For OpenSSL versions 1.1.0 and above, it properly uses the function designed for that version to retrieve CRLs using the issuer information. For OpenSSL versions between 1.0.0 and 1.1.0, a different API call is used, but the principle remains the same: the issuer is used to correctly associate the CRL with the certificate revocation authority. For even older OpenSSL versions (pre-1.0.0), the code acknowledges that the library is outdated and does not provide the CRL retrieval functionality, recommending an upgrade instead.

This change directly fixes the vulnerability by ensuring that the CRL lookup mechanism aligns with the intended security model of certificate revocation. The lookup now accurately matches certificates with the corresponding CRL entries issued by the revocation authority, reducing the risk that a certificate marked as revoked might be inadvertently trusted if its CRL was not properly found.

In summary, the repair involves:
1. Replacing the incorrect parameter (subject) with the correct one (issuer) in the calls to the CRL retrieval functions.
2. Maintaining compatibility with different OpenSSL versions while ensuring the CRL lookup aligns with standards for certificate revocation.
3. Preventing a potential security vulnerability where revoked certificates could slip through validation checks due to an incorrect CRL lookup.

This change improves the robustness of TLS certificate revocation checking, ensuring that the CRL retrieval process correctly identifies and processes the revocation information provided by the certificate issuer.
