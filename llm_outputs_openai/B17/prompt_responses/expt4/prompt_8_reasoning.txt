The repair fixes the vulnerability by changing the way the code retrieves the Certificate Revocation List (CRL) for checking whether a certificate has been revoked. Originally, the code used the certificate’s subject name for both verifying the CRL’s integrity and checking the revocation status. However, during the revocation check, it should use the certificate’s issuer name. A certificate is revoked based on the actions of its issuing Certificate Authority (CA), so checking with the issuer’s CRL is essential.

Below is a walkthrough of the key changes made in the repair:

1. First, the code extracts both the subject and the issuer names from the certificate (xs) being verified. It logs these names so that operators can trace the evaluation of the certificate’s details.

2. In the first CRL retrieval (used for signature verification and verifying the CRL’s validity period), the code retains the behavior of looking up CRLs using the certificate’s subject name. This is because, in the verification scheme implemented, the CRL corresponding to the current certificate’s subject is used to verify the CRL’s integrity one round earlier, when checking the signature of the CRL.

3. The significant change is in the second CRL retrieval, which is intended to check the certificate’s revocation status. In the original buggy code, this second call mistakenly used the subject name again. The repair modifies this by passing the issuer name of the certificate instead. This ensures that the code retrieves the CRL that is actually issued by the Certificate Authority. The CA’s CRL is what lists the certificates it has revoked.

4. Once the correct CRL is retrieved (by issuer), the code loops over the list of revoked certificates contained within it. It compares the serial numbers of the revoked entries (extracted from the CRL) with the serial number of the certificate under verification. If a match is found, it logs the revocation and sets an appropriate error in the verification context, resulting in the certificate being rejected.

5. The repair maintains backward compatibility with different OpenSSL versions by handling the function calls appropriately based on the version macro. This ensures that even with the fix, older and newer versions of the library are supported (provided they have support for the required CRL operations).

By substituting the subject with the issuer in the CRL lookup while checking for revocation, the repair directly addresses the vulnerability. A revoked certificate might have been accepted previously because the CRL that could indicate its revocation (issued by the CA) wasn’t consulted. Now, by verifying both the CRL integrity (using the subject CRL) and the certificate’s status (using the issuer CRL), the TLS verification process becomes robust against the vulnerability where revoked certificates could otherwise be mistakenly allowed.

In summary, the repair ensures that the correct CRL is referenced when checking for a certificate’s revocation: the integrity check still uses the subject (since that fits into the design of the two-phase validation), while the actual revocation lookup uses the issuer’s CRL, which accurately reflects the CA’s decision to revoke a certificate. This change effectively mitigates the vulnerability and strengthens the overall certificate validation process.
