The original code passed the certificate’s subject to the CRL lookup functions instead of its issuer. In certificate revocation checking, the CRL (Certificate Revocation List) is issued by a CA (Certificate Authority) and is signed with the CA's credentials; therefore, the lookup should be done against the issuer certificate. Using the subject field was a mistake and could potentially allow a certificate that has been revoked to bypass validation, since the CRL might not be retrieved or matched correctly.

Here's what was fixed:

1. For OpenSSL 1.1.x (and later) using the function X509_STORE_CTX_get1_crls, the original code used “subject” as the lookup argument. The repair replaces it with “issuer,” meaning that the function now retrieves CRLs associated with the issuer certificate rather than the certificate itself. This ensures that the CRL is validated in the correct context.

2. Similarly, for OpenSSL 1.0.x, the code previously used X509_STORE_get1_crls with the certificate’s subject. The fix also changes this to use the issuer. This consistency prevents the same oversight across different OpenSSL versions, making sure that the CRL check is robust regardless of the API version.

3. For OpenSSL versions before 1.0.0, the code remains unchanged and sets crls to NULL, along with a notice that an upgrade is really needed. This part isn’t directly related to the vulnerability but is kept for contexts where the code might run on an unsupported version of OpenSSL.

By using issuer for the CRL lookup, the repaired code now ensures that when a CRL is being fetched, the matching entry is correctly identified based on the certificate issuing authority. This fix stops the vulnerability where certain valid CRLs were being ignored and prevents revoked certificates from being incorrectly considered valid. In short, the CRL is now properly tied to the CA that issued the certificate, closing the gap that allowed potentially dangerous behavior in the certificate validation process.

The change is subtle but crucial: it directly modifies the parameter passed to the CRL lookup functions, which is the core aspect in validating whether a certificate should be trusted or not. Without this fix, a server might inadvertently allow a connection despite the certificate having been revoked, undermining trust and compromising security in TLS communications.
