The repair corrects the vulnerability by ensuring that the CRL retrieval for revocation checking uses the certificate’s issuer rather than mistakenly using the subject again. Here’s how it works:

1. In the first part of the function, the code retrieves any CRLs that match the certificate’s subject. This section is intended to check the integrity of the CRL itself by verifying its signature and validating its update dates. The CRL verified in this section typically comes from the CRL’s own “subject” field, which helps ensure that the CRL is issued by the certificate authority that signed it.

2. The vulnerability stemmed from the fact that in the second retrieval, meant for checking whether the certificate is revoked (by scanning the CRL’s list of revoked certificates), the code again used the current certificate’s subject to get CRLs. This was a mistake because the CRL for revocation should be identified by the issuer of the certificate (the CA issuing the certificate). Using the subject potentially retrieves CRLs that aren’t appropriate for revocation checking, which could allow a revoked certificate to be mistakenly accepted.

3. The repaired code fixes this by simply changing the parameter used for the second CRL retrieval from subject to issuer. This means that when the code later iterates through the list of revoked certificates in the CRL, it is looking at the CRL issued by the CA (matching the certificate’s issuer), where the revocations are correctly maintained.

4. By using the correct field (issuer) for the revocation check, the code now properly matches the CRL with the intended issuing CA. This ensures that if the certificate’s serial number appears on the revocation list in the CRL issued by the CA (the correct CRL), the certificate will be rejected. Hence, clients that are revoked will not be allowed to proceed with a connection.

Overall, this change removes the flaw where the code inadvertently verified a CRL from the wrong source by checking the same field (subject) twice. It clarifies the logic: first, verify the CRL’s integrity via the certificate’s subject CRL and then validate revocation by using the issuer CRL. This repair upholds the proper certificate revocation checking protocol, significantly reducing the risk of a revoked certificate being mistakenly accepted.
