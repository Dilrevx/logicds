Below is one way to fix the issue. Recall that the vulnerability arose because the code was only checking certificates starting at index 1, thereby skipping the leaf certificate. In many certificate chains the leaf (index 0) gets special treatment (or “relaxed checks”) so that an invalid policy in the leaf certificate is silently ignored. That, in turn, opens the door for a malicious CA to deliberately inject an invalid certificate policy in the leaf and bypass policy enforcement. The repair below fixes the vulnerability by iterating over every certificate in the chain (including the leaf) so that no invalid policy “slips by” unnoticed.

────────────────────────────
Old code:
────────────────────────────
   if (ret == X509PolicyChecker.X509_PCY_TREE_INVALID) {

       for (int i = 1; i < ctx.chain.size(); i++) {
           X509Certificate x = ctx.chain.get(i);

           cbFailIf(x == null || (x.hashCode() & EXFLAG_INVALID_POLICY) != 0
                   , ctx, x, i, X509Error.X509_V_ERR_INVALID_POLICY_EXTENSION);
       }

       return 1;
   }
────────────────────────────
Issues with the above:
  • The loop starts at i = 1, meaning the leaf certificate (at index 0) is not checked.
  • This allows a malicious CA to purposely put an invalid policy inside the leaf certificate and possibly circumvent important validation checks.
  
────────────────────────────
Repaired code:
────────────────────────────
   if (ret == X509PolicyChecker.X509_PCY_TREE_INVALID) {

       // Ensure we check ALL certificates (including the leaf at index 0)
       for (int i = 0; i < ctx.chain.size(); i++) {
           X509Certificate x = ctx.chain.get(i);
           
           // Fail if the certificate is null or has an invalid policy flag set.
           cbFailIf(x == null || (x.hashCode() & EXFLAG_INVALID_POLICY) != 0,
                     ctx, x, i, X509Error.X509_V_ERR_INVALID_POLICY_EXTENSION);
       }

       return 1;
   }
────────────────────────────
Explanation:
1. Instead of skipping index 0, the loop now begins with i = 0 so that every certificate in the chain is verified.
2. This ensures that even the leaf certificate’s invalid policies are rejected when using a non-default certificate policy check configuration.
3. (Optionally, if the use of x.hashCode() for validation is not intentional, you might want to replace it with the proper API call to extract certificate flags. However, the key change here is to check all certificates in the chain.)

By ensuring that every element of the cert chain (including the leaf) is strictly evaluated, we remove the vulnerability that a malicious CA could exploit.
