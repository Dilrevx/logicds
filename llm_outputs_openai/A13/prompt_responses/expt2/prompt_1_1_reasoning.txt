The vulnerability described that when processing DLZ zones, particularly writable DLZ zones, the zone transfer permission check (allowzonexfr) wasn’t executed because the code only considered zones if the dlz_searched list was non-empty. This meant that if a writable DLZ zone existed but there was no corresponding entry in dlz_searched, then no authorization check was done. As a result, transfers for such writable zones could bypass zone transfer restrictions.

In the repair, the core change was to modify the condition that determines whether to attempt a zone transfer authorization check using dns_dlzallowzonexfr. Originally, the code block checked only if the list dlz_searched was not empty. If it was empty, the code would immediately fail with a “non-authoritative zone” error. However, for writable DLZ zones, even if dlz_searched was empty, the appropriate permission check should still occur.

To address this, the repaired code adds an extra check for the writable DLZ flag, represented in the code by client->view->dlz_is_writable. The revised condition in the if-statement now uses a logical OR between checking if the dlz_searched list is non-empty and if dlz_is_writable is true. This ensures that if either condition is true, the system will proceed to call dns_dlzallowzonexfr – the function responsible for validating whether the zone transfer is allowed.

Once dns_dlzallowzonexfr is called, the code behaves as before. If the function returns ISC_R_NOPERM, meaning the transfer does not have permission, the code then logs an error with details about the zone transfer attempt and sets the result to DNS_R_REFUSED. At this point, it jumps to the failure handling code to terminate the process. If the result is not ISC_R_SUCCESS (and not ISC_R_NOPERM), the code calls FAILQ to report that the zone is non-authoritative. Finally, if the operation succeeds, a flag (is_dlz) is set to true, indicating that the DLZ mechanism has processed the zone transfer request properly.

This solution directly addresses the vulnerability by ensuring that the zone transfer control is effective in all cases. Writable DLZ zones, which were previously not subject to the allowzonexfr validation because they might not be included in dlz_searched, are now properly checked. This repair reinforces the security model by ensuring that every zone transfer request, whether it belongs to a standard DLZ zone or a writable DLZ zone, must pass through the same security validation provided by allowzonexfr.

In summary, the repair corrects the logic flaw in the zone transfer process for DLZ zones by extending the condition to include writable zones. By ensuring that the allowzonexfr method is called for writable DLZ zones, the updated code mitigates the vulnerability where unauthorized zone transfers could have been allowed. This change illustrates careful consideration of both traditional and writable DLZ configurations to uphold consistent security policies and prevent unauthorized access.
