<vulnerability_description>
OpenSSL supports creating a custom cipher via the legacy EVP_CIPHER_meth_new() function and associated function calls. OpenSSL versions 3.0.0 to 3.0.5 incorrectly handle legacy custom ciphers passed to the EVP_EncryptInit_ex2(), EVP_DecryptInit_ex2() and EVP_CipherInit_ex2() functions (as well as other similarly named encryption and decryption initialisation functions). Instead of using the custom cipher directly it incorrectly tries to fetch an equivalent cipher from the available providers. An equivalent cipher is found based on the NID passed to EVP_CIPHER_meth_new(). This NID is supposed to represent the unique NID for a given cipher. However it is possible for an application to incorrectly pass NID_undef as this value in the call to EVP_CIPHER_meth_new(). When NID_undef is used in this way the OpenSSL encryption/decryption initialisation function will match the NULL cipher as being equivalent and will fetch this from the available providers. This will succeed if the default provider has been loaded (or if a third party provider has been loaded that offers this cipher). Using the NULL cipher means that the plaintext is emitted as the ciphertext.
</vulnerability_description>

The repair adds extra conditions to the existing conditional block that determines when to trigger legacy handling. Originally, the code checked if the encryption context had an associated engine or if any of the legacy implementation variables were non-null. If any of these conditions were met, the code would free a previously fetched cipher and then pass control to a legacy handling function. This logic was too simplistic because it did not account for cases where the cipher in use originated from application-defined legacy methods rather than from the provider lookups.

The first repair step introduces additional checks related to the origin of the cipher. The new conditions evaluate whether the cipher object exists and whether it was created using a legacy custom method. Specifically, if the cipher is non-null and its origin is from a method-defined implementation, it implies that the cipher was intended to be used as defined by the application, not one that should trigger the fallback to the provider mechanism.

The second extra condition addresses the scenario where the cipher object may be null, but the context still holds an existing cipher obtained earlier. In this situation, the code checks if that already stored cipher also originates from the legacy method. This ensures that even if the cipher parameter is null, if the context’s cipher came from a legacy method, the legacy handling must be executed rather than mistakenly fetching an equivalent cipher from the providers.

Once one of these new conditions is satisfied, the code proceeds with the same cleanup operations performed in the original implementation. It first verifies if the cipher stored in the context is the same as the fetched cipher. If that is true, the stored cipher is reset to null. Then the fetched cipher is freed, and the context’s pointer to the fetched cipher is cleared. These steps prevent further misuse of any cipher object that could have been erroneously matched — for instance, the default or NULL cipher — which in effect would expose plaintext as ciphertext.

After cleaning up, the code then calls the legacy handling function. This function is designed to properly manage encryption/decryption operations using legacy methods, ensuring that even if a custom cipher has an undefined identifier, it is treated with the appropriate processing rather than defaulting to an unsafe fallback.

Overall, these modifications ensure that only genuine legacy ciphers – those that are explicitly designed as legacy implementations – will be processed using the legacy handling routine. By specifically checking for the origin of the cipher or verifying the origin of the cipher stored in the context, the repair prevents the risky situation where an application might inadvertently pass a cipher with an undefined NID and trigger the use of the NULL cipher. This approach effectively blocks the security vulnerability that allowed plaintext to be mishandled as ciphertext, enhancing the overall security of the OpenSSL encryption/decryption initialization functions.
