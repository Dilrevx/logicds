The vulnerability arises from the fact that the original code compares the OCSP response serial number (rserial) with the certificate’s serial number (cserial), but the certificate’s serial extraction does not account for potential trailing bytes that may have been allocated but remain uninitialized. The gnutls_x509_crt_get_serial function returns a value ‘t’ which is the exact size of the certificate’s serial number. However, the code previously compared rserial.size to cserial.size, even though cserial.size might include extra bytes from gnutls_malloc that are not part of the actual serial. This discrepancy means an attacker could craft an OCSP response with extra trailing bytes that, while matching the base serial number in the common length, would bypass the intended certificate validation check.

To address this vulnerability, the repair involves modifying the check to use the precise length of the certificate's serial number as determined by the return value ‘t’ from gnutls_x509_crt_get_serial rather than the potentially padded value cserial.size. In the repaired code snippet, we first obtain the certificate’s serial number and also capture the actual length in variable “t”. This length “t” represents the true number of bytes that constitute the certificate's serial number, excluding any unwanted or uninitialized trailing data.

Once we have the real length, the code immediately compares rserial.size (the size provided in the OCSP response) to this true serial number length ‘t’. If the sizes do not match, the code concludes that the OCSP response is not valid for the certificate, sets the return value to an error (GNUTLS_E_OCSP_RESPONSE_ERROR), asserts an error condition with gnutls_assert(), and then branches to cleanup. This ensures that any OCSP response with a mismatched serial length is instantly rejected before any further processing.

Following the length check, the memcmp() function is used to compare the actual content of the certificate’s serial number in cserial.data with the OCSP serial in rserial.data. The memcmp now compares exactly “t” bytes, ensuring that both the value and length of the serial numbers are strictly matched. This prevents a scenario where extra trailing bytes introduced due to improper allocation or copy practices can be used to bypass the validation logic.

The use of the variable “t” for both the length comparison and memcmp is critical. It ties the certificate’s serial length to the value officially reported by gnutls_x509_crt_get_serial. By doing so, we are no longer relying on a possibly flawed external size parameter (which might have been erroneously or maliciously padded) but rather on the exact actual size of the certificate's serial as determined by the underlying X.509 library function. This additional verification step closes the gap exploited by an attacker who could insert trailing bytes to bypass serial number verification.

In summary, the repair thoroughly ensures that the serial number in the OCSP response is not only identical in content but also in length to that of the certificate. The code now uses the certificate's serial length ‘t’ for both the size check and the memcmp. This tightly coupled length comparison prevents any discrepancies that could occur if padded or trailing data was erroneously included, effectively fixing the vulnerability described.
