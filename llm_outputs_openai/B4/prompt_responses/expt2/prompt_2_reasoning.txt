The repair makes a simple yet crucial change. Initially, the function gnutls_x509_crt_get_serial is called to retrieve the certificate’s serial number. This function not only copies the serial data into cserial.data but also outputs its exact length into the temporary variable t. However, the problematic code didn’t update the size field of the cserial structure, which meant that extra bytes from previously allocated memory (if any) might be considered when comparing with the expected serial from the OCSP response.

To fix this, once the function call has successfully returned, the code now sets cserial.size to the value of t. This explicit assignment ensures that the certificate’s serial number structure accurately reflects the real length of the serial number returned by the retrieval function.

With this update, the subsequent comparison now reliably checks that both the size and the content of the serial number match. First, it compares the sizes of the certificate serial number (now correctly recorded in cserial.size) with the serial number from the OCSP response (rserial.size). If there is any difference in the lengths, it immediately implies a discrepancy, and the response is treated as erroneous. If the sizes are equal, it then performs a byte-by-byte comparison using memcmp. This two-step validation process prevents an attacker from being able to exploit any leftover or trailing bytes that could be present because the size now truly represents the certificate’s serial number.

In summary, by capturing and updating the actual length of the certificate’s serial number, the repair stops attackers from passing validation by injecting extraneous trailing bytes. The integrity of the certificate validation process is maintained because only serial numbers with matching lengths and exact content are accepted.
