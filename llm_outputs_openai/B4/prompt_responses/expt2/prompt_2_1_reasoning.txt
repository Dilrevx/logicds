The repair addresses a subtle yet critical vulnerability in the OCSP status validation logic where the certificate’s serial number might be compared incorrectly due to a mismatch in its length. Originally, the function gnutls_x509_crt_get_serial was used to retrieve a certificate’s serial number along with its actual length set in the variable "t". However, even though the function returned the correct length, that length value was not subsequently stored in the certificate serial structure (cserial.size). This led to the possibility that cserial.size might represent an allocated size or an outdated size, rather than the true number of bytes actually read from the certificate. If the original allocated size exceeded the actual number of bytes retrieved, extra trailing bytes (potentially uninitialized or leftover memory) could be present. Such a discrepancy would allow a payload from an adversary—with carefully crafted extra trailing bytes in an OCSP response—to be padded and, when compared with the unadjusted certificate serial number, potentially pass the validation even though the real serial values differ.

In the provided fix, right after retrieving the serial number using gnutls_x509_crt_get_serial, the repair explicitly assigns the actual length "t" to cserial.size. This update is crucial because it ensures that the actual length of the certificate’s serial number (as determined during the call to gnutls_x509_crt_get_serial) is used when performing the subsequent comparison with the OCSP response serial (rserial). By synchronizing the size field with the actual number of bytes read, the validation function now accurately compares only the valid portion of the serial number. This improvement prevents any extra bytes that might be a byproduct of memory allocation idiosyncrasies (such as trailing bytes from gnutls_malloc or any other memory allocation function) from being inadvertently included in the comparison.

Once the serial size is corrected, the function then performs a two-part check: first, it verifies that the sizes of the certificate serial (cserial.size) and the serial number expected from the OCSP response (rserial.size) are equal. If the sizes do not match, it is an immediate error as the OCSP response’s serial can never be valid. Second, if the sizes are indeed equal, the function does a byte-by-byte comparison (using memcmp) of the two serial numbers. This comparison now strictly applies only to the defined length of the serial, thereby ensuring that even if one serial contains extra undefined bytes, these discrepancies would lead to a mismatch and a consequent rejection of the OCSP response.

By applying this repair, the function’s security posture is strengthened against possible bypass attacks. An attacker might have tried to exploit the gap by injecting trailing data that might match an initially allocated but uninitialized memory region. With the corrected approach setting cserial.size to the true length “t”, there is no longer any ambiguity regarding which bytes are part of the serial number. The final outcome is that the certificate’s serial is validated against the OCSP response using both the correct content and the correct length. This precise alignment between expected and actual data greatly reduces the risk of a certificate validation bypass, thereby ensuring that the certificate validation mechanism behaves as intended for all inputs.

Overall, the repair guarantees that memory artifacts do not compromise security, thereby upholding the robustness of the certificate validation process against a specific class of remote attacks targeting OCSP response handling.
