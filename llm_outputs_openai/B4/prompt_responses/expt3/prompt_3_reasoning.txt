The vulnerability stemmed from using the certificate’s cached serial length (stored in cserial.size) when comparing the serial number in the certificate with the one in the OCSP response. This cached value can potentially be longer than the actual serial number. For instance, if memory previously allocated for the cached serial happened to include extra bytes (perhaps from a previous allocation), then a naive memcmp using cserial.size could compare more bytes than intended. An attacker could exploit this by “padding” the OCSP response serial, leading to a bypass of the serial verification check.

The repair involves using the actual serial number length returned by the gnutls_x509_crt_get_serial() function. This function not only extracts the certificate serial number but also returns its exact length via the variable “t.” By directly comparing the OCSP response serial’s size (rserial.size) to this exact length “t” and then comparing the contents over those t bytes, the code avoids relying on potentially padded or oversized allocations.

Thus, the following changes were made:
1. After retrieving the serial with gnutls_x509_crt_get_serial(), the variable “t” accurately reflects how many bytes constitute the certificate’s serial number.
2. Instead of comparing the OCSP response serial’s length with cserial.size, the code now compares it with t. This ensures the lengths match exactly.
3. The memcmp function now uses t as the comparison length, ensuring that only the meaningful bytes of the serial number are compared.

By using the exact serial number length provided by the function (rather than the potentially inflated cached size), the repair ensures that both the length and content of the certificate serial number are verified rigorously. This change eliminates the risk of the vulnerability where extra, non-meaningful bytes in memory could be misinterpreted as part of the valid serial data, ultimately preventing an attacker from manipulating the OCSP response to pass the serial check erroneously.
