The repair addresses a logical vulnerability related to accepting plaintext NAS messages without proper integrity protection. Originally, certain NAS messages were allowed in plaintext even though the specification (TS 24.301 Sec. 4.4.4.2) only permits a limited set of message types in plaintext. In some cases, the code erroneously accepted Attach Reject and Service Reject messages without enforcing checks on the embedded EMM cause.

Here’s a step‐by‐step explanation of the repair:

1. NAS header parsing remains unchanged. The function writes the pcap data and parses the header to extract both the security header type (sec_hdr_type) and the message type (msg_type).

2. The repair introduces a stricter policy in the plaintext (LIBLTE_MME_SECURITY_HDR_TYPE_PLAIN_NAS) branch of the validation. It specifically lists only three message types as generally acceptable:
   • DETACH REQUEST
   • EMM INFORMATION
   • EMM STATUS

3. For Attach Reject and Service Reject messages that arrive in plaintext, the repair adds an additional check: it extracts the EMM cause (using a helper function like liblte_mme_get_emm_cause()) from the PDU. The policy mandates that plaintext Attach Reject or Service Reject messages are only allowed if the embedded EMM cause equals 25. If the cause is not 25, the function logs an error and returns without processing the message further.

4. This conditional check ensures that no other messages (apart from the three explicitly allowed types or the ones with a specific EMM cause policy) are processed when integrity protection is missing. This is in line with the mobile standard’s security requirements.

5. The rest of the message processing (parsing different NAS message types) remains intact and is carried out only after these security checks have passed. Messages with integrity protection issues or incorrect message types will be dropped, preventing unauthorized or malformed PDUs from being processed.

6. The repair also handles the reserved case for the Security Mode Command correctly. If a message has a security header type meant for a new EPS security context and the message isn't the Security Mode Command, a log error is triggered and the function returns.

In summary, the vulnerability fix lies in tightening the conditions under which plaintext NAS PDUs are accepted. By restricting plaintext to only those messages that are explicitly allowed (and enforcing an EMM cause of 25 for Attach/Service Reject messages), the repair minimizes the risk of processing potentially manipulated messages that lack integrity protection. This ensures that only messages meeting the strict criteria defined in the standard are processed, thereby mitigating potential security risks arising from vulnerabilities in message handling.
