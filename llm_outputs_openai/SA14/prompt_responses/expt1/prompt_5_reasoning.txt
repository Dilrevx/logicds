The repair works by modifying the transport logic in the ssl3_connect() function to avoid processing messages in a state where the CCS injection vulnerability can be exploited. Here’s how the repair fixes the vulnerability:

1. In the original code (the commented-out vulnerable portion), the logic processed ChangeCipherSpec (CCS) messages even after reaching the finished state of the handshake. This allowed an attacker to potentially inject CCS messages into the communication, tricking the system into accepting a zero-length master key. Such a condition could compromise the confidentiality and integrity of the TLS session.

2. In the repaired code, after sending the ClientHello (case 0) which initiates the handshake, we explicitly check for the states HandshakeStates.SSL3_ST_CR_FINISHED_A, HandshakeStates.SSL3_ST_CR_FINISHED_B, and HandshakeStates.SSL_ST_OK. Instead of processing the finished message and potentially CCs messages as before, the function immediately returns the current value of ret (which is typically set to indicate the state of the handshake).

3. By immediately returning when encountering those handshake states, the modified logic prevents any further processing that might inadvertently accept and act upon an incoming CCS message. Consequently, the repair effectively circumvents the vulnerability by “skipping” the steps where a malicious CCS injection could be harmful.

4. The print statement “Client: In Finished state or handshake complete. Skipping CCS processing for security reasons.” serves as a helpful indication during debugging or logging that the function is deliberately avoiding any processing in that critical stage. This line communicates that, for security reasons, no further CCS message handling is performed.

5. The repair minimizes risk by ensuring that once the handshake reaches a stage where further CCS message processing is not safe, the function exits rather than entering potentially dangerous territory. This change effectively bars any attacker from exploiting the handshake state by injecting spurious CCS messages.

In summary, the repair ensures that the function does not perform insecure operations (like processing CCS messages post-handshake completion) by returning early from the function. This prevents an adversary from triggering the condition that could lead to a zero-length master key, thus securing OpenSSL-to-OpenSSL communications against the CCS injection vulnerability.
