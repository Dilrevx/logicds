The repair introduces an explicit change to the state by setting a dedicated flag (state.ccsOk) to true before proceeding with the processing of the Finished message. Originally, the code directly jumped from receiving a ChangeCipherSpec (CCS) message to retrieving the Finished message without any explicit indication that the CCS message was securely validated. This lack of clear state validation allowed an attacker to potentially inject malicious CCS messages, leading to the kernel vulnerability known as "CCS Injection," where an attacker could force the use of a zero-length master key.

In the repaired code, the first important change is the addition of the line:

  state.ccsOk = true; // Mark CCS as validated

This line explicitly sets a flag in the state object that the CCS message has been properly acknowledged and validated. Setting this flag plays a key role in differentiating the properly processed CCS message from a potentially injected one. Later operations in the handshake process can check this flag to ensure that any subsequent actions (such as processing the Finished message) only occur if the CCS message was securely received.

Right after setting the flag, the repair continues by calling the ssl3_get_finished() function and performs an error check on its return value. If ssl3_get_finished() returns a non-positive value, the handshake is immediately terminated, preventing any further processing in a compromised state.

After successful processing of the finished message, the handshake stage is updated to HandshakeStates.SSL_ST_OK, which indicates that the handshake has completed securely. This state update, combined with the earlier flag initialization, ensures that both CCS validation and the handshake processing follow a secure, well-defined sequence.

Overall, this repair fixes the vulnerability by ensuring that the CCS message is explicitly validated before any sensitive operations (like retrieving the Finished message) are performed. Setting the flag eliminates ambiguity in state handling and prevents any scenario where an attacker might manipulate the handshake process to end up with an insecure state, such as using a zero-length master key.
