Below is one example of a patch that verifies the handshake was not “spoofed” via a bogus ChangeCipherSpec message. In this fix we add an extra check after processing the Finished message to ensure that a master key was properly established (i.e. that its length is non‐zero) before marking the handshake as complete. (In a full implementation you might also want to move earlier the “CCS received” flag‐setting logic so that ChangeCipherSpec records are accepted only in the proper order.) 

For example, originally the buggy code was:

------------------------------------------------------
            case HandshakeStates.SSL3_ST_CR_FINISHED_A:
            case HandshakeStates.SSL3_ST_CR_FINISHED_B:
                System.out.println("Client: In Finished state, setting CCS_OK");
                ret = ssl3_get_finished();
                if (ret <= 0)
                    return ret;
                state.handshakeStage = HandshakeStates.SSL_ST_OK;
                break;
------------------------------------------------------

A repaired version might look like this:

------------------------------------------------------
            case HandshakeStates.SSL3_ST_CR_FINISHED_A:
            case HandshakeStates.SSL3_ST_CR_FINISHED_B:
                System.out.println("Client: In Finished state, processing Finished message");
                ret = ssl3_get_finished();
                if (ret <= 0)
                    return ret;
                // Verify that a valid master key was established.
                // (In practice, state.masterSecret would have been set previously.
                //  Reject the handshake if its length is zero.)
                if (state.masterSecret == null || state.masterSecret.length == 0) {
                    System.err.println("Error: Finished message processed with zero-length master key!"
                                       + " Possible CCS injection attempt. Aborting handshake.");
                    return -1; // or an appropriate error-code/exception
                }
                // (Optional extra logic: check that the CCS was received exactly once and in order.)
                state.handshakeStage = HandshakeStates.SSL_ST_OK;
                break;
------------------------------------------------------

Explanation of the changes:

1. After calling ssl3_get_finished(), we now check that the established master key (here represented by state.masterSecret) is non‑null and non‑empty. This extra validation ensures that, even if a man‑in‑the‑middle sent a spurious ChangeCipherSpec (CCS) message to force a zero‑length master key, the handshake will be aborted.

2. (Optionally you might also verify that CCS messages are processed in the expected order. For example, by maintaining a flag such as state.ccsReceived and ensuring that a CCS message is accepted only once during the handshake. That extra check isn’t shown here but is part of a complete fix.)

This patch prevents an attacker from injecting a CCS message that would corrupt the key material, thereby mitigating the “CCS Injection” vulnerability.
