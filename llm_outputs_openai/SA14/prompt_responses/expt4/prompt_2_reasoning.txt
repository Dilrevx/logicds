The repair introduces a critical step that explicitly marks a ChangeCipherSpec (CCS) message as allowed at the appropriate stage of the TLS handshake, addressing the CCS injection vulnerability.

Originally, when the client reached the Finished state, the code immediately proceeded towards obtaining the Finished message using the ssl3_get_finished() call. However, because there was no explicit flag to indicate that a CCS message was expected or acceptable at that point, an attacker could inject a CCS message at an opportune moment. This could trick the system into processing a crafted CCS, leading to potential use of a zero-length master key, a scenario that jeopardizes session security.

In the repair, before calling ssl3_get_finished(), the code sets a flag in the handshake state using a bitwise OR operation. Specifically, the flag (for example, HandshakeFlags.ALLOW_CCS) is enabled in state.flags. This flag acts as an explicit marker indicating that receiving a CCS message is legitimate during the handshake, but only in a controlled and expected manner.

By performing this flag setting:

1. It notifies other parts of the TLS handshake implementation that a CCS message is now expected and should be treated as valid.
2. It prevents any unsolicited or premature CCS messages from being processed. Since any later verification steps would reference this flag, they would only consider CCS messages legal if this flag is set.
3. It removes the ambiguity that existed in the original code, where a CCS could be processed without explicit permission.

After setting the flag, the code calls ssl3_get_finished() to properly retrieve the Finished message. If this call fails (indicated by a return value less than or equal to zero), the function aborts further processing. Only after successfully obtaining the Finished message does the code set the handshakeStage to a state that indicates the handshake is complete (SSL_ST_OK). This sequence ensures that the CCS validation flag is only active during the appropriate phase of the handshake.

In effect, this repair prevents a scenario where a man-in-the-middle could exploit the handshake timing by injecting a CCS message too early or incorrectly. The flag serves as an internal checkpoint that helps the system differentiate between expected and malicious CCS messages. Consequently, it ensures that session keys are derived correctly and that the handshake follows a secure sequence, thereby mitigating the risk associated with the CCS injection vulnerability.

By adding an explicit control flag, the repair makes the protocol stricter about when a CCS message is allowed, directly addressing the vulnerability and enhancing the overall security of the TLS connection.
