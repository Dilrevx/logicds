The repair adds a control flag (SSL3_FLAGS_CCS_OK) to ensure that ChangeCipherSpec (CCS) messages occur only when they’re expected. Here’s how the repair works:

1. At the start of the handshake (case 0), before sending ClientHello, the code sets the CCS_OK flag on the state. This indicates that the protocol expects a properly ordered CCS message later in the handshake. This prevents any unexpected or out-of-order CCS messages from being accepted.

2. In the handling of the Finished message states (SSL3_ST_CR_FINISHED_A and SSL3_ST_CR_FINISHED_B), the code now checks whether the CCS_OK flag is set. If the flag is not set, an exception is thrown stating that an unexpected ChangeCipherSpec was received. This verification step stops manipulated or replayed CCS messages from progressing the handshake.

3. Once the CCS message is verified and processed for the correct state, the code clears the flag using a bitwise operation. Clearing the flag ensures that a duplicate or unanticipated CCS message cannot be processed later. This adds robustness to the state management preventing potential replay attacks where an attacker might trigger a zero-length master key by resending a CCS.

4. The rest of the handshake continues as before. The Finished message is processed, the handshake state is set to OK, and eventually the handshakeComplete flag is set when the handshake finalizes.

In summary, by requiring that the CCS message be explicitly expected (via the flag) and then invalidating any unexpected CCS message events, the repair prevents the exploitation scenario where an attacker could inject a CCS message into the handshake. This counters the CCS Injection vulnerability that allowed the use of a zero-length master key (or hijacked sessions) in certain crafted TLS handshakes.

Thus, the key improvements here are:
• Introducing and managing a flag to indicate expected CCS messages.
• Rejecting CCS messages that arrive out-of-order.
• Clearing the flag after processing the valid CCS, ensuring a one-time use.

Together, these modifications help mitigate the vulnerability by enforcing strict ordering and preventing unauthorized activation of the ChangeCipherSpec message, thereby enhancing the protocol’s robustness against man-in-the-middle attacks.
