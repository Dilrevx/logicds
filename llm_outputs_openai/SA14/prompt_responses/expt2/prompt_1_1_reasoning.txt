The repair introduces a crucial check for the valid reception of a ChangeCipherSpec (CCS) message before processing the Finished message. The vulnerability known as the “CCS Injection” issue is centered around the possibility that, in some circumstances, a crafted TLS handshake could trick the protocol into accepting a Finished state without a preceding valid CCS. When this happens, the normal assumptions made about the master key being appropriately negotiated can be subverted, potentially allowing man-in-the-middle attackers to use a zero-length master key or otherwise compromise the session.

In our repair, we add an explicit condition: if the state.ccsReceived flag is not set, the routine emits an error message and aborts further processing by returning an error code (in our case, -1). This check is designed to ensure that the Finished message is not processed until a valid CCS has been received. This maintains the proper sequence in the TLS handshake and prevents the undesirable state of advancing the handshake without ensuring that the CCS has been confirmed.

By including the if (!state.ccsReceived) conditional, the repair is directly addressing the vulnerability. The existence of this flag acts as a guard, verifying that the connection state has reached the point where a valid CCS has been left intact appropriately. Without such a guard, malicious actors might be able to inject a forged CCS message or bypass the CCS check entirely, as previously observed in the OpenSSL vulnerability described.

Furthermore, by logging the error using System.err.println, we improve the visibility of any potential issues in the handshake sequence. This error log helps with debugging and provides an audit trail of handshake failures, which could be vital in recognizing ongoing or attempted exploits. It reinforces the idea that a CCS must come before the Finished message and if not, the handshake cannot be considered secure, thus aborting the process before any damage might occur.

Following the conditional check, if the state.ccsReceived flag is valid, the code then proceeds to retrieve the finished messages via ssl3_get_finished(), which is the logical next step in the handshake process. Only after these messages are successfully handled does the state update to HandshakeStates.SSL_ST_OK. This ensures that every step of the handshake happens in the correct order and under the correct security assumptions.

In essence, the repair tightens the handshake process by validating preconditions before allowing state advancement. It prevents a major fault in the security architecture by ensuring that any deviation from the expected handshake sequence results in a handshake termination rather than progressing with compromised parameters. Overall, this adjustment is a clear example of how security-critical code must be vigilant about the sequence of events in cryptographic negotiations to mitigate the risk of protocol-level attacks such as CCS Injection.
