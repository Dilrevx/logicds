The repair centers on explicitly acknowledging and validating the ChangeCipherSpec (CCS) message before continuing with the finished processing. In the original code, when the state entered either SSL3_ST_CR_FINISHED_A or SSL3_ST_CR_FINISHED_B, the process immediately moved forward into handling the “finished” message by calling ssl3_get_finished(). However, by doing so, it did not explicitly track or confirm that the CCS phase had been securely completed. This omission left open the possibility for an attacker to inject a CCS message inappropriately. An attacker, by injecting a maliciously crafted CCS message, might be able to trigger the use of a zero-length master key in certain handshake scenarios, thereby compromising session security and potentially leading to severe exploitation, such as session hijacking or gaining access to confidential data.

The chosen repair introduces an explicit step that sets a dedicated flag indicating that the CCS message has been validated. Specifically, we update the state’s internal flags by OR-ing with the CCS_OK bit. This explicit flag “marks” that the CCS phase is indeed secure, ensuring that any subsequent handshake processing is only carried out if the CCS message was received and processed under expected conditions. By integrating the flag update, we enforce a strict protocol ordering guarantee: only after the CCS message is confirmed as secure do we proceed with processing the finished message. This design adds a layer of defense that anticipates potential CCS injection attacks, effectively ensuring that simply reaching the finished state without the proper CCS verification does not imply a secure handshake.

Furthermore, once the CCS_OK flag is set, the code logs this checkpoint by printing a confirmation message. This serves as both a debugging aid and a verification step that the repair logic is being executed. Following this explicit acknowledgment of a secure CCS phase, ssl3_get_finished() is called. This function is critical because it processes the finished message that finalizes the handshake and sets the session’s security parameters. After the finished message is processed, the return value from ssl3_get_finished() is checked. If any error occurs—indicated by a return value of zero or negative—the function will immediately halt further processing. This ensures that if the finished message cannot be processed correctly (perhaps due to an underlying issue that might signify an attack or misconfiguration), the handshake stops, preventing further compromise.

Finally, after all the security checks have passed and the CCS phase has been safely validated, we update the handshake state to indicate that the handshake has been successfully completed by setting the state to SSL_ST_OK. This final update is crucial because it signals that all the preliminary stages, including the properly validated CCS message, have been processed without issue, thereby allowing secure communication to continue.

In summary, the repair methodically ensures that the CCS phase is not implicitly assumed to be secure based only on reaching a certain state. Instead, it explicitly marks and tracks the secure processing of the CCS message. This explicit marking – set via a safe CCS_OK flag – provides a safeguard against CCS injection vulnerabilities, ensuring that only a properly validated finished message is accepted, effectively preventing an attacker from leveraging a CCS injection to compromise session integrity.
