The repair adds an explicit check to ensure that the plain (i.e., unauthenticated) integrity algorithm – represented by NIA0 – is not accepted when processing the Security Mode Command. This is critical because accepting NIA0 bypasses the NAS layer security activation, which forms the basis of secure communication. By doing so, the mobile network could be compromised, as it would allow unprotected exchanges, potentially opening the door to various attacks including impersonation or replay attacks.

Initially, the code was setting ctxt_base.cipher_algo and ctxt_base.integ_algo by extracting values from the received Security Mode Command's selected NAS security algorithms. However, there was no additional validation on the integrity algorithm after it was set. Consequently, even if the UE (User Equipment) selected NIA0, which effectively means using a non-secured or plain algorithm, the code would proceed with the rest of the activation process. This vulnerability could be exploited to bypass the intended security measures that are supposed to enforce robust encryption and integrity protection.

The repair introduces a check immediately after setting the ciphering and integrity algorithms. It evaluates whether ctxt_base.integ_algo is equal to IntegrityAlgorithmIdEnum.NIA0. If this condition is met, the system does not proceed further with the security mode activation. Instead, it takes two key remedial actions: First, it logs a warning message that clearly states the reason for the rejection (“Rejecting Security Mode Command: Plain (NIA0) integrity algorithm not permitted”). This logging is vital from an operational perspective, as it allows network operators or engineers to diagnose and monitor instances where insecure settings are attempted. Second, it calls the send_security_mode_reject function with the cause code Cause5gmmType.Cause.inappropriate_integrity_protection, halting the processing by returning an error code SRSRAN_ERROR.

In addition, the check is added immediately after verifying the integrity parameters. This ordering is crucial: the integrity check occurs before further context processing and before comparing the replayed UE security capabilities. Thus, any attempt to use a non-secure integrity option is detected as early as possible. Early detection and appropriate rejection of insecure options help in reducing the attack surface and prevent further processing that might compromise security.

The security mode reject response is a standard behavior when the network determines that the security capabilities provided by the UE are inadequate or insecure. By explicitly rejecting the command when NIA0 is detected, the code ensures that the mobile network does not accept configurations that bypass integrity protection. It enforces a stronger security posture by ensuring that only the approved, robust integrity algorithms are used.

Lastly, the rest of the code remains unchanged. After handling the integrity check, the subsequent conditions (such as checking replayed security capabilities and initializing the security command counters) continue as normal if all security conditions are satisfied. This careful incorporation ensures that the overall system behavior is preserved, except for the high-priority requirement of not allowing NIA0, which is the root cause of the vulnerability described.

Overall, this repair enhances the security of the NAS layer by preventing the acceptance of an insecure integrity algorithm, thereby ensuring that the critical security activation process is not bypassed.
