The repair modifies each of the conditional checks so that if a key is expected (by the signature algorithm in use) but not actually present or verified, the code logs an error message and then immediately terminates the connection by calling the ERROR_OUT macro. Here’s a walkthrough of the changes:

1. For ED25519, ED448, and ECC signature algorithms, the original code merely logged an error message when the peer-sent key wasn’t present in the verification context. However, this logging alone does nothing to stop the potentially malicious or inconsistent state from being used in the handshake. In this repair, after logging the error message (with a more descriptive output), an ERROR_OUT call is added. This effectively aborts the handshake if the expected key is missing.

2. In the RSA section, the code already terminates the connection if a PKCS#1.5 signature is detected. The repair also adds an ERROR_OUT call in the RSA-PSS check if the RSA key is either NULL or not marked as present in the verification context. This ensures that the vulnerability isn’t exploited by allowing an unverified or absent RSA key to proceed.

3. The vulnerability described involves a man-in-the-middle (MitM) attacker impersonating a TLS 1.3 server. One potential exploitation vector in the earlier versions was that if the peer sent a key (for ED25519, ED448, or ECC) but it wasn’t properly set up or verified (an inconsistency that a MitM attacker could exploit), the connection would still be accepted after merely logging a warning. By modifying the code to actually terminate the connection via ERROR_OUT when such inconsistencies are detected, any anomaly that could indicate an attack is immediately acted upon, preventing the handshake from completing.

4. This uniform behavior across all crypto types (ED25519, ED448, ECC, and RSA) helps ensure that a single weakness in key validation is not leaving an opening for impersonation. In other words, the repair enforces strict authentication checks. If the expected key is not present, the session is aborted, which directly addresses the authentication bypass vulnerability that could be exploited by a MitM attacker.

Overall, the fix ensures that the protocol does not proceed when an expected key is absent or invalid. This stops any attack vector that relies on bypassing or skipping key verification, thereby mitigating the risk of a MitM attack on TLS 1.3 clients.
