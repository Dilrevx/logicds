Below is one way to repair the vulnerable code. In the original snippet, only the RSA (PKCS#1.5) case explicitly returns an error when the corresponding public key isn’t available. For some TLS 1.3 signature algorithms the failure to verify that the expected key is present (for example, for ED25519, ED448, ECC, or even RSA-PSS) can let an attacker bypass authentication. To fix this vulnerability the code must actively reject a connection when the signature algorithm was negotiated but the corresponding public key is missing. One repair is to change the logging‐only cases to also return an error. For example:

-------------------------------------------------
#ifdef HAVE_ED25519
    if (args->sigAlgo == ed25519_sa_algo && !ssl->peerEd25519KeyPresent) {
        WOLFSSL_MSG("Error: ED25519 key missing from peer data");
        ERROR_OUT(INVALID_PARAMETER, exit_dcv);
    }
#endif

#ifdef HAVE_ED448
    if (args->sigAlgo == ed448_sa_algo && !ssl->peerEd448KeyPresent) {
        WOLFSSL_MSG("Error: ED448 key missing from peer data");
        ERROR_OUT(INVALID_PARAMETER, exit_dcv);
    }
#endif

#ifdef HAVE_ECC
    if (args->sigAlgo == ecc_dsa_sa_algo && !ssl->peerEccDsaKeyPresent) {
        WOLFSSL_MSG("Error: ECC key missing from peer data");
        ERROR_OUT(INVALID_PARAMETER, exit_dcv);
    }
#endif

#ifndef NO_RSA
    if (args->sigAlgo == rsa_sa_algo) {
        WOLFSSL_MSG("Error: PKCS#1.5 signature not allowed in TLS 1.3");
        ERROR_OUT(INVALID_PARAMETER, exit_dcv);
    }
    if (args->sigAlgo == rsa_pss_sa_algo &&
            (ssl->peerRsaKey == NULL || !ssl->peerRsaKeyPresent)) {
        WOLFSSL_MSG("Error: RSA key missing from peer data for RSA-PSS");
        ERROR_OUT(INVALID_PARAMETER, exit_dcv);
    }
#endif
-------------------------------------------------

Explanation of the changes:
1. For ED25519, ED448, and ECC, we now call ERROR_OUT (or your equivalent error handling code) when the expected peer key is missing rather than just logging a message.
2. For RSA-PSS, the absence of a peer RSA key now also triggers an error.
3. This approach ensures that when a peer indicates use of a signature algorithm, the proper key must be present. Without it, we abort the handshake to prevent a potential man-in-the-middle attack.

This fix prevents attackers from exploiting the connection by impersonating a TLS 1.3 server when the crucial key verification step fails.
