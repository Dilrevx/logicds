The implementation of PEAP in wpa_supplicant allows authentication bypass. For a successful attack, wpa_supplicant must be configured to not verify the network's TLS certificate during Phase 1 authentication, and an eap_peap_decrypt vulnerability can then be abused to skip Phase 2 authentication. The attack vector is sending an EAP-TLV Success packet instead of starting Phase 2. This allows an adversary to impersonate Enterprise Wi-Fi networks.

<repair_description>
The repair modifies the branch that handles a virus-like condition in which the implementation erroneously accepts a successful Phase 2 authentication based solely on receiving an EAP-TLV “Success” indication. In the original code, if the status was marked “success,” the system simply checked whether a previous failure had been forced. If not, it unconditionally marked the authentication as successful. This allowed an attacker to bypass actual Phase 2 verification if the supplicant was not configured to verify TLS certificates.

To fix this, the repair introduces an extra validation step that explicitly confirms whether the data provided during Phase 2 authentication meets all necessary security requirements. This extra check is implemented by calling an auxiliary function that determines if the Phase 2 authentication was sufficiently completed. The function analyzes the current state of the security module and Phase 2 data to verify that the authentication has been done correctly and meets necessary security policies.

If the function indicates that the Phase 2 process was insufficient, the repair code logs an informative message alerting that although the server signaled a successful Phase 2 result via the EAP-TLV “Success” packet, the actual authentication details do not meet the necessary security completeness. As a result, the code marks the Phase 2 authentication as failed. This prevents the system from erroneously accepting an incomplete or manipulated Phase 2 handshake, thereby closing the vulnerability that allowed an adversary to force a successful authentication with a spoofed message.

If the extra check confirms that Phase 2 was executed properly and meets all requirements, the code then proceeds to mark the authentication as successful just as it would have in the original path. This ensures that valid authentication attempts can still complete normally while mitigating the risk of bypassing security due to the vulnerability.

Overall, these repair steps strengthen the authentication process by not relying solely on the server’s indication of success. They defend against situations where an attacker might trick wpa_supplicant into believing that a successful Phase 2 authentication has occurred by simply sending an arbitrary “Success” message. By requiring a proper, detailed validation of Phase 2, the security of the enterprise Wi-Fi network is preserved.

In summary, the patch adds a methodical verification process right after receiving a success indication. It logs the event, checks for any forced failure, and then performs an additional check using the Phase 2 sufficiency function. Based on this evaluation, it decides whether to accept or reject the authentication. This series of steps ensures that the device does not complete authentication prematurely or based on manipulated messages, thereby mitigating the previously exploitable vulnerability in the EAP-PEAP process.
