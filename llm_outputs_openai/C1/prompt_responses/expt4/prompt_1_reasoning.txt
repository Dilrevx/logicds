The vulnerability arises because X509_verify_cert() may return a negative value when an internal error occurs, such as an out‐of‐memory error. The OpenSSL library then mishandles this negative number, leading to the propagation of an unexpected error code (SSL_ERROR_WANT_RETRY_VERIFY) that applications are not prepared to process. This can lead to incorrect behavior or further complications in the SSL handshake process.

In our repair, we check if the verification result (i) from X509_verify_cert() is negative. The revised code looks like this:

• If an application-provided verification callback is present, the code calls that callback.
  
• Otherwise, the code calls X509_verify_cert(ctx) and stores its result in variable i.
  
• Immediately after calling X509_verify_cert(), we check whether i is less than 0. If it is, that indicates an internal error during certificate verification.

• Instead of propagating this negative value, which could cause the SSL connection routines to behave incorrectly, we set i to 0. Setting i to 0 forces a failure in the verification process without leaving behind an internal error state that propagates unexpected error codes.

This repair fixes the vulnerability because it prevents the negative error code from being interpreted as SSL_ERROR_WANT_RETRY_VERIFY by later components in the OpenSSL code. By ensuring that i is non-negative (specifically resetting negative results to 0), the SSL handshake process handles the error as a generic certificate verification failure, a situation that application developers expect and can handle gracefully.
