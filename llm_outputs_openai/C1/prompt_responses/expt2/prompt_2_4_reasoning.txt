The vulnerability occurs because the original code did not account for the possibility that X509_verify_cert() might return a negative value. Such negative values can occur when an internal error is encountered during certificate verification, for example due to an allocation failure or other internal issues. Negative return values from this function were not expected by the rest of the code, which assumed that only a zero or a positive value would be returned. In OpenSSL’s design, a negative value is later interpreted as an indicator that a handshake function, like SSL_connect() or SSL_do_handshake(), needs a retry, represented by SSL_ERROR_WANT_RETRY_VERIFY. However, this error signal is meant only for cases where a custom certificate verification callback is used. For the usual case, where no callback is provided, the handshake process does not expect to deal with a retry condition and could end up handling the error in an unpredictable manner.

The repair addresses this by clarifying what happens when no custom verification callback is available. The code keeps the logic intact for the scenario where a callback is provided, by calling s->ctx->app_verify_callback() and using its result. However, when there is no custom callback set, the code then falls back to the internal X509_verify_cert() function and immediately inspects its return value. If the verification result is negative—thereby indicating that an internal error occurred—the repair converts this result to a standard failure signal (zero) before the function returns. This conversion is crucial because it normalizes the error state. By turning a negative result into zero, which conventionally indicates that the certificate verification failed, the code ensures that the calling functions interpret the error correctly. Zero is an expected and conventional value to indicate a verification failure, rather than an internal error that might be misconstrued as requiring a handshake retry.

The motivations behind this change are rooted in achieving more robust and predictable behavior during the handshake. Multi-layered protocols like SSL/TLS are highly sensitive to error conditions, and even minor discrepancies in error reporting can lead to unexpected behaviors. The misinterpretation of a negative result by the handshake process could lead to a situation where applications not designed to handle a retry condition might mismanage the failure. Specifically, returning SSL_ERROR_WANT_RETRY_VERIFY from SSL_get_error() in contexts where no custom callback is implemented could trigger error-handling logic that is not suited for ordinary certificate verification failures, adding unnecessary complexity and potentially exposing the application to unstable error handling.

By adopting the repair, developers ensure that an internal error during certificate verification is uniformly treated as a straightforward verification failure rather than as a special case indicating the need for retries. This normalization not only simplifies downstream error processing but also avoids the risk of miscommunicating the error state to application-level code. Ultimately, the repair restores the intended semantics of certificate verification by explicitly checking the result and converting unforeseen negative values into a benign failure state, ultimately simplifying error handling and making the SSL/TLS handshake process more robust.
