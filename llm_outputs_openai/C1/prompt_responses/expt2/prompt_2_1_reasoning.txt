The negative return value was not correctly handled in the original implementation, leading to a misinterpretation in subsequent error handling. Specifically, if a negative value was returned, functions such as SSL_connect() or SSL_do_handshake() would see an unexpected SSL_ERROR_WANT_RETRY_VERIFY code when calling SSL_get_error(). This error code is designed solely for use when a custom verification callback is set, and its appearance in the default verification scenario confuses application logic.

Our repair introduces an additional check immediately after calling X509_verify_cert(ctx) in the default verification path. After obtaining the result in “i”, we test whether i is less than zero. This repair ensures that the error does not propagate as an unexpected signal to the handshake state machine, thereby avoiding misleading error propagation. With the negative value changed to zero, subsequent functions will uniformly interpret the condition as a certificate verification failure rather than an internal error.

This change is significant because it prevents the misdirection of error handling in the SSL handshake process. In effect, if an internal error occurs during certificate verification, the handshake will fail due to a verification failure. This behavior is far more predictable and manageable for applications that rely on the standard verification process. The alteration separates internal error handling from the error codes that are intended for situations where a custom callback is used. This separation aligns the error signaling with the expectations of most applications. It also maintains consistency across different parts of the SSL library, ensuring that the handshake state machine receives only those error hints that it is designed to handle in that particular context.
