Below is one example of how to patch the bug. In the original code the checks simply “pass‐through” for sigAlgo values that aren’t explicitly rejected. This means that if the server’s CertificateVerify message uses an algorithm that does not match the one in the Certificate message (for example, right now no “default” error is returned for an unknown or mismatched algorithm) then the verification can be bypassed. The fix is to explicitly ensure that if none of the expected signature algorithms (with matching certificate key) is in effect then the connection is rejected.

One way to repair it is to add a final “else” clause that catches any unsupported or mismatched algorithm. For example, the patched code could be:

------------------------------------------------------------
                if (args.sigAlgo == CommonsConstants.ed25519_sa_algo && !ssl.peerEd25519KeyPresent) {
                    Wslib.WOLFSSL_MSG("Peer sent ED25519 sig but not ED25519 cert");
                    return CommonsConstants.SIG_VERIFY_E;
                } else if (args.sigAlgo == CommonsConstants.ed448_sa_algo && !ssl.peerEd448KeyPresent) {
                    Wslib.WOLFSSL_MSG("Peer sent ED448 sig but not ED448 cert");
                    return CommonsConstants.SIG_VERIFY_E;
                } else if (args.sigAlgo == CommonsConstants.ecc_dsa_sa_algo && !ssl.peerEccDsaKeyPresent) {
                    Wslib.WOLFSSL_MSG("Peer sent ECC sig but not ECC cert");
                    return CommonsConstants.SIG_VERIFY_E;
                } else if ((args.sigAlgo == CommonsConstants.falcon_level1_sa_algo ||
                           args.sigAlgo == CommonsConstants.falcon_level5_sa_algo) &&
                           !ssl.peerFalconKeyPresent) {
                    Wslib.WOLFSSL_MSG("Peer sent Falcon sig but corresponding cert is missing or does not match");
                    return CommonsConstants.SIG_VERIFY_E;
                } else if (args.sigAlgo == CommonsConstants.rsa_sa_algo) {
                    Wslib.WOLFSSL_MSG("Peer sent PKCS#1.5 RSA sig but certificate does not support it");
                    return CommonsConstants.INVALID_PARAMETER;
                } else if (args.sigAlgo == CommonsConstants.rsa_pss_sa_algo &&
                           (ssl.peerRsaKey == null || !ssl.peerRsaKeyPresent)) {
                    Wslib.WOLFSSL_MSG("Peer sent RSA-PSS sig but certificate does not support it");
                    return CommonsConstants.SIG_VERIFY_E;
                } else {
                    // Catch-all for unsupported or mismatched signature algorithms.
                    Wslib.WOLFSSL_MSG("Peer sent an unsupported or mismatched signature algorithm");
                    return CommonsConstants.SIG_VERIFY_E;
                }
------------------------------------------------------------

Explanation of the changes:
1. The original code did checks for several known algorithms but would otherwise (if none of the if conditions apply) continue processing. An attacker could choose a sig_algo that isn’t explicitly rejected.
2. By adding the final else-clause that unconditionally rejects any signature algorithm not matching with the provided certificate keys, we ensure that a discrepancy between the certificate’s public key type and the signature algorithm is never accepted.
3. This helps to ensure that the certificate in the handshake actually supports the provided certificate_verify signature.

This patch addresses the vulnerability by preventing bypassing of certificate checks when the sig_algo does not match the certificate’s corresponding public key.
