The repair first derives which public key type is present in the peer’s certificate by evaluating flags (for example, checking for an Ed25519 key, an Ed448 key, an ECC DSA key, a Falcon key, or an RSA key). Instead of checking each signature algorithm in isolation, it uses the certificate’s key information to determine what signature algorithm should be used. This prevents an attacker from exploiting the original code structure—which allowed a mismatch between the provided signature algorithm and the actual certificate key type—to bypass security checks.

For each type of key, the repair assigns the expected signature algorithm. When a Falcon key is detected, the repair only accepts one of the two allowed Falcon signature levels. It specifically checks if the provided signature algorithm is one of these two; if not, the repair rejects the connection. Similarly, for RSA keys, only RSA-PSS is considered valid. The repair explicitly rejects the older PKCS#1.5 algorithm, which mitigates the risk associated with using unsupported or less secure algorithms.

After determining the expected signature algorithm, the repair compares it with the signature algorithm specified in the input (for example, coming in the certificate_verify message). If they do not match, then the function logs an error indicating a mismatch between the certificate key type and the signature algorithm and returns an error. Only if they match does the function accept the input as valid.

This approach significantly improves security because it enforces that the signature algorithm in the certificate_verify message exactly corresponds to the type of key present in the peer’s certificate. Previously, an attacker might have manipulated the signature algorithm parameter without matching what was actually in the certificate, potentially bypassing verification. Now, the check is centralized: the expected algorithm derived from the certificate is directly compared to the provided one. If there is any discrepancy, the session is aborted early.

In summary, the repair fixes the vulnerability by:

• Deriving the expected signature algorithm from the actual certificate key rather than checking signature algorithms individually.
• Explicitly handling cases like Falcon and RSA by supporting only the secure and intended signature algorithms.
• Enforcing a strict match between the derived expected signature algorithm and the one provided.
• Preventing an attacker from using a mismatched algorithm to bypass certificate verification, thus ensuring the certificate’s integrity and the connection’s security.
