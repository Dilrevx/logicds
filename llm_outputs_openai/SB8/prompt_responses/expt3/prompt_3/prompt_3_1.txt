Below is one way to fix the issue. The problem is that if the TLS 1.3 client receives neither a PSK nor a key share extension, the code “falls back” to using an all‐zero (predictable) buffer for the IKM. The repair is to detect when neither extension is present and abort (or at least do not use a predictable default value) rather than continuing with an insecure IKM. One acceptable solution is to add a check that if both the PSK and Key Share extension are missing the handshake fails with an appropriate error. For example, you could modify the code as follows:

--------------------------------------------------
/* Revised code snippet (example repair) */
if (extMsgType[0] == CommonsConstants.server_hello) {
    PreSharedKey psk = null;
    // Look up the PSK extension if present
    TlsExtension pskExt = TLSX.find(ssl.extensions, CommonsConstants.TLSX_PRE_SHARED_KEY);
    if (pskExt != null)
        psk = (PreSharedKey) pskExt.data;

    // Skip over any non-chosen PSK entries; choose the active one
    while (psk != null && !psk.chosen)
        psk = psk.next;

    // In TLS 1.3, the server must send either a PSK extension or a Key Share extension.
    TlsExtension keyShareExt = TLSX.find(ssl.extensions, CommonsConstants.TLSX_KEY_SHARE);
    
    // Abort the handshake if both extensions are missing,
    // preventing the use of a default predictable IKM value.
    if (psk == null && keyShareExt == null) {
        // Option 1: return an error code indicating the handshake must be terminated.
        return fatalError(ssl, TLS_ALERT_MISSING_EXTENSION,
                          "TLS1.3 handshake aborted: neither PSK nor Key Share extension provided");
    }

    if (psk != null) {
        int ret = SetupPskKey(ssl, psk, 0);
        if (ret != 0)
            return ret;
        ssl.options.pskNegotiated = true;
    }
    else {
        // Process key share based handshake if PSK is not provided.
        // For example, call a function to derive keys from the key share data.
        int ret = SetupKeyShareKey(ssl, keyShareExt);
        if (ret != 0)
            return ret;
    }

    ssl.keys.encryptionOn = true;
    ssl.options.serverState = CommonsConstants.SERVER_HELLO_COMPLETE;
}
--------------------------------------------------

Explanation of the Repair:

1. Two separate extensions are looked up – one for PSK and one for Key Share.
2. If both are missing, the connection is aborted (or an alert is issued) rather than using any default IKM buffer.
3. If one of them is found, you proceed with the appropriate key derivation (either SetupPskKey or SetupKeyShareKey).
4. This prevents an attacker from forcing the client to use a default (predictable) IKM value, which if known to an attacker would compromise the session keys.

(This is one acceptable repair. In a production environment you would choose whether to abort the handshake outright or perform another safe operation—using a secure randomly generated IKM instead of a predictable one. However, simply aborting is usually the cleanest solution.)
