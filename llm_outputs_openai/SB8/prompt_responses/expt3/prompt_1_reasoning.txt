The repair adds a critical TLS 1.3 version check before defaulting to an insecure fallback. Originally, when no valid PSK was found, the code would simply disable session resumption and zero out the PSK key buffer. While acceptable for legacy TLS (versions prior to 1.3), this posed a risk in TLS 1.3. In TLS 1.3, both a PSK and key share extension must be present to safely compute the IKM. Without them, using a predictable buffer (like one with all zeros) could lead to compromised session keys.

In the repaired code, after the PSK search loop, if no valid PSK is found, we now check if the TLS version is 1.3 by comparing ssl.version with CommonsConstants.VERSION_TLS13. If the session is operating under TLS 1.3, the code immediately aborts the handshake by returning a TLS handshake failure alert (using CommonsConstants.TLS_ALERT_HANDSHAKE_FAILURE). This prevents the TLS stack from using a default, predictable IKM value for key derivation.

For legacy TLS versions, the new check is bypassed. In those cases, the behavior remains unchanged: the code resets session resumption parameters, clears the PSK key buffer, and continues, as this fallback mechanism is acceptable for versions that are not impacted by the vulnerability.

By enforcing an abort for TLS 1.3 connections that lack both the PSK and the required key share extension, the repair effectively prevents the possibility of a predictable IKM being used. This change safeguards against an attacker who could otherwise manipulate the negotiation process to trigger the fallback, which might lead to an insecure session key derivation and potentially allow the eavesdropper to reconstruct the master secret.

In summary, the repair adds a condition specifically for TLS 1.3: if no valid PSK is present, instead of continuing with an insecure predictable default, the handshake is terminated. This targeted abort stops insecure sessions from ever using known or predictable values in the master secret derivation, thereby mitigating the vulnerability described.
