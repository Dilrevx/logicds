The repair addresses the vulnerability by ensuring that the code does not use a predictable IKM (Input Keying Material) in the absence of both the PSK (pre shared key) and key share extensions during a TLS 1.3 handshake. In previous versions, if neither extension was present, the code would fall back on a default (zeroed-out) buffer. This predictable value could be exploited by an attacker to compromise the master secret, potentially allowing them to reconstruct encryption keys and intercept or modify the session’s data.

The first step in the repair involves locating the PSK extension within the list of TLS extensions. The code uses a helper function, TLSX.find, to search for the PSK extension. Once found, it iterates through the linked list of PSK objects to identify the one that has been “chosen” (i.e., the one that the client intends to use). If a suitable PSK is found, the function SetupPskKey is called to derive the session key from the PSK information. This is the expected behavior when a valid PSK is present.

However, the repair introduces an important additional check by also looking for the key share extension. The key share extension is vital in TLS 1.3 as it enables the use of ephemeral Diffie-Hellman key exchange parameters, ensuring that the derived session keys are strongly unpredictable. By performing another TLSX.find for the key share extension, the repair ensures that even if the PSK extension is missing, the presence of a key share extension would still allow the secure derivation of key material through an ephemeral key exchange.

The crucial part of the repair is the conditional check: if both the PSK and key share extensions are missing, the handshake is aborted by returning an error code (TLS_ERR_MISSING_REQUIRED_EXTENSION). This decision prevents the handshake from continuing with a fallback to a default (and predictable) IKM, which fixes the vulnerability. Rather than continuing with zeroed or predictable key material, the handler now safely aborts the connection, preventing any potential exploitation by an attacker capable of controlling one end of the communication.

If a PSK is found, the repair continues similarly to how the buggy code originally handled it: calling SetupPskKey, checking for errors, setting appropriate flags, and enabling encryption. However, if the PSK is absent but a key share extension is present, the repair calls SetupKeyShare. This indicates that the session will use key share parameters to generate session keys securely through the ephemeral Diffie-Hellman key exchange mechanism. In this branch, the PSK negotiation flag is set to false, differentiating this path from a PSK-based session.

Overall, the repair is designed to eliminate the fallback to default predictable keying material and ensure that either a valid PSK or a secure key share is used to derive session keys. This change directly mitigates the vulnerability by eliminating the scenario where a handshake could succeed using insecure, predictable material, thereby safeguarding against eavesdropping or man-in-the-middle attacks tied to weak cryptographic setups in TLS 1.3 sessions.
