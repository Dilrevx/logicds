The vulnerability arises in the original implementation during the processing of the ServerHello message of a TLS 1.3 handshake. In that version, the code first attempts to negotiate a pre-shared key (PSK) by checking for a PSK extension and then selecting an appropriate PSK if one is present. If a valid PSK is found, it is used to perform further key derivation. Otherwise, the code resets the PSK key buffer to zeros and continues with the handshake. The inherent risk in this approach is that if neither a valid PSK nor a key share extension (necessary for Diffie-Hellman key exchange) is provided, the system proceeds using a default, predictable input key material (IKM) for generating the session master secret. This default IKM is predictable by an attacker and can lead to compromised session keys, enabling an eavesdropper to reconstruct the session keys and potentially tamper with message contents.

The repair introduces a crucial additional safeguard. After processing the PSK extension, the modified code now performs a second, explicit check: it verifies whether a valid PSK was negotiated (via the pskNegotiated flag) and whether key share information is available by checking the named_group parameter. The named_group is expected to hold an identifier for the key share extension, which represents the key share information needed for a Diffie-Hellman exchange. If the named_group is zero, it indicates that no key share extension was provided.

This additional validation step is essential for two reasons. First, it ensures that the handshake does not proceed with insecure, default key material. The use of a default predictable IKM could enable an adversary who is capable of interfering with or observing the handshake to derive the session keys. Second, by enforcing that at least one secure key exchange mechanism must be present (either a valid PSK or a provided key share), the repair adheres strictly to the cryptographic principles on which TLS 1.3 is based. In other words, the security of the session now strictly depends on receiving adequate key exchange material from the server, making it much harder for an attacker to force the connection into a state where predictable secret derivation occurs.

If both the PSK negotiation fails and the named_group check reveals the absence of a key share, the connection is immediately terminated by returning a specific error code (TLS_ERROR_MISSING_KEY_SHARE). This error code serves as an alert that the key exchange did not meet the necessary security requirements, preventing the creation of a session that might otherwise use a weak, predictable IKM.

By introducing this additional conditional check, the repair effectively mitigates the vulnerability by ensuring that an insecure key derivation can never occur as a result of missing or incomplete key exchange material. The secure TLS handshake now mandates that either a valid PSK or a proper key share extension is provided, thereby preserving the cryptographic integrity of the session master secret. This change fortifies the overall handshaking process against potential attacks where an adversary might otherwise exploit the fallback to a default IKM, thus ensuring a more robust TLS 1.3 connection.
