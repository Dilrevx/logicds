The main goal of our repair was to ensure that the TLS handshake only continues if either a valid Pre-Shared Key (PSK) or a key share extension (KSE) is present. In TLS 1.3, secure key derivation hinges on both parties contributing sufficient cryptographic material. If neither a valid PSK nor a key share is provided, the IKM (Input Keying Material) used to generate the session master secret might default to a predictable value. Such a situation could allow an attacker to derive the session keys, thereby compromising the security of the connection.

Initially, the original code locates the PSK extension sent by the server and then iterates through any linked list of potential PSK values until it finds one marked as "chosen" (valid). After exiting the loop, it checks if no valid PSK was found. In the case of a missing valid PSK, the code resets the PSK key buffer (by zeroing its contents) and indicates that the session is not resuming. However, this approach alone still allowed the handshake to continue even if the key share extension, which contributes the necessary randomness for key exchange, wasn’t provided. This could result in a default, predictable IKM value during the session key generation.

To address this vulnerability, the repair introduces an additional check that examines whether the key share extension has provided the necessary cryptographic information. This is done by checking the value of a variable representing the named group (ssl.keys.named_group). In TLS 1.3, the named group is used to indicate the key share associated with the Diffie-Hellman exchange, which contributes crucial entropy to the key derivation process. If ssl.keys.named_group equals zero, this indicates that no key share extension was provided by the server. 

By inserting an explicit condition that returns an error code (commonly one that indicates a missing extension) when no valid PSK is present and ssl.keys.named_group is zero, the repair stops the handshake process before insecure key material is used. This defensive programming measure ensures that the cryptographic security of the session cannot be undermined by proceeding with an insecure derivation. The code now includes:

  if (ssl.keys.named_group == 0)
   return CommonsConstants.TLS_ERROR_MISSING_EXTENSION;

This proactive check prevents the use of a default, predictable IKM, which could otherwise allow an attacker to derive session secrets. In essence, the handshake is only allowed to succeed if at least one of the two secure mechanisms (a valid PSK or a key share extension) contributes sufficient entropy to the key derivation process.

In summary, the change reinforces the TLS protocol's security by ensuring that the handshake does not complete under conditions where the session keys could be compromised. It explicitly enforces the requirement for adequate key exchange parameters—either a proper PSK or key share material. This extra safeguard guarantees that insecure practices like using a default IKM do not inadvertently weaken the entire TLS session security. The attack surface is thereby minimized, ensuring that both the client and server contribute robust entropy and that no predictable values are used in generating critical session keys.
