The repair addresses the vulnerability by removing the possibility of defaulting to a predictable IKM value when both PSK and key share extensions are absent. In previous versions, if a TLS 1.3 client connected to a malicious server that omitted both a PSK extension and a key share extension, the code would ultimately fall back to a default buffer for generating the IKM (Input Keying Material). This default buffer is predictable, and its known value could be exploited by an attacker to compromise the derived master secret. The repair eliminates this fallback behavior to ensure that insecure sessions are never established.

Firstly, the code modification includes additional logic to explicitly search for a key share extension by calling TLSX.find(ssl.extensions, CommonsConstants.TLSX_KEY_SHARE). This is important because TLS 1.3 can negotiate a session key either via a pre-shared key (PSK) or through a key share exchange. By adding this search for the key share extension, the code now properly handles both methods for establishing secure keying material.

Next, the repair introduces a conditional check: if both the PSK extension (or a valid chosen PSK) and the key share extension are absent, the handshake is aborted. This is done by returning an error code (e.g., -1), though this error code may need to be replaced with one appropriate for the surrounding system. The critical concept here is that if the client does not receive one of the acceptable extensions from the server, it should not generate a master secret from a default, insecure IKM value. By aborting the handshake, the repair guarantees that insecure sessions will not be negotiated.

Following the conditional check, the code proceeds to process the PSK extension if it is present. It iterates through the linked PSK objects to locate one that is marked as “chosen.” If a valid PSK is found, the SetupPskKey function is called to generate the key material using the chosen PSK. If the PSK is not found but the key share extension exists, the code now calls SetupKseKey. This ensures that instead of falling back to a default predictable IKM, the client uses the secure key share data to establish the session key. By clearly splitting the paths depending on which secure mechanism is available, the repair reinforces that the generation of the session master secret is never based on insecure, default inputs.

Furthermore, by setting ssl.options.keyShareNegotiated or ssl.options.pskNegotiated flags appropriately after a key is successfully established, the repair maintains the correct state in the session options. This state information is critical for subsequent protocol steps and ensures that the correct key derivation approach was used.

Finally, regardless of whether the PSK or key share path is taken, the session state is updated (ssl.options.serverState) and encryption is enabled (ssl.keys.encryptionOn). This ensures that the rest of the TLS handshake will proceed as expected using securely derived keys.

In summary, the repair eliminates the vulnerability by adding explicit checks for both critical key exchange mechanisms, rejecting the connection if neither is provided, and thereby guaranteeing that only securely negotiated keys are employed to derive the session master secret.
