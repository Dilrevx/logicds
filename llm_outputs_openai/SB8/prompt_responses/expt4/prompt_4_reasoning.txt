The repair adds an extra security check that ensures a TLS 1.3 session is only permitted to continue if there is either a successfully negotiated Pre-Shared Key (PSK) or valid key share material provided by the server. Here’s how the changes work:

1. First, the code inspects the server hello to locate and validate a PSK extension. It traverses through any chained PSK entries until it finds one marked as “chosen.” If no chosen PSK is available, it cleans out any previously set PSK keys and flags the connection as not resuming.

2. If a valid chosen PSK is found, the code calls SetupPskKey to configure the PSK-based key. A flag, ssl.options.pskNegotiated, is then set to true, indicating that PSK negotiation was successful.

3. The important fix comes immediately after the PSK handling. Before enabling encryption (and hence proceeding with the session), the code now checks whether either a PSK was negotiated or a valid key share is provided. This is achieved by verifying that either ssl.options.pskNegotiated is true or that ssl.keys.namedGroup (which represents the key share state) is nonzero.

4. If neither condition is met—which means there’s no secure key material used for key derivation—the function returns an error (TLS_ERR_MISSING_KEY_SHARE). This prevents the session from proceeding with a fallback on a default, predictable Input Key Material (IKM), which would compromise the cryptographic security of the session.

By adding this conditional check, the repair directly addresses the vulnerability where a malicious server could force the client into using a default buffer for IKM. Without either a valid PSK or a valid key share, the derived session master secret might be computed from predictable data, making it vulnerable to reconstruction by an attacker. 

Thus, the fix secures the TLS session by ensuring that encryption is only enabled when there is cryptographically secure input to derive the master secret. As a result, even if the PSK negotiation fails (or doesn’t happen), the existence of key share material is mandatory to continue, and if it’s absent (i.e., namedGroup remains zero), the handshake is terminated immediately with a clear error signal.

In summary, the repair mitigates the risk of using insecure, default IKM values by enforcing that one of the two secure elements—either a properly negotiated PSK or a valid key share—is present before proceeding. This precaution stops the formation of weak session keys and protects against surveillance or tampering by attackers who might otherwise exploit the predictable key material.
