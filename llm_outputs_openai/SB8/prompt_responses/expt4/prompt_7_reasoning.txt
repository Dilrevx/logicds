The repair adds an extra check to determine whether at least one of the required extensions (PreSharedKey or Key Share) is present. Here’s how it fixes the issue:

1. Checking for Both Extensions:
 • The original code only looked for a PreSharedKey (PSK) extension. If none was found, it cleared the PSK data and continued. This would later result in using a default predictable IKM value when generating the master secret if no valid PSK was negotiated.
 • The repair introduces a lookup for the key share extension by calling TLSX.find() with CommonsConstants.TLSX_KEY_SHARE. This ensures that the code is aware of the presence or absence of both essential parameters.

2. Aborting the Handshake if Neither Is Present:
 • After obtaining pointers to both the PSK and key share extension, the repair checks: if both are null (i.e., neither extension is provided by the server), the handshake is immediately aborted by returning a HANDSHAKE_FAILURE constant.
 • This prevents continuing the handshake with a default, predictable IKM value, thus mitigating potential key derivation vulnerabilities which could be exploited by an adversary.

3. Handling Valid Extensions:
 • If a valid PSK is found (i.e., it’s marked as chosen), the existing logic calls SetupPskKey() to handle it.
 • If instead the key share extension is available, the repair calls a hypothetical SetupKeyShare() (assumed to be a function that correctly processes the key share data and derives the key material). This ensures that a proper, secure key material is used.
 • If either path succeeds, the handshake proceeds safely with encryption enabled and the server state set accordingly.

4. Preventing the Use of a Default IKM:
 • By rejecting handshakes that do not provide either a valid PSK or a key share extension, the repair ensures there is no fallback to any hardcoded or predictable default buffer for the IKM. This eliminates the risk where an attacker might force the client to use a weak or known key material.

In summary, through these changes the repair ensures that a TLS 1.3 session will only be established if it can securely negotiate a session key either by using a valid PSK or key share data. By returning a handshake failure when neither extension is available, it directly addresses the vulnerability where a fallback to a default IKM value could compromise the session’s security.
