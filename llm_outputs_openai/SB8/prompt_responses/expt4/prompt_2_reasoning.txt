The repair addresses the vulnerability by ensuring that a TLS 1.3 session does not continue unless secure key material is present. Here’s a walkthrough of the changes and how they mitigate the issue:

1. PSK Extension Check:  
   The original code searches for a pre-shared key (PSK) extension and processes the linked list of PSK entries to find one marked as “chosen.” If none is found, it clears the PSK-related data. This part remains unchanged, ensuring that if no valid PSK is provided, the client won’t mistakenly reuse any stale or default key data.

2. Setting up the PSK:  
   If a valid PSK is found, the code calls the function SetupPskKey to establish the key with the chosen PSK, sets the negotiation flag (ssl.options.pskNegotiated), and then continues the handshake. This branch highlights that a session relying on PSK key material is valid.

3. New Security Check – Enforcing Key Presence:  
   The key addition is the new conditional check inserted immediately after the PSK handling. This check verifies that either a valid PSK has been negotiated (ssl.options.pskNegotiated is true) or that a valid key share exists (indicated by ssl.keys.named_group being non-zero). The vulnerability was that if both the PSK and the key share were absent, the code would fall back to using a default predictable buffer for the input key material (IKM), thus risking a compromised session key. 

   By checking “if (!ssl.options.pskNegotiated && (ssl.keys.named_group == 0))”, the repair forces the function to immediately return an error if neither secure source of key material is available. This prevents the function from proceeding to enable encryption with a default or insecure IKM, thereby ensuring that the session master secret is derived only when proper cryptographic inputs are in place.

4. Triggering an Error:  
   Instead of blindly moving ahead to enable encryption, if the check fails (meaning neither a negotiated PSK nor a valid key share is present), the function returns an error code (e.g., CommonsConstants.TLS_ERROR_MISSING_KEY_SHARE). This halts the handshake, effectively preventing the use of the fallback option that caused the original vulnerability. 

5. Enabling Encryption When Safe:  
   Only when at least one secure input—either a PSK or a key share—is present does the function proceed to enable encryption (ssl.keys.encryptionOn = true) and mark the server state complete. This control flow change guarantees that the TLS session will use only cryptographically safe keys derived from proper, non-predictable input data.

In summary, the repair enforces a strict requirement: a TLS session cannot be established using a fallback default IKM. It mandates that either a secure PSK or valid key share must be provided. This extra validation step directly addresses the vulnerability by eliminating the fallback mechanism that could lead to predictable and insecure key derivation, thereby securing the TLS 1.3 session establishment process.
