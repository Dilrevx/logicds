The repair introduces an additional check right after the PSK (pre-shared key) handling section. In the original code, after checking for and possibly setting up a PSK, the code enabled encryption without confirming that valid cryptographic material was actually established. This means that if neither a PSK was properly negotiated nor a key share extension (KSE) was provided, the code risked using a default and predictable input key material (IKM) for deriving the master secret. The predictable IKM could allow an attacker to derive the encryption keys, compromising the confidentiality and integrity of the TLS session.

Here’s what the repair does step-by-step:

1. The code still first attempts to locate a PSK extension using the TLS extension lookup. It then iterates through the PSK linked list looking for a chosen (i.e., valid) PSK. If no valid PSK is found, it explicitly clears previous PSK data, preventing any legacy data from being reused inadvertently.

2. If a valid PSK is located, the SetupPskKey function is invoked to initialize the PSK parameters, and a flag (pskNegotiated) is set to true to indicate successful negotiation.

3. Right after the above handling, a new conditional check is inserted. This check evaluates two conditions: whether a PSK has been successfully negotiated (i.e., ssl.options.pskNegotiated is true) and whether there is valid key share data available (i.e., ssl.keys.named_group is non-zero). The key share data is critical for establishing a secure TLS 1.3 session if PSK is not used.

4. If both conditions fail (meaning no valid PSK was negotiated and no valid key share is present), the function immediately returns an error (CommonsConstants.MISSING_PSK_AND_KSE). This stops the handshake process, preventing the session from continuing with insecure, default key material.

5. If at least one of these cryptographic components is present, the encryption is enabled, and the handshake continues normally.

This repair is effective because it blocks the progression of a TLS session when neither secure PSK nor key share material is present. The threat originally stemmed from the fact that, without either of these secure components, the code would default to a predictable buffer for key generation. By enforcing this additional check, the repair guarantees that the session master secret is derived only when reliable cryptographic inputs are available, thereby mitigating the risk of attackers being able to predict or reconstruct the session encryption keys.

In summary, the repair carefully validates that secure key material—either via a chosen PSK or a valid key share—is present before proceeding with encryption. This ensures that the session cannot fall back on default buffers, closing the vulnerability where an attacker might have induced the use of predictable IKM values.
