The changes introduced in the repair prevent the fallback to a predictable default IKM value when neither a PSK nor a Key Share extension is provided during a TLS 1.3 handshake. Here’s how the repair works and addresses the vulnerability:

1. Checking for Both Extensions:
   • The repaired code first looks for the presence of two types of extensions: the Pre-Shared Key (PSK) extension and the Key Share Extension (KSE). 
   • It calls the TLSX.find() function for both CommonsConstants.TLSX_PRE_SHARED_KEY and CommonsConstants.TLSX_KEY_SHARE.
   • If both extensions are absent, the code immediately returns with an error (in this case, TLS_HANDSHAKE_FAILURE), thus rejecting a connection that might resort to using a default predictable IKM.

2. Avoiding the Default IKM Situation:
   • In previous versions, if neither extension was provided, the code would silently use a default buffer value for the IKM. This is insecure because an attacker knowing this default value might reconstruct the session keys.
   • With the check for both PSK and KSE in place, performing an early abort (returning an error) prevents the generation of a session master secret using a predictable IKM.

3. Handling the PSK Extension:
   • If a PSK extension is present, the code retrieves the PSK object and iterates through the chain (if necessary) to find the “chosen” PSK.
   • If a suitable PSK is found, SetupPskKey() is invoked to generate the PSK key securely.
   • If no chosen PSK is found, it explicitly resets the key parameters.

4. Handling the Key Share Extension:
   • On the other hand, if only the Key Share extension is present (meaning there’s no PSK extension), a new branch calls SetupKeyShare().
   • This separation ensures that the code processes whichever secure method is available rather than defaulting to a predictable secret.

5. Enabling Encryption:
   • Once the appropriate extension (PSK or key share) is processed successfully, encryption is enabled and the server handshake state is updated to complete the Server Hello.

In summary, this repair ensures that the TLS handshake will not proceed if both PSK and Key Share are missing, thereby avoiding the scenario where a default and predictable IKM value is used. By aborting the handshake early when secure key exchange parameters are not provided, the vulnerability that could allow an attacker to predict the session master secret is mitigated.
