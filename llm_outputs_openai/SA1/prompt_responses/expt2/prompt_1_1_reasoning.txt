The vulnerability arises from a flaw in the PEAP implementation that permits an adversary to bypass Phase 2 authentication by sending a forged EAP-TLV Success message. By accepting a Phase 1 success without ensuring that Phase 2 has been successfully carried out, the code fails to verify the integrity and completion of the overall authentication flow, leading to a potential authentication bypass. The issue is particularly dangerous if the certificate verification is disabled during Phase 1, as in many misconfigured Enterprise networks.

In the original code snippet, the logic handles padding and then checks if encryption initialization is needed. However, it doesn’t verify whether Phase 2 authentication has completed successfully. An attacker can exploit this by injecting or modifying packets. Specifically, if an EAP-TLV Success message is received prematurely (i.e., before Phase 2 has been properly executed), an attacker might trick the system into proceeding with encryption initialization, effectively allowing access without fulfilling both necessary authentication phases. This is precisely the vector that is described in the vulnerability details.

To mitigate this vulnerability, it is necessary to add a check immediately after the padding configuration and before any encryption routines are invoked. The repair introduces a new condition that explicitly ensures phase two authentication has been successfully completed. In the repaired code, the function ctx.isPhase2Completed() is used to determine if Phase 2 authentication has finished correctly. If this check returns false, it means that either Phase 2 has not yet taken place or it failed, and hence the process is immediately halted by throwing an exception. This prevents the possibility of bypassing the critical Phase 2 check.

The addition of this verification step is crucial because it ensures that the integrity of the authentication process is maintained. By enforcing that the callback ctx.isPhase2Completed() returns true, the implementation denies any scenario where an attacker could send a forged EAP-TLV Success message to move on to the encryption step. This change filters out invalid state transitions that are normally exploited in the attack. It also enforces a strict separation of the phases, making sure that the code path for encryption is only executed if the complete authentication (both Phase 1 and Phase 2) has been satisfactorily achieved.

After this new check, the code continues with the encryption initialization, provided the context has been successfully verified to have completed Phase 2, and it also confirms that the required encryption initialization methods are present. This repair thus preserves the intended security model by ensuring that both authentication phases are independently validated, thereby closing the door to attackers who might otherwise exploit the vulnerability by skipping Phase 2 entirely.

In summary, the repair is designed to enhance the authentication process by enforcing a verification step for Phase 2 prior to processing encryption routines. This addition addresses the core vulnerability by preventing the abuse of premature success messages, ensuring that an attacker cannot bypass the authentication mechanisms that are essential for the secure operation of Enterprise Wi-Fi networks.
