The vulnerability stemmed from the fact that the buggy code would force a return value of ISC_R_SUCCESS even in cases where the result indicated a partial match or a not-found situation (DNS_R_PARTIALMATCH or ISC_R_NOTFOUND). By doing so, the code could inadvertently signal that the mirror zone data received was secure and validated, even when it had not passed the full checks. An attacker intercepting or modifying the data could exploit this behavior by injecting forged data that would bypass proper validation, thus compromising the integrity of the DNS responses when using mirror zones.

In our repair, we have removed the section that coerced the result to ISC_R_SUCCESS for the partial match or not-found cases. Specifically, the block for handling DNS_R_PARTIALMATCH and ISC_R_NOTFOUND has been eliminated. We now have a switch statement that only acts upon the successful case (ISC_R_SUCCESS) by proceeding with detaching the key node, setting the trust levels on the keyset and keysigs to indicate secure status, and marking the goodkey flag. For all other cases – including errors, partial matches, or not-found responses – the switch statement falls through without altering the result. This change ensures that if the DNSSEC validation of the mirror zone data fails in any aspect, the code does not mistakenly treat the data as valid by overwriting the error code.

This adjustment is critical as it prevents an on-path attacker from taking advantage of the fallback mechanism. If the attacker could introduce forged data into the communication path between the recursive server and the authoritative name server, the previous behavior would allow the forged data to be treated as if it were fully validated. In a DNS environment where trust anchors are expected to ensure data integrity, this behavior undermines trust, as it essentially bypasses the DNSSEC security posture of the system. The attacker could then inject manipulated data into the mirror zone and thereby control the DNS responses provided by the recursive server.

The repaired code strictly enforces the requirement that only when the result is strictly ISC_R_SUCCESS are the subsequent operations carried out, notably detaching the key node from the secure root context and updating the trust status of the associated datasets. These operations signify that the mirror zone data has been thoroughly validated against the trust anchor. In every other case, where the validation did not fully succeed, the error code is preserved, and the operations that set the trust status are not executed. This conservative approach ensures that no forged or unverified data is inadvertently used in DNS responses.

Finally, this conservative error propagation emphasizes secure behavior by not masking any error conditions. It ensures that the recursive resolution process – or any fallback mechanism like traditional recursion – is engaged correctly. The mirror zone data is used only when it passes rigorous validation, thereby preventing the deployment of potentially malicious data, reinforcing the overall DNSSEC security model for mirror zones.
