Below is one example of how you might repair the bug. In the buggy code the cases for DNS_R_PARTIALMATCH and ISC_R_NOTFOUND are simply “fixed up” to ISC_R_SUCCESS so that even when the key data isn’t fully validated the code still treats it as secure. An attacker could take advantage of that to insert forged data into a mirror zone. One way to fix this is to ensure that only data that passes complete validation is marked as secure. For example, do not convert DNS_R_PARTIALMATCH or ISC_R_NOTFOUND into a success code. Instead, treat them as failures by returning the original (non‐success) result (or at least not marking the incoming data as trusted).

                 * partially matching or missing keys would be accepted. This introduces a risk 
                 * of accepting forged data. Simply do nothing (or optionally set result to a

                break;

Explanation:

• In the fixed code the cases for partial matches or keys not found no longer “force” a success result.
• Only when result is ISC_R_SUCCESS are the keys detached and marked as secure.
• This prevents an attacker on the network path from replacing properly validated (trust-anchored) DNSKEY data with forged data when the validation state isn’t complete.

Depending on your higher-level logic you might want to return a specific error (or trigger a fallback) rather than simply “doing nothing” for the partial-failure paths. The key point is that mirror zone data should never be marked as fully trusted unless it has passed complete DNSSEC validation.
