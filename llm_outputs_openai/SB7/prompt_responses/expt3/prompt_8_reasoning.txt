The repair first checks the certificate’s validity and hostname before duplicating the certificate chain. By performing these checks up front, any issues with the leaf certificate are caught immediately, rather than being potentially overwritten later when the chain is duplicated.

Next, when the certificate in question is the leaf (determined by depth equal to 0) and the error is not a specific expected one (X509_V_ERR_UNABLE_TO_GET_ISSUER_CERT_LOCALLY), the repair explicitly stores the error in an error array at the corresponding depth. This ensures that any error found during the validation is retained even if the verification callback advises that the process should continue.

After recording any potential error, the code checks if there’s room to store another certificate chain by comparing the current chains_count with max_chains. If there is room, it attempts to duplicate the chain. In the event of a failure during the chain duplication—indicated by a null result—the code immediately returns an error (specifically, an out-of-memory error) while preserving the error context.

Once a chain is successfully duplicated, the code increments the count of stored chains and resets the overall error context to a “no error” state (X509_V_OK). Immediately after, it assigns this “no error” status to the error array at the current depth, ensuring that the error information is accurate and reflective of the final state.

Overall, by reordering the operations so that certificate checks and error handling occur before any modifications to the chain storage, the repair guarantees that errors occurring during certificate verification are neither lost nor overwritten. This fix preserves critical error details that were previously discarded in the buggy version when a callback allowed verification to continue despite an encountered error.
