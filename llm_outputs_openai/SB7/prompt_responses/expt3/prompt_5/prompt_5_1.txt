Notice that the verification of the leaf certificate happens before attempting to duplicate the chain, and that when verifying the leaf certificate (depth zero) a specific check is made so that any error is saved in an array (here referenced as ctx.chain_errors) to record the error state for that level. Explanation of key repair steps:

• Certificate and hostname validation are now executed first. This reordering ensures that any error at the leaf (depth 0) is captured immediately.
• If the depth equals zero and the encountered error is not a specific known issuer error, then that error is stored (for example, in ctx.chain_errors[0]). This way, even if the verification callback later decides to continue after the error, the error from the leaf certificate is not lost.
• Only after successful validation is the certificate chain duplicated. If duplication fails because, for example, of insufficient memory, the error is returned immediately.
• Finally, after successful duplication, the chain count is incremented and the overall error state reset to success. The chain’s error array is updated with the fresh error code so that any further diagnostics have a complete record of errors encountered during the validation process.

This repair fixes the vulnerability by preserving the original error state from the leaf certificate verification rather than having it overwritten by the chain duplication process.
