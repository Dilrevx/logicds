The repair introduces a flag-setting mechanism to ensure that the ChangeCipherSpec messages are processed only when they are genuinely expected. In the vulnerable code, OpenSSL did not properly mark the transition states when processing ChangeCipherSpec messages, which could allow an attacker to manipulate the handshake and force the use of a zero-length master key. The repair addresses this by taking the following steps:

First, the repair adds an instruction at the beginning of the branch that processes the certificate verification phase. This instruction sets a specific flag in the session state to indicate that processing of the ChangeCipherSpec (CCS) message is allowed. This change serves as a marker that the protocol negotiation is in the correct state, meaning that the CCS message the server might receive can safely be treated as valid. That flag is only set when the server is in a state where a CCS message is expected, thus countering the possibility of an attacker injecting an unsolicited CCS message.

Next, after setting the flag at the entry point of the certificate verification stage, the routine continues as before by verifying the certificate. If there is an error during this process, the handshake is terminated. However, if successful, the state machine is advanced to expect either the finished message or, depending on specific options (such as Next Protocol Negotiation), another subsequent state. The setting of the flag ensures that the CCS is only accepted as part of the normal message sequence and not out-of-order.

Later, when handling the finished messages stage from the server’s perspective, the repair again sets the same flag before calling the function that retrieves the finished message from the client. This reinforces the expectation that a CCS message is part of the handshake, after verifying that the certificate and handshake messages are as expected. This step further solidifies the control that the system has over the handshake sequence, ensuring that the finite state machine only transitions forward when the message order is correct.

Additionally, when preparing to switch cipher states and perform the key exchange, the repair does not reconfigure the fundamental process, but it does ensure that all subsequent state transitions remain guarded by the flag. For example, during the generation and exchange of the ChangeCipherSpec and finished messages, the repair code maintains the expectation that any CCS message received is legitimate by referring back to the flag’s state. Thus, all branches of the state machine that might be vulnerable to a CCS injection check and use this flag appropriately.

In summary, the primary protection implemented in this repair is the explicit marking of valid states for CCS processing via a flag. This measure effectively prevents a man-in-the-middle from exploiting a sequence deviation by injecting a forged CCS message, ensuring that all transitions in the handshake, particularly those related to key exchange and finished messages, occur only when the protocol state is properly synchronized. This carefully targeted change mitigates the "CCS Injection" vulnerability while preserving the rest of the protocol’s flow.
