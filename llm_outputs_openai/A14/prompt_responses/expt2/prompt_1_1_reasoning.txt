The repair centers on addressing the CCS Injection vulnerability by ensuring that the TLS handshake processes a ChangeCipherSpec (CCS) message in a strictly controlled manner. The underlying issue stems from OpenSSL’s behavior of accepting CCS messages even when they occur earlier in the handshake, potentially leading to a scenario where a zero-length master key is used, exposing the session to man-in-the-middle attacks. Therefore, the repair introduces an additional check when processing the Finished message to validate that exactly one CCS record was received during the handshake.

To elaborate, the vulnerable code did not explicitly verify that a CCS message was received at the proper point in the handshake sequence. An attacker could craft a handshake that injects an extra CCS message, which could trick the server into computing keys based on incomplete or manipulated parameters. By incorporating a check for the number of CCS records, the repaired code prevents the handshake from continuing normally if more (or fewer) than the expected one CCS message was processed. This check is implemented by examining a new flag member (s->s3->change_cipher_spec_received) in the state structure of the session. The code verifies that this flag is set to 1, which indicates that exactly one CCS has been received. If the value does not match 1, then an error is raised using SSLfatal, effectively halting the handshake.

In addition, after verifying the CCS count, the flag is reset to zero to ensure that any subsequent CCS messages that might be injected are caught by new checks later in the connection’s state machine. This action prevents an attacker from reusing an already seen CCS or sending a duplicate, thereby maintaining the integrity of the handshake protocol. By doing this, the server strictly enforces the order and presence of handshake messages, reducing the attack surface that CCS injection previously exploited.

Furthermore, the repair does not modify other parts of the handshake state machine that deal with certificate verification, key exchange, and final message processing; instead, it only adds the critical validation step during the Finished message stage. This isolates the fix to the specific vulnerable logic without impacting the rest of the protocol functionality. The remaining state transitions continue to progress as intended. For instance, if the handshake reaches the Finished message processing with a valid CCS count, the state is set appropriately based on whether the session is a new handshake or a resumed session (s->hit flag) and depending on whether other TLS extensions (like Next Protocol Negotiation or session tickets) are involved.

By enforcing this additional security measure, the repair not only mitigates the CCS Injection vulnerability but also reinforces a broader principle in secure protocol implementation: explicit verification of message ordering and counts is essential. Such checks prevent adversaries from triggering unintended behavior by injecting or replaying protocol messages. Ultimately, this fix helps to ensure that the sophisticated cryptographic exchanges in TLS handshakes are resistant to manipulation, anticipating challenges that attackers might try to impose during the session establishment.
