The repair addresses the CCS Injection vulnerability by introducing and enforcing an explicit flag (s->s3->expected_ccs) that marks when the ChangeCipherSpec (CCS) message is expected during the TLS handshake. Originally, the OpenSSL code did not clearly delineate or mark the expectation state for a CCS message. This allowed an attacker to inject an unsolicited CCS at an incorrect point during the handshake process, leading to a situation where a zero-length master key could be used, allowing session hijacking or leakage of sensitive data.

In the modified code, the repair begins in the branch that processes the certificate verification phase (SSL3_ST_SR_CERT_VRFY_B). At the very start of this branch, the repair sets the flag expected_ccs to 1. This action essentially “arms” the handshake protocol, indicating that the subsequent CCS message, if received, is legitimate because it follows a valid certificate verification process. If the certificate verification fails (indicated by ssl3_get_cert_verify returning a non-positive value), the flag is immediately cleared (set to 0) to ensure no invalid state persists that could erroneously allow a CCS to be accepted later in the handshake.

Later in the handshake, when processing the Finished messages in the SSL3_ST_SR_FINISHED_A / SSL3_ST_SR_FINISHED_B state, the repair first validates that the expected_ccs flag is set. This check serves as a safeguard: if for some reason an unsolicited CCS message was injected prior to this phase, and the flag is not properly asserted, the handshake will be aborted by returning an error (ret = -1; goto end;). Then, before calling ssl3_get_finished to process the Finished message, the flag is explicitly set again. This reinforces the internal state by confirming that the CCS is expected and that the handshake protocol is in the right state before processing the critical finished message. After the Finished message is successfully processed, the flag is cleared, ensuring that the CCS state does not remain enabled longer than necessary, reducing the window of opportunity for exploitation.

In the branch dealing with sending the ChangeCipherSpec message (SSL3_ST_SW_CHANGE_A / SSL3_ST_SW_CHANGE_B), there is a similar mechanism in place. Before the CCS is sent, the code checks again whether the expected_ccs flag is active. If the flag is not set, it indicates that the CCS message is not being invoked from an expected state, and thus the handshake is terminated by returning an error. Once the flag validation is successful, the flag is cleared, and the protocol flow transitions to send the new cipher state and finished messages securely.

By integrating these checks and flag manipulations in both the incoming CCS (during the server certificate verification and finished message processing) and outgoing CCS (when sending the change cipher spec message), the repair reinforces a strict sequential order in the handshake. It prevents any out-of-sequence and maliciously injected CCS messages from being accepted. This explicit state management ensures that only a CCS message received in the correct, authenticated context will be processed, mitigating the vulnerability.

Overall, the repair uses a simple yet effective state flag to tightly control the TLS state machine’s transitions related to CCS messages, helping to eliminate the attack vector associated with the “CCS Injection” vulnerability while preserving the intended flow and security properties of the handshake protocol.
