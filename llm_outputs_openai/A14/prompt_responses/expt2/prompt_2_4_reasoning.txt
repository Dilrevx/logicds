The main idea behind the repair is to introduce an explicit flag that marks when a ChangeCipherSpec (CCS) message is expected as part of the normal, secure TLS handshake. This flag acts as a safeguard against unsolicited or malformed CCS messages that could be injected by an attacker, potentially leading to the use of a zero-length master key and thus compromising the session security.

In the certificate verification state (SSL3_ST_SR_CERT_VRFY_B), before the certificate verification function is called, the repair sets a flag (s->s3->change_cipher_spec_ok = 1) to signal that the protocol is in the correct stage to process a CCS message. This preemptive action essentially “marks” the session state so the later stages in the handshake can check if any received CCS message truly belongs to a valid handshake sequence.

Once the flag is set, the code then proceeds with the usual processing (calling ssl3_get_cert_verify) and adjusting the state (advancing to SSL3_ST_SR_FINISHED_A or an alternative state if Next Protocol Negotiation (NPN) is involved). The idea is that if the certificate verification is successful, the handshake naturally progresses to a stage in which processing the Finished message is valid, but only if a CCS message was indeed expected.

Then, in the branch handling the Finished messages (SSL3_ST_SR_FINISHED_A/SSL3_ST_SR_FINISHED_B), the code checks that the flag s->s3->change_cipher_spec_ok is still set. If the flag isn’t set, this indicates that the finished message is arriving out of the expected sequence or that a CCS was injected when it was not intended. In such a case, the handshake is aborted. When the flag check succeeds, this confirms that a CCS was validly expected and the handshake can safely proceed. To prevent misuse or reprocessing, the flag is reset (s->s3->change_cipher_spec_ok = 0) immediately after the check.

For the branches that follow (involving sending either the change cipher spec or the finished message and switching cipher states), the repair leaves the underlying logic intact. These state transitions and cryptographic operations are already designed to be robust, but they now benefit from the additional security check provided earlier in the handshake phase. By enforcing this flag check, any potential CCS injection that runs counter to the natural progression of the TLS handshake would be detected and rejected before the session is compromised.

Overall, this repair ensures that a CCS message is only processed when it is genuinely expected by the protocol state—specifically, after successful certificate verification—thereby helping to align the state machine with the intended secure sequence of operations. This explicit marking method fortifies the protocol by preventing any out-of-order or malicious CCS injections. It makes it harder for man-in-the-middle attackers to prematurely trigger key transitions in the handshake (such as advancing to a finished state with an inappropriate or zero-length master key), which would otherwise lead to session hijacking or unwanted leakage of sensitive crypto material.

By embedding this additional control mechanism at the right points in the handshake process, the repair effectively mitigates the “CCS Injection” vulnerability while adhering to the original design of the state machine, ensuring both backward compatibility and enhanced security in OpenSSL’s TLS implementation.
