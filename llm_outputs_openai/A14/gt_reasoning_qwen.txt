The vulnerability described involves a critical flaw in how OpenSSL handles ChangeCipherSpec (CCS) messages during the TLS handshake process. Specifically, the issue arises from the improper restriction on the processing of these messages, allowing a man-in-the-middle (MITM) attacker to inject a CCS message at an inappropriate time, leading to the use of a zero-length master key. This can result in session hijacking or the exposure of sensitive information.

In the provided buggy code, the handling of the TLS handshake states does not include a mechanism to ensure that CCS messages are received only at the correct point in the handshake sequence. The absence of such a check makes it possible for an attacker to inject a CCS message prematurely, bypassing the intended security measures.

The repair introduced addresses this vulnerability by adding a flag, `SSL3_FLAGS_CCS_OK`, which indicates whether a CCS message is expected at a particular stage of the handshake. This flag is set appropriately in several places within the handshake state machine:

1. **After Certificate Verify Message**: In the `SSL3_ST_SR_CERT_VRFY_B` state, the flag is set right before processing the certificate verify message. This ensures that a CCS message can be accepted only after the certificate verification step has been completed successfully.

2. **After Finished Message**: Similarly, in the `SSL3_ST_SR_FINISHED_A` and `SSL3_ST_SR_FINISHED_B` states, the flag is set after the finished message has been processed. This is crucial because the finished message marks the end of the main handshake phase, and a CCS message should logically follow this point.

3. **Before Sending Session Ticket**: In the `SSL3_ST_SW_SESSION_TICKET_A` and `SSL3_ST_SW_SESSION_TICKET_B` states, the flag is set before sending a session ticket. This adjustment ensures that the CCS message can be sent only after the session ticket has been processed, maintaining the integrity of the handshake sequence.

4. **Before Sending Next Protocol**: In the `SSL3_ST_SR_NEXT_PROTO_A` state, the flag is set before processing the next protocol message. This is important for ensuring that the CCS message is handled correctly when the next protocol negotiation extension is used.

By setting the `SSL3_FLAGS_CCS_OK` flag at these specific points, the repair ensures that the CCS message is only processed when it is expected according to the TLS protocol specification. This prevents an attacker from injecting a CCS message at an incorrect time, thereby mitigating the risk of using a zero-length master key and protecting against session hijacking and data exposure.

In summary, the repair enhances the robustness of the OpenSSL implementation by enforcing stricter control over the timing and processing of CCS messages during the TLS handshake, effectively addressing the CCS Injection vulnerability.
