The repair adds an extra conditional check to differentiate between a truly “no ACL file provided” situation and the case where an ACL file was provided but is empty (or contains only comments/blank lines).

Originally, the code checked whether both the in-memory ACL list (securityOpts.aclList) and the ACL patterns (securityOpts.aclPatterns) were null. If they were, it returned MOSQ_ERR_PLUGIN_DEFER, which signals that no ACL file has been defined. This behavior inadvertently allowed an empty ACL file—containing no functional entries—to be treated as if no ACL file was provided, leading to a default allow-all access policy that poses a security risk.

Here’s how the repair addresses the vulnerability:

1. The additional nested check determines whether an ACL file was explicitly configured by the administrator. This is done by checking if securityOpts.aclFile is null.
  • If securityOpts.aclFile is null (i.e., no ACL file was provided at all), the code returns MOSQ_ERR_PLUGIN_DEFER. This preserves the original default behavior for cases where no ACL configuration is given.
  • However, if an ACL file is present—even if its ACL list and patterns are empty—the code returns MOSQ_ERR_ACL_DENIED. This ensures that an explicitly provided ACL file, even when empty, does not default to allowing access but instead denies access by default.

2. By implementing this check, the system now correctly interprets an empty ACL file as a deliberate configuration decision. This differentiation is crucial because an ACL file without operational rules (empty or containing only comments) should enforce a “deny-all” policy, aligned with a secure-by-default approach.

3. The modified logic ensures that administrators’ intentions are respected. If an ACL file is provided, even if it is empty, the broker enforces no access rather than mistakenly falling back to a permissive allow policy. In contrast, if no ACL file is specified, the legacy behavior of deferring to the plugin (and, by extension, a default mechanism) remains intact.

Overall, the repair enhances the security posture by ensuring that only explicitly undefined ACL configurations default to plugin-based decision-making, while any form of explicit ACL file presence—even if functionally empty—results in a deny-all stance. This prevents an unexpected gap where the broker could unintentionally allow access, thus fixing the originally described vulnerability.
