This could potentially allow an invalid certificate chain to be incorrectly accepted or the original error to be masked.

In the repaired code, before each block of strict validation, an additional condition (ret > 0) is added. This means that if ret has been set to 0 (indicating an error) during a previous check, the subsequent verification steps are entirely skipped. Specifically:

In the block performing the elliptic curve strict check, the code now first checks whether ret > 0 alongside ensuring that strict mode is enabled and there is more than one certificate in the chain. If an error has already been detected (i.e., ret is not greater than zero), the elliptic curve check will not execute. This prevents the situation where a previously set error code might be overwritten by a new error from the curve check.

2. Similarly, before verifying if a certificate lacks the appropriate CA flag when strict mode is enabled, the code checks that ret > 0. If ret is already 0 due to an earlier failure, this check is skipped, thereby preserving the initial error state. This is critical because if a certificate already failed one of the elliptic curve or CA checks, we do not want a secondary check to alter the error code and report a different failure.

By sequencing the checks in this manner, the repair ensures that once an error is encountered in the validation process, all subsequent checks within the iteration over the certificate chain are either not performed or do not interfere with the already set error state. The result is that the chain validation process remains true to the first encountered error, preserving the integrity of the error reporting. This makes certificate verification more robust since the issuer of the error (whether it be due to EC parameters or CA flag issues) is clearly reported without risk of later overwriting.
