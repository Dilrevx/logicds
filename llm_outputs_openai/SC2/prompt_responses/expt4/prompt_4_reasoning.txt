The repair adds an extra condition (ret > 0) to each strict-check block. This ensures that subsequent test blocks only execute if no previous validation has failed.

Originally, each check ran as long as strict mode was enabled, regardless of whether an earlier check had already set an error. For example, if the elliptic curve check failed and set ctx.error to an elliptic-curve-related error, the CA status check (which verifies that non-CA certificates couldn’t issue certificates) might still run. That could overwrite the initial error, losing the original failure indication, and potentially letting an invalid certificate pass further later checks.

In the repaired code, the first block now executes only if strict mode is active, there are multiple certificates (num > 1), and no previous error has been found (indicated by ret > 0). This means if any earlier check had already set ret to 0 (failure), then the elliptic curve check won’t be attempted. The CheckCurve functionality verifies the certificate’s elliptic curve parameters. If CheckCurve returns an error, the code sets an unspecified error or a specific elliptic curve error appropriately. This limits certificate validation only to cases that haven’t already failed.

Similarly, for the CA check block, the condition now tests for strict mode and that ret is still positive before executing. The block examines whether the certificate has the CA flag set (by checking x.ex_flags & X509.EXFLAG_CA) and whether the path length is valid. Importantly, by verifying ret > 0 first, the code ensures that if a previous error (for example, the elliptic curve issue) was already logged, this check won’t overwrite that error with a generic invalid extension error. This prevents potential errors from being lost or masked.

Overall, the repair ensures that error reporting remains consistent: once an error is encountered, no further checks modify the error state. This sequential, condition-based approach helps maintain the integrity of the verification process by preserving the first error encountered, thereby preventing accidental error replacement. The vulnerability was thus fixed by ensuring that the error code from a failing check (whether due to elliptic curve parameters or non-CA certificate misuse) is not inadvertently overwritten by a subsequent unrelated check.
