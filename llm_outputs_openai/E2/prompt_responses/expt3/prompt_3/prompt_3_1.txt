Below is one example of how you can address the vulnerability. In the buggy code the NAS message type used for “new NAS security context” (for instance, used during registration) is accepted even when the UE is already registered. That can allow a replay of NAS Session Management (SM) commands after registration is complete. The fix is to verify whether the UE has completed registration and, if so, reject any NAS message that carries a “new NAS context” (which in this example corresponds to the replay attack).

One approach is to maintain a flag or call a function (for example, is_registration_complete()) that returns true if registration was successfully completed. Then, in the branch for the new security context messages—for example, the integrity_protected_with_new_5G_nas_context type—add a check that rejects further updates after registration.

Here is the updated code snippet with the repair applied:

------------------------------------------------------------
  if (nas_msg.unpack_outer_hdr(pdu) != SRSRAN_SUCCESS) {
    logger.error("Unable to unpack outer NAS header");
    return SRSRAN_ERROR;
  }

  switch (nas_msg.hdr.security_header_type) {
    case nas_5gs_hdr::security_header_type_opts::plain_5gs_nas_message:
      break;

    case nas_5gs_hdr::security_header_type_opts::integrity_protected:
      if (integrity_check(pdu.get()) == false) {
        logger.error("Not handling NAS message with integrity check error");
        return SRSRAN_ERROR;
      }
      break;

    case nas_5gs_hdr::security_header_type_opts::integrity_protected_and_ciphered:
      if (integrity_check(pdu.get()) == false) {
        logger.error("Not handling NAS message with integrity check error");
        return SRSRAN_ERROR;
      } else {
        cipher_decrypt(pdu.get());
      }
      break;

    // This branch is used for NAS messages that contain a new security context. 
    // These messages are only expected during registration. If registration is already complete,
    // a replay attack might be attempted, so we must reject them.
    case nas_5gs_hdr::security_header_type_opts::integrity_protected_with_new_5G_nas_context:
      if (ue_is_registered()) {  // ue_is_registered() returns true if registration is already complete.
        logger.error("Rejecting NAS SM command replay: registration already complete");
        return SRSRAN_ERROR;
      }
      break;

    // This message type is not supported at all.
    case nas_5gs_hdr::security_header_type_opts::integrity_protected_and_ciphered_with_new_5G_nas_context:
      return SRSRAN_ERROR;

    default:
      logger.error("Not handling NAS message with unknown security header");
      break;
  }
------------------------------------------------------------

Key Points:

1. We introduced a check (ue_is_registered()) to determine if the UE has already completed registration.
2. In the branch for integrity_protected_with_new_5G_nas_context, we reject the message if registration is complete, thus preventing replay attacks.
3. The rest of the branches are left as they were (although additional hardening might be required depending on the overall design).

Make sure that the function or flag (ue_is_registered()) is properly implemented and reflects the UE’s current registration state.

This repair fixes the vulnerability by ensuring that NAS session management commands or replays that are meant only for the registration phase will be rejected when registration is already complete.
