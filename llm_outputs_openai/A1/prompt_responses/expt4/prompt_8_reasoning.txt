The repair adds a block (under #if !defined(FIPS_MODULE)) that preprocesses the OSSL_PARAM array before the cipher’s key and IV are used to initialize the algorithm. Here’s how it works:

1. When the parameters (params) are provided, the repair creates a temporary parameters array (tmp_params) that can hold up to two parameter entries. This array is initialized with the sentinel OSSL_PARAM_END values.

2. It then searches for the key length parameter using OSSL_PARAM_locate_const() with the identifier for key length (OSSL_CIPHER_PARAM_KEYLEN). If found, it copies this parameter into the temporary array.

3. Next, it searches for the IV length parameter. To be thorough, it first checks for OSSL_CIPHER_PARAM_IVLEN and, if that isn’t found, checks for OSSL_CIPHER_PARAM_AEAD_IVLEN (which in some cases is just a synonym for the IV length). If found, this parameter is also stored in the temporary array.

4. The repair then immediately applies these pre-extracted parameters by calling EVP_CIPHER_CTX_set_params(). This call updates the cipher context’s configuration for key and IV lengths before any key or IV data is used in the encryption or decryption routines.

5. If EVP_CIPHER_CTX_set_params() fails (for example, if the specified lengths are invalid), the function raises an error (EVP_R_INVALID_IV_LENGTH) and aborts further processing, thereby preventing the context from being left in a misconfigured state.

By processing the desired key and IV lengths before the actual initialization routines (such as einit or dinit) are called, the repair ensures that the parameters take effect early. This preemptive adjustment prevents the vulnerability where the IV might be truncated or overrun due to later parameter processing. The change is critical for preserving the required uniqueness of the IV, which is key for the confidentiality guarantees provided by many cipher modes.

Moreover, this repair preserves the original behavior in FIPS builds (where the new internal behavior must be maintained) by wrapping the new parameter processing code in a conditional compilation block that is disabled when FIPS_MODULE is defined. Similarly, the original behavior of preserving the no-padding setting is unchanged.

Overall, the repair secures the initialization process by ensuring that key and IV lengths are correctly set at the earliest point possible during context initialization, thus mitigating risks associated with incorrect or truncated lengths that could compromise the encryption scheme’s confidentiality.
