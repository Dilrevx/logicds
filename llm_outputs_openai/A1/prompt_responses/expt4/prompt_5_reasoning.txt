The repair adds a validation step immediately after setting up the provider’s cipher context – before passing control to the cipher’s initialization functions. Here’s a walkthrough of the change:

1. A new check is inserted that iterates over the provided OSSL_PARAM array (if it isn’t NULL). Using a simple loop, each parameter’s key is compared with the reserved parameter names for key length and IV length (namely "OSSL_CIPHER_PARAM_KEYLEN" and "OSSL_CIPHER_PARAM_IVLEN").

2. If any parameter in the list matches one of these reserved keys, the function immediately raises an initialization error and aborts by returning 0. This prevents any subsequent code from using a parameter that could override the key and IV lengths already determined by the EVP_CIPHER_CTX.

3. By ensuring that the OSSL_PARAM array does not attempt to modify these critical lengths later during the initialization (after the key and IV data have been processed), the repair eliminates the potential for truncation or an overrun. This is important because such modifications could lead to non-unique IVs or improper key sizes, undermining the confidentiality offered by certain cipher modes.

4. This safeguard is placed well before the actual calls to the encryption or decryption initialization functions (ctx->cipher->einit or ctx->cipher->dinit). Therefore, if a caller inadvertently (or maliciously) supplies parameters that attempt to override these lengths, the initialization routine fails fast and does not proceed with compromised settings.

In summary, the vulnerability was caused by an unsafe design where key and IV lengths, once established, could later be modified by parameters. The fix explicitly blocks any attempt to change these lengths by inspecting the OSSL_PARAM array and rejecting any reserved keys. This preserves the integrity of the key and IV values, ensuring that they remain consistent with the established lengths and thereby maintaining the confidentiality guarantees of the cipher operations.
