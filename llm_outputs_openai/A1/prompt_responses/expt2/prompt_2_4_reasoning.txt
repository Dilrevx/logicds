The repair addresses the vulnerability by ensuring that key and IV length parameters are applied to the cipher context at an earlier stage in the initialization process, thereby mitigating the risk of truncation or overrun vulnerabilities that could compromise cryptographic security. Previously, the EVP_EncryptInit_ex2(), EVP_DecryptInit_ex2(), or EVP_CipherInit_ex2() calls accepted the key and IV parameters, but only processed the accompanying OSSL_PARAM array afterward. This sequence risked having the critical length parameters be applied too late, which in certain modes—especially those requiring unique IVs, such as AEAD modes—could allow truncation or misconfigured lengths that undermine the cipher's security.

In the repair, an early conditional check for a non-null “params” array is introduced immediately after the no-padding flag check. This early stage is crucial because it allows us to capture the key and IV lengths before any further cipher initialization steps are taken. By conditionally compiling the block with “#ifndef FIPS_MODULE”, we ensure that this code is only applied when not building the FIPS module, since the FIPS provider manages these parameters differently. This separation is important to avoid interference with the FIPS-approved configuration process.

Within this early processing block, the code creates a local array of OSSL_PARAM objects (named local_params) that is intended to temporarily hold the key length and IV length parameters. The array is sized with space for two parameters plus an end marker, ensuring a proper termination of the parameter list. The code then utilizes the helper function OSSL_PARAM_locate_const() to search for a parameter with the identifier corresponding to the key length. If such a parameter is found and is successfully retrieved using OSSL_PARAM_get_size_t(), the key length parameter is added to the local_params array using OSSL_PARAM_construct_size_t(). This explicit extraction and copying of the key length ensures that the cipher context is aware of the caller-provided key length from the very beginning.

A similar process is followed for the IV length parameter. The code searches for the IV length using OSSL_CIPHER_PARAM_IVLEN. In cases where modes might have alternate identifiers for the IV length, additional searches or logic may be required (though in this repair only the standard identifier is used). Once found and validated, the IV length parameter is also added to the local_params array.

After preparing the local parameter array with any found length parameters, the code calls the function EVP_CIPHER_CTX_set_length_params() to apply these settings immediately. This proactive configuration step is critical because it locks in the correct key and IV lengths, ensuring that when the final call to the cipher’s initialization routine is made, the cipher context has already been properly configured. If the setting of these parameters fails, the repair immediately raises an appropriate error and aborts initialization, safeguarding against proceeding with a misconfigured cipher context that could lead to security issues.

Finally, after these critical parameters are set, the original cipher initialization call (ctx->cipher->einit()) is executed. This preserves the intended behavior of the cipher initialization while ensuring that the integral length parameters have been secured. Overall, the repair ensures that secure cryptographic operations are maintained by processing sensitive length parameters early, thereby closing the window where timing issues or delayed parameter processing could compromise confidentiality and integrity within the cipher initialization process.
