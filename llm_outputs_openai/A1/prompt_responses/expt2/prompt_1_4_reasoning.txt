The original code uses functions like EVP_CIPHER_CTX_get_key_length(ctx) and EVP_CIPHER_CTX_get_iv_length(ctx) to determine the lengths of the key and IV, respectively. The concern highlighted in the vulnerability description is that these lengths might be altered or misinterpreted during later processing of the provided parameters through an OSSL_PARAM array. This processing occurs after the key and IV have already been established, meaning that if the code relies on these potentially modified values, it risks truncation of the IV or even overruns. Such discrepancies can cause the IV to be non-unique, a severe issue for certain encryption modes where IV uniqueness is critical to maintaining confidentiality.

To address this, the repair replaces the calls to EVP_CIPHER_CTX_get_key_length() and EVP_CIPHER_CTX_get_iv_length() with direct references to the intrinsic key and IV lengths that are stored in the cipher object itself (i.e., ctx->cipher->key_len and ctx->cipher->iv_len). This change is important for a couple of reasons:

1. Integrity of Data: By directly referring to ctx->cipher->key_len and ctx->cipher->iv_len, the code uses the original, predefined, and, crucially, unmodified lengths of the key and IV as intended by the specific cipher implementation. This ensures that no subsequent parameter processing can interfere with the expected size requirements of the cipher. It tightly couples the length data to the cipher's own specifications, preventing external modifications that could lead to vulnerabilities.

2. Avoiding Truncation/Overrun: The vulnerability description emphasizes that modifications in the processing order could lead to truncation or overruns when the key/IV lengths are determined after the cipher has started initialization. By using the intrinsic lengths, the repair prevents scenarios where the cipher could mistakenly be provided with an incorrectly sized key or IV. This effectively prevents cases where an IV could be truncated (thus lacking the required uniqueness) or extended, potentially reading into memory regions not intended for use.

3. Consistency and Predictability: Accessing the stored parameters (key_len and iv_len) means the behavior is consistent regardless of how external parameters (OSSL_PARAM array) are processed. This consistency is vital to ensure the cipher operates safely across varied cryptographic modes. Different modes may impose additional constraints on key and IV sizes; hence, using the cipher’s built-in lengths removes any ambiguity and potential for misinterpretation.

4. Shielding Against Post-Initialization Changes: Since the OSSL_PARAM array is processed after the key and IV have been established, using values determined dynamically via EVP_CIPHER_CTX_get_* functions could reflect unintended adjustments made during that parameter processing. The repair effectively decouples the initialization values from any subsequent modifications.

Overall, the repair focuses on using reliable, intrinsic values associated with the cipher object to enforce the integrity of the key and IV lengths. This deliberate change directly mitigates the vulnerability by ensuring that potential side effects from later parameter processing do not affect the cipher’s fundamental properties, thus preserving confidentiality and operational correctness in cryptographic processing.
