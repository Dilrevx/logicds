The repair introduces a helper function, x509_crt_verify_san(), and modifies the x509_crt_verify_name() function to use it. Here’s how the repair works and fixes the vulnerability:

1. The vulnerability stemmed from the fact that when a certificate included a Subject Alternative Name (SAN) extension, the original code iterated over every SAN entry and compared the expected name (the “cn”) with each entry regardless of its type. That meant that even SAN fields representing IP addresses could be matched against a domain name, opening the door to potential impersonation if an attacker controlled the corresponding IP address.

2. The new helper function x509_crt_verify_san() was created to perform a type-aware scan of the SAN entries. Inside this function, the code iterates over the certificate’s SAN list, but crucially, it only accepts entries that have the allowed type—here, it checks if the SAN entry’s tag is MBEDTLS_X509_SAN_DNS. This explicitly filters out any SAN entries representing IPv4, IPv6, or other types that are not permitted for CN verification.

3. By comparing the tag (which indicates the entry type) against MBEDTLS_X509_SAN_DNS, the repair assures that only proper DNS names are considered in the name matching process. If a DNS SAN field matches the expected CN using x509_crt_check_cn(), the helper function returns success immediately.

4. In the main function, x509_crt_verify_name(), the code first checks if the certificate has the SAN extension. If it does, it calls x509_crt_verify_san(). A valid match from this helper function leads to an immediate return, meaning that the possibility of any misused SAN entry (due to an insecure type) is bypassed because only valid DNS SAN entries are ever checked.

5. If the helper function does not find a valid DNS name—a situation where either the SAN entries do not include a properly-typed DNS name or the names simply do not match—the code then falls back to checking the subject’s common name (CN) in the traditional way. This is done by scanning the subject names for the CN OID and comparing them with the expected name using x509_crt_check_cn().

6. Finally, if no valid name is found in either the SAN list (with proper type verification) or in the subject DN, the code sets an error flag (MBEDTLS_X509_BADCERT_CN_MISMATCH) to indicate the certificate has a common name mismatch, ultimately leading to a verification failure.

In summary, by delegating the SAN verification to a helper function that enforces type-checking (ensuring only DNS names are matched), the repair prevents an attacker from exploiting a misconfiguration, such as matching an IP address. Moreover, the fallback to subject CN checking maintains backward compatibility and robust handling. This dual approach not only remediates the vulnerability by eliminating the possibility of comparing unsupported SAN types but also simplifies and clarifies the overall verification logic.
