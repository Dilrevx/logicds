The repair adds an extra check when processing the Subject Alternative Name (SAN) entries. In the original code, as soon as a SAN extension is present, the function looped over every entry in subject_alt_names and called x509_crt_check_cn regardless of the name’s type. This meant that names representing IP addresses could accidentally be used when checking a common name, allowing an attacker to match using an IP address vulnerable to exploitation.

In the repaired code, before calling x509_crt_check_cn, the function now checks if the current SAN entry’s tag equals MBEDTLS_X509_SAN_DNS_NAME. This tag ensures that only DNS names are evaluated against the expected common name (cn). By filtering out other SAN types, such as IP addresses, the repair stops the vulnerability: an attacker can no longer rely on a certificate containing non-DNS names (say, IPv4/IPv6 addresses) to satisfy a common name match. Only entries with the proper DNS name type will trigger a match.

The code change is confined to the branch where the crt->ext_types flag indicates the presence of SAN. The check:

  if( cur->buf.tag == MBEDTLS_X509_SAN_DNS_NAME && ... )

ensures that only DNS entries are considered. If no DNS entry in the SAN list matches the expected common name, the error flag MBEDTLS_X509_BADCERT_CN_MISMATCH is set. The behavior in the absence of a SAN extension (falling back to subject common names) remains unchanged, ensuring backward compatibility.

Overall, the fix resolves the vulnerability by restricting name matching only to SAN entries of the correct type (DNS names) and preventing the unintended comparison of non-DNS names (e.g., IP addresses) with the expected common name.
