The repair introduces a new helper function, x509_crt_verify_subject_alt_name(), which is responsible for validating the Subject Alternative Name (SAN) entries in a type-aware manner. Previously, the code looped through all SAN entries and applied a generic name-checking function regardless of the type of the SAN. This approach allowed an attacker to deliberately include non-DNS entries (like IP addresses) that could match the expected common name, potentially enabling a bypass of the intended hostname validation.

In the helper function, we iterate through the SAN list. However, before comparing an entry with the expected name using x509_crt_check_cn(), we first check that the entry is of a permitted type for hostname validation—in this case, a DNS name (represented by MBEDTLS_X509_SAN_DNS_NAME). If the current SAN entry is a proper DNS name and the comparison function returns zero (indicating a match), the helper function immediately returns success. If none of the entries meet these criteria, it returns a failure code.

Back in the x509_crt_verify_name() function, the logic now first checks if the certificate contains the SAN extension. If so, it calls x509_crt_verify_subject_alt_name() to perform the enhanced, type-restricted verification. If the helper function finds a valid DNS match, the function returns immediately, accepting the certificate. If no acceptable SAN match is found, the repair then falls back to examining the certificate's subject fields. It iterates through the subject entries to locate a Common Name (CN) by checking the Object Identifier (OID) against the known CN OID (MBEDTLS_OID_AT_CN). If a match is found in the subject, the function again returns immediately.

Only if neither the sanitized SAN check nor the traditional subject CN check yields a match does the code set the flagged error (MBEDTLS_X509_BADCERT_CN_MISMATCH), indicating a certificate name mismatch.

By introducing the helper function and filtering out SAN entries that are not proper DNS names, the repair prevents attackers from exploiting the vulnerability of an overly permissive name check. This ensures that only valid DNS names are used for hostname comparison, thereby reducing the risk of an impersonation attack using alternative name types (such as IP addresses) that could otherwise be misinterpreted as valid identifiers.
