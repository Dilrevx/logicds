void verify_certificate_cn( const mbedtls_x509_crt *crt,
                            const char *cn, size_t cn_len,

{
    mbedtls_x509_name *name;

    /* If the certificate includes a SAN extension, verify via the helper */
    if( crt->ext_types & MBEDTLS_X509_EXT_SUBJECT_ALT_NAME )
    {
        if( x509_crt_verify_san( crt, cn, cn_len ) == 0 )

            /* Valid SAN match found; certificate accepted */
            return;
        }
    }

    /* Either no SAN extension or no valid SAN entry.
       Fall back to verifying the subject field's common name only. */
    for( name = &crt->subject; name != NULL; name = name->next )
    {
        if( MBEDTLS_OID_CMP( MBEDTLS_OID_AT_CN, &name->oid ) == 0 &&

        {

            return;
        }

Step by step, this repair does the following:

1. It checks if the certificate includes a SAN extension.  
2. If so, it calls a dedicated helper function (x509_crt_verify_san) that iterates over only the allowed SAN entries—ensuring that names of disallowed types (like raw IP addresses) are not considered—and immediately returns success (0) if a match is found.
3. If the SAN verification fails (or if the certificate does not have a SAN extension), the code falls back to iterating over the subject field for entries specifically marked with the common name (CN) OID.
4. If neither method finds a matching CN, the MBEDTLS_X509_BADCERT_CN_MISMATCH flag is set to indicate a certificate name mismatch.

This dual-path approach helps prevent the vulnerability where an attacker might abuse the SAN field by having a non-compliant type (e.g., an IP address) match the expected CN.
