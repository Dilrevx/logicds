The repair adds an additional check to ensure that when matching the expected common name using the subjectAltName extension, only entries that are explicit DNS names are accepted. In the original code, during the iteration of subjectAltName entries, every entry was compared against the expected name without discriminating its type. This faulty behavior allowed an attacker to register an IP address (or any other name form) in the subjectAltName field. Such a certificate could potentially match a domain name if the expected name superficially matched the IP address string, leading to an impersonation risk.

The repair changes the logic inside the loop that processes subjectAltName entries by adding a condition: it now checks if the current entry’s tag indicates that its type is MBEDTLS_X509_GENERALNAME_DNSNAME. This flag signifies that the entry is a DNS name, complying with the requirements in RFC1034 and RFC1123. In other words, the code becomes selective—it ignores subjectAltName entries that are, for example, IP addresses or other non-DNS identities. Only if the entry is of the correct DNS type does it perform the actual common name check against the expected name.

By doing so, it ensures that when a certificate contains a subjectAltName extension, the only names considered for CN matching are valid DNS names. This prevents an attacker from misusing a certificate with a controlled IP address (or similar non-DNS name) for impersonating a domain name. With this explicit type check in place, the mismatch flag (MBEDTLS_X509_BADCERT_CN_MISMATCH) is only cleared if there is a DNS entry that properly verifies the CN. If none of the subjectAltName entries qualifies, the code then correctly flags the certificate as having a CN mismatch.

The rest of the logic, where the certificate does not have a subjectAltName extension, remains unchanged. There, the matching is done against the subject field’s CN attribute. This repair strictly applies to cases where the subjectAltName extension is present, ensuring adherence to the relevant specifications on identity verification via DNS names.

In summary, by filtering subjectAltName entries to only process those that are explicitly DNS names, the repair mitigates the risk described. It prevents an attacker from exploiting misinterpreted alternate name types when matching the expected common name, thereby aligning the behavior of the certificate verification process with the intended security policies.
