The main security issue in the original code relates to how certificate common names are validated when subject alternative names (SANs) are present. In X.509 certificates, the subject alternative name extension can include multiple types of identifiers, such as domain names, IPv4 addresses, or IPv6 addresses. When a client expects a DNS name but the SAN list contains an IP address, the certificate might be erroneously validated by comparing the expected DNS name against an IP address field. This can lead attackers who can control an IP address to impersonate a DNS identity if they obtain a certificate with a matching IP in the SAN field.

To address this, our repair introduces an additional check within the loop that iterates over the list of SANs. Specifically, before comparing any SAN with the provided common name (CN), the code now inspects the type of each SAN entry. It does this by ensuring that the SAN entry’s type is MBEDTLS_X509_SAN_DNS_NAME. This filtering mechanism prevents any non-DNS SAN entries (such as IPv4 or IPv6 addresses, which would have different designated types) from being considered in the CN validation process. By doing so, our fix enforces that only the DNS-related identifiers are used when the client expects a DNS name.

In the original vulnerable code, there is a loop that directly calls x509_crt_check_cn on every entry in the SAN list without discriminating between types. If a SAN entry was, for example, an IP address that happened to match the expected pattern, the function might return success and incorrectly validate the certificate. Our change resolves this by adding a conditional statement that checks the type of each SAN entry. If the type does not match MBEDTLS_X509_SAN_DNS_NAME, the loop uses the “continue” statement to skip the entry. This ensures that the x509_crt_check_cn function is only executed for a SAN entry that is genuinely intended to represent a domain name.

Moreover, the updated iteration initialization now correctly starts at the head of the SAN list (using crt->subject_alt_names instead of &crt->subject_alt_names) which improves readability and maintains consistency with the subject name handling in the “else” block. In the absence of the SAN extension, the code continues to retrieve the common name from the subject field. The verification logic in the subject branch remains unchanged because certificates without a SAN extension typically embed the common name directly in the subject field, and thus do not face the same ambiguity of identifier type.

In summary, our repair addresses the vulnerability by ensuring that the common name comparison is performed solely on DNS type SAN entries. This prevents misinterpretation of an IP address (present in the SAN list) as a valid match for a DNS hostname. It improves the overall integrity of the certificate verification process and eliminates an attack vector where an attacker might otherwise leverage an address SAN to impersonate an expected domain name. The fix is a precise and minimal change that adapts the certificate matching logic to modern security recommendations, ensuring a strict correspondence between expected name types and the actual certificate data.
