The repair was necessary because the original code compared the expected common name (CN) against every entry found in the Subject Alternative Name (SAN) extension, regardless of the name type. In X.509 certificates, the SAN extension can include several types of names, such as DNS names and IP addresses. The vulnerability arose from not discriminating between these types. An attacker might partially exploit this by obtaining a certificate with an IP address in the SAN and then using it to pass validation when a DNS name is expected. By comparing names of varying types indiscriminately, there is a risk that one could match a seemingly valid CN even when the type is incorrect, enabling unexpected trust in a certificate that should fail verification.

The repair confines the SAN matching logic to only consider names commonly associated with domain names (DNS names). This is implemented by adding a condition that checks the tag (or type) of each entry in the SAN list before performing a string comparison. Specifically, we introduced the condition “if( cur->tag == MBEDTLS_X509_SAN_DNS_NAME && … )”. The constant MBEDTLS_X509_SAN_DNS_NAME represents an entry of the DNS name type. This check ensures that only SAN entries that are explicitly marked as DNS names are compared to the expected CN. Any SAN entry with a tag that is not of the DNS name type, such as entries representing IP addresses (either IPv4 or IPv6) or even other non-related types, are simply skipped without being included in the CN verification process.

By making this change, the certificate verification process becomes more specific. It guarantees that the CN in the certificate is only matched against DNS names which are relevant for domain name verification and are what the application expects. This helps to mitigate the potential risk where an attacker might manage to obtain control over an IP address entry in a certificate, even if controlling control over the IP for server operations would be a high bar. This also aligns with best practices in certificate validation, where the type of SAN entry should match the expected usage context. For instance, web servers typically need to validate that the DNS name provided by the user matches the DNS name in the certificate, not any other type of name.

The rest of the code remains unchanged because if the SAN extension is absent, the fallback mechanism is to check the subject field (the distinguished name) for a common name attribute. This part of the code is already correctly handling the common name validation against the subject. Thus, we do not apply any modification to that segment.

In summary, the repair effectively isolates the concern to only valid DNS names when handling SAN entries. It directly addresses the mis-handling of non-DNS name types which could previously be used to bypass expected checks. The remediation aligns with proper certificate validation practices ensuring that only appropriate name types are used during the verification of X.509 certificates. This improvement is crucial for tightening security and preventing potential certification mismatches that could arise due to permissive name type comparisons.
