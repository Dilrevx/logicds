In the repair, we added a filter to ensure that only DNS names are used when comparing names from the Subject Alternative Name (SAN) extension. Here’s how the fix works:

1. In the original code, the loop iterated over all SAN entries without checking their type. This meant that even non-DNS entries—like IP addresses—would be compared against the expected common name. Since IP addresses (IPv4 or IPv6) can be only a few bytes in size, an attacker controlling a specific IP could potentially misuse this behavior to impersonate a domain by matching the expected name to an IP address in the SAN extension.

2. The repair introduces a check right at the start of the loop: 

  if( cur->tag != MBEDTLS_X509_SAN_DNS_NAME )  
    continue;

   This condition skips over any SAN entries that are not of the DNS type. MBEDTLS_X509_SAN_DNS_NAME is assumed to be the macro representing the DNS name type. By doing so, only SAN entries that actually contain a domain name are compared with the provided expected name (the 'cn' value).

3. This change effectively means that if the certificate contains a SAN extension, the verification process ignores any non-DNS entries. It only compares entries of type DNS with the expected common name. This elimination of non-DNS comparisons prevents the possibility of an attacker leveraging IP addresses (or possibly other types) to satisfy the name match requirement.

4. In the else branch (when the certificate does not have a SAN extension), the code continues to search through the subject field for a common name (CN) using the Object Identifier (OID). That behavior remains unchanged because it does not fall under the specific vulnerability being addressed.

5. By filtering the SAN entries with this additional type-check, the repair ensures that even if an attacker manages to include alternative names in the SAN extension, only those of the proper type (i.e., DNS names) are considered. This effectively mitigates the risk of impersonation via non-DNS names, addressing the reported vulnerability.

In summary, the remedy prioritizes security by verifying that only appropriate (DNS) names from the SAN extension are matched. This targeted check avoids misinterpretation or abuse of other name types, ensuring that the certificate verification process is both accurate and resistant to the specific attack vector described.
