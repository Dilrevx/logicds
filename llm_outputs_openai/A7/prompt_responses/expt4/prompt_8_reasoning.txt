The repair focuses on the section of code that handles alternative certificate chains when an alternate trusted chain is found. In the original code, when an alternate chain was discovered, the while loop removed certificates from the chain one by one and manually decremented the last_untrusted counter each time. This manual decrement risked getting out of sync with the actual number of untrusted certificates, which could erroneously allow a leaf certificate to be treated as if it were issued by a trusted Certification Authority.

Here’s how the repair fixes the issue:

1. Removal Loop Adjustment:
 • In the original implementation, within the alternative chain checking loop, the code popped certificates off the chain and decremented the counter (ctx->last_untrusted) on every removal. This left room for error, as the manual count could easily become inaccurate.
 • The repair removes the manual decrement inside the while loop. Instead, the code purely pops certificates off the chain until the desired state is reached. This means that during the process of discarding certificates above the alternate chain point, the counter is not updated incrementally.

2. Accurate Counter Reset:
 • After the while loop that removes unnecessary certificates completes, the repair explicitly resets the counter (ctx->last_untrusted) by recalculating it based on the actual number of certificates remaining in the chain (using sk_X509_num(ctx->chain)).
 • This ensures that the counter precisely reflects the current state of the chain, which is now a trusted or alternative chain that has been correctly pruned.

3. Ensuring Chain Consistency:
 • By ensuring that the untrusted counter is correctly set to the actual chain length after pruning, the repair prevents a situation in which a mismatched counter might allow a non-trusted or improperly issued certificate to slip through as a trusted certificate.
 • This is crucial later in the verification process, where the integrity of the chain, including the exact count of untrusted certificates, is used to determine if the certificate path is valid or if any spoofing is taking place.

Overall, the changes close the vulnerability by assuring that any alternative certificate chain used in verification has been processed correctly and that the data structures (specifically the untrusted certificate counter) reliably represent the chain’s state. The removal of incremental manual updates minimizes human error in state bookkeeping, and the direct reset guarantees consistency. This fix thus mitigates the risk where a valid leaf certificate could trigger unintended verification if the chain’s state is improperly validated.
