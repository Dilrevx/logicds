The repair makes two critical changes to address the vulnerability.

First, in the original code, when an alternate chain is detected (i.e., when ok > 0), the code enters a loop that repeatedly pops certificates off the chain and manually decrements the untrusted counter (ctx->last_untrusted) with each removal. The manual decrementing can become error-prone because it may fall out of sync with the actual number of certificates in the chain. This discrepancy can lead to a situation where a leaf certificate might be treated as if it belongs to a trusted certification authority, potentially allowing attackers to spoof authority roles. The repair eliminates the manual decrement operation inside the loop. Instead, it simply removes the certificates by popping them off the chain and freeing the memory, ensuring that the chain is pruned without any immediate adjustments to the counter.

After the loop has removed the extra certificates, the repair then resets the untrusted certificate counter (ctx->last_untrusted) by recalculating the actual number of certificates remaining in the chain using sk_X509_num(ctx->chain). By setting the counter to the precise value of certificates present, the repair ensures that the bookkeeping is accurate and consistent. This accurate count is essential for later verification steps because the certificate chain’s integrity—and whether a chain is considered trusted—is partly determined by the correct count of untrusted certificates.

By making sure that the counter reflects the exact state of the chain, the patch prevents potential exploitation where the untrusted counter might have been manipulated or fell out of sync, thus misrepresenting the chain’s trust status. This is particularly important in preventing scenarios where a valid leaf certificate inadvertently triggers a chain verification that mimics a Certification Authority (CA), thereby closing the vulnerability where remote attackers could spoof a CA role.

In summary, the repair works by:
1. Removing extra certificates with a loop that only handles memory cleanup, and not adjusting the counter mid-loop.
2. Correctly recalculating and resetting the untrusted certificate counter after the cleanup is complete.

These changes ensure that subsequent certificate verifications have an accurate view of the certificate chain’s state, preserving the intended distinction between trusted and untrusted certificates. This integrity check prevents an attacker from exploiting the chain manipulation logic to obtain unintended CA privileges from a leaf certificate.
