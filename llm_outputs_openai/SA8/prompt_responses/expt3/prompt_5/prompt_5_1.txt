In this repair the roles of both client and server are handled separately so that any extension markers–which signal an insecure downgrade–are removed from the respective lists. For instance, when the session is operating in client mode the client’s key exchange method list is sanitized by removing any extension marker (such as the one defined in SSHConstants.KEX_EXTENSION_CLIENT). Similarly, when the session operates as a server the server’s methods string is inspected for the corresponding server extension marker (here assumed as SSHConstants.KEX_EXTENSION_SERVER) and, if found, is truncated to disallow any insecure negotiation parameters.

Below is a sample repair in Java-like pseudocode that implements this logic:

-----------------------------------------------------------
if (session.isClient()) {
    // Retrieve the client's key exchange methods string
    String clientKexMethods = clientMethods[SSHConstants.SSH_KEX];
    
    // Look for the insecure extension marker in client mode
    int extIndex = clientKexMethods.indexOf("," + SSHConstants.KEX_EXTENSION_CLIENT);
    if (extIndex != -1) {
        // Truncate the string up to the marker to exclude additional extension parameters
        clientMethods[SSHConstants.SSH_KEX] = clientKexMethods.substring(0, extIndex);
    }
}

if (session.isServer()) {
    // Retrieve the server's key exchange methods string
    String serverKexMethods = serverMethods[SSHConstants.SSH_KEX];
    
    // Look for the insecure extension marker in server mode
    int extIndex = serverKexMethods.indexOf("," + SSHConstants.KEX_EXTENSION_SERVER);
    if (extIndex != -1) {
        // Truncate the string to remove the extension marker and any appended parameters
        serverMethods[SSHConstants.SSH_KEX] = serverKexMethods.substring(0, extIndex);
    }
}
-----------------------------------------------------------

Explanation of the Code:
1. First, the code checks the session role using session.isClient() or session.isServer(). This explicit role separation is key to ensuring that both endpoints enforce the appropriate security restrictions.
2. In client mode, the client’s key exchange methods string is scanned for the extension “marker” (",<KEX_EXTENSION_CLIENT>"). If found, everything from that marker onward is removed.
3. Similarly, in server mode the server's key exchange methods string is scanned for an analogous marker (",<KEX_EXTENSION_SERVER>") and is truncated in the same way if the marker is found.
4. By cleaning up the method list on both sides, any possibility of an attacker causing a downgrade (such as prompting the use of ChaCha20-Poly1305 or CBC with ETM in a compromised state) is minimized.

This dual-check handling keeps integrity checks properly enforced during the handshake phase, thus mitigating the Terrapin attack vulnerability.
