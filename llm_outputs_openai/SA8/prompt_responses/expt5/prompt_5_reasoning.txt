The repair begins by distinguishing whether the current session is running as a client or as a server. This clear separation is critical because both parties in the SSH key exchange have different responsibilities in ensuring that only secure methods are negotiated.

For a client session, the code checks if the client’s key exchange methods string contains an extension marker (signaled by a predefined constant specific to client extensions). If found, the string is truncated at the detected position. This removal of any appended or extended parameters prevents the client from inadvertently accepting weaker or non-standard negotiation parameters that could lower the security of the connection.

Similarly, for a server session, the repair introduces a new block of code that mirrors the logic used on the client side. It examines the server’s list of key exchange methods for an insecure extension marker specific to server operations. If such a marker is identified, the server’s method string is likewise truncated, thereby ensuring that any insecure or unexpected extensions are excluded from the negotiation process.

This dual-check approach mitigates the risk of an attacker exploiting the absence of proper validation on one end of the connection. Previously, if only the client’s string was processed, an attacker might have been able to manipulate the negotiation from the server side (or vice versa), bypassing the integrity checks. By validating both the client and server sides, the repair eliminates the possibility that insecure or downgraded algorithms (such as those associated with ChaCha20-Poly1305 or specific CBC modes with ETM vulnerabilities) may be negotiated through crafted extensions.

Additionally, this split responsibility enhances the overall robustness of the handshake mechanism. Each side now independently enforces strict constraints on the acceptable cypher suites, thereby ensuring that even if one side’s validation were to be bypassed or misconfigured, the other side would still reject any insecure extension.

In summary, by introducing role-specific logic:

1. The client’s method list is sanitized to ensure that any optional, possibly insecure extensions are not used, which prevents an attacker from coercing the client into weakening its cryptographic options.
   
2. Correspondingly, the server’s method list undergoes the same rigorous checking and truncation, ensuring that the server won’t accept any extension that could degrade the security of the negotiated parameters.

Together, these measures effectively close the vulnerability that previously allowed for the possibility of a downgrade attack during the SSH handshake by ensuring that both endpoints enforce secure key exchange practices amid any potential extension negotiations.
