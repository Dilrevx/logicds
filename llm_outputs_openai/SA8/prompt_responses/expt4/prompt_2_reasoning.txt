The repair adds an explicit check to determine whether the session is acting as a client or a server. Previously, the code only modified the client’s key exchange methods list by removing a specific extension marker. This left the server’s list unmodified, potentially allowing an attacker to introduce insecure or downgraded key exchange method extensions on that side. By splitting the responsibilities, the revised code ensures that both client and server enforce strict boundaries on what extensions may be accepted.

For the client side, the repair verifies that the session is operating in client mode. It then retrieves the list of key exchange methods (KEX) and searches for a specific client extension marker. If the marker is found, the code truncates the string to remove any additional negotiation parameters that might allow an attacker to downgrade security. This removal is crucial because it ensures that the client does not accidentally enable optional or insecure features that could compromise the handshake’s integrity.

For the server side, a similar strategy is applied. When the session indicates that it’s acting as a server, the code retrieves a corresponding list of key exchange methods (assumed to be stored in a similar structure to the client’s methods). It then looks for a server-specific insecure extension marker. If this marker is detected, the code likewise truncates the server’s method string, ensuring that the insecure extension is not processed. This isolation on both ends of the session helps maintain consistent security requirements across the connection.

By doing this double-check, the repair addresses the Terrapin attack vulnerability. Previously, an attacker could bypass integrity checks by manipulating the negotiation process—omitting or adding packets on one side of the handshake to force the use of a vulnerable cryptographic algorithm like ChaCha20-Poly1305 or CBC with Encrypt-then-MAC. With the new changes:

1. Any additional or non-standard extensions appended to the client’s or server’s key exchange methods are detected.
2. The insecure portion (post-extension marker) is removed, preventing the use of a downgraded or undesired security feature.
3. Both endpoints now consistently enforce the allowed set of key exchange methods, preventing a mismatch in expectations during the handshake.

Overall, the repair creates a clear separation of responsibilities between the client and server in the SSH handshake process. Each side is held accountable for ensuring that only secure, expected key exchange methods are used. This prevents an attacker from exploiting lax enforcement on one side of the connection—specifically the vulnerability where attackers could bypass integrity checks by omitting certain packets—and guarantees that both parties adhere to stronger cryptographic standards.
