The repair begins by distinguishing whether the current session is operating in client mode or server mode. This separation is crucial because each side might include its own set of insecure or optional extension markers. Previously, only the client side was checked and its key exchange (KEX) string was truncated; the server side was not sanitized, potentially leaving room for an attacker to manipulate or omit packets carrying insecure information.

In the updated code, if the session is acting as a client, the code looks for a specific client-side insecure extension marker (denoted by SSHConstants.KEX_EXTENSION_CLIENT) within the client's KEX method string. If found, the method string is truncated at that marker, effectively removing any portion of the string that includes insecure or extra negotiation parameters. This ensures that the client does not accept any optional renegotiated or downgraded security features that might lower the integrity of the key exchange.

Similarly, the repair introduces a corresponding check on the server side. The code now verifies if the session is running in server mode by calling server.isServer(). If true, it searches for a server-side insecure extension marker (here represented by SSHConstants.KEX_EXTENSION_SERVER) within the server's KEX method string. Upon detection, the string is truncated in the same manner as on the client side. This ensures that the server’s list is cleansed of any entries that could potentially downgrade the negotiated security features.

After sanitizing both the client and server method strings, the code then moves into the loop where it iterates over the available key exchange methods. During each iteration, the code finds the matching algorithm between the sanitized client and server arrays and sets the corresponding KEX method to be used. The loop also contains logic for handling cipher authentication codes, specifically checking if newer AEAD constructions (like ChaCha20-Poly1305) can be used, and then setting the appropriate value. 

The loop also manages null-checks: if a required method (i.e., before the language negotiation phase) is not found, the function returns an error, preventing an improperly negotiated or insecure connection from proceeding. For any optional extended fields (typically after the main negotiation phase but before the language negotiation), the code safely sets an empty string if no corresponding method is found.

By separating the handling of client and server, and ensuring that both parties remove unsupported or insecure extension markers from their negotiation data, this repair forces both ends of the communication to only work with secure, agreed-upon methods. As a result, it mitigates the Terrapin attack by eliminating the possibility that an attacker could exploit mismatched or downgraded negotiation parameters. This stricter enforcement of the valid negotiation parameters helps ensure that integrity checks and sequence number management during the handshake phase are correctly implemented on both sides of the connection.
