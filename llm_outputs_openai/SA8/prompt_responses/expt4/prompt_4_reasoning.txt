The repair splits the processing of key exchange methods into two separate branches based on whether the session is acting as a client or as a server, addressing a critical oversight in the original code that only handled client-side extensions.

In the first branch, the code checks if the session is a client by calling session.isClient(). If true, the code retrieves the client-side key exchange methods string from clientMethods at the SSH_KEX index. It then constructs a marker string by prepending a comma to the constant defining the client-side extension. By using the findSubstring function to search for this marker in the client’s methods string, the code detects if any extended or insecure key exchange extensions have been appended. If the marker is found, it indicates that the key exchange list contains an extension that should not be accepted; therefore, the code truncates the string at the marker position using the truncateString function, effectively removing the extension parameters from the list. This ensures that only the approved, secure key exchange methods are retained for negotiation.

Similarly, the second branch handles the server scenario. The repaired code checks if the session is a server through session.isServer(). Upon confirmation, it retrieves the server’s key exchange methods string from serverMethods at the same index. A server-specific marker, formed similarly by concatenating a comma with a dedicated server extension constant, is then searched within the server string. If found, this marker signifies that the server method list also contains an insecure extension that could potentially lead to a downgrade of security. The code again applies the truncateString function to remove the unwanted extension. This dual processing is crucial as it ensures that both ends of the SSH connection implement strict policies concerning key exchange extensions, preventing any unexpected or insecure methods from influencing the final negotiated parameters.

By implementing these two checks, each tailored to the client and server roles, the repair directly mitigates the Terrapin attack vulnerability. In the original code, the oversight of only processing the client’s methods left the server’s methods unchecked, thus giving an attacker an opportunity to bypass integrity checks by exploiting the mismatch between the client and server processing. With this repair, both ends verify and clean their negotiation parameters, maintaining the integrity of the SSH handshake and preventing any downgrade or disabling of security features.

Overall, the repair enforces a robust separation of duties: clients ignore unsupported client-side extensions, and servers ignore unsupported server-side extensions. This ensures that regardless of which side initiates the connection or how the key exchange expands, both endpoints adhere to mutually secure configurations, closing the vulnerability exploitable via selective omission of key exchange parameters.
