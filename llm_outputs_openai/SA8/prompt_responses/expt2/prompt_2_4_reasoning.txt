The repair was designed to address the vulnerability by clearly segregating the handling of key exchange (KEX) methods based on the session role—client or server. The Terrapin attack exploits imbalances in how extensions appended to KEX method lists are managed during the SSH handshake. If one side receives additional or tampered extension data that is not properly validated or removed, it can lead to a downgrade of the intended security features. This repair ensures that both the client and server strictly validate and purge any extension markers that could be exploited to bypass the integrity checks associated with the SSH handshake.

For a client session, the repair begins by retrieving the existing KEX methods string that includes the available key exchange algorithms. The code constructs a specific client extension marker by prepending a comma to the identifier associated with client-side extensions. This marker is used to determine if any extra, potentially insecure, or non-standard options have been added into the handshake message. When the marker is found (i.e., the function findSubstring returns a valid position), the repair truncates the KEX string at that point. This truncation effectively removes all the data from the marker onward, ensuring that only the expected and secure algorithms remain available for key negotiation. It prevents malicious actors from injecting arbitrary extension data into the handshake process, which could otherwise lead to a weakening of the negotiated security parameters.

Similarly, for server sessions, the repair applies an analogous approach. The server’s KEX methods string is accessed and a different server-specific extension marker is constructed. This server extension marker is distinct from the client marker to maintain a clear boundary between the two roles. The code then searches for the presence of this marker in the server’s KEX string. If found, the server-side KEX string is likewise truncated to eliminate any extraneous, potentially harmful extension data. The existence of this additional check for the server side is critical because the original implementation neglected to perform any validation or cleansing for server-supplied messages. Attackers could exploit this discrepancy to balance or bypass security checks by embedding malicious extension data intended only for client handling.

The reasoning behind handling the session endpoints differently stems from the asymmetrical nature of the handshake process in SSH. By ensuring that both the client and the server actively search for and remove any non-standard extension data tailored to their respective roles, the repair tightly controls the list of allowed key exchange methods. This maintains the integrity of the cryptographic negotiation process. Each endpoint is forced to adhere strictly to predefined, secure protocols, which substantially reduces the avenues through which an attacker might force a downgrade or bypass the established security checks during the critical handshake phase.

Overall, the repair fortifies the security posture by enforcing role-based validation of extension data. This approach closes the gap that previously permitted a discrepancy between client and server handling of extensions, thereby mitigating the risk of a Terrapin attack. Both ends of the SSH connection now explicitly validate their handshake messages, eliminating potential vulnerabilities resulting from inconsistent parsing or handling of extension messages.
