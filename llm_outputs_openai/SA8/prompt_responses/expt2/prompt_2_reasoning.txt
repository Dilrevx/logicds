The repair divides the processing between client and server sessions, ensuring that both endpoints strictly enforce allowable key exchange methods during the SSH handshake.

For client sessions, the code first checks if the current session is a client using session.isClient(). It grabs the client's key exchange methods string from the clientMethods array. The code then searches for a specific extension marker—denoted by a constant (SSHConstants.KEX_EXTENSION_CLIENT)—within that string. If this marker is found, the truncateString function is used to remove the extension from the methods list. By doing this, the client prevents any insecure or unintended key exchange methods (such as those that might lead to using downgraded mAC algorithms like ChaCha20-Poly1305 or weak CBC modes) from being considered during the negotiation. This ensures that the client only processes approved and secure key exchange proposals.

For server sessions, a parallel process is introduced. When the session is identified as a server via session.isServer(), the server's key exchange methods string is similarly processed. The code looks for a different extension marker (represented by SSHConstants.KEX_EXTENSION_SERVER) that, if present, signals a potentially insecure or downgraded security feature. Once identified, the methods string is truncated to remove such extensions. This prevents the server from inadvertently negotiating weaker crypto algorithms or accepting insecure extensions that were not meant for strict server operation.

This strict separation in treatment between client and server addresses the vulnerability outlined for the SSH transport protocol. Originally, the client-side code only truncated its own method list, potentially leaving the server accepting additional, insecure options. Attackers exploiting the Terrapin attack could manipulate the handshake or omit crucial parts of the extension negotiation messages, leading one endpoint to use downgraded security algorithms. 

By incorporating disjointed checks for both roles—with each endpoint removing its own insecure markers—the repair ensures that neither side is tricked into falling back to weaker ciphers or compromised security configurations. The careful management of sequence numbers and proper handling of the handshake phase now preemptively eliminates the possibility of an attacker leveraging mismatched security parameters for a Terrapin attack.
