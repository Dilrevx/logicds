Below is one recommended patch. In the original code the call to Driver.dlzAllowZonexfr was conditioned solely on whether the DLZ‐searched list was nonempty. That meant that for writable zones where dlz_searched remained empty, the zone transfer (XFR) check was never performed.

One way to fix this is to adjust the conditional so that if the zone is writable (for example, if a “writable” flag is set on the view), then the allowzonexfr call is made regardless of whether dlz_searched is empty. For example, assuming that the view now has a Boolean flag (here called writableDLZ) to indicate a writable DLZ zone, you can update the snippet as follows:

-------------------------------------------------
    if (result != DnsResult.ISC_R_SUCCESS) {
        // Call zone transfer check if the zone was already found
        // or if it is a writable DLZ zone.
        if (!client.view.dlz_searched.isEmpty() || client.view.writableDLZ) {
            result = Driver.dlzAllowZonexfr(new DbData("dlz-db"), questionName, client.peeraddr);
            return result;
        } else {
            // [Other processing…]
-------------------------------------------------

In this fix the condition now uses an OR:
  – If there were previous DLZ search hits OR if the zone is marked as writable,
  the Driver.dlzAllowZonexfr method is called. This ensures that zone transfer controls are applied for writable DLZ zones too.

If you do not have an explicit writable flag in your view, you might need to add one or use an equivalent test that correctly identifies writable DLZ zones.

This patch makes sure that allowzonexfr is called in both cases—thereby repairing the vulnerability described.
