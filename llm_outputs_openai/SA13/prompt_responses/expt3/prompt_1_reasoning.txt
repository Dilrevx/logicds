Below is an explanation of the repair:

The original vulnerability was that writable DLZ zones were not properly checked for zone transfer permissions. The buggy code only called the allowzonexfr method if the DLZ zone had been “searched” (i.e., if client.view.dlz_searched was not empty). This condition inadvertently bypassed the permission check for certain writable zones, potentially allowing unauthorized zone transfers.

In our repair, we removed the condition that depended on the dlz_searched property. Now, whenever result is not DnsResult.ISC_R_SUCCESS, the code always invokes the dlzAllowZonexfr method regardless of whether the zone was marked in dlz_searched or not. This ensures that the proper zone transfer control is enforced consistently.

By calling dlzAllowZonexfr without checking if client.view.dlz_searched is empty, the code correctly applies the zone transfer scan to all DLZ zones. This guarantees a mandatory policy check for zone transfers, closing the vulnerability wherein writable zones could have bypassed this control.

Thus, the repair addresses the vulnerability by ensuring the allowzonexfr method is always called for error cases during DLZ queries, effectively enforcing zone transfer controls for all writable DLZ zones.
