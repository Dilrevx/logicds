Below is one example of how you might patch the issue. In the original code, any cert that’s flagged with OCSP “No Check” causes the verification mode to be changed to NO_VERIFY regardless of whether that certificate is actually part of the chain. An attacker can supply an OCSP response matching an unrelated certificate (with the NoCheck extension) to disable checking of the “real” cert that’s used in the chain. The fix is to first verify that the certificate marked with “No Check” is at least part of (or related to) the certificate chain under verification before disabling the check.

For example, assume that you have a helper function isCertInChain(cert, chain) that returns true only when cert is one of the certificates in the provided chain. Then you can change the code like this:

-----------------------------------------------------
                if (cert.ocspNoCheckSet && verify == Commons.VERIFY_OCSP 
                    && isCertInChain(cert, chain)) {
                    verify = Commons.NO_VERIFY;
                }
-----------------------------------------------------

In this example:
• The new condition “&& isCertInChain(cert, chain)” ensures that the NoCheck extension only disables OCSP verification if the certificate actually appears in (or is directly related to) the chain in question.
• If it isn’t related, the code continues to verify it normally, thereby protecting the chain from having unrelated certificates “white‐listed” by an attacker. 

Of course, the implementation of isCertInChain(cert, chain) must correctly determine the relationship (typically by matching certificate subjects, issuers, or thumbprints). This patch prevents an attacker from tricking the OCSP verification logic by using an unrelated certificate with the NoCheck extension.
