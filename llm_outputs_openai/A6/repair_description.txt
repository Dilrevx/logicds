The repair addresses a critical issue in how the AEAD cipher configuration handles nonce (IV) lengths, ensuring that only valid lengths are accepted. In the original code, when a control command was issued to set the nonce length, it checked the provided length against a constant associated with a different cipher mode (indicated by CHACHA_CTR_SIZE). This constant did not properly reflect the maximum nonce length for ChaCha20-Poly1305, which requires a 96-bit (12-byte) nonce as defined in RFC 7539, but also permits a few extra bytes under a different contextual use. The vulnerability arose because this check mistakenly allowed nonce values that were too long—up to 16 bytes. Such extended nonces could lead to situations where the application mistakenly believes it is using a unique nonce by modifying the leading bytes, even though the cryptographic algorithm disregards them. This discrepancy in nonce length validation opens the risk of nonce reuse, which is dangerous and can lead to serious confidentiality and integrity failures.

The repair begins by updating the upper bound of the permitted nonce length from the old constant to a new constant specifically defined for ChaCha20-Poly1305, namely CHACHA20_POLY1305_MAX_IVLEN. This constant correctly represents the highest acceptable length for nonce values in the context of ChaCha20-Poly1305 operations. By checking the provided nonce length against this correct maximum, the implementation prevents lengths that exceed the valid range.

The revised flow now proceeds as follows. First, upon receiving a command to set the nonce length, the code verifies that the provided length is greater than zero. In addition, it ensures that the length does not exceed the upper limit defined by CHACHA20_POLY1305_MAX_IVLEN. If the provided argument does not fall within these safe bounds, the function returns an error, thereby halting any further processing with an invalid IV size. Otherwise, if the nonce length falls within the acceptable range, the function stores this value in the internal state responsible for tracking the nonce length and ends by indicating success.

This change is crucial because the ChaCha20-Poly1305 cipher critically depends on the uniqueness of the nonce for every encryption operation. Using the wrong constant risked both accepting nonce sizes that could lead to ignored bytes (thereby masking nonce reuse) and inadvertently promoting the reuse of nonce values if applications change only part of the IV expecting the change to result in a unique nonce. By properly bounding the nonce length with the correct maximum value, the repair eliminates the possibility of misconfigured nonce sizes, safeguarding against potential attacks that exploit nonce reuse.

In summary, the repair redefines the acceptable nonce length range for ChaCha20-Poly1305 by using a proper constant check that accurately reflects the cipher’s design requirements, thus closing an avenue for serious cryptographic vulnerabilities.
