The repair addresses a crucial issue in how the nonce length is verified when setting the IV (Initialization Vector) for ChaCha20-Poly1305. Previously, the code incorrectly permitted a length up to CHACHA_CTR_SIZE (which is typically larger than 12 bytes), allowing for nonce lengths beyond what ChaCha20-Poly1305 should accept. According to RFC 7539, only a 12-byte nonce is used in authenticating and encrypting data. Permitting a longer nonce could lead developers to mistakenly believe that modifying leading bytes creates a new, unique nonce, even though OpenSSL ignores any bytes beyond the required 12. This could result in nonce reuse, which in turn risks catastrophic confidentiality and integrity failures.

Here’s how the repair works:

1. In the case for setting the IV length (EVP_CTRL_AEAD_SET_IVLEN), the repair replaces the check that previously compared the argument “arg” with CHACHA_CTR_SIZE. Instead, it now uses a constant called CHACHA20_POLY1305_MAX_IVLEN. This constant is defined to match the correct maximum length (typically 12 bytes) as dictated by RFC 7539 for ChaCha20-Poly1305. The check now ensures that the provided nonce length is both positive and does not exceed CHACHA20_POLY1305_MAX_IVLEN. If the provided value is outside these bounds, the function returns an error.

2. With the corrected validation in place, any attempt to set an IV length that isn’t strictly within the accepted range will be rejected immediately. This prevents the caller from inadvertently using improper nonce lengths, which is critical because a nonce that is too long might lead to only the trailing 12 bytes being used—thus potentially reusing the nonce if the application assumes the full provided nonce is used.

3. By enforcing the correct nonce length during the encryption initialization, the repair helps guarantee that the ChaCha20-Poly1305 cipher is used according to its specification. This preserves the unique and crucial requirement that every nonce must be used only once, meaning even subtle mistakes in handling nonce bytes are avoided.

Overall, the repair tightens the security of the application by using a constant (CHACHA20_POLY1305_MAX_IVLEN) that reflects the true limits placed by the cipher’s design. It ensures that developers cannot inadvertently set a nonce length that might lead to accidental reuse. In summary, the repair aligns the nonce length validation with both the cryptographic specification and best practices, thereby reducing the risk of severe security vulnerabilities arising from nonce reuse in an AEAD scheme.
