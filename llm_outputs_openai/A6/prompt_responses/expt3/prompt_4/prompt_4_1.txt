The issue is that the code permits any nonce length between 1 and CHACHA_CTR_SIZE (typically 16 bytes) even though ChaCha20‐Poly1305 requires exactly a 12‐byte nonce (96 bits) per RFC 7539. Allowing nonce lengths other than 12 bytes can lead to reuse of nonces due to the way OpenSSL pads the nonce when it is less than 12 bytes and ignores extra leading bytes in longer nonces. This inadvertently breaks the uniqueness guarantee and can compromise both confidentiality and integrity.

To fix this vulnerability, the code should enforce that the nonce length (arg) is exactly 12 bytes. For example, assuming a defined constant for the required nonce size (say, CHACHA20_POLY1305_NONCE_SIZE equal to 12), the fixed code becomes:

--------------------------------------------------
    #define CHACHA20_POLY1305_NONCE_SIZE 12

    case EVP_CTRL_AEAD_SET_IVLEN:
        if (arg != CHACHA20_POLY1305_NONCE_SIZE)
            return 0;
        actx->nonce_len = arg;
        return 1;
--------------------------------------------------

• The check now requires that the provided nonce length (arg) is exactly 12.
• If arg is not 12, the function returns 0 (an error), preventing insecure usage.
• This change ensures that every encryption operation uses a 12‐byte nonce, maintaining the necessary properties for ChaCha20-Poly1305.

By enforcing the nonce length strictly, the vulnerability where a longer nonce might be used (and its leading bytes ignored) is mitigated, preserving the cryptographic strength of the scheme.
