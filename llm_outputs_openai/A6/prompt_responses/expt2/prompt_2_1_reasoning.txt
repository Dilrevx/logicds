In the buggy code, the check allowed any nonce length up to CHACHA_CTR_SIZE, which is inappropriate because it does not precisely reflect the security requirements for ChaCha20-Poly1305. The vulnerability arises because if a nonce longer than 12 bytes is accepted, the additional leading bytes are effectively disregarded by the underlying OpenSSL implementation. This discrepancy may create a false sense of uniqueness when an application modifies the leading bytes, thinking it has generated a new nonce. In truth, the encryption operation uses only the last 12 bytes of the provided nonce. If those trailing 12 bytes repeat, even though the complete nonce appears different, it results in the actual reuse of nonce values. Reusing the nonce in an AEAD cipher such as ChaCha20-Poly1305 can lead to devastating cryptographic failures including leakage of sensitive information and corruption of the integrity guarantees provided by the MAC component.

To mitigate this risk, the repair modifies the conditional check in the control command case that is responsible for setting the nonce length.
