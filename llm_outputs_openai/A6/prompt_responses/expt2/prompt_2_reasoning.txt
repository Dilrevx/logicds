This could lead to developers mistakenly believing that changing those extra bytes would produce a unique nonce. If the unique nonce requirement is violated, it could lead to catastrophic confidentiality and integrity breaches.

By enforcing this check, the repair ensures that any nonce provided must be within a range that the cipher supports without ambiguity. This eliminates the risk that altering any bytes outside the allowed range could inadvertently create a reused nonce scenario.

Once the provided nonce length passes the updated validation check, the code assigns this value to the context’s nonce_len field. Such silent misinterpretation is dangerous, as nonce reuse in AEAD ciphers like ChaCha20-Poly1305 can compromise both confidentiality and integrity, allowing attackers to potentially recover plaintexts or forge messages.
