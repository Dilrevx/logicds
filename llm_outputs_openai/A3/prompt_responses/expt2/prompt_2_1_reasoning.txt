The repair introduced in the code focuses on ensuring that custom ciphers created using legacy methods are explicitly handled rather than inadvertently replaced by provider-based implementations. Originally, the code only checked for the presence of non-null pointers (such as an engine, temporary implementation, or provided implementation) to decide whether to follow the legacy code path. However, the vulnerability arises when a custom cipher—created via the legacy EVP_CIPHER_meth_new() routine with an improper NID (specifically NID_undef)—ends up matching the NULL cipher in the default provider. In such a scenario, the provider returns a NULL cipher, and encryption proceeds with plaintext output as ciphertext. The repair adds two new conditions to the if-statement to catch this case.

The first additional condition explicitly checks whether a locally available cipher object is non-null and flagged as legacy using a helper function (EVP_CIPHER_is_legacy). This function is responsible for determining whether the cipher was created by the legacy routines. By checking this, the code can ascertain that the provided cipher was initialized in a manner that might have been susceptible to the vulnerability, thereby forcing the code to take the legacy branch no matter the state of other implementation-specific pointers.

The second new condition covers cases where the explicit local cipher pointer is NULL, but the ctx->cipher field is not. It then verifies whether the cipher stored in ctx->cipher has the legacy flag set. This is significant because, in many flows, the legacy cipher might reside in the context rather than being directly passed via the local pointer. By ensuring that such a cipher is correctly recognized, the repair guarantees that all possible legacy ciphers are processed via the legacy handling path. This prevents any unintended fallback to the provider’s cipher implementation, which could lead to using the undesired NULL cipher.

Once the conditions are met, the repair code then de-associates any potentially dangerous fetched cipher by comparing ctx->cipher with ctx->fetched_cipher. If they are the same, it explicitly nullifies ctx->cipher and frees the fetched_cipher, thereby removing any provider-sourced cipher that might have been wrongly substituted due to the NID misconfiguration. This cleanup is critical because it prevents the use of a cipher that was obtained erroneously from the provider mechanism and which may perform no encryption at all.

After ensuring that the mistakenly fetched cipher is cleared, the execution jumps to the legacy initialization label. By doing so, the code ensures that the subsequent initialization process uses the intended legacy methods, which understand and correctly handle custom cipher implementations even if NID_undef was used. Overall, these modifications close the security gap by verifying the origin of the cipher and by enforcing the correct processing path for legacy ciphers. This prevents the potential risk of exposing plaintext encryption, thereby maintaining the confidentiality of sensitive information and ensuring that custom cipher implementations behave as expected. The repair is a targeted fix that preserves existing functionality while effectively mitigating a critical vulnerability introduced in OpenSSL versions 3.0.0 to 3.0.5.
