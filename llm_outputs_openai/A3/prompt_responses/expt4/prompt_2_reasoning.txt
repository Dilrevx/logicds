The repair adds two extra conditions to the if statement that check if the cipher (or the fetched cipher) was created using legacy custom methods. Here's a breakdown of how the modifications work to fix the vulnerability:

1. Existing Conditions:
   • The original code checked if certain pointers like the engine, an alternative implementation (tmpimpl), or the implementation (impl) are not NULL.
   • If any of these conditions are true, then the code treats the current cipher as potentially coming from non-standard sources and jumps to the legacy handling branch.

2. New Conditions:
   • The first additional condition checks if ctx->cipher is non-NULL and if this cipher has the flag indicating it was created using the legacy custom method (identified by EVP_CIPH_FLAG_CUSTOM_LEGACY). This flag signals that the cipher was created by older methods, perhaps with an undefined NID that could match the NULL cipher.
   • The second condition deals with the scenario where the primary cipher pointer (ctx->cipher) is NULL, but the ctx->fetched_cipher is still present and carries the legacy custom marker. This ensures that even if the primary pointer is unset, any legacy-derived cipher in the fallback slot is properly detected.
  
3. What Happens if Conditions are Met:
   • When any of these new conditions (or the older ones) are true, the code enters the if branch. Inside that branch, it first checks if the primary cipher pointer equals the fetched cipher pointer, and if so, it sets the primary pointer to NULL.
   • It then frees the fetched cipher and nullifies the fetched_cipher pointer.
   • Finally, it jumps to the legacy branch (label "legacy") for special handling.
  
4. How It Fixes the Vulnerability:
   • The core vulnerability was that OpenSSL might fetch a cipher from an available provider using a mistakenly provided undefined NID (like NID_undef). This bad behavior could inadvertently select the NULL cipher, meaning that encryption would be bypassed entirely (producing plaintext ciphertext).
   • By explicitly checking for legacy origins via the new flags, the code now recognizes any cipher that was created using the legacy custom functions. It prevents these ciphers from getting mixed up with equivalent provider ciphers.
   • This avoids a situation where an undefined cipher identifier triggers fetching the NULL cipher, because the code correctly diverts legacy ciphers to the specialized legacy handling pathway, ensuring that they are not replaced by a potentially dangerous provider cipher.
  
In summary, the repair ensures that if a cipher or fetched cipher originates from a legacy custom setup, the code clearly identifies it through the custom legacy flag and routes it through a safe legacy handling process. This prevents the inadvertent use of the NULL cipher, effectively mitigating the vulnerability where plaintext might be emitted as ciphertext.
