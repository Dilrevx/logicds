The fix is to add extra conditions (by checking a new “origin” field) so that if the cipher comes from the legacy custom method, we always branch to the legacy handling code rather than attempting a substitution with a provider cipher.

1. If the primary cipher is non-null and its “origin” field indicates that it was created using the legacy method, then we know to handle it in the legacy branch.
2. Even if ctx->cipher is null, if the fetched cipher (or some context field maintained for legacy ciphers) is present and flagged as coming from the legacy custom method, we likewise transition to the legacy branch.

1. The original code checked for various non-NULL pointers (like an engine, tmpimpl, or impl) to decide whether to use the “legacy” branch. However, the problem was that a legacy custom cipher with an undefined NID was not detected.
2. We add two extra disjunct conditions:

   - The second condition handles the scenario where the primary ctx->cipher is NULL but a fetched legacy cipher is still present.
3. If any one of these conditions is true, the code frees the fetched cipher (after cleaning up pointer state) and jumps to the legacy branch.
4. This prevents the later code from mistakenly using a legacy cipher (with a bad, undefined NID) to search for a provider-based cipher (which may retrieve the NULL cipher).

This patch thereby prevents the unintended matching of an undefined cipher to the NULL cipher.
