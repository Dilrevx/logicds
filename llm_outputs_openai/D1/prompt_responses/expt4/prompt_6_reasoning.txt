The repair addresses the vulnerability by ensuring that the SRTP transport’s current cryptographic policies (for both transmission and reception) are saved before the transport state is reset. Previously, the code would stop the SRTP transport first, which could inadvertently clear or modify key internal state (such as crypto policies or roll-over counters) needed for proper reinitialization. This could lead to a scenario where, after a restart, SRTP is not properly reestablished and falls back to using basic RTP, causing insecure media transmission.

Here’s a walkthrough of the key changes:

1. Preservation of Crypto Policies:
  • The repair first saves the current transmit (tx_policy) and receive (rx_policy) crypto policies into local variables right before stopping the SRTP transport. This guarantees that the original, unaltered security parameters are captured.
  • By preserving these settings (tx and rx), the restart process will have the exact policies needed for reinitialization.

2. Stopping the SRTP Transport:
  • After saving the required policies, the code then calls pjmedia_transport_srtp_stop() to stop the current SRTP operation. At this point, it’s normal for some internal state to be reset.
  • The previously saved crypto policies ensure that any necessary state required for proper security is not lost in the process.

3. Restarting SRTP with Preserved Policies:
  • Following the stop, the repair issues a restart command using pjmedia_transport_srtp_start(), supplying the preserved tx and rx policies.
  • This step is critical because the restart now occurs with the exact same policy parameters, preserving the integrity of the media's encryption.
  • If the restart fails, an error is logged to facilitate debugging and troubleshooting.

4. Reattempting SRTP Unprotection:
  • In the event of a restart, if the SRTP transport is still active (i.e., bypass_srtp is false), the code then reattempts to unprotect the packet using srtp_unprotect(). This ensures that incoming packets are processed under the secure, reinitialized context rather than mistakenly being treated as insecure RTP.

By reordering these operations—saving policies before stopping the transport—the repair ensures that no critical security information is lost. This correct ordering is essential to maintaining continuous SRTP protection during restart scenarios. Ultimately, these changes uphold the secure handling of media packets, thereby fixing the vulnerability that previously allowed a switch to insecure basic RTP data transmission.

In summary, the repair guarantees that the correct SRTP parameters are maintained during a restart, preventing the accidental fallback to an insecure mode and protecting the integrity of the media stream.
