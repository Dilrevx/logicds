Below is an example showing the change made to the DTLS handshake code. In the original version, the code used a condition like:

  if (helloVerifyRequestCount == 0) {
    /* Issue: the client random value was never really randomized */
    memset(client_random, 0, sizeof(client_random));  // Insecure: fills with zeros
  } else {
    RAND_bytes(client_random, sizeof(client_random)); // Safe: uses cryptographically secure randomness
  }

Because the DTLS specification requires that the client random value carry proper entropy once a HelloVerifyRequest is received, the bug was that the condition was inverted – the client random was generated (or left as a constant zero value) when no HelloVerifyRequest had been processed.

The repair inverts this condition so that the random value is generated only after at least one HelloVerifyRequest has been received. The corrected code looks like this:

  if (using_dtls_handshake) {
    if (helloVerifyRequestCount != 0) {
      /* Now that we know a HelloVerifyRequest was received,
      generate a genuine random value. */
      if (RAND_bytes(client_random, sizeof(client_random)) != 1) {
        /* Handle error: random generation failed */
      }
    } else {
      /* Optionally, delay generating the client random until after the HelloVerifyRequest is processed */
    }
  }

Key points in the repair:

1. Instead of checking for helloVerifyRequestCount equal to zero, the code now checks for a nonzero count:
  if (helloVerifyRequestCount != 0)
   This way, the client random is generated only after a HelloVerifyRequest has been received.

2. The call to RAND_bytes() (or an equivalent secure random generator) replaces any insecure default initialization (such as setting the bytes to zero).

3. This change adheres to DTLS protocol requirements by ensuring that the client random contains cryptographically strong randomness. Without this, the handshake could be vulnerable to replay or prediction attacks.

By applying this change, the handshake process now correctly uses strong randomness for DTLS sessions, thus repairing the vulnerability.
