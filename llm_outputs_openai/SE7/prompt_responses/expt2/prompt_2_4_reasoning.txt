The repair was focused on addressing a critical security vulnerability in the processing of plaintext NAS (Non-Access Stratum) messages in the system. Originally, the code allowed several sensitive NAS message types—such as Detach Request, EMM Information, and EMM Status—to be processed even when they were not accompanied by integrity protection. This design flaw posed a significant risk, as attackers might be able to send malicious or manipulated messages in plaintext, bypassing built-in security checks and potentially causing denial-of-service conditions or unauthorized signaling actions.

The initial implementation checked whether the message header indicated a plaintext NAS message (i.e., lacking integrity protection) and then employed a switch-case to determine whether the specific message type should be processed. The core problem was that the original list within the switch statement included message types that should be secured and not treated as safe. In effect, allowing messages like Detach Request, EMM Information, and EMM Status in plaintext opened the door to exploitation. For example, if an attacker could force a mobile device to process a Detach Request, it might lead to unwanted disconnections or service interruption. Similarly, processing EMM Information and EMM Status messages without verification could expose vulnerabilities that allow unauthorized information disclosure or manipulation of the mobile subscriber’s state.

In the repair, the list of allowed message types for plaintext processing was intentionally tightened down. The modified switch-case now only permits a smaller, safer subset of message types: those that are essential for the initial phases of connection setup or failure recovery, like Identity Request and Authentication-related messages (Authentication Request and Authentication Reject) and some responses such as Detach Accept and Tracking Area Update Reject. These messages are deemed safe to process even when integrity protection is not present because they either serve to guide the establishment of a connection with proper security later or are part of error recovery mechanisms that do not carry sensitive control signals.

The decision to remove the cases for Detach Request, EMM Information, and EMM Status was deliberate. By removing these cases, any attempt to process such messages without proper integrity protection now falls to the default branch of the switch statement. When the default branch is executed, it logs an error message detailing both the message type and the security header type, and then returns an error code (SRSRAN_ERROR). This behavior effectively blocks the processing of potentially unsafe plaintext messages, ensuring that only messages which have been explicitly audited and deemed safe are processed when integrity protection is absent.

This repair streamlines the control flow and secures the processing of NAS messages. By adopting a "fail secure" approach—where any message not explicitly allowed is rejected—it avoids ambiguity in security policy enforcement. This reduces the likelihood that future modifications to the code will inadvertently reintroduce vulnerability by adding insecure message types. In summary, the repair enhances the code's security posture by ensuring that only a minimal, well-defined set of NAS messages can be accepted in plaintext, and by enforcing strict logging and error handling when unsafe messages are encountered. This not only minimizes the attack surface but also promotes a more robust security framework that safeguards against potential exploits exploiting plaintext NAS communications.
