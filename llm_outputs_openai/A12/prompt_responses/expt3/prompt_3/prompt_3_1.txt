The root cause is that even when mutual authentication is required (for example, when ssl->options.verifyPeer is set) the code does not verify that the client sent its certificate‐verify message. In order to require a valid client certificate, an explicit check must be added so that if the client did not send a valid certificate_verify message, the handshake is aborted. (In your code base you may track the presence of the CertificateVerify with a flag such as ssl->receivedCertVerify.)

One example patch is as follows:

/* Existing context */

if ((ssl->options.verifyPeer) && (ssl->receivedCertVerify != 1)) {
    /* Optionally, log the error here */
    return MUTUAL_AUTH_FAILED;  /* Use an appropriate error code */

if (ssl->options.handShakeDone) {
    ret = DeriveFinishedSecret(ssl, ssl->clientSecret,

    if (ret != 0)

    secret = ssl->keys.client_write_MAC_secret;
}

Step by step explanation:
1. The patch adds a conditional check immediately after verifying buffer sizes. It checks if mutual authentication is required (here assumed as ssl->options.verifyPeer being true) and then verifies that the CertificateVerify message has been received (tracked by ssl->receivedCertVerify).
2. If the flag is not set (i.e. ssl->receivedCertVerify is not equal to 1), the function returns an error (MUTUAL_AUTH_FAILED). You can define or map this error code to a proper error code in your system.
3. If the check passes, the code continues with deriving the Finished secret.

Adjust the variable names (like ssl->receivedCertVerify and error code MUTUAL_AUTH_FAILED) as needed to match your code base. This repair ensures that a client cannot bypass mutual authentication by omitting the certificate_verify message.
