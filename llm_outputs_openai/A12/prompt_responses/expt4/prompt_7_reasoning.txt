The repair adds an additional check in the Finished message processing to verify that, when running as a TLS v1.3 server that requires mutual authentication, the client actually sent its certificate verification message. This is done by checking a flag (ssl->gotCertVerify) that should have been set earlier when the certificate_verify message was processed.

Here’s how the repair works:

1. After computing the expected Finished message hash (using BuildTls13HandshakeHmac) and verifying that the received Finished data matches the computed MAC, the code now checks that if the entity is a server (ssl->options.side == WOLFSSL_SERVER_END) and mutual authentication is in use, then ssl->gotCertVerify must be true. This flag is assumed to be set during proper processing of the certificate_verify message.

2. The check is conditional on the TLS context indicating that peer verification is enabled (ssl->ctx->verifyPeer). This serves as an indication that mutual authentication is required (i.e., the server expects a valid client certificate along with its certificate_verify message).

3. If the flag is not set (indicating the client did not send or properly process the certificate_verify message) and mutual authentication is required, then the repair logs an error message, sends an alert (with a fatal bad_certificate alert), and returns a CERTIFICATE_VERIFY_MISSING_ERROR. This forces the handshake to fail, preventing a malicious client from bypassing certification verification.

4. The added check is placed strategically after Finished message verification. This ensures that even if an attacker bypassed the certificate_verify message earlier in the handshake, the server will not complete the handshake without confirming that the client presented a valid certificate_verify.

By introducing this additional safeguard, the vulnerability is mitigated because the server will no longer allow clients to complete the handshake without having submitted a certificate_verify message when mutual authentication is expected. Thus, if a malicious client omits the certificate_verify message in a TLS v1.3 handshake, the connection will be terminated and not allowed to proceed.

In summary, the repair ensures that the expected certificate_verify message has been received and properly processed, reinforcing mutual authentication and closing the bypass vulnerability mentioned in the description.
