The repair adds an early validation step at the beginning of the function to verify that when the server expects mutual authentication, it has indeed received the client’s certificate verification. This early check is crucial because it prevents a malicious client from bypassing mutual authentication by simply not sending the certificate_verify message.

Here’s how the repair works:

1. It first checks if the current instance is running on the server side (ssl->options.side == WOLFSSL_SERVER_END) and only performs the additional check when sniffing is disabled (sniff == NO_SNIFF). This ensures that the check applies only during an actual handshake rather than during packet sniffer operations.

2. The repair then verifies whether mutual authentication is required by checking the flag ssl->requireClientCert. This flag should be set when the server configuration mandates a client certificate.

3. Additionally, to avoid interfering with certain conditions like session resumption, it checks that the session is not resumed (ssl->sessionResumed) since mutual authentication might be relaxed in that case.

4. Finally, it checks if the certificate verification message has been processed (ssl->receivedCertVerify). If this flag is false, it indicates that the client did not send the required certificate_verify message, which is necessary for proper mutual authentication.

If all these conditions hold true (meaning that the server is expecting a certificate and the client hasn’t provided it), the repair logs a message, sends a fatal alert (using SendAlert) with an appropriate error like bad_certificate, and then returns an error code (CERTIFICATE_VERIFY_MISSING) immediately. This halts the handshake process before any further processing, ensuring that no keys are derived or handshake messages processed under insecure conditions.

By inserting this early termination, the repair ensures that the handshake does not proceed if the client fails to provide a certificate when one is mandated. This directly addresses the vulnerability by ensuring the server does not mistakenly accept connections from clients that skip the certificate_verify step, thereby reinforcing mutual authentication for TLS 1.3 sessions.

The rest of the function then continues the normal handshake processing only if the certificate_verify message has been received properly. Thus, if the early check passes (i.e., when the client has presented their certificate correctly), the subsequent steps for secret derivation, HMAC calculation, and final verification proceed as before. This means that the vulnerability is mitigated without affecting correct behavior when proper authentication is followed.

Overall, the repair effectively prevents an attacker from bypassing client certificate verification by enforcing a strict check early in the handshake process and rejecting connections that do not meet the mutual authentication requirements.
