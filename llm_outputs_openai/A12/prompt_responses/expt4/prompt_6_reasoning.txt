The repair adds an early check at the beginning of the function to ensure that when mutual authentication is required, the client has indeed sent the certificate_verify message. Here's a step-by-step explanation of how this change fixes the vulnerability:

1. Server-side and Mutual Authentication Check:
   - The code first confirms that it is running on the server side (ssl->options.side equals WOLFSSL_SERVER_END).
   - It then checks whether mutual authentication is required by verifying a flag (for instance, ssl->options.requireMutualAuth). This flag is assumed to be set in configurations where the server demands a client certificate.
   - Additionally, it checks if the session is not a resumed session (ssl->sessionResumed) because mutual authentication might only be strictly enforced on new handshakes.

2. Verification of Certificate Presence:
   - The new code examines a flag (ssl->receivedCertVerify) that should have been set when the client successfully processed and sent the certificate_verify message.
   - If the flag is not set when it should be (i.e., if the client did not send its certificate verification), the repair logs a message, triggers a fatal alert using SendAlert, and returns an error (VERIFY_PEER_CERT_ERROR). This immediate abort prevents further progression of the handshake without the required certificate verification.

3. Early Termination:
   - By performing this check before any further processing (like verifying sizes or deriving finished secrets), the repair ensures that the handshake does not proceed under insecure conditions. This effectively mitigates the vulnerability where a malicious client could bypass mutual authentication simply by omitting the certificate_verify step.

4. Normal Processing Otherwise:
   - Once the early check is satisfied (i.e., the certificate_verify message is confirmed to be present), the function continues with its usual processing—calculating the finished secret, verifying the HMAC of the handshake, and setting up the client or server finished state.
   - This ensures that the rest of the TLS handshake remains unchanged and functions as originally designed when proper authentication occurs.

In summary, the repair fortifies the TLS 1.3 mutual authentication process by ensuring that if a certificate is required, the connection is aborted immediately when the client fails to send the certificate_verify message. This crucial verification step prevents attackers from exploiting the absence of the certificate_verify message to bypass the intended authentication mechanism, thereby sealing the vulnerability effectively.
