The repair adds an early validation step to ensure that, on a server set up for mutual authentication, the client’s certificate has been verified before continuing with the handshake. Previously, a malicious client could bypass the requirement to present a certificate by simply omitting the certificate_verify message. This vulnerability allowed an unauthorized client to proceed with a TLS connection even when mutual authentication was expected.

In the updated code snippet, after entering the function with WOLFSSL_START and WOLFSSL_ENTER, the repair first checks if the connection is running on the server side (ssl->options.isServer), and then it verifies two additional conditions: whether mutual authentication is required (ssl->options.requireMutualAuth or ssl->options.strictCertPolicy) and that the session isn’t being resumed (ssl->sessionResumed). The resume exception is important because, during session resumption, the handshake process may not re-negotiate the certificate details as strictly. 

The key check here is if the client’s certificate was verified (indicated by ssl->clientCertVerified). If this flag isn’t set, the code concludes that the certificate verification step was skipped by the client. At this point, the code logs a message that the required certificate_verify message is missing, sends a fatal handshake failure alert using SendFatalAlert, and then returns an error code (NO_CERTIFICATE_E). This immediate exit prevents the handshake process from continuing under insecure conditions.

Following the new check, the rest of the function remains unchanged. The original logic that verifies the message size and attempts to derive finished secrets only executes if the certificate check passes. Thus, the handshake will securely proceed only if the client has met the mutual authentication requirements imposed by the server’s configuration.

By inserting this early guard check, the repair effectively blocks any attempt by a malicious client to bypass the certificate requirement. This ensures that the mutual authentication mechanism in TLS v1.3 is enforced, preventing potential security breaches where unauthorized clients might otherwise gain access by neglecting to include a certificate_verify message.

Overall, this repair strengthens the TLS handshake by integrating a direct validation of the client’s certificate status, stopping the handshake early with an error and fatal alert if the validation condition fails. This guarantees that the integrity of the security protocol is maintained, and that both parties in the TLS session can be confident that the authentication process has been correctly executed.
