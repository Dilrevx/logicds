The repair addresses a critical vulnerability in the TLS v1.3 protocol implementation, specifically concerning mutual authentication between a server and a client. In the original buggy code, the server did not properly enforce the requirement for the client to present a certificate during the handshake process. This oversight allowed malicious clients to bypass the mutual authentication step by simply omitting the `certificate_verify` message, thus connecting to the server without providing the necessary credentials.

To understand why this is a significant security issue, it's important to recognize the purpose of mutual authentication in TLS. Mutual authentication ensures that both parties involved in the communication are verified and trusted. In the context of TLS v1.3, when a server requires mutual authentication, it expects the client to provide a certificate that proves its identity. The `certificate_verify` message is part of this process, as it contains a signature from the client that verifies they possess the private key corresponding to the public key in their certificate.

The repair introduces a crucial check before proceeding with the rest of the handshake process. It first determines whether the current entity is a server (`ssl->options.side == WOLFSSL_SERVER_END`) and whether mutual authentication is required (`ssl->options.mutualAuth || ssl->options.failNoCert`). If these conditions are met, the server then checks if the client has provided a valid certificate (`ssl->options.havePeerVerify`) and if the session is not being resumed (`!ssl->options.resuming`). Resuming a session typically means that the server already trusts the client from a previous interaction, so no new certificate verification is necessary.

If the client has not provided a certificate and mutual authentication is required, the server responds with a fatal alert indicating that no peer certificate was received (`NO_PEER_CERT`). This prevents the handshake from progressing further, ensuring that the connection cannot be established without proper authentication.

By adding this check, the repair ensures that the server strictly enforces the requirement for mutual authentication, thereby preventing unauthorized access and maintaining the integrity and security of the communication channel. This change aligns with the expected behavior of TLS v1.3, where mutual authentication is a fundamental aspect of secure communication, especially in environments where both parties need to verify each other's identities.
