The repair adds an extra comparison to ensure that the ASN.1 tag of the algorithm parameters is identical between the certificate and the expected value. Previously, the code only checked if the lengths and, if nonzero, the content of the parameters were the same. This allowed a scenario where a parameter explicitly set to NULL (which carries a specific tag in ASN.1 encoding) could be mistaken for an empty array of REAL values (which might also have a zero length), thus incorrectly validating the certificate.

Here’s a step-by-step walkthrough of the repair:

1. The first two conditions remain unchanged:
   • It first checks if the signature algorithm OID lengths match.
   • It then compares the actual content of the OID bytes from the certificate (crt->sig_oid) with the expected one (sig_oid2). This confirms that the basic algorithm identifiers are the same.

2. Next, the repair introduces a new check comparing the tag fields of the algorithm parameters (sig_params1 and sig_params2). In ASN.1 encoding, the tag indicates the type of data (e.g., NULL, INTEGER, etc.). By comparing these tags (sig_params1.tag != sig_params2.tag), the code now differentiates between a parameter that is explicitly NULL and one that is an empty array. This comparison is critical because even if both are “zerolength”, a NULL parameter is semantically different from an empty array of REAL values. The new tag check thus prevents the vulnerability by ensuring the type consistency of the parameters.

3. After the tag comparison, the repair continues with the existing logic by verifying the lengths of the parameter arrays. This step makes sure that even if the tags match, any discrepancy in the length of the parameters will trigger a mismatch. This guards against cases where the content might be off, even if it appears to be valid by type.

4. Finally, if the parameter lengths are non-zero, the repair performs a byte-for-byte memory comparison of the parameters. This ensures that the actual encoding of the parameters in both the certificate and the expected value exactly matches.

This systematic approach—first comparing the OID, then the tags, followed by the lengths, and finally the content—ensures that every aspect of the parameters is properly validated. It guarantees that the certificate’s parameters are the exact type and value expected, so that certificates with mismatched parameter types (NULL versus empty arrays) or contents are correctly identified as invalid. Hence, this fix directly addresses the vulnerability by preventing certificates with malformed or misinterpreted parameters from being erroneously accepted.
