Below is one way to repair the code.

▸ Background

The vulnerability is that a NULL algorithm parameters entry (i.e. when the pointer is NULL) is treated as “empty” (length zero). That means an explicitly absent field (NULL) will compare equal to a present empty (zero‐length) field, even though they represent different conditions. In some cases the parameters must either be both “absent” or they must match exactly (including their internal encoding).

▸ The issue in the buggy code

The original code only compares the lengths and, when nonzero, calls memcmp. In particular, when the length is zero, the memory pointed to by the parameter is never checked. As a result, one entry encoded as “NULL” (with its pointer set to NULL) and another encoded as an empty array (pointer non‑NULL but zero length) wind up being accepted as matching. This is not acceptable since a mismatch in the presence of parameters should cause validation to fail.

▸ The repair

We must add an explicit check so that if one algorithm parameters pointer is NULL and the other is not (even in the case of a zero length), then the certificate is considered invalid. In other words, the test must ensure that either both parameters (pointers) are NULL or both are non‑NULL; and then, if non‑NULL, if the lengths are the same and (if not zero) the contents are identical.

▸ Example of a repaired code snippet

Below is one way to fix the vulnerability:

------------------------------------------------------------
    /* First check that the signature OIDs match */
    if( crt->sig_oid.len != sig_oid2.len ||
        memcmp( crt->sig_oid.p, sig_oid2.p, crt->sig_oid.len ) != 0 )
    {
        mbedtls_x509_crt_free( crt );
        return( MBEDTLS_ERR_X509_SIG_MISMATCH );
    }

    /* Now compare the algorithm parameters. 
       First ensure that both pointers are either NULL or non-NULL.
       Then check that the lengths match.
       Lastly, if non-zero length, compare the actual contents. */
    if( ((sig_params1.p == NULL) != (sig_params2.p == NULL)) ||
        (sig_params1.len != sig_params2.len) ||
        (sig_params1.len != 0 && 
         memcmp( sig_params1.p, sig_params2.p, sig_params1.len ) != 0) )
    {
        mbedtls_x509_crt_free( crt );
        return( MBEDTLS_ERR_X509_SIG_MISMATCH );
    }
------------------------------------------------------------

▸ Explanation

1. The code first verifies that the signature OIDs match exactly.
2. For the parameters, it now begins by comparing the pointers. The expression (sig_params1.p == NULL) != (sig_params2.p == NULL) evaluates to true if one is NULL but the other isn’t.
3. Next, it checks if the lengths match.
4. Finally, if there is data (i.e. length is non‑zero) the code uses memcmp to verify that the memory buffers are identical.

With these additional checks the comparison no longer “confuses” a NULL (absent) field with an explicitly present (but empty) field, thereby fixing the vulnerability.
