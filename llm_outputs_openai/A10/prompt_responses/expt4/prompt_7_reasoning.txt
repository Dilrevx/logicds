The fix ensures that when comparing the two sets of parameters used in the signature algorithm, the code does not mistakenly accept an empty (zero-length) parameter field. In the original code, if both sig_params1 and sig_params2 had a length of zero, they would compare as equal, and the certificate would be accepted even though a NULL (or absent) parameter isn’t permitted according to the standard. 

Here’s what’s changed:

1. In the check that follows the call to mbedtls_x509_get_alg() for the signature algorithm after processing the TBSCertificate, the repaired code now explicitly checks if sig_params1.len is zero. This additional condition (“sig_params1.len == 0”) causes the function to return a signature mismatch error if the algorithm parameters field is empty. 

2. The code still compares both the object identifiers (the algorithm OIDs) of the signature algorithm and their associated parameters. The memcmp shows that if the OIDs or the parameters (when non-empty) don’t match exactly, the certificate will be rejected. This is important because, per the vulnerability description, a NULL algorithm parameters entry (which should be encoded as “0x05 0x00”), should not be confused with an empty REAL (size zero array). 

3. By adding the explicit check that the length must not be zero, the repair prevents a scenario where an algorithm’s expected parameters field might be missing or incorrectly encoded and accepted. This addresses the vulnerability, because if parameters are missing—i.e. their length is zero—the certificate is now correctly considered invalid.

In summary, the repair forces the certificate parsing logic to reject certificates with an empty signature algorithm parameters field. The core change lies in the conditional block where it compares sig_params1 and sig_params2. In the repaired code, before doing a detailed memory comparison, the check “sig_params1.len == 0” is added, ensuring that an empty parameter is not mistakenly accepted. This guarantees that the certificate’s parameters match exactly what is expected rather than treating an empty REAL field as equivalent to a proper NULL value.
