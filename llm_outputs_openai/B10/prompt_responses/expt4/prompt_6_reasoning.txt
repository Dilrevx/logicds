The vulnerability was that after properly generating a random IV with wc_RNG_GenerateBlock (which is critical for AES-CBC or DES3 with TLS 1.2/1.1), the code immediately cleared the IV memory with a call to XMEMSET(args->iv, 0, args->ivSz). This incorrect zeroing of the IV meant that instead of using a random IV, an all-zero IV was used. Using a non-random (static) IV can severely compromise the security of block cipher modes like CBC, as it can lead to predictable encryption patterns and weaken confidentiality.

The repair addressed this issue by simply removing the line that resets (zeroes) the generated IV. In the repaired code, after the call to wc_RNG_GenerateBlock fills args->iv with random bytes, the following XMEMSET call is omitted. This ensures that the IV contains the expected random bytes when it is later copied into the output buffer and used in the encryption process.

In summary, here’s what happened in the repair:

1. The code first allocates memory for the IV and generates the random IV using the secure RNG.
2. The original code then erroneously zeroed out this IV with XMEMSET, effectively discarding the randomness.
3. The repaired code removes the zeroing step so that the generated IV remains intact and random.
4. This change ensures that every message encrypted using AES-CBC or DES3 has a unique, random IV as required by TLS 1.2 and TLS 1.1, thereby mitigating the vulnerability.

By preserving the random IV, the repair restores the intended security properties of the encryption scheme and prevents potential attacks that exploit predictable IV values.
