The repair begins by retaining and exercising the existing logic that examines if the initial key exchange guess was correct, based on comparing the client's and server's key exchange and host key algorithm lists. This part logs whether the guess was wrong or right. Although this initial step remains unchanged, it sets the stage for ensuring that the entire handshake process is handled securely.

Next, the patch introduces a new segment focused on enforcing a “strict key exchange” (strict KEX) mechanism. This step is crucial because it addresses the fundamental flaw where the SSH Binary Packet Protocol mishandles the handshake phase—specifically, the handling of sequence numbers and the ordering of packets. Attackers might exploit these weaknesses to cause the connection to operate with downgraded security features, as seen in what is known as the Terrapin attack.

The repair code now checks whether either the server or client supports the strict key exchange feature. In the repair, this is achieved by using a matching function that inspects the available key exchange methods against a predefined strict group of algorithms. The key idea is that if the peer (whether a server or client) advertises support for strict mode, the corresponding flag in the session is set. This flag then serves as an indicator that the connection must perform additional, more rigorous validation of packet sequence numbers and handshake integrity.

If the peer supports strict KEX on the server side, the new logic logs an informative message and sets a session flag dedicated to enforcing strict key exchange. Similarly, if the peer is the client, a corresponding check is performed to see if the server advertises strict KEX support. Again, if a match is found, the session flag is enabled. The main consequence of enabling this flag is that it forces the SSH session to adhere strictly to the integrity checks, especially concerning the handling of sequence numbers. This prevents attackers from exploiting the gap in the handshake procedure to omit or misplace packets, which might otherwise lead to a security downgrade.

Overall, the repair enhances security by adding another layer of verification based on whether the parties support a strict form of key exchange. This extra step helps ensure that any anomalies in packet ordering or sequence numbering are caught early in the handshake process, thereby mitigating the risk of integrity bypass as exploited in the Terrapin attack.
