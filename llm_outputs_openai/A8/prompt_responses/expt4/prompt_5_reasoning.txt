The repair’s core improvement is that it cryptographically binds all data in the KEXINIT message—including the extension negotiation fields—to the session hash, ensuring no parts of the message can be omitted or modified by an attacker during the handshake.

Earlier, the code processed only the fixed portions (fixed number of algorithm strings, cookie, and certain flag fields) while ignoring any additional data that might be appended (such as extension data). An attacker could potentially remove or modify these extra bytes and thereby downgrade the security of the connection (a Terrapin attack).

Here’s what the repair does:

1. After handling the fixed portions of the KEXINIT message, the repair checks whether there is any remaining data in the packet:

2. If additional data is detected, the code extracts its length and calls ssh_buffer_add_data() to add all of the remaining bytes to the transcript hash buffer. This ensures that the entire payload is included in the session’s hash, which in turn is used to derive the session identifier.

3. By consuming (advancing the pointer of) the extra data (via ssh_buffer_consume), the code guarantees that nothing is accidentally left out.

By including the extra negotiation data in the hash, the fix binds all negotiated parameters and extension information into one cryptographic checksum. Consequently, any tampering or omission in these extension fields would result in a mismatch in the computed hash during the handshake, preventing the connection from being established or resulting in a security violation being detected.

In summary, the repair closes the vulnerability by ensuring that the complete KEXINIT message—both standard and extension parts—is hashed and protected against modification. This stops attackers from selectively omitting extension data (which might disable security features) while still producing a valid session hash, thus effectively mitigating the Terrapin attack vector.
