The repair ensures that the protocol does not attempt to “guess” the negotiated algorithms when the first key exchange packet follows flag is set. In the original code, when first_kex_packet_follows or session->send_first_kex_follows is true, the software compares the client's initial guess of key exchange algorithms with the server’s provided algorithms. This comparison determines whether the initial guess was right or wrong. However, the SSH transport protocol with certain OpenSSH extensions—including chacha20-poly1305@openssh.com and the CBC with Encrypt-then-MAC algorithms—can be exploited to bypass integrity checks. In such a situation, the adversary can omit portions of the first key exchange packet, leading both client and server to potentially use downgraded security algorithms without proper verification, a condition known as the Terrapin attack.

By trusting the initial guess determined via the comparisons of both client and server methods (using cmp_first_kex_algo), the implementation mistakenly allows the possibility for an attacker to manipulate or omit parts of the handshake. This manipulation results in an inaccurate or “guessed” connection state where one might assume the connection is secure even though parts of the negotiation have been tampered with. In other words, the problem originates from relying on the integrity of a potentially tampered handshake phase. Because an attacker could force the protocol into using an incomplete or manipulated key exchange algorithm negotiation, the resulting session might end up with key exchanges or MACs that are less secure than intended.

The repair addresses this vulnerability by unconditionally marking the initial guess as wrong when first_kex_packet_follows or session->send_first_kex_follows is set. This means that when the initial key exchange packet is sent out-of-band or the corresponding flag is set, the code no longer attempts to compare or trust the client’s and server’s proposed algorithms. Instead, the repair forces the session’s state to assume that the initial guess was incorrect (session->first_kex_follows_guess_wrong = 1), regardless of any comparisons. This design choice is deliberate: by disregarding any “guess” based on suspect or incomplete handshake data, the secure protocol must fully verify the key exchange against a complete and verified set of messages, thereby mitigating the possibility of an attacker bypassing the integrity check.

This adjustment eliminates the vulnerability by avoiding the use of potentially attacker-manipulated initial guesses during the handshake. The decision to disable the guess ensures that the protocol does not mistakenly rely on incomplete or omitted data when determining the security parameters for the connection. Instead, it enforces a complete and verified key exchange process, meaning that only after a full, uncompromised, handshake will the client and server settle on the secure crypto parameters. Consequently, the repair effectively prevents scenarios where an attacker might exploit the missing packets to force a downgrade of the secure communication, thereby greatly improving the overall security of the SSH session.

This approach underscores a general security principle: in any critical negotiation phase, especially those influencing cryptographic parameters, the code should never trust incomplete or externally influenced state. By unconditionally marking the guess as wrong, the repair enforces a fallback to a safe, fully verified handshake process.
