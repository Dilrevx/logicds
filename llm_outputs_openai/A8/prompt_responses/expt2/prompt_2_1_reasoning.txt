The repair begins by preserving the original logic that checks whether the initial key exchange guess was correct. This portion of the code compares the client’s and server’s lists for both the key exchange algorithms and the host key algorithms using the function cmp_first_kex_algo. By logging whether the guess was “wrong” or “right,” this part establishes a baseline verification during the handshake process. The repair acknowledges that while this method is important, it is not sufficient on its own to fully protect the handshake process from potential exploits such as the Terrapin attack.

The main focus of the repair was to address a vulnerability in the prompt handling of packet sequencing and integrity during the SSH handshake. In the original scenario, the mishandling of sequence numbers and potential omission of packets could allow an attacker to lower the level of security during the connection. This, in turn, could result in the exploitation of certain encryption or MAC (Message Authentication Code) algorithms, such as chacha20-poly1305 and CBC-etm, leading to downgrade attacks that compromise the session’s integrity.

To mitigate this, the repair introduces a new segment that enforces a “strict key exchange” (strict KEX) mechanism. This mechanism is designed to ensure that if strict mode is supported by either side of the connection, additional integrity checks are upheld throughout the handshake process. In the added code segment, a search is conducted through the key exchange algorithm lists provided by both the client and the server, looking for a special strict algorithm identifier “strict-kex@openssh.com”. This identifier acts as a flag indicating that the party involved supports enhanced integrity checks during the key exchange.

The repair uses two loops: the first loop iterates through the client’s available algorithms, checking if any of them match the strict key exchange algorithm. If a match is found, the repair sets a flag (strict_kex_found) indicating that strict mode is supported. If the client’s list does not include this identifier, the repair then repeats the check for the server’s list of algorithms. When either party advertises strict key exchange functionality, a log message is issued to note that strict KEX support has been detected, and a flag in the session (strict_kex_enabled) is set accordingly.

By enabling the strict key exchange flag, the session is marked for heightened scrutiny during the handshake. This flag serves as an internal directive to enforce rigorous validation of sequence numbers and packet integrity, ensuring that any attempts at packet omission or reordering—techniques used by an attacker in a Terrapin attack—are effectively countered. Thus, this additional verification step counters the underlying vulnerability by adhering to a “better-safe-than-sorry” philosophy, enhancing the overall security posture of the SSH connection.

Ultimately, the repair provides an extra layer of security by explicitly checking for and enforcing strict key exchange capabilities when available. This prevents potential exploitation through packet omission or mis-sequencing, ensuring that even if an attacker were to target the handshake phase, the integrity and sequence order of the exchanged packets remain uncompromised. The enhancement in strict KEX verification represents a targeted fix for the identified vulnerability while maintaining the previously established handshake validation logic.
