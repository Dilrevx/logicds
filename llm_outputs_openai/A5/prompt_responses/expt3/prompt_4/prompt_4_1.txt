However, according to the intended semantics of X509_verify_cert, a “failed verification” (returning 0) should not be treated as fatal but simply reported as failure (with a 0 return value). Only a negative ret value (indicating a fatal error) should trigger an error raise. One way to repair the issue is to change the condition to test for strictly negative return values. For example:

--------------------------------------------------
    if (ret < 0) {
        ret = X509_STORE_CTX_get_error(ctx);
        ERR_raise_data(ERR_LIB_OCSP, OCSP_R_CERTIFICATE_VERIFY_ERROR,
                       "Verify error: %s", X509_verify_cert_error_string(ret));
        goto end;
    }
--------------------------------------------------

Explanation:
• By changing the condition from “if (ret <= 0)” to “if (ret < 0)”, the function no longer raises a fatal error when ret is 0.
• In the case where ret is 0 (meaning the verification failed in a non‐fatal way), the function will now correctly report a failure with a 0 return value.
• This avoids the contradictory behavior observed with the OCSP_NOCHECKS flag (or the equivalent command-line “-no_cert_checks”) where error messages were logged even while a “success” was returned.

This repair ensures that only fatal errors (negative ret values) result in an error raise, and a non-fatal failure (ret equals 0) is signaled in the normal manner.
