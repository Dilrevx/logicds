The vulnerability arises because when a certificate verification fails (for example, when the OCSP_NOCHECKS flag isn’t used), the function returns a negative error code (retrieved via X509_STORE_CTX_get_error(ctx)). This negative return value is then interpreted as a fatal error. However, the expected behavior for a verification failure in OCSP_basic_verify is to return 0. This discrepancy can cause confusion in applications (such as the command-line “ocsp” tool) which then mistakenly treat the error condition as a success or as a non-fatal state despite the error messages, leading to the reported contradictory behavior.

Our repair makes a simple but crucial change: before we jump to the cleanup section (using goto end), we explicitly set the return value ret to 0. By doing so, even though an error is logged using ERR_raise_data (with the detailed error message obtained from X509_verify_cert_error_string), the function ultimately returns 0 instead of a negative value. This aligns with the expected specification—where a certificate verification failure should yield a 0 return, signaling that while verification did not succeed, no fatal error occurred that would lead to a misinterpretation by higher-level logic.

This repair ensures that the error information is still available for logging and debugging, but it prevents the OCSP response from being incorrectly considered successful (or causing fatal error misinterpretations) by the calling applications.
