Below is one acceptable repair. In the original source, the code looks up the AAD parameter and then (later) uses its contents as if they were MAC key material. Because the AAD is public and predictable (sent in the clear as part of TLS), using it as a MAC key makes the MAC trivially forgeable. The proper fix is not to mix up the two values at all. In this example the patch replaces the lookup for the AAD field with a lookup for a separately provided MAC key value. (Of course a proper fix also requires that the MAC key get generated or provided securely.) For example, if you have an appropriate OSSL_CIPHER_PARAM value for the MAC key (say, OSSL_CIPHER_PARAM_AEAD_TLS1_MAC_KEY), then the repair is as follows:

------------------------------------------------
/* BUGGY CODE:
        p = OSSL_PARAM_locate_const(params, OSSL_CIPHER_PARAM_AEAD_TLS1_AAD);
*/

/* FIX: Look up the dedicated MAC key parameter rather than reuse the AAD.
   This way, the key used for authentication isn’t simply public AAD data.
   (In addition, ensure that the MAC key is generated or loaded securely.)
*/
        p = OSSL_PARAM_locate_const(params, OSSL_CIPHER_PARAM_AEAD_TLS1_MAC_KEY);
------------------------------------------------

Explanation:

1. Instead of retrieving the AAD value (which is public and predictable) and using it as the MAC key, we now look up a separate parameter (here assumed to be OSSL_CIPHER_PARAM_AEAD_TLS1_MAC_KEY) that carries the actual MAC key.

2. This ensures that the MAC key is generated, stored, and used independently from the data that is sent in the clear (AAD).

If your build does not include a definition for OSSL_CIPHER_PARAM_AEAD_TLS1_MAC_KEY, you should define it appropriately (and update the corresponding parameter-passing code) so that the MAC key is securely provided.

This patch closes the vulnerability by preventing a man‐in‐the‐middle attacker from being able to manipulate the MAC verification by guessing the MAC key based on the AAD.
