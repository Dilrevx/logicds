Step 1: Understand the issue
────────────────────────────
The original code is retrieving AAD data using the constant OSSL_CIPHER_PARAM.AEAD_TLS1_AAD:

  p = OSSL_PARAM_locate_const(params, OSSL_CIPHER_PARAM.AEAD_TLS1_AAD);

This AAD value is then (incorrectly) used as the MAC key. Since AAD is generally predictable or even known, using it as a MAC key makes it trivial for an attacker to generate a valid MAC even after modifying the message.

Step 2: Identify the proper parameter
────────────────────────────
Based on the repair description, the correct approach is to retrieve the genuine MAC key from a secure, separate parameter that is designated for the AEAD MAC key. The parameter that should be used is one associated with the MAC key (for example, OSSL_CIPHER_PARAM_AEAD_TLS1_MAC_KEY). This change ensures that the MAC key comes from cryptographically secure, properly randomized material rather than from predictable AAD.

Step 3: Make the code modification
────────────────────────────
Replace the original constant used in the call to OSSL_PARAM_locate_const with the new constant corresponding to the MAC key. The revised code becomes:

  p = OSSL_PARAM_locate_const(params, OSSL_CIPHER_PARAM.AEAD_TLS1_MAC_KEY);

By doing so, the code now retrieves the correct secure MAC key rather than the predictable AAD.

Step 4: Verify the fix
────────────────────────────
After making the change, testing should ensure that:
 • The MAC key is now generated and used properly.
 • Modifications by an attacker will cause MAC verification to fail.
 • The overall cryptographic integrity of the session is maintained.

This fix eliminates the vulnerability by ensuring that a robust, securely managed key is used for MAC computations, effectively preventing the man-in-the-middle attack vector described.
