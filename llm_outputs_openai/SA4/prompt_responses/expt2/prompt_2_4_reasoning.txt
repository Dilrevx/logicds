The repair replaces the use of the AAD parameter with the correct MAC key parameter. Initially, the code was calling OSSL_PARAM_locate_const(params, OSSL_CIPHER_PARAM.AEAD_TLS1_AAD). This retrieves the AAD (Additional Authenticated Data) for TLS1, an element of the data that can be used to provide some degree of integrity protection. However, due to a vulnerability in OpenSSL 3.0’s implementation of the RC4-MD5 ciphersuite, using a parameter intended for AAD as if it were a MAC key opens the door for potential attacks. The AAD data is not designed to be a secret or a cryptographically strong key. It is often transmitted in clear text along with the other parts of the message. This means that if an attacker is able to intercept the communication, the key that is supposed to protect the MAC (Message Authentication Code) integrity check is completely predictable, thus weakening the entire integrity protection mechanism.

The proposed fix changes the parameter that is being accessed. Instead of using AEAD_TLS1_AAD, which returns the AAD data, the code now correctly locates the MAC key parameter by using OSSL_CIPHER_PARAM.AEAD_TLS1_MAC_KEY. The MAC key is used to compute a cryptographic checksum that ensures the message has not been tampered with. Since the MAC key is generated in a secure, random manner and is kept secret between the communicating parties, it provides the necessary security barrier that prevents an attacker from forging or modifying messages undetected. If an attacker were to alter the message, the MAC computed using the secret key would not match the attached MAC, and the tampering would be detected.

This patch addresses a particularly insidious vulnerability because it corrects the subtle misuse of cryptographic parameters: the difference between data intended solely for authentication (the MAC key) and data that, due to procedural constraints, is made available (the AAD). By ensuring that the code fetches the correct MAC key, it guarantees that the message integrity check is performed using a key that remains unknown to potential adversaries. This fix is critical in establishing that the computed MAC fingerprint is derived securely, and any tampering with the message would require knowledge of that secret MAC key—a significantly harder task for an attacker.

Moreover, this change is exemplary of a broader principle in cryptographic implementations: it is not only the algorithms that need to be robust but also their correct parameterization. Using a predictable AAD value instead of a secure MAC key undermined the very integrity that cryptography is meant to uphold. With the revised code snippet, the secure architecture is restored. The MAC validation is now dependent on a securely generated MAC key, effectively closing the vulnerability. This repair thus not only fixes the specific bug but also reinforces the commitment to correct and secure usage of cryptographic primitives, preserving both data integrity and the overall security of communications.
