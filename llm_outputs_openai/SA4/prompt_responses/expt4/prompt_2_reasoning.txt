The vulnerability arose because the code was incorrectly retrieving and using the Additional Authenticated Data (AAD) as the Message Authentication Code (MAC) key. AAD is generally predictable or even publicly known, meaning that if it’s used as the MAC key, an attacker could forge or modify messages without triggering an integrity check.

In the original code, the parameter for the TLS1 AAD was used:

  p = OSSL_PARAM_locate_const(params, OSSL_CIPHER_PARAM.AEAD_TLS1_AAD);

This incorrectly picked the AAD value instead of the secret MAC key. The repair involved identifying the correct parameter that was meant to provide the MAC key for the AEAD operation. By replacing the parameter constant from AEAD_TLS1_AAD to AEAD_TLS1_MAC_KEY, the code now correctly retrieves the secret MAC key instead of the predictable AAD:

  p = OSSL_PARAM_locate_const(params, OSSL_CIPHER_PARAM.AEAD_TLS1_MAC_KEY);

With this change, the system now uses the securely generated and managed MAC key when performing the MAC integrity check. This key is not predictable by an attacker, which significantly reduces the risk of a man-in-the-middle attack where an adversary could alter messages and still produce a valid MAC.

In summary, the fix resolves the vulnerability by:
1. Recognizing that the AAD (which is meant for additional verification data) was mistakenly being used in place of the actual MAC key.
2. Replacing the input constant with one that specifically points to the MAC key parameter, ensuring that the code fetches the right secret.
3. Strengthening the overall integrity of the authentication process since the actual MAC key is secure and unpredictable, thereby preventing unauthorized modifications by external attackers.

This repair ensures that cryptographic operations follow proper security protocols and maintain robust integrity checks during encryption and decryption processes.
