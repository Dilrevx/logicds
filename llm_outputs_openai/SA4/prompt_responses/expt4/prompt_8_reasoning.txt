The repair addresses the vulnerability by replacing the use of the AAD parameter as the MAC key with a dedicated, correct parameter intended for the MAC key. Here’s the breakdown of the changes and why they matter:

1. When the function reads parameters, it first processes the KEYLEN and IVLEN as before, ensuring that the provided key length and IV length match the expected values. This part of the code remains unchanged because it doesn’t contribute to the vulnerability.

2. The code then processes the AEAD_TLS1_AAD parameter. This parameter is correctly used to initialize TLS-specific state via the tls_init() function, and it’s solely responsible for handling additional authenticated data (AAD) as required in TLS protocols. The function uses the AAD exclusively to calculate a padding size, which is important for maintaining the TLS record format—but it does not treat it as a MAC key.

3. The vulnerability was triggered by a second block of code that again retrieved the same AEAD_TLS1_AAD parameter and directly passed it to the init_mackey() function, thereby using predictable AAD data as the MAC key. In the repaired version, this block no longer retrieves AAD; instead, it now looks for a distinct, dedicated parameter: AEAD_MAC_KEY.

4. By using OSSL_CIPHER_PARAM.AEAD_MAC_KEY, the code now fetches the correct MAC key data. This parameter is intended to hold a securely generated and unpredictable MAC key, which is critical for ensuring message integrity and preventing man-in-the-middle attacks. The init_mackey() function then uses this secure key, aligning the implementation with the correct cryptographic design.

5. Finally, the function still checks and uses the TLS_VERSION parameter to set the TLS version appropriately. This step is not affected by the vulnerability and remains intact.

The key fix is the substitution of the parameter identifier. Previously, the code mistakenly assumed that the AAD used in TLS1 could be safely repurposed as a MAC key. However, the AAD is often known or predictable, making it an insecure choice for MAC verification. By switching to the dedicated MAC key parameter, the implementation now ensures that the key used for MAC calculations is not exposed to attackers. This change removes the possibility of a man-in-the-middle attacker being able to modify data and still passing the MAC check, as the attacker would not know the securely generated MAC key.

In summary, the repair separates the roles of AAD and MAC key by:
• Correctly initializing TLS-specific data with the AEAD_TLS1_AAD parameter.
• Retrieving the MAC key from the proper AEAD_MAC_KEY parameter rather than misusing the AAD.
This adjustment realigns the code with secure cryptographic practices and effectively closes the vulnerability stemming from predictable key use.
