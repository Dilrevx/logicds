The repair adds a conditional check to determine whether the current cipher is RC4-MD5. In the original code, the function always attempts to retrieve the additional authenticated data (AAD) parameter. For most ciphers this parameter is used safely, but for RC4-MD5, OpenSSL 3.0 mistakenly uses the AAD data as the MAC key. This predictable MAC key creates a vulnerability that can be exploited by a man-in-the-middle attacker.

Here’s what the repair does:

1. It checks the cipher ID using EVP_CIPHER_CTX_get_cipher_id(ctx) to determine if the current context is using RC4-MD5. In our repair, if the cipher ID is not equal to NID_rc4_md5, the code proceeds to locate and retrieve the AAD parameter as usual.

2. If the cipher is indeed RC4-MD5, the repair avoids using the AAD by setting p to NULL. This prevents the insecure behavior of incorrectly using the AAD data as the MAC key. By disabling the AAD extraction specifically for RC4-MD5, we remove the potential for an attacker to predict or manipulate the MAC key.

3. The added comment explains the reasoning behind the conditional check, ensuring that developers and maintainers understand why the AAD parameter is being skipped for RC4-MD5.

This approach fixes the vulnerability by explicitly isolating and handling the insecure behavior for the RC4-MD5 ciphersuite, thereby preventing the accidental use of a fixed, predictable key for MAC calculation. It ensures that the MAC integrity check is not compromised by attacker-controlled data.

Overall, this repair avoids a dangerous behavior without affecting the correct functionality for secure ciphers.
