Below is one example fix. The issue is that when using the default certificate verify call—
  i = X509_STORE_CTX.verify_cert(ctxStore);
—a negative return (which signals an internal error) is simply propagated. That negative value later leads to an unexpected SSL_ERROR_WANT_RETRY_VERIFY from functions such as SSL_connect() or SSL_do_handshake(), which is reserved for when an application‐supplied callback is used.

To fix this vulnerability, the code can check if the return value is negative and, if so, convert it into a proper failure code (such as zero). One correct repair looks as follows:

  if (s.ctx.app_verify_callback != null) {
    i = s.ctx.app_verify_callback.verify(ctxStore, s.ctx.app_verify_arg);
  } else {
    i = X509_STORE_CTX.verify_cert(ctxStore);
    if (i < 0) {
      /* Treat negative return (internal error) as a verification failure
        so that later error handling in the handshake does not get confused. */
      i = 0;
    }
  }

In this repair, if the built‐in verification returns a negative value, the code resets i to 0 (failure) so that later functions do not receive an unexpected negative value. This change ensures that the SSL handshake does not later return SSL_ERROR_WANT_RETRY_VERIFY, which could lead to improper handling by applications not expecting that error code.

This repair fixes the vulnerability by ensuring that any internal error in verifying the certificate is properly reported as a failure rather than an unexpected negative value.
