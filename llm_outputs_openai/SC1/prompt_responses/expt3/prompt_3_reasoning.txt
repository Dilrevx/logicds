The repair introduces an additional check right after the built‐in certificate verification is performed. In the original code, when the built‐in verification function (X509_STORE_CTX.verify_cert) is used, it might return a negative value. A negative return indicates an internal error. However, this value was directly passed along the process, which can inadvertently lead to unexpected behavior later in the handshake process—particularly returning an SSL_ERROR_WANT_RETRY_VERIFY. This unexpected error code is problematic because it is reserved for cases when an application‐supplied callback is used and can confuse the error handling logic.

In the repair, after calling the built‐in verification function, the code immediately checks if the return value is negative. If it is, the code resets the value to zero. Changing the result from a negative value to zero serves to convert an internal error into a straightforward certificate verification failure. This ensures that when SSL_connect() or SSL_do_handshake() later evaluates the outcome, it encounters the expected failure status rather than an unexpected negative error.

This approach effectively avoids any misinterpretation in later stages of the handshake process because it ensures that the error codes remain within the anticipated range. In other words, by masking internal errors (visible as negative values) and presenting them as a generic failure (0), we prevent the handshake from erroneously triggering a retry behavior that is reserved only for application callback scenarios.

Overall, the fix makes the error handling more robust by guarding against internal errors being misinterpreted downstream. It ensures that the handshake process receives a consistent and expected result regardless of whether the built‐in verification or a custom application callback was utilized.
