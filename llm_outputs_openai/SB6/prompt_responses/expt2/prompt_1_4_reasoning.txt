The primary issue with the original code is that it does not discriminate between the various types of entries that can exist in the subjectAltName (SAN) extension of an X.509 certificate. In X.509 certificates, the SAN extension can contain multiple types of identifiers such as dNSName, iPAddress, uniformResourceIdentifier, and more. The original code uses a helper function, CommonUtils.x509_crt_check_cn, that compares the expected common name (passed as “cn”) with any identifier retrieved from the certificate, irrespective of its type. This opens the door for a vulnerability: if, for example, a certificate contains an IP address in its SAN (even if it looks like a domain name string in format), an attacker might craft a certificate where the IP address field is manipulated to match a specific domain name expected by the verifier. Although an attacker would still need to control the IP address, this misalignment in type verification undermines the trustworthiness of the identity check.

To address this vulnerability, the repair selectively restricts the matching function to consider only entries of type dNSName. Domain names provided in certificates should be represented as dNSName in the SAN extension. By enforcing that the expected common name is only compared against dNSName entries, the fix ensures that any entries of other types—such as those for iPAddress—are ignored during the verification process. This coupling of the expected data type (a domain name) with the actual type in the certificate provides an extra layer of validation, thus adhering to the principle of type matching during certificate verification.

The repair makes a minimal yet crucial change by passing an additional parameter to the CommonUtils.x509_crt_check_cn function. This parameter, denoted in the code as MBEDTLS_X509_SAN_DNS, flags the function to constrain its comparison solely to SAN entries that are explicitly of type DNS. By doing so, the function no longer considers other SAN types, thereby eliminating a potentially exploitable entry that would otherwise allow misinterpretation of the certificate’s identity. Encapsulating this verification logic into a clearly defined function with type parameters also makes the code more maintainable and self-explanatory, which is a good practice for security-critical code.

This adjustment is particularly important in scenarios where certificates include both a common name in the legacy field and additional identifiers in the SAN extension. The prevailing best practice is to consider the SAN extension over the common name field, but only if the SAN is of the appropriate type. With this repair, if the function finds a match between the expected common name and a dNSName in the certificate, the verification process can safely conclude by breaking out of the loop. This behavior is a safeguard ensuring that only trustworthy, type-consistent domain names are used when establishing secure connections.

In summary, the code change not only directly addresses the vulnerability by narrowing the scope of the comparison to dNSName entries but also reinforces the overall integrity of the X.509 certificate verification process. It carefully mitigates an avenue for potential impersonation attacks that could arise from a broader, less discriminating check of certificate identity elements.
