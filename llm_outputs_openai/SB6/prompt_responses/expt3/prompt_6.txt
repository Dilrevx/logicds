Below is one example of a repair. In many cases the vulnerability arose because the function’s “match‐found” result could be triggered even when the certificate’s common name only partially matched the expected name. One fix is to make sure that the entire string is compared (for example, by comparing the lengths before doing the memory compare) so that extra trailing characters do not allow an attacker to bypass the certificate check. For example, you can replace the call to CommonUtils.x509_crt_check_cn() with an explicit length check using strlen() and memcmp() as shown below.

<repair>
                if (cur.buf != NULL && cn != NULL) {
                    size_t cert_cn_len = strlen(cur.buf);
                    if ((cert_cn_len == cn_len) && (memcmp(cur.buf, cn, cn_len) == 0))
                        break;
                }
</repair>

In this repair the certificate’s common name is only considered a match when its length exactly equals cn_len and its contents exactly match the expected cn. This change prevents a situation where an attacker’s crafted common name (with extra trailing characters) could mistakenly be accepted.
