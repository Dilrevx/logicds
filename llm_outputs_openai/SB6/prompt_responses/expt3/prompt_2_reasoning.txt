The repair replaces the old call to x509_crt_check_cn with a new function, x509_crt_verify_certname, which implements stricter logic for comparing the expected certificate name (CN) with the names presented in the certificate. In the original code, the function x509_crt_check_cn only checked if the expected common name appeared in any name field, including the subject alternative name (SAN) extension. This allowed an attacker to exploit the vulnerability—for example, by obtaining a certificate for an IP address type (like a 4-byte or 16-byte IP address) and then impersonating a domain name.

In the repaired version, the function x509_crt_verify_certname is called instead. This function is designed to perform a more selective verification process:

1. It first detects if the certificate includes the SAN extension. If the extension exists, the function does not simply check if the expected name is present somewhere in the SAN list. Instead, it iterates over the SAN entries and compares the expected name only with those entries that are of the same type as the expected input (for example, comparing against DNS names when a domain name is expected). This prevents the case where an IP address certificate entry, which might be part of the SAN, is accepted as a valid match for a domain name.

2. If the certificate does not include the SAN extension, the function falls back to performing the check using the certificate’s common name (CN) field. This maintains backward compatibility and expected behavior for certificates that do not include SAN entries, ensuring that valid certificates without SAN entries still pass the check correctly.

3. The overall benefit is that only the correct types of names are compared, and false positives—where an IP address is mistakenly considered a match for a domain name—are avoided. This stricter verification ensures that an attacker cannot bypass the security by using a certificate with a manipulated subject alternative name.

By changing the control logic to depend on the outcome of x509_crt_verify_certname, where a return value of 0 signals a successful and validated match, the repair aligns the certificate validation process with best practices. This update minimizes the attack surface by requiring explicitly matching name types and enhances the system’s security posture against authentication bypass exploits that could otherwise be leveraged by malicious parties.
