The repair replaces the call to a function that merely checks the certificate’s common name (CN) with a call to one that specifically examines the subject alternative name (SAN) extension. In the original code, using x509_crt_check_cn could lead to scenarios where any name in the SAN—even those of a different type than expected—might inadvertently satisfy the verification, thus enabling an attacker to exploit alternative types (such as an IP address) to impersonate a legitimate domain.

By switching to x509_crt_verify_san, the verification process becomes more stringent. This new function is designed to filter the SAN entries so that only those corresponding to the expected name type (for example, DNS names when verifying domain names) are considered. As a result, if a certificate contains a SAN extension with multiple types of identifiers, the verification logic will ignore identifiers that do not match the expected type. This targeted check prevents attackers from leveraging non-corresponding SAN entries—like a 4-byte IPv4 or a 16-byte IPv6 address—to satisfy the certificate validation process.

Thus, the repair ensures that the certificate’s identity is validated using the correct, context-sensitive name information, aligning the verification process more closely with the X.509 standards and good security practices. The use of the appropriate verification function effectively mitigates the risk of an attacker presenting a certificate with a manipulated SAN entry to impersonate the required identity.
